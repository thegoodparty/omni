### Shared — the page, its gates and analytics

- **Analytics live under `EVENTS.DoorKnocking`** (`Door Knocking - *`). **The canonical `Outreach - Campaign Completed` fires off the TURF being completed (`turfLifecycle.ts`), not off the walk session** — a session ends whenever a canvasser stops for the evening, so firing there counted a fifty-door list walked over three evenings as three campaigns. Every path that finishes a turf comes through that one mutation: the walk's own auto-complete (`walkCompletion.ts`), the walk footer's Mark done, and the drawer's per-row Mark done; the campaign-level press has its own fire in `campaignLifecycle.ts`, one per turf it finished. Both carry the turf's `priorityId` (the server reads it off the campaign's anchor envelope) and its `purpose`. `Outreach - Campaign Created` fires per turf beside `Door Knocking - List Created`, and `Door Knocking - Door Logged` carries `medium`/`fanout`/`listId`. Full schema: `docs/features/voter-outreach-analytics.md`.
- **The voter pack and every turf read resolve a district server-side** (`resolveEligibleDistrict` in gp-api's `doorKnockingPack` / `doorKnockingCreate` services), so an org with no resolvable district can only 400. `NativeDoorKnockingPage` gates both queries on `useDistrictResolution` (`app/dashboard/shared/`) and explains instead. Gating at the shell also covers the write paths (`POST turfs`, `POST interactions`) because their affordances never render. The unavailable branch has to come **before** `packQuery.isPending`, or that branch claims to be loading forever.
- **The pack query never retries, and it has its own deadline.** `useVoterPack` sets `retry: 0` and a 90s `AbortSignal.timeout`, and both are load-bearing rather than tuning. Abandoning the request does not cancel the district scan behind it, so a retry competes with a build that is still running — on 2026-08-25 that turned one visible failure into 165 seconds of spinner. The 90s sits deliberately under the gateway's ~120s idle ceiling so the client fails first, cleanly, instead of waiting on a connection something upstream already killed. `packDecoder` also throws when the response ends before the pack arrives; a truncated body is a failed build, not an empty district. Background: gp-api `docs/door-knocking.md` § The pack.
- **The who step also asks the server one question the pack cannot answer: does this list keep anybody at all?** `POST /v1/door-knocking/audience-check` (`audienceCheckQueryOptions`) resolves the list's own filters against Postgres and returns one flag, which gates Continue and prints a sentence naming the criteria (`emptiableCriteria.ts`). It exists because the three criteria that can resolve a list to NOBODY — support status, previous outreach, contacts made — are three the pack has no plane for, so such a list shades as the whole district and every count on the way to the boundary looks healthy until the paid create refuses. **Fired from `CreateListSurface`, not the step**, because that is where a picked list's non-boolean clauses are already assembled for the address-preview request; the step's own draft carries them only as marks. It is cheap where the preview is not (no voter scan, no district resolve), which is what lets it fire on a pick rather than a press — the preview costs a voter-data scan, so it runs only on an explicit request. **It fails open on error and while pending, and it caches nothing** (`staleTime: 0`, `gcTime: 0`) — its own empty message sends the candidate to contacts to fix the list, so a held `true` would refuse the list they just fixed; do not add a staleTime back to save the round trip, which is the half of the trade the endpoint was made cheap to afford. The create's 400 is still the backstop: a missed empty audience is the status quo, a false block is a list nobody can cut. `empty: false` means "the id-set did not collapse", never "somebody is in there" — party and age narrow a query instead of resolving a set, and only the people database knows.
- **Every other count in the create flow is pack arithmetic, so the whole flow is gated on a download that runs 4.5s at p50 and 34s at p95.** `districtHouseholds` is `runFilter(...).households` and the draw step's stops/doors/people fall back to `polygonStats`; none of them is a server call, so all of them read zero until the pack lands. That zero is indistinguishable from an empty district, which is why the who step's CTA **drops its count entirely while the pack is pending or failed** rather than printing `Continue (0)` — the same shape phone banking's shell already uses. The wait and the failure are both stated **inside the sheet**: the map's `LoadingAnimation` is painted under the create flow, so during the one wait that matters nobody can see it. `retry: 0` (above) makes the error branch permanent, so a pack that fails without in-sheet copy is a dead button and no explanation anywhere. **The server's `POST /v1/contacts/count` is not a substitute for the district figure, and the reason is not that it cannot count households.** `buildCountSql` does `COUNT(DISTINCT householdKey())` on request and `ContactsService.segmentGroupsByHousehold` already returns true for `doorKnocking` — but the count path is the one that never asks: `fetchCount` passes `false`, and `CountContactsDTO` carries neither a segment nor the flag, so nothing on the wire can request the grouping `listContacts` and `downloadContacts` apply to that same segment. It also applies no `ROOFTOP_ONLY`, which every door-knocking read does. Both have to be closed server-side before the swap is defensible; either one alone silently inflates the number.
- **Doors logged on a walk are overlaid onto the pack, not refetched.** `endWalk` records the walk's pins through `recordLoggedKnocks` (`useVoterPack`) and `applyLoggedKnocks` (`filterEngine`) merges them into `statusPerDot` at render, because the alternative was re-downloading a district — hundreds of thousands of rows, 5-30s — to change a handful of status bytes. The overlay keys on the dot's own coordinate, which is what `runFilter` already rolls people up by, and it may only move a dot **less** actionable: the pack's status is a rollup over everyone at that address, so a logged knock at a multi-unit dwelling has not answered for the units nobody visited. `gcTime` is an hour for the same reason — a candidate who steps away and comes back should not pay the download twice.
- `doorKnockingServe.service.ts` in gp-api is about **serving a route** to a canvasser — it is not the Serve product, and the name collision predates the wiring below.
- **Door knocking runs on both surfaces now, and one page draws both.** Unlike social and phone banking, where the Serve caller is a separate page passing a `surface` prop, `/dashboard/door-knocking` is the only route — so the answer lives in a context, `native/doorKnockingSurface.tsx`. The page decides it once, from the same predicate `DoorKnockingPageGate` uses to admit the org at all: a `Campaign` takes precedence and an `ElectedOffice` is consulted only in its absence, which matches how gp-api's `POST /v1/door-knocking/turfs` answers the same question, so a list is always created onto the surface that asked for it. **Read the turf list through `useTurfsQuery` and never `turfsQueryOptions` directly** — the page is the one exception, because it is where the mode is decided and it passes its own `serveMode` in; everything below it reads the hook, so two readers cannot disagree about which org's lists they are looking at. The isolation is real and not cosmetic: an org holding both a Campaign and an ElectedOffice would otherwise see its Win lists on its Serve surface (ENG-10976), which door knocking could not even express before every turf had an outreach envelope to carry the scope.
- **Ethnicity appears nowhere on the Serve surface either, and it rides party's gates rather than adding its own.** The rule is gp-api's (`src/contacts/AGENTS.md`): an elected official may not have a list cut by ethnicity. #1933 removed the dimension from both products; Win's half was reverted, so what is left is a Serve gate, not an absence. (1) The **served route** nulls `ethnicityGroup` per target for an `eo-` org, in `demographicsOf` beside the `politicalParty` null, which fixes the walk and the person sheet together. (2) `demographicFacts` **drops** the Ethnicity group row for Serve rather than leaving it to `withFallback`, which would print "Not on file" — a claim about a gap in the voter file, where the truth is that this product does not state ethnicity to an elected official. (3) `ethnicity` is in `WIN_ONLY_FILTER_FIELD_KEYS`, so the create flow's who step does not render the group and `savedListFilterKeys` strips the six option keys a pre-rule saved row still carries — the same back door party's keys leave open, and closed the same way. There is a fourth road here that party also has: gp-api 400s an ethnicity filter for an `eo-` org (`assertNoEthnicityFilterForElectedOffice`), so an official who got a pill checked anyway gets a dead address preview rather than a route bought against a cut they cannot see. **The pack's `ethnicity` dim is deliberately still there**, exactly as party's is: it is district-scoped and cacheable, nothing can select it once (3) holds, and Win's create-flow preview shades on it. `PACK_FORMAT_REVISION` moved to 5 on the restore — it could not rewind to 3, because a revision-4 buffer carries no ethnicity plane and reusing 3 would serve those cached buffers as current.

- **Party appears nowhere on the Serve surface, and it took four gates rather than one, because party reaches this feature by four independent roads.** The system-wide invariant is gp-api's (`src/contacts/AGENTS.md`): the `eo-` org-slug prefix is the whole rule and a party value in any `eo-` response is a bug. Door knocking was the last surface still leaking one. (1) The **served route** nulls `politicalParty` per target server-side, which is what fixes the walk, the person sheet, the printed walk sheet and the PDF at once — `describeTarget` in `print/walkFacts.ts` collapses on the null with no branch of its own. (2) `voterDemographicFacts` **drops** the Political party row rather than leaving it to `withFallback`, which would print "Not on file" — a claim about a gap in the voter file, where the truth is that this product does not state party to an elected official. (3) The create flow's who step hides the `political_party`, `voter_likely` and `contacts_made` groups, matching the CRM wizard's `VoterFileStep` strip; party is the sharpest of the three, since gp-api 400s a party filter for an `eo-` org and an official who picked a pill got a dead address preview and then a create that could not buy its route. (4) `savedListFilterKeys` strips those same fields' option keys, and that one is the back door the other three leave open: it re-expands **every** boolean column on a saved row, so a list cut on the Win surface — or before any of this existed — would re-check party pills inside a group that is no longer rendered, shade the map to a cut nobody can see or clear, and then 400. `TurfDetailsSheet`'s read-back is gated for the same reason, since nothing backfills a saved filter. The field keys live once, in `savedListFilters.ts` as `WIN_ONLY_FILTER_FIELD_KEYS`, and the option keys are derived from `filters.config.ts` rather than written out — a party value added to the catalog cannot arrive un-stripped. **The pack's `party` dim is deliberately still there**: it is district-scoped and cacheable, nothing can select it once (3) and (4) hold, and removing it would fork the district cache for no user-visible gain. `PACK_FORMAT_REVISION` does not move.
- **All three client-side gates hang off one boolean, `isServeOrg`, and it is the org slug rather than either of the two booleans next to it in `NativeDoorKnockingPage`.** The question these gates ask is what gp-api will accept, and `ContactsService.hasElectedOfficeAccess` reads the `eo-` prefix and nothing else. `isElectedOfficial` (an ElectedOffice row exists) would hide a party pill the server would have honoured for a campaign-slug org. `serveMode` (`!campaign && isElectedOfficial`) is a different question again — it decides which rail's LISTS are on screen and lets a Campaign take precedence, so an `eo-` org holding one would be offered filters its every request 400s on. The orchestrator derives it once and passes it as a prop to `CreateListSurface` and `TurfDetailsSheet`; neither reads `useOrganization()` for itself, which is what keeps both testable without an organization provider and is why the prop is not named after the office.
- **`isServe` rides the route payload, and the reason it is not four context reads is the two paper surfaces.** `useDoorKnockingServeMode()` answers this for anything under the page, but `print/[turfId]` and its PDF sibling render server-side with no organization provider above them, so the printed sheet cannot get this answer any other way. One field on the payload also means the walk, the person sheet and the two paper formats cannot arrive at different answers about one list. It is optional on the contract for the reason `history` and `notes` are — a service worker's pre-ship snapshot carries no such key and has to keep parsing on a phone that cannot refetch — and absent reads as Win, which is the surface every route frozen before it shipped belonged to.
- **Door knocking is Pro-gated (ENG-10888).** `canUseProFeatures` — `!!campaign?.isPro || !!electedOffice`, the CRM's own spelling (`ContactsTableProvider`) of gp-api's `ContactsService.assertProAccess` — decides the branch in `DoorKnockingPageGate`. Every `/v1/door-knocking` route enforces it server-side **except** `POST /do-not-knock` and `POST /not-a-voter`, so a lapsed org can still honor "don't come back" — see "The Pro gate" in `gp-api/docs/door-knocking.md` for the full route table. Reads are gated too, so there is no locked-preview mode: a map you can open but not route is worse than a clean upgrade message, and creating a list spends real vendor routing credits. **The upgrade card lives in `DoorKnockingPageGate`, not a file of its own** — that keeps the `'use client'` ratchet flat (the gate is already a client component; a new one would need the baseline bumped). It is a safety net for a URL or a stale tab, not a funnel: it is deliberately shorter than `OpponentProLockedView` and fires no exposure event. One consequence worth knowing before touching this gate: an in-flight `useElectedOffice` is **not** a refusal — a Serve org's access comes from that query and its campaign is never `isPro`, so the page gate waits (and only for a campaign that isn't already Pro) instead of flashing the upgrade card at the org most entitled to the feature.
- **The create flow carries milestone 2's in-flow gate, and under `outreach-pro-gating-v2` the page lock in front of it opens.** `CreateListFlow` mounts `useOutreachGate('door')`: the draw step's Create campaign opens `OutreachGate` instead of calling `save.mutate()` when `requirement` is non-null, its completion runs the save, and `GateBanner('door')` rides every stage but `draw` (where the map is the content and a footer banner would cover the shape being cut). **The press it guards no longer spends anything, and that is deliberate for now.** The Geoapify spend moved to the first knock, which is a dialog, and a dialog is not a surface the gate's full-sheet screens can mount in — so the gate stayed on the last press before the money, where a free candidate meets Pro exactly where they always did rather than building a campaign that dead-ends at the door. gp-api refuses the buy without Pro either way (`assertProAccess` on `POST /v1/door-knocking/turfs/:id/route`), so this is about where the candidate is told, not about what is enforced. Moving it onto the knock press is the follow-up. With the flag on, `DoorKnockingPageGate` admits a non-Pro campaign, because gp-api opened the three reads the map needs to a free campaign (`GET /v1/door-knocking/pack`, `GET /turfs`, `POST /audience-check`; `POST /address-preview`, `POST /turfs` and `POST /turfs/:id/route` stay Pro — the first scans people-db, the other two buy a Geoapify route), and the hub's door tile is in `ChannelTileGrid`'s `gatedInFlow` set alongside text, robocall and phone banking. Off the flag the lock stays exactly as before.
- **Door knocking is a channel of Voter Outreach, not a peer of it — there is no standalone left-rail entry, and the outreach hub's tile is the only way in.** The product call is that a candidate picks a channel on the outreach hub, and the tile in `outreach/v2/ChannelTileGrid.tsx` is the only entry that can hand a saved list across (`?listId=`, ENG-10762); a top-level nav item would be a second front door that arrives with nothing. `DashboardMenu.tsx` carries no door-knocking gate or menu item at all. **Removing the entry removed no access check** — Pro is enforced by `DoorKnockingPageGate` and by every `/v1/door-knocking` route, and the hub tile is `requiresPro` in `OUTREACH_OPTIONS`, so it renders locked and opens `ProUpgradeModal` for a non-Pro candidate rather than navigating. What the nav entry carried was reachability, not entitlement. **The route and its deep links are untouched and must stay that way**: `/dashboard/door-knocking?create=1` (plus `&listId=`) is what the tile pushes, `OutreachDetailsDrawer`'s "Continue knocking" CTA links to `?walkTurfId=&outreachId=`, and `e2e-tests/src/helpers/door-knocking-e2e.ts` still reaches the surface by URL on purpose — deep links into this feature are the thing the tile depends on, so a spec that could only get here by clicking would be testing the nav and not the page.

- **This route draws no page header and no left nav, because the design draws door knocking as a modal over the outreach hub.** There is no `<h1>Door knocking</h1>` bar and no compact `PDF` link in one, and `DashboardLayout` is passed `hideMenu` so the sidebar is not rendered either — the map runs edge to edge at every width. Every title that row used to carry is already on the surface that owns it: the create flow names its own step through `OutreachFlowShell`'s stepper, and the walk names its list on its sheet at the `peek` snap. The sidebar is the same argument: door knocking is reached from the hub's tile and returns to the hub from every exit, so the nav it would offer leads exactly where the surface's own close button already goes. **`hideMenu` rather than rendering outside `DashboardLayout`**, which is what keeps the providers this tree sits in — `SidebarProvider`, the impersonation banner — and costs the map only the chrome the design does not draw. **Nothing paper-shaped was lost with the header's PDF link**: `WalkView` already renders the design's own full-width `Export this list to PDF` above the stop list, from the same `ExportWalkSheetButton`, so the canvasser who is about to walk out of signal gets it from the surface they are standing on.
- **The page is exactly the height the dashboard chrome leaves, and it gets there by measurement rather than by arithmetic.** `NativeDoorKnockingPage` asks `DashboardLayout` for a `min-h-0 overflow-hidden` content wrapper and fills it with `h-full`. It previously sized its own column with `h-[calc(100dvh-4rem)]`, and both halves of that were wrong. The `4rem` is `MobileMenuTrigger`'s `h-16`, which is `lg:hidden` — so above `lg` it subtracted a bar that was not on screen and **the map ended 64px short of the bottom of the window on every desktop**. And a hard height on the child did nothing about the parent: the wrapper is `flex-1` inside `SidebarInset` inside `SidebarProvider`'s `min-h-svh` row, and a flex item's default `min-height: auto` lets its CONTENT set the floor, so anything the layout rendered beside this page pushed the document past the window. Something does: when the campaign-story flag is on, `DashboardCampaignManagerChat` renders an in-flow `h-24` spacer next to the page, reserving scroll room for its fixed footer bar — **96px of pure overflow, and the reported "have to scroll to see the full map".** `min-h-0` removes the floor so the chain resolves the other way (the row settles at `min-h-svh`, the wrapper takes what the chrome above it leaves, at whatever width), and the spacer is then honoured INSIDE the window: the map stops 96px short and the bar sits in the gap instead of over the map. **Nothing in `DashboardLayout` changed to do this** — that file is every dashboard page's, and the classes this page needs are ones it already accepts through `wrapperClassName` and `hideMenu`. `svh` is inherited rather than chosen, and is the right value: it is the viewport with mobile browser chrome at its largest, so the page is whole in every chrome state — and a page that cannot scroll never retracts that chrome, which leaves `dvh` permanently equal to it here. **Do not re-introduce a viewport unit on the column.** The number it would have to encode is the height of chrome that changes at a breakpoint, and that is the layout's to measure, not this page's to guess. Both surfaces float over a map that fills this column at every width, so nothing under here has a height of its own to reconcile; MapLibre v4 carries its own `ResizeObserver` on the container and deck.gl's `MapboxOverlay` follows the map, so nothing here needs a resize call of its own.

- **Seven query parameters reach this page, plus a chat card's link, and each one is consumed once.** A priority's door-knocking card adds `?proposalKey=&priorityId=&stepId=&side=` (parsed whole with `ProposalLinkSchema` in `page.tsx`, dropped whole if it does not parse); `CreateListFlow` sends it on the create of a new campaign's anchor turf only: the whole link on Serve, where the server puts that priority's check out, and the key alone on Win, where a Campaign Manager card has no check. `?listId=` preselects a saved list in the create flow (the outreach tile's hand-off); `?recommended=<variant>` is the same hand-off for a voter data page recommendation not saved yet — the flow opens on the who stage with the goal the variant's intent maps onto (`purposeForRecommendedVariant`, initial state in `CreateListFlow` since it mounts fresh on every open), fetches it cut for door knocking (`staleTime: 0`, and never applied while `isFetching` — a cached copy from before the list was saved would build it a second time) and applies it as a card tap would; creating the list invalidates both door-knocking recommendation caches (`docs/features/recommended-lists.md`). A link may add `?purpose=` and `?area=` to `?listId=`: `purpose` is a Serve door purpose (`SERVE_DOOR_KNOCKING_PURPOSE_VALUES`), read on Serve only and only while the carried list is unspent, so once the list matches a picker row the flow goes straight to the talking points, drafted for it (`outreachLandingStep`). A priority's door card sends `?purpose=community_input&question=` (the card's message, cut to `COMMUNITY_INPUT_QUESTION_MAX_LENGTH`, `agent-chat/cards/proposalFlows.tsx`), so the walk opens on that goal with the check's question already asked; `community_input` counts as answered only with its `question`, and without one the flow opens on the question stage, since a blank question is refused at the create; `area` is a `west,south,east,north` box (`native/walkableAreaParam.ts`, anything else dropped), loaded on the first arrival at the draw step with no turf yet as the campaign's first turf (`draw.loadRing`, named `Turf 1` like an unnamed turf is saved) instead of a blank session, and spent like the list. The turf takes the list's households inside it; the Pro gate on Create campaign and the route bought at first knock are unchanged. `?walkTurfId=` opens that list's walk directly, and `?outreachId=` beside it says the walk was entered from the outreach history drawer. `?create=1` says the hub's tile was pressed, which no longer decides whether the create flow opens — it always does — only whether closing it pops that history entry or pushes the hub. The page reads them on mount and does not keep them in the URL as state: a walk is a mode, and a mode encoded in a query string comes back on the next Back button press.
- **Every exit from door knocking lands on the Outreach hub, and `WalkOrigin` still exists because one of them is more specific than that.** `WalkOrigin` is `hub`, `details` or `outreach`, set by whichever handler started the session and read by `endWalk`: the hub, that list's details sheet, or the outreach history row that sent the candidate here through `?outreachId=`, which reopens in its own drawer rather than merely being somewhere in the history table. `hub` is the default and the design's own exit — the prototype's `walkClose` falls through to `exitDoor` and lands on Voter Outreach. **It used to be `rail`, which meant "stay on this page"**, and that was correct while the landing surface was a rail of saved lists worth returning to; with no such surface, staying would leave a bare map with nothing on it and no control to make anything, so the constant `OUTREACH_HUB` is where every kind now goes but `details`. (`details` is currently unreachable along with the sheet that sets it — see the unreachable-surfaces note above.) **The origin is the page's** and not the walk surface's, for the same reason `endWalk` is: only the orchestrator knows both modes.
- **The create flow opens itself on arrival, always, and `closeFlow` is what reads how you got here.** Arriving at this route is asking to build a campaign — there is no landing surface to choose from — so a single effect opens the flow however the page was reached, whether the hub's tile sent us with `?create=1` or the URL was typed. It requires only two things: no walk being asked for or already running, and a resolvable district. **It does not read the turf list to decide whether to open**, which is the shape of the old opener and must not come back: there were two openers, one gated on the org having no unarchived turfs and one on the tile's param, and collapsing them is what let the turf query stop being a precondition for opening a funnel that never looks at it. **A `?walkTurfId=` defers to the walk only while it could still become one.** Once the turf query has settled without that id in it — a stale bookmark, a list deleted in the CRM, another org's — `deadWalkLink` lets the arrival proceed as an ordinary one, because deferring forever is the bare-map dead end the exit rules above exist to prevent, and there is no longer a rail behind this screen to be stranded on. Settled rather than successful, so a failed turf read counts too rather than waiting on a query that is not coming back; until then the link is merely slow, and a list that arrives late still gets its walk, since the id is spent only once a turf is found. What `?create=1` decides now is only where CLOSING goes: `tileOpened` makes `closeFlow` call `router.back()`, which pops the entry the tile pushed and keeps the hub's scroll position, and everything else pushes `OUTREACH_HUB` outright.
- **`landingOpened` is never unset, and that is load-bearing — do not merge it back into one ref.** The old `autoOpened` was both the once-guard and the record of where closing should return to, and `handleListCreated` cleared it because the second job needed clearing. Creating a list invalidates the turf query; the effect re-ran, found a turf list that had not refetched yet, and reopened the create flow at step one **on top of the walk that had just started**. The fix is that they are two refs with two lifetimes: `landingOpened` is spent for the life of the mount and never unset, and `tileOpened` is the close destination and is spent when the flow hands over to a walk. This is exactly the class of bug this file exists to prevent: a ref that answers two questions will eventually be cleared for one of them.
- **No e2e spec here may create a saved list, and the empty account is why there is still a spec at all.** A list IS a bought Geoapify route since 3.0 — one transaction — so the `seedTurf` helper that used to stand a row up for `door-knocking-turf-rail.spec.ts` had to go with it: seeding one would bill a shared credit pool on every run of the suite that gates every PR in the monorepo, and take a 30s vendor call as a dependency of the gate. `door-knocking-zero-state.spec.ts` replaced it, and covers the same cross-service question — page, Pro gate and `GET /turfs` lining up on a live preview — through the one surface an org with no lists can reach. Everything about a list that exists is asserted in unit tests, where a list costs a fixture: `TurfDetailsSheet.test.tsx`, `WalkView.test.tsx`, `WalkSheet.test.tsx`, and gp-api's `doorKnocking.routes.test.ts` for the write itself.
- **Ending a walk marks the list Done, but only a walk that finished one.** `endWalk` calls `useWalkCompletion` (`native/walkCompletion.ts`), which imports `useTurfLifecycle` rather than posting `turfs/:id/complete` itself — one writer for the mutation, and it already invalidates the turf query before its snackbar, so the outreach history row the candidate lands back on reads Done rather than lagging the message. It lives on the page because `endWalk` does: only the orchestrator knows a walk is ending. **The unconditional version was rejected, and not narrowly.** Done is the one lifecycle write with no undo beside it — archive is a boolean that can be flipped back, delete has a confirm — and what it takes away is Knock. Leaving is also the ONLY way out of a walk, so stamping every exit would read "I am done for now" as "this list is finished" and take the way back in away from a canvasser who knocked three doors of fifty. **"Finished" is the walk's own progress bar**: every knockable person logged, per `routeCounts` — do-not-knock and not-a-voter residents dropped, `logged` meaning an answer is written down and not that a conversation happened. That is the number the canvasser has been watching climb all evening, so a list stamping itself Done as they leave a 40/40 walk is the outcome they already believe in. **Two states are deliberately not finished**: a route that isn't in cache (a serve that never landed reports zero targets, which is indistinguishable from a list with nobody in it — never stamp off a fetch that failed), and a list where nobody is knockable at all. Both are the same asymmetry: another walk of the same list is one tap away on the hub, while an unwanted Done cannot be taken back from anywhere in this feature, so erring toward not completing is the cheap mistake. **The manual half of that bargain exists again**: `Mark this route done` in the walk's own footer and `Mark done` on the outreach drawer's sibling rows, both behind a confirm naming how many people are still unlogged. Between the rail's deletion and those two there was no manual control at all, which quietly made this rule the ONLY way a list could become Done. **The turf the write runs against is held in a ref for the length of the mutation.** `useTurfLifecycle` reads its turf out of the render it was called in, and a mutation observer pushes each new render's options onto the request already in flight — so `walk.end()` clearing the session in the same handler that starts the write swapped the id out from under it and the POST went to the hook's standin turf. That is a property of calling a row-shaped hook from a page, not of this feature; anything else the orchestrator writes on the way out of a mode needs the same care.

- **One campaign holds many turfs, and a turf becomes real the moment its third corner lands.** The create flow is purpose → who → points → name → draw (an event invite adds a `details` stage after purpose: when and where, which the talking points' ask then names — see `outreach/AGENTS.md`; the question-asking goal, `community_input`, adds a `question` stage the same way, and its card is offered only while `useIssueCaptureFlag(false)` is on, filtered in `CreateListFlow` rather than in the purpose files, so a campaign already on that goal keeps its labels and its question step), and `name` asks for the CAMPAIGN's name before anything is drawn, because a campaign is the container the turfs are cut into. On the drawing surface the candidate cuts as many as they like: `handlePolygonChange` on the page commits the ring to a `TurfDraft` (`native/turfDrafts.ts`) as soon as it is valid, and thereafter rewrites that same draft's polygon on every vertex. **Eager rather than on a press**, because the toolbar hangs a colour, a name and an assignee off the turf being drawn, and a turf that existed only as loose page state until some later button would have nowhere to put those answers. Nothing below the page commits one — `CreateListFlow` and `CreateListSurface` can name, colour, assign and drop a draft, never create one — since only the page is told what the canvas drew.
- **`activeDraftId` is both state and a ref, and the ref is not a convenience.** Switching from Turf A to Turf B sets the active turf and asks the canvas to load B's ring; the canvas answers after paint. In the window between, `ring` still holds A's boundary, so anything deciding where to write it by reading STATE writes A's shape onto B. `activeDraftRef` is moved at the switch, before the load is asked for. Same class of bug as the `landingOpened` note above: the fix is that the synchronous question gets a synchronous answer.
- **The turf being edited is drawn by the drawing session, so `visibleTurfs` leaves it out.** Otherwise the same boundary renders twice — once frozen at the shape it had when committed, once live — and a vertex drag trails a ghost. The page still passes that turf's id as `selectedTurfId`, which is deliberately an id `turfs` does not contain: `turfInteractiveAlpha` reads it as "a selection is live and this turf is not it" and pulls every other ring back, which is exactly the receded backdrop wanted. Off the flow it is null and the layer is byte-identical to before.
- **Per-draft counts are cached on polygon identity, and the cache is what makes them affordable.** `draftStats` on the page runs `polygonStats` per draft — a ray-cast over the whole pack — and the draft being edited has its polygon rewritten on every dragged vertex. Without the cache each of those frames would re-stat every other turf for answers that cannot have changed; `updateDraft` replaces only the draft it touches, so an untouched draft keeps its polygon reference and its entry. The cache clears wholesale when the pack or the filter selections change, because the audience is what the counts are OF.
- **The paid press buys N routes, and the anchor is bought alone.** A campaign has no row of its own — it is the anchor `Outreach` plus every sibling carrying its id — so the first turf of a NEW campaign has to exist before anything can point at it. `save.mutationFn` creates it on its own, reads `outreachId` off the response, and sends the rest together behind it. Arriving through "Add turf" skips the wait: the anchor is already bought and every draft is a sibling. **`DoorKnockingTurfSchema.outreachId` exists for exactly this** — the client had just bought the anchor and had no way to learn what to call it.
- **The batch is `allSettled`, and a partial failure is not an error.** Each turf is an independent, billed purchase, so a vendor 502 on the third must not throw away two routes that were paid for. Successful drafts are dropped in `onSuccess`, failed ones stay in the list, and `createdAnchorRef` remembers the anchor so the retry does not mint a second one — a candidate holding two campaigns of one turf each has nothing in the product that can merge them. The draw step says so in its own words: a thrown error wrote nothing ("nothing was saved"), a resolved result carrying failures wrote some ("the turfs that were created are saved"), and the retry those two offer is not the same retry. `createdFilterIdRef` is only cleared on a complete batch, because the turfs still owed attach to that same audience.
- **`EVENTS.DoorKnocking.ListCreated` fires once per turf, with that turf's own figures.** A campaign is cut into turfs and each is its own list, so collapsing a four-turf campaign into one event under-reports it by three, and a shared `people` total would make every turf look the size of the whole campaign. **It no longer carries `mode`, `loop` or `suggestedMode`**: creating a campaign chooses no travel mode, and a default reported as a choice is worse than a silence. It also no longer means a route was bought — that is now a separate press, which is worth knowing before reading it as an activation number.

Everything else moved into the panel, including **Cancel and Save**: they are decisions about the CAMPAIGN — keep this work, or put it back — and a footer bar for them across the map was 88px of the thing being drawn on. The confirm is gated on the session having changed something, because this exact button used to carry a "Discard this turf?" prompt that fired on every press with any vertices down — for a gesture that discarded nothing — and it was removed for crying wolf.

Its colour has to be excluded from the next seed by hand, since `seedColor` is a memo over drafts the same call has only just added to. Undo takes back one corner and cannot take back the turf, so a candidate who started one by mistake had nothing to press.

It has no draft behind it, so without this the name typed into its open card, the canvasser picked for it and the card itself go when the cursor leaves — reported from the app as "name the turf, click a different one, and the named one disappears". It is committed SHAPELESS, so the corners already placed do go; a ring below three points is not a boundary and there is nowhere to keep two of them. **Both callers park unconditionally, empty or not.** Parking only what had a name or a canvasser was tried and reported again the same day: the candidate had pressed `Add turf` to get that card, so an empty one is no more disposable than a named one. The rule is the simpler sentence — a card on this panel is a turf they started, and the only thing that takes one off is delete.

Reported from the app: delete the second of two turfs and the turf and its name go, but an empty card is left behind. The turf being cut IS a card, so opening a session on delete ADDED one at the exact moment a turf was removed. With nothing left to fall back to there is no card either — the panel returns to its empty state and the session waits behind it. The freed colour goes back into the palette rather than the session advancing past it: removing the only turf and drawing again should give back the blue Turf 1 was cut in.
- **Save is never disabled, and deliberately NOT gated on having no turfs — including on the empty state.** Leaving a surface you are standing on is never the thing to block: a candidate who opened the map and cut nothing hands back to a step whose own Continue is already disabled, which says so once. (This was briefly gated on the empty state and reverted the same day — the empty state's own CTA is the invitation, not a reason to trap anybody on it.) - **The 150-stop cap is per TURF, and every turf is checked — not the one under the cursor.** `overStopCap` (`createFlow/stopCap.ts`) owns both the constant and the one sentence the two turf lists print, shared for the reason `draftCounts` is shared. The pencil is the draw step's alone — it is the way back to the map, and the boundary is the one thing that can only be edited there. `TurfDraftCard` is deleted.
- **`TurfCard` and `RemoveTurfDialog` also draw a constituent list's shapes** (`contacts/crm/map/ListShapePanel.tsx` and the CRM wizard's `BoundaryStep`), which is how a list boundary and a campaign's turfs look like one product. `noun="shape"` rewords the name field, its placeholder and the delete confirm; `team={[]}` hides the canvasser picker; `dialogLayerClassName` raises the confirm above the full-screen layer that surface lives in. All three default to this feature's behaviour, so a change here is a change there — check both.
- **Undo and the stop count live at the foot of maplibre's control cluster, together.** Four placements were tried on the way here and the failures are the useful part. Following the last placed point puts a 44px target over the 12px vertex handle you grab to drag, and a control that moves cannot be pressed twice — which is Undo's commonest use. Bottom-centre is inside the area being tapped, so a `pointer-events-auto` control there eats the taps meant for the shape. Top-left is out of reach of the thumb doing the drawing. The cluster is the one place already understood to hold controls, already clearing the sheet by measurement, already under the hand. The count sits **left of** Undo inside the same row so the two move as one object; Undo is **labelled** rather than an icon button, because three universal map glyphs above it would make a bare arrow read as a fourth map control. Both live in `VoterMapCanvas` now — `DrawFullScreen` had nothing left to render and is deleted, and the flow's draw branch returns `null`, which is still what takes its own sheet off the map.
- **The map opens out of the pressed rectangle and folds back into it** (`useDrawExpand`). Clip-path, not a transform or a box animation: the map is a WebGL canvas with maplibre's own `ResizeObserver`, so animating its box would drive a resize and re-render the scene every frame, and a scale transform would show it blurred and mis-zoomed the whole way. The Web Animations API rather than a keyframe, because the start geometry is the card's position on screen and is only known at the press — which is why `onOpenFullScreen` and `onEditDraft` carry a `DOMRect` up through the seam. Closing runs the fold BEFORE the flow's sheet returns, since the sheet's destination is the card being folded into. **The clip is released by us, never by the animation ending**: a backgrounded tab suspends the animation clock outright — `playState` stays "running", `currentTime` freezes, `onfinish` never arrives, and the frozen frame keeps applying — so switching tabs during those 280ms would stay clipped forever. Three ways out, first wins: finish, `visibilitychange`, or a deadline. This was not hypothetical; it is what an automated browser hit on the first run.
- **The flow's sheet resumes rather than arrives after the map.** `OutreachFlowShell`/`OutreachSheet` take an optional `instant`, which drops the vaul slide-up; `CreateListFlow` sets it via a ref the first time it hands off to the drawing surface. The sheet is full-screen and modal, so it genuinely cannot stay open over the map — what it can do is stop announcing itself as a new arrival every time the candidate comes back from a surface they were already inside.
- **The draw step's preview is a backdrop, not a map to read.** Short (140/170px), washed LIGHT (`bg-background/65`), one large unadorned button. Dark was the first attempt at the wash and was wrong twice: it turned the basemap into a muddy blue-grey and put a saturated blue button on a dark blue field. The button lost its pencil — it is the only control on the card and the words say what it does. Its label is **"Add turf"** once a turf exists: the press cuts ONE turf, and "more" invited the candidate to expect the next screen to take several. The static image is requested at the height it is drawn at, so `object-cover` does not crop the district out of its own picture.
- **Nothing on this surface explains how to draw.** A modal listing four numbered rules opened over the map on every single mount and inerted it — a toll rather than teaching, paid again on the fifth turf of an evening. Deleted, along with the centred hint before it. The three-point minimum shows itself (the card reads "Drawing" until a shape closes) and the cap is on the pill. **First-run orientation is a real gap and is tracked as its own piece of work** — whatever replaces it must be once-per-candidate, not once-per-mount, and must not inert the map.
- **The palette is SEVEN colours, and the eighth slot is the reason.** Lime sat one slot from Green and read as the same colour in a row of swatches and as the same ring on a map; brown replaced it and was rejected as a turf colour; cyan took it. Then red left — the drawing panel reddens a card that cannot be saved, so a turf cut in red sat under that treatment wearing the same hue, a red dot and a red border beside a red line about a problem, two of the three chosen by the candidate. **An error colour has to mean one thing**, which is the rule to apply before adding any hue back. Retired hues keep their entry in `TURF_COLOR_NAMES` so a turf already cut in one still announces a name rather than its hex. Eight maximally distinct hues was genuinely hard and the eighth was attempted twice; seven is what those attempts kept pointing at.
- **No user-facing copy in this feature mentions buying, and that is a standing rule rather than a wording preference.** The candidate is never the one paying — GoodParty pays the routing vendor — so "nothing has been bought yet" invented a worry the product does not have and explained our billing to do it. The delete and discard confirms say what is lost (the drawing) and nothing about what it costs. The internal notes in this file still say "bought" freely; that is about the transaction, not about anything on screen.
- **A turf's row is one line, and the count holds the right edge.** Name, then who walks it, then what it is worth, separated by a mid dot — the canvasser used to be a second line under the name, which made a closed card's height depend on whether anybody was assigned. Stops is last because it is the more important of the two on this surface: it decides whether the turf can be bought at all (the 150 cap is stated in it), it is on every drawn turf, and it moves as the shape is dragged, where an assignee is optional and set once. Last also means its right edge lands in the same column on every row, which is the only arrangement `tabular-nums` pays off in — a variable-length name to its right would put every number at a different x. The assignee is between the two rather than outside them because it is the one that can be absent: hard-right it would push the count inboard on assigned turfs only, and the count's position would then encode whether somebody is assigned.
- **Removing a turf asks first, and removing the one being cut clears the canvas with it.** Both are recent corrections to the same control. The confirm (`removeTurfDialog.tsx`, shared by the panel's rows and the draw step's cards so one gesture is not worded two ways) **overturns a recorded decision**: Remove used to fire immediately on the argument that a draft costs nothing and has bought nothing. What that understates is that drawing a turf is corner-by-corner work over a neighbourhood, Undo takes back one corner at a time, and there is no undo for the turf itself — so the tap is unrecoverable in the only currency the drawing surface has, and the trash icon sits a thumb's width from the row that names the turf. The clear is the other half: `removeDraft` let go of the draft but left the drawing session holding its boundary, so the ring stayed painted with nothing in the panel that owned it — deleting every turf left an empty campaign with a turf still drawn on it. It now blanks the ring and clears the pending canvasser before handing the cursor on (see `handBackCursor` above). When nothing is left to hand it to, the empty session it opens is **in the freed colour**, computed against the list minus this turf rather than from `seedColor`, which is a memo over state the call has only queued — so deleting the only turf returns the surface to exactly the state it opened in, blue Turf 1 included, unlike `startNextTurf`, which advances the palette on purpose. A turf that was not the one being cut needs none of this: its ring is drawn from `turfDrafts` through `visibleTurfs` and goes with the draft.
- **A canvasser can be picked before the turf exists, so the page holds one.** `pendingAssigneeId` sits beside `newDraftDefaults` and is stamped onto the draft when it commits; `startNextTurf` clears it, because a fresh turf takes the palette's next colour and never the last turf's volunteer. Without it the open card's assignee control would be live and do nothing, which is the exact failure the empty-roster rule beside it exists to prevent. Colour needed no such state — `pickActiveColor` already falls through to `draw.pickColor`, which is the hue the next turf is born in.
- **Undo below three corners keeps the turf and takes away its boundary.** `handlePolygonChange` used to ignore a null ring on the argument that nothing is dropped by doing so; what is dropped is the draft's own polygon, which stays at whatever it was when the third-from-last corner landed — so the panel went on printing "43 stops" about a shape no longer on the map, and `visibleTurfs` and `draftStats` went on answering for it. The draft is **blanked rather than deleted**, because the colour and the canvasser already set on it are work Undo must not silently throw away, and because deleting would renumber the turfs that follow. `isDrawnTurf` (`turfDrafts.ts`) is the one predicate for "this draft has a boundary": both turf lists print `Drawing` instead of a count through it, the map skips it, the per-draft stats skip it, and `CreateListFlow` counts `drawnDrafts` rather than `turfDrafts` everywhere a turf is about to be bought — the save guard, the pending label, the anchor/siblings split and the draw step's own Continue. A blank draft that reached the paid press would post a polygon of nothing.
- **A destructive confirm has to be spelled destructive.** `AlertDialogAction` defaults to `buttonVariants()`, which is the brand blue — so the panel's Discard shipped in the same colour as the Save two inches below it. Every other delete confirm in the app carries `bg-destructive text-destructive-foreground hover:bg-destructive/90` on the action, and this one does now too.
- **The two turf lists share their sentence and nothing else.** The draw step's cards and the panel's rows both print `About N · M doors` through `draftCounts.tsx`, so a correction to that wording cannot land on one surface only; the layouts stay separate, because a 430px row and a spacious card are different objects and the repo's rule is WET over premature DRY. They are never on screen together — the panel is up while the map is, the cards when it is not.
- **Issue capture is a SECOND write after the knock, and the knock must never wait on it.** On both products, behind one flag (`useIssueCaptureFlag()` reads `issue-capture`, resolved for the org's owner, so a volunteer gets their campaign's value), an engaged knock carrying a note posts that note again to `POST /v1/constituent-feedback`, which extracts the issues the person raised, each with a stance and an outcome, and hands them back for the canvasser to confirm. Three things about the sequencing are load-bearing. **The knock saves first**, because the memo resolves its knock by the `clientKey` that write persisted as `sourceId` — there is no interaction id to hand back, the response being `{personId, knockStatus}`. **The memo reuses that same `clientKey`**, so one knock has one memo and a dead-zone retry upserts rather than forking. And **every exit from the capture step advances the walk** — confirmed, skipped, capture failed, confirm failed — through the one `advance()` helper, because the door is already logged by then and holding a canvasser there over a second request that failed is strictly worse than losing the memo. `RecordKnockForm.issueCapture.test.tsx` asserts that failure path directly; if a future change can trap the walk at a saved door, that test is what should catch it. **With no signal** the form sends nothing: `useOfflineMemo` (`app/dashboard/shared/dictation/`) holds the knock and its memo in IndexedDB, knock first, the walk moves on with the status `deriveKnockStatus` would give (computed in the form), and a snackbar says "Saved on your device. It will be sent when you have signal." It holds when `navigator.onLine` is false at Save, when the dictation socket failed to open for this door, and when the knock's request gets no answer at all, so a weak-signal door never shows "Saving failed". All of it only where capture is on: with the flag off a save is exactly what it was (mounting the form still opens IndexedDB for a fire-and-forget queue read), and the mic records on the phone only on an engaged door with capture on (anywhere else it is the ordinary dictation mic). There is no confirm card: the memo is transcribed, extracted and confirmed server-side once sent (`app/dashboard/issue-capture/AGENTS.md`). The queue files a knock and its memo under the stop target, so saving the same door again offline replaces them, and, with capture on, a save that reaches the server drops whatever the phone still held for that door (with it off the save never touches the queue). A knock saved online whose only memo is an earlier recording sends the recording after it ("Note saved on your device. Sending it now."); words, when there are any, win over a recording. The queue drains from the form and, through `useOfflineQueueDrain`, from `NativeDoorKnockingPage` and `VolunteerWalkPage` themselves, on mount, `online` and a return to view, so a canvasser who closed the door's form and walked on still sends everything when signal returns, on the same page and the same walk: the walk lives in the page's state, which is why the service worker never reloads the page on reconnecting (`app/shared/AppServiceWorker.tsx`); `drainQueue` runs one drain at a time, so the two never send an entry twice. A 401, 5xx or no answer keeps an entry for the next drain (a 401 is what a request looks like in the moment after reconnecting, before the session refreshes). A 400, 403, 404, 409 or 422 with a reason drops it (a 403 is a lapsed Pro, refused every time), except the 404 the `issue-capture` flag gives while it is off or Amplitude does not answer (`errorCode: ISSUE_CAPTURE_OFF`), which keeps the memo until the flag is back, and so does an upload S3 refuses with a 4xx other than 403 (reported to Sentry with S3's reason; a 403 there is an expired policy and is renewed); a dropped knock takes its memo. An empty recording is never kept, since S3 refuses an empty file every time. Saving a door or call again with no memo drops the one held from the earlier save. Any drain that sends something, the form's included, tells every mounted page through `useOfflineQueueDrain({ onSent })`, which is how the phone caller re-reads its list.
- **`recordedRef` is a ref and not state, for the reason `activeDraftRef` is.** `advance()` is called from mutation callbacks in the same tick the knock's success handler sets the value, before any render — read from state it would be null and the walk would silently stop advancing on exactly the failure paths that need it most.
- **A door's unsaved answers outlive its form, and only for the walk.** `PersonSheet` keys `RecordKnockForm` on `stopTargetId`, so tapping a housemate and back, or closing the sheet, remounts it on a blank ladder. `WalkSurface` holds a `useUnsavedDrafts<KnockDraft>()` store (`app/dashboard/shared/useUnsavedDrafts.ts`) and the per-target replay keys, in memory and never in browser storage, and hands both to `WalkView`: the sheet's `peek` snap unmounts `WalkView`, and a key lost there turns a dead-zone retry into a duplicate knock. The form stashes its answers and typed note into it on unmount and restores them on mount. Not a recording in progress, and not a confirm card, whose knock is already saved. A save that lands, a hold and Cancel clear it, and once a save has landed the form stashes nothing until Cancel, so a transcript arriving after Save cannot bring the saved answers back. A knock that failed to save keeps its answers this way, so a reopened sheet retries it with Save alone. The phone caller does the same with `PhoneBankingOutcomeForm`, keyed `entryId:personId`, from `PhoneBankingCallerPage`.
- **Capture analytics live under `EVENTS.IssueCapture`, not `EVENTS.DoorKnocking`.** The same three events fire from a knock and from a call, on both products, so `channel` and `product` are properties and the group is named for the feature rather than the surface or the product; a Door Knocking-named event would have to be written twice and the rollup metric would have to add two events together. `MemoSkipped` matters as much as `MemoConfirmed` — together they are the only measure of whether a canvasser will answer a question about a conversation they have just finished, which is the riskiest assumption in the feature. `MemoConfirmed` carries `corrected`, a boolean over whether the canvasser changed what the model proposed (an edit or a removal; `wasCorrected` in the card), and `issueCount`, how many issues were confirmed, and **never what either of them said**: a person's words are not an analytics payload, the same rule `DoorLogged`'s `hasNote` already follows.
- **A turf links to what people said on it through `WhatWeHeardLink`** (`app/dashboard/issue-capture/`), keyed on `turf.outreachId`, the envelope the report is read by. `TurfSummaryRow` puts it in the card's `heard` slot, on finished turfs too since Done is what starts a summary, and `TurfDetailsSheet` puts it under Progress (unreachable with the sheet). It reads the product's capture flag without exposure (the confirm card is the treatment) and the report for its two counts, and renders nothing while the flag is off or until somebody has answered, so the success screen's brand-new turfs never show it. The sheet passes `isServeOrg`, because gp-api picks the flag by the org's slug.
- **`IssueCaptureConfirmCard` is one block per issue, and "Looks right" confirms the list as it stands.** A note can name up to five issues, in the order they came up. Each block (issue, where they stand, what they want) can be edited or removed, and the confirm sends the whole list (`PATCH :id/confirm { issues }`), which replaces the memo's issues: a removed one is left out, a block with no issue name is left out, and an empty list confirms a note that named none (the card then reads "No issue came up in this note."). Each issue carries the `fromIssueId` of the proposed issue it started as, so gp-api keeps that row, and the model's answer on it, beside the canvasser's; an id and not a position, because confirming renumbers positions and a confirm tapped again after a lost response has to land on the same rows. A failed extraction shows one empty block to fill in. It is `IssueCaptureConfirmStep`, a step of the `PanelDrawer` the questions were answered in (below). **Skip saves too**: it confirms the note with no issues (`PATCH :id/confirm { issues: [] }`), so the note's words still go into the summary; `MemoSkipped` rather than `MemoConfirmed` is the only difference. Dismissing the step (swipe, overlay, close, Escape) is a Skip, since the knock or call is already saved; a dismiss while a save is in flight is ignored.

Stacked at different heights, a step read as one that came up short, and the same step at two heights on two surfaces read as two different components.
- **`IssueCaptureConfirmCard` deliberately carries no `'use client'`.** `RecordKnockForm` is the boundary and pulls it into the client graph; a directive of its own would cost a tick on the ratchet (`scripts/check-use-client-count.mjs`) for nothing. - **Do-not-knock and not-a-voter are shaded off the map, and they are a MASK rather than a filter.** `KNOCKABLE_DIM_KEY` is a third per-organization plane beside `canvassStatus` and `contactsMade`, built from the same `personIdsByFieldValue` reads the preview and the create already make. Nothing selects it: `runFilter` and `polygonStats` drop byte-0 people unconditionally, with no `FILTER_KEY_TO_DIM` entry and no pill — which is exactly what lets this ship without the deferred filter-catalog review. **Its encode is the inverse of every other plane's `?? 0`**: the default is knockable and byte 0 is the suppressed one, so getting the polarity backwards hides the whole district rather than nobody. **Absent means do NOT suppress**: a plane of yeses would claim every door is open, which is the wrong way to be wrong about somebody who said don't come back, so gp-api omits it rather than guessing and the client falls open.
