## Analytics

Events live under the `Contacts` group in `helpers/analyticsHelper.ts` and fire frontend (screen views and user clicks the browser directly observes). Every event carries a `context: 'win' | 'serve'` property sourced from the provider's `isWinContext` — so Win adoption of the unified path is a property filter in Amplitude, not a duplicate event set. Don't mint per-context events.

- `Contacts - Contacts Viewed` — fires once on page entry from `CrmContactsPage`, `{ context, surface: 'crm' }` (ready-gated + ref-latched). `surface: 'crm'` dates from ENG-10767, when this page's users had vanished from the Viewed chart under the old (flag-gated) event; historical rows without the tag predate that fix.
- `Contacts - Voter Data Unavailable` — fires once per page entry from `CrmContactsPage` when `voterDataUnavailable` is true, i.e. the org has no resolvable district and the page can only offer the support handoff. `{ context }`, same `isWinContextReady` gate and ref latch as `Contacts Viewed` (firing before the mode settles would label a Win user as Serve). 437 active campaigns are in that state; this measures how many actually land there, which is the input to whether self-serve remediation is worth building.
- `Contacts - Download` / `Segment Viewed` / `Segment Created` / `Segment Updated` / `Segment Deleted` — existing events, now carrying `context`.
- `Voter Data - Contact Searched` (Win) / `Constituent Data - Contact Searched` (Serve) — the one deliberate exception to the context-property rule: the CRM brief specs the typeahead search events as product-specific by nav surface, each with `resultCount`. They fire once per distinct resolved search from the `settled` derivation in `useContactTypeaheadSearch` (ENG-10688) — never on aborted/superseded requests, sub-3-char input, or the non-pro modal path; an empty result set fires with `resultCount: 0`. Mode comes from `useWinVoterContext()`, gated on `isReady` like the mount event.
- `Voter Data - Note Added` (Win) / `Constituent Data - Note Added` (Serve) — same product-specific naming exception, no properties. Fires from `NotesSection` exactly once per successful create (never on edit, delete, or a failed create). Mode comes from `useWinVoterContext()`, gated on `isReady`.
- `Constituent Data - Follow Up Changed` — Serve-only, the mirror of the Win event below. Fires from `FollowUpRow` once per confirmed-successful PATCH `/v1/contacts/:personId/follow-up`, `{ from, to }`. Never on a failed PATCH.
- `Voter Data - Contact Status Changed` (ENG-10836) — Win-only (no Serve variant: the status row only renders for Win). Fires from `StatusRow` once per confirmed-successful PATCH `/v1/contacts/:personId/status`, `{ field: 'voter_likelihood' | 'support_status', from, to }`. Never fires on a failed PATCH or a reselect of the already-current value.
- `Voter Data - Contact Viewed` (Win) / `Constituent Data - Contact Viewed` (Serve) — same naming exception, no properties. Fires from `PersonContent` once per record open, gated on `useWinVoterContext().isReady` (a person remount via `key={person.id}` re-arms the latch). Distinct from `Contacts - Contacts Viewed`, which fires from the contacts page itself.
- `Voter Data - List Created` (Win) / `Constituent Data - List Created` (Serve) — same naming exception (ENG-10709). Fires from `crm/wizard/CreateListWizard.tsx`'s create-mutation `onSuccess`, once per successful create, only for the voter-file branch. `{ variableCount, hasParty }` — `variableCount` is the number of `filters.config.ts` categories with a selection (`crm/shared/voterFileFilterTransform.util.ts`'s `countSelectedFilterCategories`; a Support Status selection counts as one more category). `hasParty` (via that file's `hasPartyFilterSelection`) is Win-only — Serve never renders the Political Party section (`VoterFileStep` strips it for `isElectedOfficial`), so the property is omitted as a key entirely for Serve, never sent as `false`.
- `Voter Data - Activity List Created` (Win) / `Constituent Data - Activity List Created` (Serve) — same seam, fires only for the activity branch. `{ sourceCampaign, actionFilter }` — the wizard supports N stacked conditions (`crm/wizard/ActivityStep.tsx`), so both properties aggregate across all of them: `sourceCampaign` joins each condition's resolved outreach name (or `'any'`) with `', '`; `actionFilter` is the deduped union of every condition's selected outcome values, as an array (not a HubSpot-email-driving event, so no flatten-to-scalar requirement). `WizardActivityCondition` carries an `outreachName` field (resolved at selection time, never sent to the backend) purely so this handler doesn't need a second outreaches fetch.
- `Voter Data - List Exported` (Win) / `Constituent Data - List Exported` (Serve) — same naming exception. Carries `{ surface: 'listDetail' | 'recommendedDetail' }` plus `{ listSize }` (the people count already shown on the sheet). **Two export surfaces, both in `crm/`:** `crm/lists/ListDetailSheet.tsx` (`listDetail`, the saved-list CSV) and `crm/recommended/RecommendedListDetailSheet.tsx` (`recommendedDetail`, the variant download route) — the only two consumers of `crm/shared/useContactsDownload.ts`, and the event fires from nowhere else. The two former outreach surfaces (`outreachWizard`, `outreachTable`) and the `outreach/util/downloadVoterList.util.ts` helper they routed through were all deleted in the outreach v2 rewrite; historical rows still carry those `surface` values. Fires only from the cookie-confirmed **success** branch, never the ambiguous 15s fallback or a failed download (`awaitDownloadStarted` resolves a boolean specifically to keep that distinction), and is additionally gated on `isWinContextReady` and on the demographics count being known at confirm time — so a click landing before `GET /v1/contacts/list-detail` resolves emits nothing at all rather than a `listSize`-less event.

  **Counting exports: use this event, not `Contacts - Download`.** `Contacts - Download` fires at click time and always fires; `List Exported` fires only on confirmed success behind the gates above. A union of the two double-counts, and substituting `Contacts - Download` overstates. The gap between them is a useful health signal (failed downloads plus the readiness race), not a demand signal. Audited 2026-09-16 (DATA-2343).

ENG-10767 closed the remaining CRM gaps (all ready-gated on `isWinContextReady` like the events above):

- `Contacts - Segment Viewed` — also fires from `ListDetailSheet` on every sheet open once the segment resolves (`{ segment, type: 'custom', context }`), restoring the legacy segment-picker parity for "which lists get used".
- `Contacts - Segment Deleted` / `Segment Updated` / `Segment Created` — the CRM management surfaces reuse the legacy events: `DeleteListDialog` fires Deleted (`{ context }`), `CreateListWizard`'s edit mode fires Updated with `{ action: 'filters', context }`, and `useDuplicateList` fires Created with `{ source: 'duplicate', context }` (the wizard's product-specific List Created events stay a pure wizard-outcome metric).
- `Contacts - List Wizard Method/Conditions/Boundary/Name Viewed/Completed` — per-stage funnel for the URL-stable create-list wizard (`{ context }`, + `{ branch }` on conditions/boundary/name). Viewed re-fires on Back re-entry (effect keyed on the open session + active-stage identifier only); Name Completed fires alongside the List Created outcome on a successful create. Serve's wizard never fires the Method stage. **Boundary Completed carries `{ hasBoundary }`** — the step is skippable, and how often it is skipped is the question the stage exists to answer. `STAGE_VIEWED_EVENTS: Record<WizardStepName, string>` is exhaustive over the step union on purpose: a step added without a registered event fails the typecheck.
- `Voter Data - List Boundary Saved` (Win) / `Constituent Data - List Boundary Saved` (Serve) — same product-specific naming exception, mode from `useWinVoterContext()` inside the hook. Fires once per confirmed-successful `PUT /v1/voters/voter-file/filter/:id` from `crm/map/useSaveListBoundary.ts`, the hook both drawing surfaces write through, `{ listId, cleared, surface }` — `cleared: true` is a boundary removed, which is a different act from setting one and has to be countable apart from it, and `surface` is `listDetail` or `chat` because "does anyone ever draw from inside a conversation" is the question the second surface was built to answer and cannot be asked of one undifferentiated event. Never fires on a 409 or any other failure. The wizard's own boundary rides `List Created` and the funnel stage instead; there is no second Saved event for a list that is born with one.
- `Contacts - Assistant Chat Opened` — `CrmAssistant` fires Opened per surface open (`{ context, source: 'message' | 'history' | 'toolbar' }`). Each send is `AI Chat - Message Sent` with `surface: 'contacts_assistant'`, fired once per visible user send by the chat body (`analyticsSurface`), which covers the bar's first message (`via: 'assistant_bar'`, sent as `pendingMessage`) and every composer follow-up alike — so `CrmAssistant` must NOT also fire it on submit, or the first message double-counts. Hidden kickoffs and sentinels never fire it.
- `Voter Data - Send Outreach Clicked` — the CRM list → outreach funnel entry, fired when a "Send outreach" button opens the channel picker, from every surface, with `{ surface: 'listCard' | 'listDetail' | 'universeRow' | 'recommendedCard' | 'recommendedDetail' }` + `{ listId }` wherever a saved list is behind the click (the two saved-list surfaces, and a recommended card that already matches one) + `{ variant }` on the two recommended surfaces. Win-only by construction (ENG-10749), so no ConstituentData variant. **It is the funnel's entry point only.** The `audienceSource`/`audienceListId` half of the join lived in the legacy outreach wizard's audience step; the v2 channel flows emit no counterpart, so a completed campaign cannot currently be attributed back to the CRM click that started it. Closing that needs a deliberate event decision, not a revived property name.

Source the `context` from `isWinContext` (single source of truth in `ContactsTableProvider`) — don't recompute Win-vs-Serve. New events: follow `.claude/skills/instrument-analytics-event/SKILL.md`.

Import contacts (Serve only, behind `serve-import-contacts`) fires three events from `crm/import/ImportContactsWizard.tsx`; gp-api owns `Contacts - Import Completed` and the review events.

- `Contacts - Import Started` — once a chosen file is read and passes the CSV, 25 MB, empty and 100,000-row checks, `{ sourceType: 'csv', rowCount }`. Choosing another file fires it again.
- `Contacts - Import Consent Affirmed` — once `POST /v1/contact-uploads/:id/uploaded` accepts the upload, which is only sent with the consent box checked, `{ rowCount }`. Never when a presign, PUT or confirm request fails; it still fires for a file the queue job later rejects.
- `Contacts - Import Abandoned` — when the wizard closes before an upload is accepted, `{ lastStep: 'file' | 'columns' | 'name', rowCount }` (`rowCount` null before a file is read). Closing is blocked while the upload is in flight, so it never fires mid-upload.
