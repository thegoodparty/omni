# app/dashboard/door-knocking/

Door-knocking / canvassing dashboard. Tracks volunteer interactions logged in the field, summarizes by day / rating / survey, and lets campaigns design custom door-knocking surveys.

## The four surfaces, and what the orchestrator keeps

`NativeDoorKnockingPage` is an orchestrator, not a place to build UI. Four surfaces are rebuilt independently behind four frozen prop interfaces, so **a change to one surface should not touch this page**. Each interface is documented in its own file above the props; read that comment before adding a prop, and prefer a new file to growing a shared one.

| Seam                                                                 | Owns                                                                                                                     | Gets from the orchestrator                                                                                                |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `DoorKnockingManageView` (`MapScope`, `DoorKnockingManageViewProps`) | The saved-list rail, the legend, their layout at every width, and `railOpen`                                             | `scope`, `statusCounts`, `statusFilter`, `hiddenTurfIds`, and one callback per gesture                                    |
| `CreateListSurface` (`CreateListSurfaceProps`)                       | Every wizard step, and the whole ADR 0010 address preview (`previewRing`, the query, and the four props derived from it) | `step`, `filters`, `ring`, `turfStats`, `districtHouseholds`, `unpreviewableKeys`, `isElectedOfficial`, the draw controls |
| `TurfDetailsDrawer` (`TurfDetailsDrawerProps`)                       | Resolving the turf's saved list and running its pre-route counts                                                         | `turf`, `pack`, `packPending`, `onClose`, `onDeleted`                                                                     |
| `WalkSurface` (`WalkSurfaceProps`)                                   | The stop list, the door sheet and its notes, the knock form, and which resident's sheet is open (`selectedTargetId`)     | `turfId`, `openStopRequest`, `selectedStopId`, `onSelectStop`, `onKnockRecorded`                                          |

**What stays in the orchestrator is what the MAP also reads.** `VoterMapCanvas` is shared by all three modes, so any state the canvas consumes — the drawn `ring`, the filter draft, the selected list, the walk's marked stop (`selectedStopId`), the hidden set, the status chips, the camera's `focusTurf` — lives on the page and arrives as props. **`selectedStopId` and `selectedTargetId` are not the same selection**: the marked stop is up here because the map rings it, while which resident's sheet is open stays inside the walk, which is why only the first crosses the seam. Everything else moved down. The couplings between those values are the page's too (selecting a hidden list reveals it; hiding the selected list deselects it), so a surface reports the **gesture** and never the consequence: `onSelectTurf` means "a row was tapped", not "select this".

**Two surfaces own a half of the canvas each, as hooks the page calls at the top level** — `useCreateListDraw` and `useWalkMapSession`. The canvas outlives both surfaces, so their map state (draw tokens, the point count, the two coach marks, the route pins, the tapped-pin request) cannot live inside a component the page unmounts. Keeping it in the surface's own file is what lets an agent change what its step asks of the map without editing the orchestrator: the page only spreads the hook's result onto `VoterMapCanvas` and renders `DrawHintOverlay` / `WalkMapHint`.

**Display state that only one surface reads belongs to that surface, and resets by being unmounted.** `railOpen` is the worked example: the create flow and the walk each replace the manage surface outright, which is exactly the "leaving the landing map resets it" rule the page used to enforce by hand in `closeFlow` and `endWalk`. `hiddenTurfIds` and `statusFilter` cannot follow it, because the canvas reads both — those are still reset explicitly, and that asymmetry is the rule, not an oversight.

**The knock dialog is deliberately the page's**, not the manage surface's: it is the handoff from a list into a walk, it starts the walk session, and it is the one moment both modes are live at once.

## Patterns

- **Charts use shared color tokens** from `components/interactionsColors.ts` — keep palette centralized; don't inline hex values.
- **Surveys are campaign-scoped**: each campaign authors its own survey questions, used by canvassers in the field. Survey CRUD lives in `surveys/`.
- **Aggregations come from gp-api**, not computed client-side. The components display rather than compute.

## Gotchas

Grouped by the surface each decision belongs to, and the headings are stable:
**append inside the section your change belongs to**, never at the end of the
file. The grouping exists because this list is edited by several agents at once
and a flat tail is a guaranteed conflict; the sections are the same four
surfaces as the seams above, plus the shared concerns none of them owns alone.
A decision that spans surfaces goes in a `Shared` section rather than being
written twice.

### Shared — the page, its gates and analytics

- The legacy tabs on this page only _display_ data sourced from third-party canvassing tools (eCanvasser etc.) via gp-api. Knocks are logged in-app from `native/` (`RecordKnockForm` → `POST /v1/door-knocking/interactions`), which writes to the CRM's own tables and never to eCanvasser.
- **Analytics live under `EVENTS.DoorKnocking`** (`Door Knocking - *`), not the legacy `EVENTS.Dashboard.VoterContact.DoorKnocking` group, which belongs to the script/eCanvasser surface. A completed walk also fires the canonical `Voter Outreach - Campaign Completed` with `medium: 'doorKnocking', method: 'native'` — that's what the door-knocking activation metric counts, so don't remove it while refactoring the walk exit.
- **The voter pack and every turf read resolve a district server-side** (`resolveEligibleDistrictId` in gp-api's `doorKnockingPack` / `doorKnockingKnock` services), so an org with no resolvable district can only 400. `NativeDoorKnockingPage` gates both queries on `useDistrictResolution` (`app/dashboard/shared/`) and explains instead. Gating at the shell also covers the write paths (`POST turfs`, `POST turfs/:id/knock`, `POST interactions`) because their affordances never render. The unavailable branch has to come **before** `packQuery.isPending`, or that branch claims to be loading forever.
- `doorKnockingServe.service.ts` in gp-api is about **serving a route** to a canvasser — it is not the Serve product. Door knocking is Win-only (`v2Category: 'campaign'` in `DashboardMenu.tsx`).
- **The sidebar entry mirrors `DoorKnockingPageGate`'s branch, and must keep doing so.** `getDashboardMenuItems` takes a `doorKnocking` gate: flag on needs a resolvable district (the eCanvasser record is irrelevant, because the route renders the native map either way) **and `proAccess`** (ENG-10888 — see the Pro-gate note below), flag off or unsettled needs the eCanvasser record, because the legacy dashboard is all the page can render. The link was previously pushed on the eCanvasser record alone, which hid the native pilot from every candidate who had never integrated eCanvasser. The flag read here passes `trackExposure=false` — the page is the treatment surface, and counting a nav render as an exposure would inflate the denominator with people who never clicked.
- **The native feature is Pro-gated (ENG-10888), and both the nav and the page read the same predicate.** `canUseProFeatures` — `!!campaign?.isPro || !!electedOffice`, the CRM's own spelling (`ContactsTableProvider`) of gp-api's `ContactsService.assertProAccess` — decides the sidebar entry in `DashboardMenu` and the branch in `DoorKnockingPageGate`. Keep them identical: the nav must never be stricter than the API, or a candidate the API would serve loses their link. Every `/v1/door-knocking` route enforces it server-side **except** `POST /do-not-knock` and `POST /not-a-voter` (ADR 0007 / ADR 0008), so a lapsed org can still honor "don't come back" — see "The Pro gate" in `gp-api/docs/door-knocking.md` for the full route table. Reads are gated too, so there is no locked-preview mode: a map you can open but not route is worse than a clean upgrade message, and each knock spends real vendor routing credits. **The upgrade card lives in `DoorKnockingPageGate`, not a file of its own** — that keeps the `'use client'` ratchet flat (the gate is already a client component; a new one would need the baseline bumped). It is a safety net for a URL or a stale tab, not a funnel: because the nav entry is hidden for non-Pro — unlike Know Your Opponent, which shows its entry to non-Pro candidates as an upsell — it is deliberately shorter than `OpponentProLockedView` and fires no exposure event. **Control is untouched**: the flag-off eCanvasser dashboard was never Pro-gated and still isn't. Two consequences worth knowing before touching either surface: an in-flight `useElectedOffice` is **not** a refusal — a Serve org's access comes from that query and its campaign is never `isPro`, so the page gate waits (and only for a campaign that isn't already Pro) instead of flashing the upgrade card at the org most entitled to the feature; and `door-knocking-flag-gate.spec.ts` now has to provision a Pro campaign (`setupProCampaignUser`), because the entitlement it used to be able to ignore is upstream of the native arm it asserts.

- **Ending a walk marks the list Done, but only a walk that finished one.** `endWalk` calls `useWalkCompletion` (`native/walkCompletion.ts`), which imports the rail's own `useTurfLifecycle` rather than posting `turfs/:id/complete` itself — one writer for the mutation, and it already invalidates the rail before its snackbar so the candidate lands back on a card that reads Done. It lives on the page because `endWalk` does: the rail card could wire its own Done button in #1395 and the walk's exit could not, since only the orchestrator knows a walk is ending. **The unconditional version was rejected, and not narrowly.** Done is the one rail action with no undo beside it — archive has Restore, delete has a confirm — and what it takes away is Knock, since a done card offers Details and Move to Archive instead. Leaving is also the ONLY way out of a walk, so stamping every exit would read "I am done for now" as "this list is finished" and take the way back in away from a canvasser who knocked three doors of fifty. **"Finished" is the walk's own progress bar**: every knockable person logged, per `routeCounts` — do-not-knock and not-a-voter residents dropped, `logged` meaning an answer is written down and not that a conversation happened. That is the number the canvasser has been watching climb all evening, so a list stamping itself Done as they leave a 40/40 walk is the outcome they already believe in. **Two states are deliberately not finished**: a route that isn't in cache (a serve that never landed reports zero targets, which is indistinguishable from a list with nobody in it — never stamp off a fetch that failed), and a list where nobody is knockable at all. Both are the same asymmetry: the card's "Mark this list done" is one tap away, while an unwanted Done can only be undone by archiving and restoring, so erring toward not completing is the cheap mistake. **The turf the write runs against is held in a ref for the length of the mutation.** `useTurfLifecycle` reads its turf out of the render it was called in, and a mutation observer pushes each new render's options onto the request already in flight — so `walk.end()` clearing the session in the same handler that starts the write swapped the id out from under it and the POST went to the hook's standin turf. That is a property of calling a card-shaped hook from a page, not of this feature; anything else the orchestrator writes on the way out of a mode needs the same care.

### Shared — counting, vocabulary and status presentation

- **Stops, doors and people are three different numbers — `routeCounts.ts` owns the definitions.** A stop is a geocoded coordinate the router visits, a door is an address (unit included), a person is a targeted voter; a block of flats is one stop, many doors, more people. Anything user-facing that says "doors" must count doors: `countDoors` for a frozen route, `polygonStats().households` for a shape being drawn. This drifted badly once — `WalkView` printed `stopCount` as doors, `WalkSheet` summed targets as doors, and the same route reported two different door counts depending on the surface. The 150 cap is on **stops**, so a "150-stop limit" message next to a doors count is correct, not a mismatch. **Every people figure counts knockable people** — `isKnockable`/`knockableTargets` in the same file, which drop ADR 0007 do-not-knock residents _and_ ADR 0008 not-a-voter residents. One predicate covers both because they differ only in what to say at the door, which is the walk UI's problem; to a count they are the same fact — nobody to talk to. That covers the printed sheet's header, the details sheet's progress stat and `WalkView`'s logged-of-total, because a door nobody should knock is not a conversation anyone can have: counting it promises an evening that can't happen and holds a canvasser who correctly skipped it below 100%. The sheet still _lists_ flagged residents one row each, since paper freezes at print time and has to carry their skip instruction — a sheet listing more names than its header counts is intended, the header being the evening's work and the rows the index. Status rollups follow the same rule: `rollupStopStatus` (the webapp's, and gp-api's call site in `doorKnockingServe.service.ts`) drops flagged residents, because `unknown` outranks every other status and one flagged neighbor would otherwise report a fully-logged stop as still-to-knock. Same reason the collapsed stop row omits their per-person dot. There are **four** suppression sites and they must not drift: `knockableTargets`, `rollupStopStatus`, `WalkView`'s `advanceFrom`, and `print/pdf/walkListRows.ts` — auto-advance would otherwise walk a canvasser back into the door they just flagged, and paper would print a blank form beside the name of someone who moved away.
- **`WalkView` says "logged", not "reached".** `not_home`, `inaccessible` and `refused` all satisfy the `knockStatus !== 'unknown'` predicate the progress bar counts, so a canvasser who knocked forty doors and spoke to nobody used to read "40/40 reached" — a claim about conversations that never happened. The quantity is doors with an answer written down. `TurfDetailsSheet` states the same figure and uses the same word.
- **A flagged resident's marker replaces their status, everywhere they are listed beside other people.** `targetMarker` (`native/statusPresentation.ts`) is the one source: `WalkView`'s collapsed and expanded stop rows, and **both** of `PersonSheet`'s rosters (the resident switcher and the Household section). The sheet's rosters were the gap — the same person read "Do not knock" in the list and "Support unknown" one tap later, two answers to one question. Do-not-knock outranks a not-a-voter reason, because it is an instruction about the door rather than a fact about one of the people behind it. Paper's longer form is `skipInstruction` in the same file, read by `print/WalkSheet.tsx` and `print/pdf/walkListRows.ts` so the two formats cannot word it differently. The short marker reuses `NOT_A_VOTER_LABELS` from contracts — the CRM activity feed's vocabulary — so one flag isn't called two things in one product.
- **The pre-route walking estimate is local, not the vendor's.** 45 doors/hour (`DOORS_PER_HOUR` in `native/walkEstimate.ts`, from the POC) turns **doors** into a time before any route exists. The real duration only arrives once the route is built server-side — and building it is a billed, irreversible Geoapify call, so the surfaces that help someone decide whether a list is a reasonable evening all have to answer before it: the draw step while drawing, and `TurfDetailsSheet` on a saved-but-unknocked list. Both quote the shared helper and both **name the rate** in the copy, so it reads as a rule of thumb rather than a computed promise; that is why the constant does not live in the draw step that first needed it. Once a route exists, `route.totalSeconds` is the number. 100 stops warns and 150 blocks — the soft limit must stay non-blocking.
- **A missing saved list is not an unfiltered one.** `savedListFilterKeys(undefined)` is `{}`, and `polygonStats` reads `{}` as "no filters" and answers with every door in the polygon — the exact number `TurfDetailsSheet` exists to stop reporting. The list can be missing while `savedListsQuery` is in flight, after it errors, or because the filter was deleted in the CRM, so the page resolves it **before** computing and yields no stats in all three cases; the sheet then distinguishes pending (skeleton) from settled-with-nothing (`Unavailable` plus a line saying so). Never let an absent list fall through to a computation, in either direction — it fails silently and plausibly. **The landing rail follows the same rule off one value.** `scopeSelections` is `null` — not an empty map — when the selected turf's list hasn't resolved, and `selections`, `filterResult`, `statusCounts` and the rail's own copy all propagate that rather than each deciding for itself: four surfaces hang off this scope (the heading, the count line, the seven legend chips, the dot mask) and they agreed on the whole polygon's population under one list's name. `scopePending` renders "Counting the voters in this list…" with skeletons in the chips; `scopeUnavailable` (errored, or the filter is gone from Contacts, which never self-corrects) says the filters could not be loaded and prints an em dash per chip. **Pending has to gate on both queries**, because `scopeSelections` needs the pack's manifest as much as the list: asking only about `savedListsQuery` left a warm list cache against a cold pack — the ordinary ordering, since Contacts populates the lists while the pack is this page's own large fetch — falling through to `scopeUnavailable` and printing the permanent-failure em dashes at something still loading. `packPending` is named once and shared with the sheet's `listStatsPending` so the two surfaces can't answer that question differently. The chips are `disabled` in both — a chip narrows _within_ a scope, so with no scope it could only flip its own `aria-pressed`. `filterResult` becomes an all-zero result rather than `null`, so the map keeps its instance and shades nothing; the heading still names the list in all three states, because it is the scope the candidate picked and not a claim about its size, and **`Show all` renders in all three** since the unresolved scope is the one someone most needs a way out of. A list that exists with no options set is a _different_ state from an absent one — it legitimately targets everyone in its ring, and the page test's default fixture is that list, so the two can't be conflated.
- **`route.totalSeconds` is travel time, not the evening.** It traces to Geoapify's `agentPlan.getTime()`, and the jobs gp-api sends carry an id and a location and **no `duration`** — so it is the walk between doors with zero time spent at them. A 100-door route reports 50-60 minutes against ~2h15m of actual work at the app's own 45-doors-an-hour figure. `TurfDetailsSheet` therefore labels it **"Travel time"** (mode-free: the adjacent "Route type" stat already says walk or drive, and the mode is unknown while the route is still loading), and keeps **"Knocking time"** for the pre-route estimate, which is the opposite quantity — a sustained pace with conversations included. Two labels rather than one that has to be a lie for one of them; the alternative, synthesizing travel + time-at-doors into one figure, would invent a number no other surface reports. **The word is "travel", everywhere the number appears**: `WalkView`'s stops header and `walkFacts.ts`'s `walkSummary` (which both paper surfaces read) print `31m travel` rather than a bare duration, matching the per-leg number that already reads `3m walk`. "travel" and not "walk" for the totals, because on a screen called WalkView "the walk" is the whole outing — the exact thing the number is not.
- **Nothing says "reached".** `knockStatus !== 'unknown'` counts not-home, inaccessible and refused alongside the answers, so it is the count of doors **logged** — the detail sheet's stat is "People logged". Calling it reached credits a walk with conversations it did not have.

### Shared — the map canvas

- **Don't put `items-center` on a `flex` `<button>` here.** `app/globals.css` carries an unlayered legacy rule (`a.flex.items-center:not([data-slot])`, and the `inline-flex` variants) forcing `display: flex; flex-direction: row`. Unlayered CSS outranks everything in `@layer utilities`, so `flex-col` **and** `lg:hidden` both silently lose on such a button — the rail's sheet handle was laid out as a row and still displayed at desktop until it dropped `items-center` and centered its children instead. Styleguide `Button` carries `data-slot`, so this only bites raw `<button>`s.
- **The map opens at street level, and the page is what says so.** `NativeDoorKnockingPage` passes `initialZoom={16}` to `VoterMapCanvas`; without it the canvas falls back to `fitBounds` over the whole pack, which is district zoom — a candidate opening the page landed on a shape with no street names in it and nothing to orient against. 16 is where they first appear. **Where it opens is `packOpeningCenter`, not the middle of the pack's bounding box.** A bbox midpoint is a geometric artifact rather than a place: on an L-shaped or crescent district, one split by a lake or a park, or two towns with fields between them, it lands where nobody lives — and at zoom 16 that spot is the whole screen, which is how this opened as a street with no dots on it and got reported as the district's dots being missing. It is also the statistic one bad coordinate moves furthest, since it reads only the four extremes, and nothing bounds a coordinate on the way in — `MAPPABLE_ONLY` in gp-api's `voterPack.service.ts` gates on rooftop accuracy and a numeric-text regex, never on a range or on the district's own shape, and the district join is a registration fact rather than a geographic one. So the anchor is a component-wise **median** and the answer is the real dot nearest it: a cluster holding more than half the dots brackets the median rank on both axes, so a two-town district opens in the larger town rather than the farmland, one mis-keyed row moves the anchor by a rank instead of by its own distance, and snapping to a dot makes "there are voters here" unconditional rather than likely — including the even split where the median itself sits in the gap. A mean was rejected for the same reason the bbox was; the pack's own over-allocated `Float32Array` was **not** the cause and structurally cannot be, since `PackEncoder.toBuffer` writes exactly `positionsLength` and the manifest schema refines `positions.elementCount === counts.dots * 2` before `decodePack` mounts the view. The prop is read **at mount only** and names the opening view rather than controlling the camera: reacting to it later would fight the canvasser's own panning, and turf focus and route framing still `fitBounds` on purpose once there is something specific to frame. Its standing `react-hooks/exhaustive-deps` warning is correct and must stay — `--quiet` means it never gates CI, so don't be surprised by it in an editor and don't silence it by adding the dep.
- **The map lives as long as its container, not as long as the pack.** The mount effect is keyed `[hasTilesKey]` and reads the pack through `packRef`, because its one use of it — `packBounds` for the opening view — is a mount-time fact of exactly the same kind as `initialZoom` beside it. Keyed on the pack object it wasn't: `endWalk` invalidates the pack whenever doors were logged (correctly — the landing dots are stale), `decodePack` returns a fresh object, and the effect's cleanup runs `map.remove()`, so leaving a walk destroyed the MapLibre instance and re-framed the district. The camera lives on that instance, so a canvasser who had panned to one block came back to the whole district. The **overlay effect keeps its own `pack` dependency** and is what repaints — the dots still recolour, which was always the correct half. Don't collapse the two: one owns the instance for the container's life, the other owns everything dynamic.
- **One selection, drawn on both halves, and it lives on the page.** `selectedStopId` moved out of `WalkView` and into `useWalkMapSession` (`WalkSurface.tsx`, called by the orchestrator), which **supersedes the walk section's "the reverse direction is not built"** — read that sentence as history. The state had to move for the reason the canvas rule says: the map draws it, the canvas is shared by all three modes, and a surface the page unmounts cannot hand the canvas anything. It sits beside `openStopRequest` on purpose, because the two are one conversation in opposite directions — a pin tap becomes a door the list opens, and whatever the list opens becomes the pin the map rings — and keeping the two ends in one hook is what stops the next change to either from needing the orchestrator. **The walk is still the only writer**: `WalkView` reports through `onSelectStop` from `openSheet`, which is the single place a row tap, a pin tap and `advanceFrom` all pass through, so the mark is always the door the sheet is offering rather than a history of taps. It is deliberately NOT set in `onPinTap`, where it would be one line shorter: a tap for a stop the served payload doesn't carry is dropped by the walk, and marking it on the map would ring a pin whose door never opened. `selectStop` takes a stop and never null, so the only thing that clears the mark is the session's own `reset()` on the way out — the mark outliving the sheet is the list's rule made structural, and every walk opens on a route with nowhere marked. On the canvas it is a **`route-pin-selection` layer of its own**, a hollow ring outside the pin rather than another accessor on `route-pins`: the pin's fill is already the stop's status and its stroke is already `knockable`, so both of its own channels are spoken for and taking either back would cost a fact the canvasser is standing in front of the house to read — the same reason the list row rings the numbered circle instead of filling it. Drawn after `route-path` (a ring the route's own blue runs over reads as a kink in the path) and before `route-pins` (so the pin sits inside it), `pickable: false` so the tap still reaches the door underneath. The colour is `#1e63ec` as a literal, which is `--primary`, matching the row's `ring-primary` — nothing on this canvas can read a CSS variable, and a near-miss shade would read as two different marks rather than one. **Matched on `stopId`, never on `seq`**: `seq` is what both surfaces draw, and selecting on the label rather than the identity is exactly how the two would come to disagree about the thing the numbering exists to keep in agreement.
- **An archived list's ring is dimmed, not dropped, and the eye still wins.** `saved-turfs` scales its fill and line alpha by `ARCHIVED_RING_ALPHA` when the row carries an `archivedAt`. Not removed, because archiving is a rail decision about which lists a candidate is working through and not a claim that the streets stopped existing — a ring that vanished on archive would leave the shelf looking exactly like a delete on the one surface where nothing else tells them apart, which is the same trap the rail's own archived section exists to avoid. Not recoloured either: the ring's colour IS the card's accent bar, so a grey archived outline would break the only thing tying an outline to the row that names it. **It composes with the per-list eye rather than competing with it**, because the two are different kinds of answer — the eye REMOVES a ring (`hiddenTurfIds` filters `visibleTurfs` before the canvas is handed anything), while the archive only quiets one. So an archived list the candidate also hid is gone, nothing in the dimming can put back an outline the eye took away, and the archived row keeps its eye toggle, which is the only way to get an archived outline off the map entirely. **Read off `archivedAt` directly rather than through `turfStage`**: for "is it archived" the field read is the definition, and importing the rail's lifecycle module would pull its mutations, its snackbars and its fetch client into the maplibre/deck.gl chunk to answer a one-field question — the same chunk boundary `MIN_POLYGON_POINTS` is mirrored across, in the other direction.
- **The live-location dot is a deck.gl layer, not maplibre's `GeolocateControl`** (`native/useLiveLocation.ts` + `LiveLocationControl.tsx`, drawn by `VoterMapCanvas`). Continuous tracking in `GeolocateControl` requires `trackUserLocation: true`, which also flies the camera to the user and fights the view's own `fitBounds` framing of the route and focused turfs; its one-shot mode doesn't watch at all. The layer also lets a coarse fix render as a muted dot plus a real-metre accuracy halo instead of the same confident blue dot at any accuracy. It is **opt-in** (the watch, and therefore the permission prompt, only starts when the canvasser taps the control) and `clearWatch` runs on unmount, on disable, and on a permission denial — a watch left running is a phone battery draining after the walk. **Coordinates are display-only**: nothing sends them to gp-api or to analytics.

### Manage view — the saved-list rail and the legend

- **The landing legend's counts describe the selected scope, not the district.** `canvassStatusCounts` (`filterEngine.ts`) takes the scope's selections plus the selected turf's ring, so picking a list rescopes the seven chips along with the heading above them. They were previously one pass over the whole pack's `canvassStatus` plane, which left district-wide numbers sitting under a heading naming one list and a line reading "N voters in this list". They are memoized on `scopeSelections` and deliberately **not** on `selections`: the chips' own narrowing has to stay out of their counts, or pressing one would zero the other six and leave nothing to press back. The chips narrow **within** the selected list — `selections` merges a `canvassStatus` entry into the list's own filters rather than replacing them, which is safe because no saved-list filter key maps onto that dim. Before that merge the turf branch returned early, so a chip clicked with a list selected flipped its own `aria-pressed` and changed nothing on the map.
- **The rail's list count is "About N", and the softening is not about arithmetic.** `maskToPolygon`'s `people` is `sum(matchedPerDot)` — exact for the pack, and the only count it returns, since the rail never prints households. It is softened because it is a **superset of who gets knocked**: filters with no pack bucket don't narrow it at all (above), and knock time additionally applies the list's activity conditions, support status and prior-contact clauses — none of which the pack carries in any form — then drops do-not-knock and not-a-voter residents. So the rail reads `About N voters in this list` plus one always-on line naming the map as the limitation, and the draw step's own `unpreviewableKeys` sentence verbatim when there is a specific filter to name. The **district** figure stays exact and un-softened; its existing caveat is that the pack is rooftop-geocoded rows only. `TurfDetailsSheet` matches this wording — the two surfaces describe the same quantity.
- **On a phone the rail is a sheet over the map, not a column beside it.** `NativeDoorKnockingPage`'s shell is a flex row whose rail is `w-96 shrink-0`, which on a 390px viewport left the map about six pixels wide — the tool is a map, so that is the whole product on the device it is used on. Below `lg` the rail is instead `absolute inset-x-0 bottom-0` over a full-bleed map: a peeking handle (the same grab pill the create flow's drag-down sheet uses) that opens to `max-h-[60dvh]` in one tap, capped so a status chip still recolors dots the canvasser can see. `lg` is the boundary because `PersonSheet` already switches there (`max-lg:` bottom sheet, `lg:` right panel) — one breakpoint for the feature. The open/closed state is **only ever a display class**: the rail's content is mounted at every width, so the desktop two-pane column doesn't depend on it, nothing reads `matchMedia`, and there is no hydration branch. It is, however, the one piece of landing state that can be **stranded**, because both of the page's other modes replace the rail entirely: the create flow makes `rightRail()` return `null` and a walk makes it return `WalkSurface`. A sheet left pulled up on the way into either would spring back over the map on the way out with nobody having asked for it — which is why `railOpen` now lives **inside** `DoorKnockingManageView` and the unmount is what resets it, rather than `closeFlow` and `endWalk` each remembering to. (`handleSaved`'s last-list branch still goes through `closeFlow` rather than repeating its body.) Walk mode needed no layout work of its own — `walkTurf` already stacks the shell at every width (`flex-col`, map pinned to 40%). The draw step needs none of this — the rail returns `null` while the create flow is open, so drawing already has the whole map at any width.
- **Per-list visibility is client-side display state, and deliberately ephemeral.** `hiddenTurfIds` in `NativeDoorKnockingPage` filters `visibleTurfs` into the canvas's `turfs` prop; `TurfList` renders the per-row eye toggle. Same category as `selectedTurf` and `statusFilter`, and as short-lived as they are — no `visible` column, no migration, no `localStorage`, nothing to gp-api. The rail row is the only surface that discloses hiddenness, so a ring hidden last week and still gone on the next open is a map missing an outline for a reason nobody remembers setting; that is worse than re-hiding it. "Short-lived" means **leaving the landing map**, not only closing the tab: both `closeFlow` and `endWalk` clear the set, because the create flow and the walk each unmount the manage surface and every eye toggle with it, which is exactly the stranding those other resets exist for. It is reset **by hand** — unlike the manage surface's own `railOpen`, which resets by being unmounted — because the canvas reads it and it therefore cannot live inside a surface the canvas outlives. **`statusFilter` is the deliberate exception to the "one rule for all of this page's display state" claim**: `closeFlow` clears the chips, `endWalk` does not, and that difference is now a decision rather than the gap it was previously recorded as. The stranding rule exists for state whose reason you won't remember on return, which is what a hidden ring is. A status chip isn't that, because **a walk changes the very statuses the chip filters on** — coming back to a pressed "unknown" chip showing a visibly smaller set is the most useful reading of the map there is, and it is the natural next question after an evening out. The chip also renders pressed, so nothing about the narrowing is concealed. Leaving the create flow is the opposite case: the chips are hidden and `selections` short-circuits while the flow is open, nothing about the drawn shape changes a canvass status, so one left pressed would re-narrow the district invisibly and for no reason. Don't "fix" the asymmetry by making `endWalk` match `closeFlow` — the two exits differ because only one of them changes the data. Hiding is display-only: the dots are the pack's and don't move, and the row keeps Details, PDF and Knock, because a quiet ring is not an archived list. Two couplings keep the controls from contradicting each other — hiding the **selected** list deselects it (the heading, count, legend and mask all describe the selection, and keeping it would leave the loudest thing on screen pinned to a list whose outline is gone), and selecting a **hidden** list reveals it (the camera is about to `fitBounds` that ring and the dots are about to mask to it).
- **`TurfList` is a rail of rows, not a select.** Each row carries four independent affordances — focus/scope (the name), visibility (the eye), Details, Knock, plus the PDF link on a locked list — and the page owns every piece of state behind them. Keep new per-list controls here rather than in the details sheet: the rail is where a candidate compares lists, and the sheet covers the row that opens it.
- **`TurfList` renders on an empty account.** It returns a real empty state (what a list is, and that "Create list" above makes one) rather than `null`, which left a new candidate's rail showing a heading, status chips and nothing else on the first screen of the feature. Pending gets a skeleton; a failed fetch stays silent, because the page already explains a map that could not load and "No lists yet" would be a guess about an account nobody has read.
- **The rail's per-list counts are gp-api's, and they are null on an unlocked list.** `GET /v1/door-knocking/turfs` carries `doorCount`, `peopleCount` and `loggedCount` beside `locked`, all three `.nullable()` in `DoorKnockingTurfSchema`. **Null, not 0, without a route**: lockedness IS the frozen route, an unlocked list has no doors to count, and `0 of 0 logged` would claim a list somebody walked and found empty. `TurfList` renders the line only when all three are non-null, so the unlocked row keeps no numbers. **They are not computed client-side, and that is the whole point** — the details sheet one tap away derives its own figures from the route payload (`countDoors`, `knockableTargets`, `knockStatus !== 'unknown'`), and a rail that disagreed with it about the same list would be worse than a rail with no numbers on it. gp-api's `doorKnockingStatus.service.ts` is the one derivation both paths read: `latestKnockStatuses` / `doNotKnockPersonIds` / `notAVoterReasons` used to be private to `doorKnockingServe.service.ts` and were extracted rather than copied. The equivalence is also asserted directly — `doorKnocking.routes.test.ts`'s "reports counts the details sheet derives identically" computes all three off the SERVE payload and compares, against a fixture carrying a shared door, a do-not-knock resident, a not-a-voter resident, an answered-but-unsure knock that derives back to `unknown`, and a not-home knock that counts as logged. **None of the three is a Prisma `_count`, and none could be.** Doors are `DISTINCT (stop_id, address_key)`, not stop rows — stops group by COORDINATE, so pairing the key with its stop is what makes this the same number `countDoors` reports rather than nearly the same one; shipping stops as doors is the bug this feature already had and fixed. People count knockable targets, so they need `ContactCurrentStatus`, joined on `(organizationSlug, personId)` with no relation to traverse. "Logged" is derived from `ContactInteractionDoorKnock` history (latest answer-bearing row preferred, manual `support_status` override winning) — there is no `knockStatus` column anywhere. **One batched aggregate for the whole rail, never a fan-out.** `serve` is the feature's heaviest read — nested route fetch, people-api round trip, four CRM queries — so running it per list on the first screen a candidate lands on is exactly the cost this avoids; `DoorKnockingTurfCountsService.forRoutes` takes every locked route at once and the person-keyed reads deduplicate across lists, so a resident in three lists is looked up once. Measured on the dev database: **11 SQL statements for the whole request at 12 lists and still 11 at 25**, and median endpoint latency 27ms at a dozen 150-stop lists (2,760 targets / 2,128 people) against a 8ms floor for the same rail with nothing locked. A routes-suite test asserts `forRoutes` is called exactly once and `serve` not at all. **The label is `N doors · N of M logged`, and it is deliberately not the prototype's `8 / 24 doors knocked`** — that pairs a people-derived numerator with a door denominator, which is the stops/doors/people rule above being broken in a single sentence. Doors stand alone; the ratio is people over people, the quantity `TurfDetailsSheet` labels "People logged", worded with the same verb per the "nothing says reached" note. The visible line leaves the noun to context and an `sr-only` span supplies it, because a screen reader has none of the column layout that makes it obvious.

- **The rail floats over a full-bleed map at every width, and `lg` now changes only its shape.** The Voter Outreach 2.0 canvas replaced the flush edge column with an inset card, and the reason is the same one the phone sheet already had written down: `w-96 shrink-0` in the page's flex row takes a fixed 384px out of the map, and the map is most of what the tool is. So the `<aside>` is `absolute` unconditionally — `inset-x-0 bottom-0` as the sheet below `lg`, `lg:inset-y-4 lg:right-4 lg:left-auto` as the card above it — and the orchestrator's map div goes full-bleed by keeping its `flex-1` with nothing beside it. **Nothing in `NativeDoorKnockingPage` changed to do this**, which is the seam working as intended: the surface owns its layout at every width, and the page owns only that the rail is rendered into a `relative` container. The sub-`lg` treatment is untouched (peeking handle, `max-h-[60dvh]`, `railOpen` as a display class only) — the canvas is the desktop half of the decision, not a replacement for the phone half. Inside the card, **only the lists scroll**: the scope heading, its count line and the legend are pinned in a `shrink-0 border-t` footer, because they describe what the map is shading right now and scrolling a dozen lists must not take the reading of the dots off screen with them. `lg:max-w-[40vw]` is the canvas's, and it is load-bearing on a small laptop in a way `w-96` is not: at 1024px the card would otherwise be 37% of the window before the browser chrome.
- **`ListCard` is a shared component in `app/dashboard/shared/`, not a row shape in `TurfList`.** The designer reuses this card in voter data and campaign manager, so it is domain-agnostic: an accent colour, an eyebrow slot, a title, a `meta` list, an `actions` row, a `controls` cluster and an `expandedActions` slot. It knows nothing about turfs, and `TurfList` supplies every door-knocking word. Two decisions in it are not cosmetic. **Selection is a button on the title, never a handler on the card** — the prototype makes the whole card clickable and then needs `stopPropagation` on all five controls inside it, which is a bug waiting on the sixth, and announces to a screen reader as a button containing buttons. **Every `meta` figure carries an `sr-only` noun**, because on this card the numbers are numerals beside icons and the three quantities the rail reports (doors, people, logged people) are exactly the ones that must never be read as each other.
- **The card's numbers stay `N doors` and `N of M logged`, and the eyebrow is the lifecycle stage.** The prototype's card leads with `8 / 24 doors knocked` as an overline; that pairs a people-derived numerator with a door denominator, which is the stops/doors/people rule broken in one sentence, so the two figures moved into the meta row as separate items (house icon, people icon) and the overline carries `Done` / `Archived` instead. Same numbers as before, same source (gp-api's, not computed here), same null-on-unlocked rule — a different arrangement.
- **The legend is one horizontally scrolling row of DS `FilterPill`s, and the row is what makes it fit.** Seven wrapped chips stacked into three rows inside a 384px rail and pushed the saved lists off the first screen of the feature. It scrolls rather than truncating, because a chip a candidate cannot reach is a filter they cannot clear. `FilterPillGroup type="multiple"` reports the whole next selection, so `TurfLegend` diffs it against `statusFilter` and reports the single status that moved — the surface still reports the gesture and never the consequence. The tri-state presentation is unchanged (count when `ready`, skeleton when `pending`, em dash when settled-unavailable, `disabled` in both non-ready states).
- **The list lifecycle is surfaced entirely on the card, and `turfLifecycle.ts` is the one place the three calls live.** `complete`, `archive` and `restore` share a module because they share every decision worth making once: archive and restore are the same endpoint with the boolean flipped, and all three must invalidate the rail _before_ their snackbar fires, or the message announces a move the screen has not made. Nothing is optimistic — both stamping directions are idempotent server-side, so a retry is cheaper than a rollback path. **All three require a knocked list** (`lockAndFindKnocked` 409s a turf with no route), so `canCompleteTurf` / `canArchiveTurf` gate on `locked` and a control is never rendered for a call that can only fail. **Done lives at the bottom of the expanded card** — the 2026-08-20 call's placement, and the right one: it is the only rail action with no undo beside it (archive has Restore, delete has a confirm), and the card expands on the same tap that scopes the map, so it is never one stray thumb from a list that stops offering Knock. **The CTA pair is `Details / Knock`, becoming `Details / Move to Archive` once the list is Done** — the canvas's states exactly.
- **Archived lists are sectioned, not hidden — the prototype's `filter(l => !l.archived)` is the one place this build refuses it.** `GET /v1/door-knocking/turfs` returns archived rows carrying `archivedAt` on purpose (see `gp-api/docs/door-knocking.md`), and the prototype drops them with no archived view anywhere, which makes a one-tap action irreversible from the only surface that offers it. So the rail renders a second `Archived (N)` section below the active one, each card keeping Details and gaining Restore. The counts are parenthesised on both headings rather than the prototype's `Saved lists · N`: the same call added a count to the outreach Filters CTA, and door knocking has no filters CTA to hang one off, so the count sits beside the group it describes. **An all-archived rail gets its own copy**, because `No lists yet` would otherwise be a lie told to an account with lists in it, and the archived section alone gives no way back to an active one.
- **Delete is live at every stage now, and the confirmation is the guard.** gp-api's `delete` no longer runs `assertNotLocked` — an unlocked turf is hard-deleted and a locked one is tombstoned with `deletedAt`, intact underneath — so `DeleteTurfControl` no longer renders `disabled` with a reason, and the disabled-with-`LOCKED_TURF_MESSAGE` treatment recorded in the details-drawer section above is superseded. **`locked` is still a prop, and now decides what the dialog says**: the two deletes destroy very different amounts, so an unknocked list is warned about as a drawing that really goes, while a knocked one is told its route, its frozen doors and its outreach-history entry are kept and only the rail loses it. Describing both as "removed for good" would over-warn on one and under-warn on the other, on the one screen where the warning is the whole safety mechanism. **`LOCKED_TURF_MESSAGE` survives, re-worded to the lock's remaining consequence** (the route and drawn area are frozen, so the list cannot be renamed, recoloured or redrawn) — `update` still asserts the lock, `TurfDetailsSheet` prints this sentence beside the Edit control it does still hide, and a rule met in two wordings reads as two rules. It is also the 409 snackbar, which a current gp-api cannot produce and one deployed behind this client can; that path still closes the confirm, because a server that refuses once will refuse the retry.
- **Two pieces of the canvas are deliberately not here.** The persistent AI chat bar the prototype restored on this screen belongs to its own app shell and is not a door-knocking surface. Its Pro-upgrade prompts are placeholders from an unrelated project, per the canvas brief. Its map is an unwired SVG placeholder; ours is MapLibre/deck.gl and stays.

### Create-list flow

- **Two denominators live in the create flow — never mix them in one sentence.** `runFilter` answers "across the district", `polygonStats` answers "inside the drawn ring". The filters step has no polygon yet, so it shows the district-wide count and its label says so (`districtHouseholds`); the draw step reports only `turfStats`. These were once rendered side by side, which put a district-wide household count next to an in-polygon door count at the moment of commitment. `polygonStats`'s household count is person-level exact: a household counts only when someone in it survives the filter. The interlock behind `districtHouseholds` is worth knowing before touching either — the create flow renders only while `flowStep` is set and `maskToPolygon` runs only while it is null, so the value can only ever be `runFilter`'s district-wide one. `FilterResult.households` is optional for exactly that reason: `maskToPolygon` no longer returns one at all, so the compiler stops anyone reading a household count off a masked result.
- **A filter the pack can't shade must be disclosed, not hidden.** `unpreviewableFilterKeys` (`createFlow/voterFilterPreview.ts`) reports selections with no pack bucket — age 65+ today, since the pack's legacy age buckets can't split it from 50-64. An unmapped key adds **no entry at all** to its dim (there is a test asserting `selections.has('age') === false` for `age65Plus`), so the effect is not a loose bound but no bound: a 65+ list shades every age. Mapping it onto `50_plus` was considered and rejected, because two different pills would then preview identical cohorts. **The gap is the preview's, never the filter's** — `voterFileFilter.utils.ts` pushes a real `{ min: 65 }` range and knock time targets exactly who was asked for — so the copy says the map can't _show_ the filter and that the list still applies it when you knock. Never phrase it as the filter not being applied: a candidate who reads that concludes their targeting is silently failing, which is a worse misunderstanding than the overcount being disclosed. The disclosure names the selected **option** ("65+", which stands on its own) except for prior contacts made, whose options are the bare counts `'0'`…`'5+'` — "the map can't shade by 0 yet" reads as a bug, so that group is named once however many of its buckets are selected. `unpreviewableDisclosureLabels` in the same file is the one place that resolution lives: the draw step, the landing rail and the details sheet all print the sentence, and a candidate meeting them in one session must not find one filter named two ways.
- **Continue is the draw step's finish gesture, so it explains itself while it can't be pressed.** The canvas has no Done — every tap places a vertex and the shape closes itself — and `onPolygonChange` only reports a ring from three points, so `Continue` is dead until then. Neither fact was anywhere on screen, which reads as a broken step to anyone who placed two points and went looking for a confirm button. The button now says what it is waiting for (`Tap 3 points to continue` → `1 more point to continue` → `Continue (N doors)`, and `No doors in this area` for a shape drawn over nothing), and the coach mark names the closing behavior. `MIN_POLYGON_POINTS` is mirrored in `CreateListFlow` rather than imported from `VoterMapCanvas`: that module carries maplibre and deck.gl, and the flow is deliberately outside that chunk.
- **The draw step lists the real street addresses it encloses, and they come from gp-api** (ADR 0010). It reported a door count and never said which doors it meant, at the one moment the shape can still be redrawn and before the billed route call — the walkthrough's words were "I can't see a list of the households that are in my list". The pack cannot answer that: it is `positions`, two index arrays and demographic byte planes, and carries no address at all. So `POST /v1/door-knocking/address-preview` runs the **same evaluation the knock path runs**, minus the Geoapify call and the freeze, and returns one row per **door** grouped by the coordinate the doors share — a block of flats reads as one location holding several doors rather than as several stops. `addressPreviewQueryOptions` (`turfQueries.ts`) is the client half; the door's line comes back rendered by gp-api's shared `renderUnitAddress`, the same helper the route serve uses, so a candidate cannot be shown one house spelled two ways. **No numerals on the rows**, per the stop-numbering note above: no visiting order exists until Geoapify picks one. **An earlier revision of this note recorded that endpoint as rejected** — on the grounds that an exact in-ring count printed beside the pack's superset count is the two-denominator failure in a new costume. That reasoning was right about the risk and wrong about the remedy, and the product owner has since required the addresses. What changed is that the two counts are **not both on screen**: the preview's counts replace the estimate rather than joining it (next note). Don't re-reject it; if you are about to, read ADR 0010 first.
- **When the preview is live it is the only count on the step, and the pack's is the loading state.** This is the "two denominators" rule held rather than broken: one quantity, one number. `CreateListFlow` reads `addressPreview?.stops ?? turfStats?.stops` (and the same for doors and people), so the moment gp-api answers, the bar, the walk-time estimate, the cap warnings and the Continue button all move onto the exact figures — the ones the route will actually be built from, with the list's activity, support-status and prior-contact clauses applied and do-not-knock and not-a-voter residents already dropped. The estimate's two hedges go with it: the `unpreviewableDisclosureLabels` line explains a shortfall these counts don't have, and the party mix is a breakdown of the superset's people that would no longer sum to the people figure above it. **The two count doors differently and that is the point** — the pack's `households` groups at `AddressLine` (a building), while `evaluate` and the freeze use the unit-level key, so `Apt 1` and `Apt 2` are one household to the pack and two doors to the route. Blending them, or hedging the exact one, would have printed a number that matched neither. Anything that reports pre-route counts and cannot see the preview (the rail, `TurfDetailsSheet`) still says "About N" — those surfaces describe a saved list or a district, not the shape being drawn, and the hedged-vs-exact split there is unchanged.
- **The panel is opt-in, and what the create-list surface owns is the shape it was asked about — not a boolean.** `previewRing` in `CreateListSurface` holds the ring that was on screen when "See the addresses" was pressed, and `previewRing === ring` (reference identity; the canvas emits a fresh array per change) is what makes an answer belong to a boundary. **Nothing is ever fetched by drawing.** Moving a vertex doesn't refetch, doesn't debounce into a refetch and doesn't invalidate — it makes the answer _stale_, which the panel says out loud ("Your boundary changed…") while the counts fall back to the pack in the same render, and re-asking is another press. That is the cost rule: a people-db scan per vertex is both a bad experience and a real bill, and a debounce would have spent one on every shape passed through on the way to the intended one. The query key is `[shape, filters]` with `staleTime: Infinity`, so Back from confirm returns to a cached answer rather than a second scan. **The ring outlives the draw step**, which is what makes `previewRing`'s lifetime the interesting part: Back to filters keeps the shape and so does Continue. `CreateListSurface` clears it when the next step is `filters` — in the same batch as the page's own `changeFlowStep`, which it wraps — and its `onSaved` draw-another branch does the same — both mean a re-cut audience and a wiped shape, so the next thing drawn is a different list against a different question, and the panel springing back over it is the stranding the manage surface's own sheet and the status chips are reset for. Going **forward** to confirm deliberately does not clear it: that is one shape being reviewed, Back has to return the step as it was left, and the confirm summary then quotes the same exact counts the draw step did. The query is additionally `enabled` on `flowStep === 'draw'`, so a step-change path added later that forgets to reset can't reintroduce a hidden request; the reset is the behavior, the gate is what stops the invariant depending on every call site remembering it. `NativeDoorKnockingPage.test.tsx` counts the requests rather than trusting the claim. gp-api caps the listing at `MAX_STOPS` (150) while still reporting the true `stops`, so a shape over the cap is blocked by the same number the panel prints "Showing the first N of M stops" against. Tapping a row to highlight its dot was rejected: the panel covers the map band it would highlight into, a phone has no hover, and it would need a new layer inside the maplibre/deck.gl chunk this flow is deliberately outside of. Closing the flow resets it by unmounting `CreateListSurface`, the same way the manage surface's sheet resets.
- **A tap lands in the nearest edge, not on the end of the ring.** Appending every point was right for the first three and wrong from the fourth: tapping between two vertices already placed sent the boundary across the shape and back, so a gesture that reads as "put a corner here" produced a criss-crossed, self-intersecting outline with no way out but Clear. `ringInsertIndex` (`native/VoterMapCanvas.tsx`) reads the ring as closed from three points and splices the tap into whichever edge it is nearest by perpendicular distance; under three there are no edges yet, so it appends. Distances are measured with longitude scaled by `cos(latitude)` first — a degree of longitude is only ~0.74 of a degree of latitude at US latitudes, so compared in bare degrees a tall narrow ring's long sides read as nearer than they are and the wrong edge wins on exactly the shape a street-following turf is. The **double-click guard moved with it**: it compared the tap against the last point in the ring, which is "the vertex just placed" only under append semantics. The second click of a double-click now lands _on_ that vertex and would splice beside it, so the guard checks every vertex instead.
- **Undo and Clear are requests to the canvas, not edits made in the flow.** `VoterMapCanvas` owns the in-progress ring, so `CreateListFlow` only renders the two controls and `useCreateListDraw` (in `CreateListSurface.tsx`, called by the page because the canvas outlives the flow) turns them into token bumps: `undoDrawToken` drops the vertex most recently placed, and Clear reuses `startDrawToken`, because a restarted drawing session (empty ring, still in draw mode) is exactly the state Clear returns to. **"The vertex most recently placed" stopped being "the last element of the ring"** once taps began splicing into the nearest edge, so `addOrderRef` records placement order beside the ring and undo walks that. Slicing the end off instead would take a corner placed several taps ago and leave the one just misplaced standing — silently, because on screen they are both just vertices. Undo is still **last-add only**: drags are deliberately not recorded, since a dragged vertex is already correctable by dragging it again and making undo drag-aware would turn the ring into an edit stack for a gesture that doesn't need one. Both paths re-emit `onPolygonChange(next.length >= 3 ? next : null)`, which is why undoing from three points to two drops the stats and disables `Continue` instead of leaving stale figures on screen. They sit bottom-right of the live map band, **in flow above** the stats bar rather than absolutely positioned over it, so a cap warning or a disclosure line pushes them up instead of covering them; only the button cluster is `pointer-events-auto`, since the rest of that row is map the canvasser is still drawing on. The instruction card deliberately does **not** come back after Clear: it is a first-run coach mark that covers the whole map (a full-inset button, so its dismissing tap can't drop a stray vertex), and someone who just cleared has already learned the gesture.
- **Win-only filters are gated by prop, not by context.** `CreateListFlow` takes `isElectedOfficial` (like the CRM's `VoterFileStep`) and `NativeDoorKnockingPage` sources it from `useOrganization().electedOfficeId`. Keep the read in the page: `useOrganization` throws outside its provider, so a context read inside `CreateListFlow` forces every test of it to mount an organization provider. The prior-contacts (`contacts_made`) group is the one this hides — gp-api's `assertNoContactsMadeFilterForElectedOffice` rejects that selection from an elected-office org, so offering it there only ever surfaces as a failed knock.
- **The flow has two vocabularies for where it is, and only one of them crosses the seam.** `CreateFlowStep` (`filters` / `draw` / `confirm`) is the ORCHESTRATOR's, frozen by #1380: the page opens the flow at `filters` and `changeFlowStep` starts a drawing session on exactly the `filters` → `draw` transition, so renaming or reordering those three silently breaks drawing — the canvas never enters `draw_polygon`. `CreateFlowStage` (`createFlow/createFlowSteps.ts`) is the FLOW's own — purpose → who → draw → confirm, plus a conditional `name` — and the three pre-draw stages all live inside the page's single `filters` step. **That nesting is the whole mechanism**: this flow grew from three steps to five without the orchestrator learning a thing, and the next step added before the draw is free for the same reason. Read `filters` as "the phase that decides the audience", not as "the filter pills" — the pills are one stage of three. `stageStep` is the one place the two vocabularies meet, so a stage change and a step change are one decision rather than two that can disagree.
- **`totalSteps` is computed, never a constant.** The flow is four steps, or five when the draft needs saving as a reusable voter list first, and `stepperPosition` shifts draw and confirm along with it. A hardcoded `of 4` under the five-step path is the kind of wrong that only shows up on the last screen, so `createFlowSteps.test.ts` asserts the property rather than the numbers: the final step's index always equals the total, and walking `previousStage` from confirm back to purpose always takes `totalSteps - 1` moves. `needsName` is `savedListId === null && activeFilterCount > 0` and is **stable from the who step onward** — nothing after it can edit either input — so the count only ever moves while the candidate is still on the step that decides it.
- **Door knocking writes its own purpose labels, and its name suggestions are a separate record.** `createFlow/doorKnockingPurposes.ts` follows `outreach/v2/phoneBankingPurposes.ts`'s shape and none of its copy: these goals are about a conversation on a doorstep ("Discover local issues", "Turn out my supporters") and have no equivalent on a channel that sends a message. Robocall and phone banking both shipped with social's labels copy-pasted and had to be corrected in #1379 — the correction is cheaper than the copy-paste. The **third** record, `DOOR_KNOCKING_PURPOSE_NAME_SUGGESTIONS`, exists because of what that correction then did (#1385): a card label doubling as a default title renamed live records. A label is copy on a card, phrased as a goal; a suggestion is a default title for a saved list ("Turnout walk"). There is a test asserting no purpose shares a string between the two, so collapsing them fails rather than ships. The slugs are local rather than a contracts enum, unlike `PhoneBankingPurpose`: nothing persists a door-knocking purpose — it shapes the flow and seeds a name, and never crosses the wire.
- **The who step's count lives inside the Continue button, and the line beside it still names the denominator.** The canvas puts the matching count in the CTA; the two-denominator rule above is unaffected and had to survive the move, so the paragraph that used to carry both the number and "in your district" now carries the qualifier alone ("Across your whole district. You'll draw the area to knock next.") while the number is in the button. Dropping the qualifier would leave a bare count on the one step where no polygon exists, which is the exact confusion the rule was written for. Zero matches disables the button and it says so rather than reading `Continue (0 households)`.
- **The who step can start from a saved list, and counts every option in parentheses.** `createFlow/savedListOptions.ts` runs one `runFilter` pass per saved list over the decoded pack, from `CreateListSurface`, so the picker's counts are the SAME quantity and the SAME derivation as the step's own `districtHouseholds` — a second derivation is a second chance to disagree with the number in the CTA once a list is picked. The pack is read through `useQuery({ ...voterPackQueryOptions, enabled: false })`: the page already fetches it, gates the whole feature on it and disables the button that opens this flow until it decodes, so a fetch here would be a second tens-of-MB download. An observer rather than `getQueryData` because the counts have to appear if it lands late; a surface test asserts no `/pack` request is made. A list whose count has not arrived still renders — a picker that hides its rows until the pack decodes shows an empty audience step to a candidate who has lists. Re-expansion goes through the shared `savedListFilterKeys`, so the rail, the details drawer and this picker cannot disagree about which filters a list carries. **Editing any pill clears the selected list**, because the draft is then no longer that list — which is also what brings the fifth step back.
- **`OutreachFlowShell` was deliberately not adopted.** It is shared with social, robocall and phone banking, and the draw step is why it cannot take this flow: the step is chrome floating over a live MapLibre canvas the candidate taps to place vertices, so a Vaul drawer over it swallows every tap, and `OutreachSheet`'s 608px column and step-resetting scroll body have no notion of the drag-down peek `sheetTopPct` exists for. What adopting it would have bought was taken instead: the hand-rolled stepper segments are gone in favour of the styleguide's `bar` `Stepper` (which already renders "Step X of Y" and lays its track out from `totalSteps`, exactly what a sometimes-five-step flow needs), and the discard-confirm it lacked is now an `AlertDialog` here. **Only the who step peeks** — its pills recolor the dots underneath live, so the map is worth uncovering; purpose is a card list and name is a text field, and pulling either down reveals a map nothing on screen changes.
- **The step components carry no `'use client'`, and adding one back breaks the build.** `PurposeStep`, `WhoStep` and `NameStep` are only ever imported by `CreateListFlow`, which has the directive — a module pulled into a client component is already client-side, so the directive on the child buys nothing and `check:use-client` counts it against the repo's baseline. gp-webapp's `Validate` job fails on the count, not on a lint rule, so the failure names a number rather than the file.
- **The discard confirm asks only when there is something to discard.** `dirty` covers everything the candidate typed, picked or drew, the ring included — a shape is work however it got there. A pristine flow closes on the first press, which is what keeps the dialog from becoming noise on an X nobody meant to press twice.
- **Two names, two records: the saved list's and the route's.** With the name step in the path, its name goes on the `voter-file/filter` and the confirm step's Route name goes on the turf, so renaming a route on the confirm step cannot rename the reusable audience behind it. Without it they are the same string — the flow having only one name to give. The confirm step arrives pre-filled from whichever upstream record has one: the list just named, else the purpose's suggestion. Two separate things stop the seeding, and conflating them is the bug to avoid. **A typed box is theirs**: one keystroke and no upstream rename overwrites it again. **A suggestion is spent once applied**: while the box is untouched it follows the records, so backing out to rename the list and returning brings the new name, but the same suggestion is never re-applied. That second rule is what leaves the next turf of a "draw another" run blank with Save disabled — its audience is unchanged, so re-offering the name just saved is an invitation to end up with two lists called the same thing — while a goal changed or a list renamed after that save still produces a different suggestion and still offers it. A single "already seeded" flag cannot express both, and swallows the new goal's suggestion.
- **A picked list is attached to, not copied — and it must never reach `createdFilterIdRef`.** A saved list already IS a `voter-file/filter`, and its id is the same one a turf attaches by (`TurfDetailsDrawer` resolves a turf's list by matching them), so the save path reuses it instead of filing a near-identical list per shape cut from the same audience. The ref is the dangerous half: it means "a list this flow minted and may still have to clean up", and its cleanup **deletes** what it holds — putting the candidate's own saved list in it would delete their list on the way out of the confirm step. Only a filter this flow created goes in.
- **The filter pills use the CRM's `PILL_TOGGLE_ITEM_CLASSNAME`, not a local copy.** The local copy carried smaller padding than the shared constant while claiming in a comment to match it, which is the drift that constant exists to prevent.
- **A "draw another" keeps the audience and drops both names.** The flow mints a fresh `voter-file/filter` per turf, so the list the name step named belongs to the turf just saved: carrying its name forward files the second list under a name already taken, from a step the candidate can walk straight past. The route name goes for the same reason. What is kept is the purpose, the chosen list and the pills — the page keeps `filters` across the transition too, because the second turf is usually the same audience cut somewhere else.
- **After a save, the audience is saved work — the discard confirm stops counting it.** "Save and draw another" deliberately keeps the purpose, the list and the pills (the page keeps `filters` across it for the same reason: the second turf is usually the same list cut somewhere else). Counting them as unsaved would make the X ask "Discard this list?" about a session with nothing in it, before a single point had been placed. From the first successful save on, only the shape and the route name in progress make the flow dirty.
- **There is no "Top issue" filter group, and its absence is asserted.** The canvas puts it first in the shared filter pool, but no per-voter issue attribute exists anywhere — no column on `Voter`, no key in `voterFilterBaseSchema`, and `filterDimensions.catalog.ts` names top-issue a deliberately blocked dimension. The flow renders `filterSections` whole, so the group is omitted by being absent from the shared config rather than filtered out here; the test exists because the day someone adds it there is the day it appears in this flow by accident. Platform-wide, not this surface's to solve.
- **Previously created shapes are already on the draw step, and the snap is already the page's.** `NativeDoorKnockingPage` passes `visibleTurfs` to `VoterMapCanvas` unconditionally — the create flow does not gate it — so saved outlines render under the shape being cut, and `focusTurf` is what fits the camera when a list card is selected. Nothing in the flow was needed for either, and nothing in the flow should acquire it: both are canvas state, which by the rule above lives on the page. **One gap is the page's and left alone**: `hiddenTurfIds` is not cleared when the flow opens, so a list hidden from the legend stays hidden on the draw step. That is the orchestrator's state and a manage-view decision, not this surface's to reach into.

- **The canvas's per-option counts on the filter pills are refused, and the refusal is the preview rule again.** `dkStepWho` computes `countMatching(universeFor(f.customListId), {...DEFAULT_FILTERS, [key]:[opt.value]})` for every option and disables any that scores zero. We cannot honestly do either half. The count would be the **pack's**, which has no bucket for several keys gp-api converts into real bounds at knock time (`age65Plus` is the standing example) — so an unmappable option adds no constraint at all and would report the whole universe, while a mappable one sits beside it reporting a narrowed slice, in the same row, looking like the same kind of number. Disabling at zero is worse than wrong: it would grey out a filter that the saved list applies perfectly well, which is the one misunderstanding this feature works hardest to avoid — the gap is the preview's, never the filter's. The step's feedback is the map recolouring live underneath instead, which is the pack answering the question it can actually answer.
- **The colour swatches are named, not hexed, and one map names them.** `turfColorLabel` (`native/turfQueries.ts`) sits next to `TURF_COLORS` because the create flow's confirm step and `EditTurfDialog` draw the same eight swatches and must not label them differently. Both previously used the hex as the accessible name, so picking a list colour without sight meant eight hex codes read a character at a time; the canvas labels its own `opt.label`. The selected swatch also carries the canvas's tick **inside** it, so "which one is chosen" is not left to a thin ring around a block of colour on a control whose entire content is colour — and the tick **inverts with the swatch it sits on**, via `turfColorTick` beside the label map. A fixed white tick failed WCAG AA on four of the eight (green, amber, teal and lime), which is the mark meant to make the choice legible being the one thing on the swatch that isn't. It delegates to `readableInkOn` in `native/statusPresentation.ts` rather than carrying its own copy of the rule, because the walk list's stop numeral on its status circle asks exactly the same question of a fixed fill, and two copies of one crossover is how one of them ends up white on amber. `statusPresentation.test.ts` sweeps **both** palettes against the 4.5:1 ratio computed from the spec, so a ninth list colour or an eighth status added without a thought for its ink fails there rather than on a doorstep.

### List details drawer

- **`TurfDetailsSheet` hedges the pack's counts and not the route's.** Pre-route Doors and People read `About N` and carry the landing rail's two disclosure lines **verbatim** off `unpreviewableDisclosureLabels` — one surface reporting the same quantity as another in different words is how a candidate learns to distrust both. The frozen route's counts stay exact: they came through knock-time evaluation, so they _are_ the audience, and "about" there would invent doubt about the one precise number this sheet has. `unpreviewableKeys` is computed by `TurfDetailsDrawer` from the **saved list's** filters; the page's memo of that name describes the create-flow draft, which is empty whenever Details is open, so reading it would have disclosed nothing on every list that needed it.
- **Editing a list is name and color only, and only while it is unlocked.** `PUT /v1/door-knocking/turfs/:id` also accepts `geoPoly`, which is exactly why gp-api's `update` runs `assertNotLocked`: the polygon is what the frozen route was computed from, so accepting one after a knock would desync the two. `EditTurfDialog` is hidden for a locked turf, and still handles the 409 for the case where a teammate knocks it while the dialog is open. **Delete no longer follows that rule** — it renders disabled with a reason instead of vanishing; see the delete note below for why the two now differ. Consequence worth knowing: **a knocked list cannot be renamed**, so a typo outlives the walk. Relaxing that means splitting the endpoint's fields, not loosening the lock.
- **Travel mode is suggested before the route is bought, and only ever re-read after.** The choice used to be made in `KnockTurfDialog` with nothing on screen to inform it, at the one moment it becomes permanent. `travelMode.ts` now derives a default from the stops' own geometry, mirroring the prototype's rule: walkable only if **every** leg between consecutive stops is under a five-minute walk, otherwise the whole list is a drive list — no mixing, because one mode buys one route. Visit order is Geoapify's and doesn't exist yet, so "consecutive" is read as the best case any order could achieve — the widest edge of the stops' spanning chain (Prim's, O(n²) over at most 150 stops), which is order-independent and can't be fooled by the order the pack happens to list them in. Distances are crow-flies, discounted by a 1.3 street-detour factor before becoming minutes; erring toward `drive` is the cheaper mistake, since the path bought is mode-specific and can never be re-bought while a suggestion is one tap to override. The suggestion is **derived, not seeded into state** — the pack decodes on its own schedule, so a `useState` initializer would freeze whatever was known at mount. `RouteBuilt` carries `suggestedMode` beside `mode`; equal means accepted, different means overruled, null means there was nothing to derive from.
- **The post-freeze mode toggle changes the label and the estimate, and nothing else.** `TurfDetailsSheet` lets someone re-read a frozen route's travel time in the other mode. It writes nothing: the route row is never mutated, `pathGeometry` is the bought mode's alone, and there is no second path — so the toggle recomputes `totalMeters` at the other mode's speed (`estimateTravelSeconds`) and says out loud that the stops, their order and the drawn path are unchanged. "Route type" keeps naming what was **built**, deliberately, so a flip can't relabel a walk route as a drive route it is not; the flipped figure is prefixed "About" and hinted as ours rather than the vendor's, and flipping home restores Geoapify's own `totalSeconds`. It lives on Details rather than in `WalkView` because that is the pre-walk planning surface — mid-walk is the wrong moment to reconsider transport — and because Details already states mode and travel time side by side under the same lock-aware branching. **Loop/open gets neither treatment**: geometry can't suggest it (whether you must return to a parked car is a fact about the canvasser, not the doors), and unlike mode it is load-bearing on the artifact — loop anchors start=end at the first stop, open anchors the farthest-from-centroid one — so ordering and geometry really do differ by it, and a post-freeze flip of that label would contradict the path on the map.
- **A locked turf HAS a route, so route-derived stats branch on lockedness, not on `routeQuery.data`.** Every stat that reads the route (`TurfDetailsSheet`'s doors, people, travel time, route type, people-logged) used to fall back to the unknocked copy on falsy data, so opening Details on a knocked list read "Not knocked yet" three times for the length of the fetch and permanently if it failed — while doors and people quietly swapped population mid-load. `routePending` / `routeFailed` come off `liveTurf.locked` instead: pending renders a skeleton, failure renders `Unavailable` plus a visible line saying the route could not be loaded. `Not knocked yet` is now reachable only when the turf really is unlocked.
- **`TurfDetailsSheet` reads `liveTurf` for name and color, not the prop.** The prop is the snapshot the page captured when the row was clicked; since the sheet can now rename and recolor, rendering it would leave the header showing the old name after a save. The prop stays the source for identity (`id`, `voterFileFilterId`), which no edit can change. Its PDF link follows the same lock rule as the `TurfList` row's, for the same reason — only a locked list has a route to print, so the link would 404 on an unknocked one.
- **The details sheet's pre-route stats are the list's audience, not the polygon's population.** `listStats` (`TurfDetailsDrawer`) runs `polygonStats` with the turf's **saved filters**, via the same `savedListFilterKeys` (`native/savedListFilters.ts`, shared so the two surfaces cannot re-expand a list's income and language filters differently) → `filtersToDimSelections` path the landing map's scoped preview uses. Computed with empty selections, as it originally was, "Doors"/"People" described everyone inside the ring while sitting directly above the "Applied filters" pills — a Democrats-only list reporting every person in its polygon, which the labels hedged at ("in this area") rather than fixed. Because it is now the same computation the draw step ran on the same shape, Details reproduces the number the list was committed against, and inherits that step's disclosed caveat instead of a new one: an unshadeable filter (age 65+) leaves it a superset, and knock-time evaluation stays canonical.
- **Delete is a disabled control with a reason, not a missing one — and it lives on the rail row as well as in the sheet.** gp-api's `doorKnockingTurf.delete` runs `assertNotLocked`, so a knocked turf 409s and the button genuinely cannot work. It used to render only when `!liveTurf.locked`, which is how the feature got reported as **missing entirely**: a candidate whose lists were all knocked found no Delete anywhere, and an affordance that removes itself without a word is indistinguishable from one that was never built. It now renders `disabled` with `LOCKED_TURF_MESSAGE` as its `title`, and the details sheet prints the same sentence under the header. **That message has one definition** (`DeleteTurfControl.tsx`) used three ways — the disabled `title`, the sheet's line, and the 409 snackbar — because the rule met in three wordings reads as three different rules. Note this makes delete and **edit** diverge deliberately: edit stays hidden because renaming a locked list is a limitation nobody goes looking for, while delete's absence was the actual bug report. `DeleteTurfControl` also owns the mutation, the `ConfirmDeleteDialog` and the 409 path once for both callers, which is the whole reason it is a component — a second copy of the 409 handling is a second chance to get the lock rule wrong. A 409 **closes** the confirm rather than leaving an enabled Delete that can only 409 again, and refetches so the live row disables its own trigger. **Both callers hand it the live row, not the snapshot** — `locked`, so a list knocked by a teammate since the rail rendered stops offering a delete that can no longer land, and `name`, because the sheet can rename a list and this control names it twice (its label and the confirm dialog's title, the last thing read before something is destroyed). That is the `liveTurf` rule below applied to a control that both gates behavior and displays an editable field; identity is unaffected, since `liveTurf` is found **by** `turf.id`. The two triggers carry **different accessible names** (`Delete {name} list` on the row, `Delete {name}` in the sheet) because the sheet is an overlay inside the rail's own container and both are mounted at once — one name would be ambiguous to a screen reader and to a test alike. Putting it on the row follows the "`TurfList` is a rail of rows" note: the rail is where lists are compared, and the sheet covers the row it acts on.
- **The drawer is an overview, and the household roster that used to be in it has been removed.** `TurfRoster` shipped in #1372 against a real report — the sheet gave counts and never said _which_ doors — and listed one row per **address** off the frozen route's stops, with numerals, phones and `otherResidents` deliberately omitted, flagged residents listed-but-not-counted, and a `MAX_ROSTER_DOORS` cap. The Voter Outreach 2.0 canvas reverses it: the list details drawer is the same drawer the outreach history table opens, and neither draws a per-door list. Read that as a scope correction rather than a mistake being undone. The roster was a **third** listing of one route — `WalkView` lists the same doors in the order they are to be knocked with `PersonSheet` behind a tap, and `print/WalkSheet.tsx` is the take-it-with-you copy — and each of those three had to carry the flagged-resident caveat and the cap disclosure in its own words, which is three chances for them to drift. The unlocked branch never had a roster to lose (the pack is `positions`, two index arrays and demographic byte planes, carrying no name and no address at any price), so its "Street addresses arrive with the route" line went with the section: with no roster on either branch there is no absence left to explain. **What was learned is worth keeping if this comes back:** doors are addresses and not stops (`countDoors`, so a block of flats is one stop and many doors); a flagged resident's `targetMarker` **replaces** their status rather than sitting beside it; and any caveat about "the residents listed here" must be computed over the **shown** rows, since scanning the full list printed it above a capped page that held no marker at all. If a per-door listing is ever wanted again, the walk is where it belongs.
- **The sheet says what the audience _is_, not just what was asked for — in the two dimensions both its sources can answer.** "Applied filters" pills are the request; the Audience breakdown is the result. It is **party and age only**, and that is a data constraint rather than a design preference: the pack carries sixteen dimensions, but a frozen route's targets carry a live `age` and `politicalParty` and nothing else, so a breakdown built on the pack's full set would empty itself the moment the list was knocked — a candidate watching fourteen dimensions disappear as a reward for walking. Two that survive the lock beat sixteen that don't. It branches on lockedness exactly as the other route-derived stats do (`routeAudienceMix` off `knockableTargets`, never the raw stops, so it sums to the People stat rather than quietly using a wider denominator), and pre-route it is `polygonStats`'s own `partyMix`/`ageMix` and therefore the same superset the counts are, sitting under the same disclosure. `audienceMix.ts` mirrors gp-api's `encodeAge` bound for bound and duplicates it rather than importing a server module — but the two **must** agree, or knocking a list would re-shape its own age breakdown while the audience behind it never moved. Two prototype groups have **no honest equivalent** and were dropped: "top issues" is not a fact this product holds about a voter (no pack dim, no route field, no column), and its "support" breakdown is the landing rail's seven `canvassStatusCounts` chips in a second visual form — reporting one quantity twice on surfaces reached from each other is how two presentations start disagreeing. **The people-logged stat carries a progress bar, and the two properties that make it honest are not cosmetic.** An earlier revision of this note recorded the bar as rejected — a bar reading "40% complete" against a denominator of knockable people being the same credit-for-conversations-never-had failure in a shape that's harder to argue with. **The product owner has since overruled that**, so don't re-reject it; what the objection bought instead is the two constraints it forced. **The denominator stays knockable people** — `knockableTargets`, per the stops/doors/people note, so the bar fills to 100% for a canvasser who correctly skipped every flagged door rather than holding them short of it. **The word stays "logged"** — the bar is drawn beneath the existing "People logged" stat and adds no label of its own, so it cannot reintroduce "reached" or "complete" through a caption. It is `aria-hidden` and adds no accessible name for the same reason: the value above it already reads `12 of 40 · 30%`, and the bar is a picture of that sentence rather than a second claim. Both the printed percent and the bar's width come off one `loggedPercent`, so they cannot round apart. **It is drawn only when a frozen route exists** — the same `route` value the surrounding stats branch on, not `loggedPercent`, which is `0` for an unlocked list, a pending fetch and a failed one alike; a 0% bar beside "Not knocked yet" draws an untouched list as a walk barely begun. Two spans (`bg-muted` track, `bg-info` fill) copied from `WalkView`'s bar, which reports this same quantity mid-walk and must not look like a different measurement on the planning surface. Deliberately **not** the styleguide `Progress`, whose `h-3`/`bg-primary` indicator class isn't overridable, and deliberately not floored to a visible sliver the way `Breakdown`'s bars are — there a hairline means "under 1% of the audience", here zero means no door has been logged and a sliver would invent one.
- **Both list details drawers are one component family, and the shared pieces live in `outreach/v2/listDetails/`.** The product call was that "the List Details drawers opened from the table and from the cards are now consistent", and consistency here is structural rather than a pair of stylesheets kept in sync: `ListDetailsSheetShell` owns the drawer container, the 608px content column, the close's position inside that column and the header/body/footer split; `ListDetailsMetric` owns the Overview cell, the two-column grid, the labelled filter-pill group and the section eyebrow; `ListDetailsFooter` owns the action row. They sit under `outreach/v2/` rather than in door knocking because the outreach drawer is the one the canvas draws and the one every other channel already lands in — door knocking is the surface that joined it. What each caller still owns is the **body**, because the two answer about different objects: an outreach envelope read from `GET /v1/outreach/:id`, or a saved list whose figures come from the voter pack and, once knocked, a frozen route — with pending and unavailable states the envelope has no equivalent for. That is why `Metric` carries `pending` and `progress` that only door knocking passes: the shared cell is the **union** of what the two surfaces needed, so a door count and a people count look like the same kind of fact on both, rather than the intersection, which would have pushed door knocking back into a private copy.
- **The footer is a closed set of four modes, and door knocking sections on the same lifecycle the rail does.** `footerMode.ts` is the whole vocabulary (`edit`, `continue`, `automatic`, `done`, plus `none`), so a channel cannot word the same action differently or add a fifth one-off. An unlocked list is the canvas's `edit` mode — **Delete and Edit list**, landed here because this is the one object in the product with both a `PUT` and a `DELETE` genuinely behind it, rather than on a paid campaign nobody can edit. A knocked list still being walked is `continue`, and a done or archived one is `done` — `turfStage`, not a second reading of the timestamps, so the drawer and the card it covers cannot disagree about which section a list is in. **`continue` carries no CTA on this surface**: the walk is entered from the rail's Knock control, which `NativeDoorKnockingPage` owns behind a frozen prop interface, so "Continue knocking" is a plain link in the outreach history drawer instead. `done`'s canvas primary is "Show results", which here is the drawer already being read, so that slot carries the shelf action. Edit moved into the footer's primary slot and **lost its `Edit {name}` aria-label**: one full-width button under one list's overview, and an aria-label not containing the visible text breaks label-in-name.
- **Archiving a list is one action, one request, and the second row is gp-api's to move.** Two rows carry an `archivedAt` for one walk — the turf is the object a candidate acts on and exists for a Serve org with no campaign at all, while `Outreach` is the campaign-reporting projection the v2 history table's Archive toggle filters on — and #1375 added the first while the second already existed, with nothing joining them, so a list could be shelved on one rail and live on the other. **`setArchived` now moves both inside its own transaction**, the way `complete` has always mirrored `status: completed` onto the same envelope, so `useTurfLifecycle` (`native/turfLifecycle.ts`) posts `turfs/:id/archive` and is done. Both surfaces that offer the shelf — the rail card and this drawer — go through that one hook, and neither needs route data to do it.
- **The client mirror that used to live here is gone, and it should not come back.** #1396 shipped it in `useTurfLifecycle` as a stopgap while gp-api was frozen: archive the turf, then resolve turf → route → envelope through `GET turfs/:id/route` + `GET /v1/outreach`, then `PATCH outreach/:id/archive`, reporting "your outreach history has not caught up" when the second half failed. Two writes with no transaction is a mirror a phone can die in the middle of, and — the part no amount of client care fixes — **any caller of the archive endpoint that isn't this code skips it entirely**. What went with the mirror: the two lookups, the 404-means-no-campaign special case, `MIRROR_LAG_MESSAGE`, and the `{ mirrorFailed }` result the mutation threaded to decide between a success and a lag snackbar. A failed archive is now just a failed archive — the one call committed both rows or neither — so `FAILURE_MESSAGE`'s "This list could not be archived. Try again." is honest advice again, which it was not while the turf was written first. The drawer's tests keep one assertion pointed at this: archiving issues exactly **one** request. The mirror's own behavior (the repair path, restore, a Serve org with no envelope) is asserted server-side in `doorKnocking.routes.test.ts`, not here — a client test can only observe that it made one call.

- **The header carries the list's lifecycle stage, through the outreach drawer's own component.** The canvas draws a status indicator beside the name in **both** details drawers (`renderDkDetails`: `statusIndicator(list.completed?'done':(knocked>0?'in-progress':'scheduled'))`), and `OutreachDetailsDrawer` has always rendered one — this drawer rendered nothing, so Details on a finished list said so nowhere except by swapping its footer button. `turfStatusLabel` (`native/turfLifecycle.ts`) maps our four states onto that vocabulary and `HistoryStatusText` renders it, deliberately the **same component** rather than a local mapping: the whole product claim about these two drawers is that they are one component family from two entry points, and a second icon/tone table is a second chance for one list to be "In progress" here and something else there. Lockedness _is_ the canvas's `knocked>0` — a turf is locked iff its frozen route exists, and a route exists iff someone started knocking it. `Archived` is ours (the canvas has no shelf) and was added to the shared `STATUS_DISPLAY`, which is additive rather than door-knocking-only because gp-api's `setArchived` stamps the outreach envelope in the same transaction, so the state really is the history table's too. It reads `liveTurf`, like everything else here that can move under an open drawer. **Two canvas header elements were deliberately not copied**: its channel badge (a drawer that can only ever describe door knocking does not need a pill saying so) and its `Name` and `Channel` Overview metrics (the name is the heading two lines above, and the channel is a constant — printing either as a statistic spends a grid cell on nothing).
- **The canvas's status breakdown is not built, and `UI-DRIFT-REVIEW.md` § 6's reason for it is weaker than it was.** The canvas puts a seven-row outcome table on this drawer; § 6 ruled it out as the landing rail's `canvassStatusCounts` chips reported twice. That still holds for an **unknocked** list, where both readings would come off the same pack pass. It holds much less well for a knocked one: the rail's chips are the pack's superset over the polygon and say "About", a frozen route's outcomes are exact, and Details can be opened on a list that is not the selected scope at all — so they are two quantities that legitimately differ rather than one drawn twice. `VOTER-OUTREACH-2.0-AUDIT.md` records the argument. Do not build it on the strength of that argument alone; § 6 is a recorded product decision and reversing it is product's call.

### The walk — stop list, door sheet and knock form

- **A stop with nobody knockable says so, and the status is not what says it.** Its rollup comes off an empty list, which is the same grey `unknown` as still-to-knock, so a surface reading only `rollupStopStatus` renders a fully flagged household and one nobody has started identically. `stopIsKnockable` (`native/statusPresentation.ts`, beside the rollup) is the other half — a second value rather than an eighth status, because "not a target" is a different question from "which status", and answering it with a colour would put it in the legend as a kind of outcome. `WalkView`'s row reads it and prints "Nobody to knock here" in place of the count and dots. **The map pin reads it too, and draws hollow** — the surface where it matters most, per the map-pin note above, since a pin is what a canvasser is standing in front of. `RoutePin` (`native/VoterMapCanvas.tsx`) carries `knockable`, populated as `stopIsKnockable(stop)` where `NativeDoorKnockingPage` builds the pins, and the `route-pins` layer inverts on it: near-transparent fill, the stop's own status colour moved to a thicker ring, and the `route-pin-numbers` numeral inverted with the fill (white on a hollow pin is a number nobody can read). **Hollow rather than an eighth fill colour** — an outline says "not a target", where a new colour would say "another status", would owe the legend an entry for something that isn't an outcome, and would join seven colours a canvasser is still learning. The status still comes off `rollupStopStatus`, so a flagged stop keeps whatever its colour was; the two values stay two answers to two questions.
- **The walk list is numbered again, and the numeral is the handle the map and the list share.** The Aug 14 walkthrough took the numerals out of `WalkView`'s rows; the **2026-08-20 product call put them back**, so the removal is history rather than a rule — and, like the quick-chips note below, reversing this again takes a product decision and not a review round. What the removal missed is that the map has always drawn `seq` on every pin (`route-pin-numbers`), so a list with no numerals gave a canvasser standing in front of a house no way to turn the pin under their thumb into the row that opens its door: the two surfaces described the same street in two vocabularies. The row prints **`seq`**, never its position in the DOM — the list sorts by `seq` and paper prints it, so an index would be a fourth name for the same stop the moment anything but the whole route is listed. It rides the **status circle** rather than a neutral badge beside it (the prototype's shape): one circle carrying the stop's two facts is what the map pin already is, and two circles per row put a number and a color in a staring contest. The numeral colour therefore has to invert with the fill the way the pin's does — `stopNumeralColor` picks white or black by WCAG relative luminance (crossover 0.179), which clears 4.8:1 on all seven statuses; a single hardcoded colour cannot, since the palette runs from `not_home` yellow to `refused` black. Fixed hex and not `text-foreground`, because the fill under it doesn't follow the theme either. **The old argument still stands and is why the number is a label rather than an instruction**: nothing holds a canvasser to walking the list top-to-bottom, `advanceFrom` still skips anything statused or flagged, and the printed sheet keeps its numbering for the different reason that a sheet cannot reorder itself. `PersonSheet`'s header circle stays gone — its fill was a constant `bg-info`, so the numeral was the only thing in it — and the details sheet's roster and the draw step's address preview keep their omissions: no visiting order exists in either, which was always the real content of "map-and-paper only".
- **One selection, set from either surface, shown in the list.** `selectedStopId` in `WalkView` is set by a row tap, by a pin tap (through the same `openStopRequest` that opens the door) and by `advanceFrom`, so the marked row is always the stop the sheet is offering rather than a history of taps. It shows as `aria-current` plus a tinted row and a **ring** on the numbered circle — a ring because a filled selection state would have to take the status colour's place. It deliberately **outlives the sheet**: the door just worked is the one worth keeping marked, and a mark that cleared on close would leave a fifty-row list saying nothing about where in the street the walk had got to. A pin tap additionally scrolls its row into view, because the map band and the list are stacked and the tapped stop's row is usually off screen — without it, closing the sheet returns the canvasser to some other part of the street. **The reverse direction is not built**: nothing on the map renders the selection, because `VoterMapCanvas` takes no such prop and adding one means changing a canvas all three modes share plus the frozen orchestrator seam. The prototype doesn't draw it either (`WalkMode` keeps `activePinId` for its own list), so the list is where a selection is read, and the pin's own numeral is what makes that readable.
- **A map pin opens the same door a stop row opens, and the map says a pin is tappable.** Neither half existed: `route-pins` was `pickable: false` with no handler, so a canvasser standing in front of a house could not tap its pin, and nothing on the walk map suggested they should try. Now the map's own click handler picks the layer (`PIN_TAP_RADIUS` of slop on top of the pin's 11-14px radius, so the target clears the ~44px a thumb needs in the street), `useWalkMapSession` (in `WalkSurface.tsx`, called by the page because the canvas outlives the walk) turns the hit into `{ stopId, token }`, and `WalkView` turns that into **`openSheet`** — the stop row's own path, so the replay keys and the ADR 0009 feed refresh come with it and a door still has exactly one way to be logged. A **token** rather than a bare stop id, because closing the sheet leaves the page's state alone and the second tap on the same pin would be inert; `WalkView` remembers the token it acted on, since every knock patches the route cache and rebuilds the stops its effect reads, which would otherwise spring the sheet back open on a canvasser who had closed it. Gated on the same `drawActiveRef` the vertex path is, so a pin tap can never become a boundary point and a drawing tap can never open a door. A **household** goes straight to the sheet rather than expanding the way its row does: the row's list is under the finger that pressed it, a pin is on a map band the list is scrolled away from, and the sheet's resident switcher is the same picker one step further in. It opens on the first resident still worth knocking, so a household with one flagged member lands on the person there is a conversation to have with. **A hollow pin opens too** — deliberately, per the `stopIsKnockable` note above. A tap that silently does nothing is the bug being fixed, and a sheet is not a form: `PersonSheet` withholds the script and `RecordKnockForm` for a flagged resident and renders the flag's own control and its `STATUS_CHANGE` row instead, so the tap answers "why am I being told to skip this house?" at the doorstep — the one place a flag set on the wrong resident is caught — without offering a knock to log. The coach mark is the prototype's words verbatim (`Tap a pin to log the door.`) as a `pointer-events-none` pill at the bottom of the walk map. Unlike the draw step's card it is **not** a full-inset dismiss button: there is no stray-vertex problem to solve here and swallowing the first pin tap would make the hint the bug, so it is dismissed by the gesture it teaches. Sitting low is safe because walk mode already stacks the shell `flex-col` with the list below the map — the sub-`lg` rail sheet that would cover it belongs to the landing map and is unmounted for the length of a walk. It is per-walk, reset beside the tapped pin by the session's own `reset()` on the way out, because every walk opens on a route the canvasser has not seen before.
- **Free-text notes use the shared dictation stack**, not a door-knocking one: `useDictationAppend` + `DictationMicButton` + `DictationFeedback` from `briefings/shared/`, wired into `RecordKnockForm`'s `Textarea` with `analyticsLabel: 'door_knocking_note'`. That label is what `EVENTS.Dictation.Started` / `Failed` are sliced by — don't add a door-knocking-specific dictation event. The knock event still reports only `hasNote`; a transcript is free text about a named voter and never travels.
- **The "not a voter" reason is asked _after_ the door is saved, never before it.** This is one of the two deliberate departures from the prototype — this one on _timing_, for the correctness reason below; the other is the note field, on _layout_, by product decision (see the notes bullet). The prototype asks "What happened?" → Moved / Deceased inside the flow and gates its Save on an answer. ADR 0008's follow-up is **optional**, and a door that is only written once an optional question has been answered is a door lost whenever the canvasser walks away mid-question — so `NotAVoterControl` renders nothing until the target's `knockStatus` is already `not_a_voter`, and `RecordKnockForm` ends that branch at Save like every other. The one concession is that `WalkView` does **not** auto-advance off a `not_a_voter` outcome: advancing would ask the question and take the answer away in the same frame. The door is saved either way, so a canvasser who ignores the prompt and walks on has still logged a valid door. Answering turns the prompt into the marker, which withholds the form the way do-not-knock does; the prompt keeps the form visible, because that is how a mis-tapped outcome gets corrected.
- **`RecordKnockForm` is the prototype's walkthrough, and nothing sits beside it.** The form opens on "Did they answer?" and expands downward as answers land: answered → "Did they engage?" → engaged → support → will-vote, with the note arriving at the end of whichever branch was walked (see the notes bullet below). Every question already answered **stays on screen** (the answer a canvasser wants to check before saving is the one they gave two taps ago), tapping a chosen answer again clears it and collapses whatever it opened, and Cancel resets the walk without closing the door's sheet. **Save appears only once the branch has nothing left to ask, and Save is the only thing that writes a knock** — which is also what keeps `advanceFrom` off the trigger until a record is complete, since the mutation is the only path to it. This **supersedes the two-tap design, by an explicit product-owner decision that the prototype (`VoterPanel.tsx`) is the spec and this build stops deviating from it.** The brief asking for two-tap capture is the **older** input and it was **overruled, not forgotten** — so neither that brief, nor a review round reading this diff cold, nor an agent resuming from it is grounds to put the chips back. Reversing this takes another product decision, not a code review. The superseded design was `QUICK_RESULTS`: one flat row of seven complete results, each saving on a single tap, with the cascade hidden behind "Add a note or more detail" and the two paths kept exclusive. Its field cost is what the decision knowingly spent — a not-home door is two taps inside the sheet rather than one, an engaged voter five rather than one — and what it bought back is the questions actually being asked, since a flat row can only carry outcome plus support: will-vote had nowhere to land, so a walk logged entirely through the chips produced no vote-intent data at all, which is half of what the Aug 14 walkthrough asked us to record for an engaged voter. `logMode` on `DoorLogged` existed only to measure which of those two paths canvassers used, and went with them — **removed rather than frozen at a constant**, because a payload key that can only ever report one value still reads as a dimension while answering nothing. Removing it was safe to do outright: it was introduced by the same change that built the two paths, nothing in this repo ever read or grouped on it, and `DoorLogged` itself still fires — so this is a property going away, not an event, and the retire procedure in `instrument-analytics-event` (which is event-scoped, as is the provenance CSV) doesn't apply.
- **A note can be written on every outcome, this is the one place the walkthrough's _layout_ departs from the prototype on purpose, and it is the second of the two deliberate departures (the other is the `not_a_voter` follow-up's timing, above).** The prototype puts the note field on the engaged branch only, after support and will-vote. **The product owner overruled that specifically**, because most doors never open and those are the ones a canvasser most often has something to say about: "dog in the yard, come back Saturday" is the archetypal note, the pre-prototype detail path supported it, and the faithful port removed it. So the field renders whenever `complete` is true — which is exactly "this branch has nothing left to ask" — meaning it is always the last thing offered, arrives together with Save, and never sits stranded between two unanswered questions. On the engaged branch that is unchanged (still after will-vote); on a one-question door it is one tap in. **A note is never required**: `complete` does not consult it, so Save is live the moment the questions are done and a not-home door is still two taps. **Read this bullet next to the one above before changing either.** Removing the quick chips and restoring notes-on-every-door are _both_ product decisions and they point in opposite directions — the first moves away from the old design, the second away from the prototype — so "match the prototype" is not a licence to re-hide the note field, and "restore what we had" is not a licence to bring the chips back. What forced the question was a real defect: with the field engaged-only, a note typed in the engaged branch and then corrected to a non-engaged outcome stayed in state and was **saved while invisible**. The fix is the field being visible there, **not** `setNote('')` or an `engaged &&` guard at save — those delete text a canvasser wrote about a named voter, which is strictly worse than the bug. Hence the general rule in the form: **collapsing a row discards the _answers_ it would otherwise re-offer pre-filled and unnoticed, but never the _text_ someone typed.** No contract change was involved — `note` has always been `.optional()` on every outcome, and only `supportAnswer`/`willVote` are refined to `answered`. Paper needed nothing either: both surfaces already print a Notes field for every person, and `print/pdf/WalkListPdf.tsx` already tells a canvasser to write _why_ a door didn't answer in Notes — an instruction that, while the app had no such field, produced a paper note that could not be transcribed back. That gap is now closed.
- **The app asks the outcome as two questions; paper prints it as five options.** `DoorKnockOutcome` is a flattening of the tree the canvasser walks, so `native/knockQuestions.ts` carries both shapes — `ANSWER_OPTIONS` (Answered / Not home / Inaccessible) and `ENGAGEMENT_OPTIONS` (Engaged / Refused / Not voter) for the app's two steps, and `OUTCOME_OPTIONS`, all five, for paper and for `walkFacts.ts`'s last-contact line, which name an outcome on its own. **Step two is the outcome the contract gets**; step one's `answered` only ever meant "keep asking" and must never reach it, which is why backing out of the engaged branch also clears the support and will-vote answers picked inside it — the contract rejects them on any other outcome. `answered` deliberately carries two labels, `Answered` in the flat row and `Engaged` in step two, because by the second question "did they answer" is behind the canvasser and the thing being asked is whether the conversation happened. **Paper keeps the flat five because a sheet cannot branch** and has to offer every ending at once; the mapping back is total — Refused to engage is Answered → Refused, Not a voter is Answered → Not voter, the other three are step one — so a sheet is still transcribable into the form. Change either list and both paper surfaces change with it.
- **Saving advances to the next door** (`advanceFrom` in `WalkView`) — "always show the next door so there is no thinking between houses". Forward only, skipping anything already statused or flagged do-not-knock, and the sheet closes when nothing is left ahead; walking a canvasser backward up the street to a door they passed is worse than leaving it on the list. `advanceFrom` reads the **pre-patch** cache, so the just-logged target is excluded by id rather than by status. Because the sheet stays open across residents, `PersonSheet`'s selected person is controlled by `WalkView` — internal state would keep showing the person just logged.
- **The door script is the candidate's own saved issues, not AI copy and not the survey designer.** `native/doorScriptContent.ts` assembles it from two stores the issues editor already writes to — `campaign_position` rows (`GET /v1/campaigns/:id/positions`, catalog stance in `position.name`, the candidate's wording in `description`) and the bespoke `details.customIssues` — because a candidate who only ever used one of them still needs a script. Titles are de-duplicated case-insensitively, since re-entering a curated issue as a custom one is easy and saying it twice reads as a glitch. An issue with a heading but no stance is dropped rather than printed bare, and with nothing written at all `DoorScript` renders `null`: the fix is in Campaign Details, not here. The `surveys/` designer is a different, eCanvasser-era surface — don't wire it, and flag-on users no longer reach it (see below). Deliberately **screen-only**: the printed sheet stays a transcription form.
- **Phones are on screen only, and live only.** `cellPhone` / `landline` ride the route payload for `PersonSheet` and are **deliberately absent from both paper surfaces** — paper leaves the building and stops being access-controlled when it does; `WalkSheet.test.tsx`, `walkListRows.test.ts` and `WalkListPdf.test.tsx` each assert the omission rather than trusting it, and their fixtures carry a number so the assertion can fail. They come from the live residents join, the same source `mayHaveMoved` is derived from, so a mover shows no number instead of one belonging to whoever lives there now. `otherResidents` stays name-only: a non-target resident is context for the conversation, not someone the candidate asked to contact. These are the same two columns the voter-file download already exposes as "Cell Phone" and "Landline" behind the same district access check, so this is not new disclosure. **Voter email does not exist** — no column on the `Voter` model, no field on the `Person` contract.
- **The door shows eleven demographic attributes for a target, and the disclosure argument is precedent, not judgement.** `PersonSheet`'s "Demographic information" card renders registered voter, turnout likelihood, marital status, has children under 18, veteran, homeowner, business owner, level of education, estimated household income, language and ethnicity off the route payload. **Every one of those columns is already in `DOWNLOAD_COLUMNS`** and handed to candidates today as a CSV, behind the same district access check and the same Pro gate — so this is a new surface for existing disclosure rather than new disclosure, and that is the argument, written down here so it doesn't have to be re-derived at the next review. Values arrive already mapped for display by gp-api's `transformToPersonOutput.util.ts`, the same mappers `/v1/contacts` person detail uses, so a voter's education is not worded one way in Contacts and another at the door; `demographicFacts.ts` turns them into label/value rows and invents no vocabulary of its own. **Three labels are deliberate.** "Turnout likelihood" is _not_ the prototype's "Voter status": `Voter_Status` holds turnout propensity (Super/Likely/Unreliable/Unlikely), while "voter status" in this industry means active-or-inactive registration, so the prototype's word would name the field as something it isn't. "Has children under 18" is a household Y/N flag with no count behind it. "Estimated household income" says household because that is what the column models, and it is bucketed through contracts' `INCOME_RANGE_MAPPING` rather than printed to the dollar — a modelled figure shown to five significant figures implies a measurement nobody took. **Absence renders as "Not on file", one string for all eleven**, which is what makes the card safe: sparseness is the normal condition of this file, and `veteranStatus`/`businessOwner` are presence-only (`z.enum(['Yes']).nullable()` — the column holds a value meaning yes or nothing at all), so "No" there would state a fact the data cannot support. `registeredVoter` is the one that _does_ have an honest No, being a real boolean off `StateVoterID IS NOT NULL` — the same derivation the pack calls "registered", and deliberately not the `Person` contract's hardcoded `'Yes'`. The route payload's keys are **optional** for the reason `history` is: a walk snapshotted offline before this shipped carries none of them, nothing parses this payload in the webapp, and a bare ternary would turn that `undefined` into "No". **Targets only** — `otherResidents` stays name-only, per the phones bullet above. **Screen only** — both paper surfaces omit all eleven, for the reason they omit phone numbers and with more force, since a printed profile of a named voter stops being access-controlled the moment it leaves the building; `WalkSheet.test.tsx`, `walkListRows.test.ts` and `WalkListPdf.test.tsx` each assert the omission against a fixture carrying all eleven, so the assertions can fail (verified by mutation).
- **The activity feed is per-resident, reuses the CRM's rows, and survives a flag** (ADR 0009). `ActivityFeedCard` renders `target.history` off the route payload — no fetch, because the sheet has to open a block into a walk with no signal — using `DoorKnockActivityRow` / `TextActivityRow` / `RobocallActivityRow` / `StatusChangeActivityRow` imported from `contacts/crm/person/ActivityFeedEntry`. Don't fork those: the point is that `do_not_knock` and `not_a_voter` can't read one way in Contacts and another at the door. It sits in the sheet's **scrolling body** with Contact information and Household, not in the footer fragment with the script, `RecordKnockForm`, `NotAVoterControl` and `DoNotKnockControl` — so it keeps rendering for a flagged resident whose footer is withheld, which is deliberate: the feed is where the flag's own `STATUS_CHANGE` row lives, and hiding it would hide who set the flag from the person best placed to spot it was set on the wrong resident. Being outside that fragment is also why it needs no `key`; moving it in requires a namespaced one (`not-a-voter-`/`do-not-knock-`), which has been a real collision twice. **The door's feed carries no navigation** — `ActivityFeedCard` strips `outreachId` before drawing, because `TextActivityRow`/`RobocallActivityRow` turn it into a same-tab "View outreach" link, and unmounting `WalkView` discards the per-target replay keys that let a retried knock upsert instead of duplicating; that's the same reason the printed sheet and Open in Maps use new tabs. Stripping locally rather than adding a prop to the shared row keeps Contacts unchanged. **`mayHaveMoved` is not a feed row** — it's a voter-file hint with no date and no author, so it stays a line in Contact information; it can co-occur with a canvasser's firsthand `notAVoterReason: 'moved'`, which _does_ appear as a dated, attributed status change, and the two are meant to read as corroboration rather than one event logged twice. **A knock logged mid-walk joins the feed on the next serve, and `WalkView` asks for one when a resident logged this session is opened again** — via `openSheet` and the sheet's resident switcher, the two ways back to a door already logged. `patchPerson` still writes only `knockStatus`, so the feed alone would stay as served while the status landed everywhere else in the panel, which reads as a broken feature rather than a stale cache. The row stays the server's: widening `RecordKnockForm`'s callback so the card could be handed a client-built `DOOR_KNOCK` entry was the rejected option, because it invents a second construction of a row the serve already builds — and it lands in the save path beside the replay keys. Refetching after _every_ door was rejected too: the serve is the feature's heaviest read and a walk is meant to run on the payload it opened with, so the cost is tied to the only moment the staleness is visible (`advanceFrom` never lands on a logged door, so a forward walk pays nothing). Two invariants hold it safe — a failed refresh is silent and never surfaced (`routeQuery.isError` gates the "route could not load" banner on `!routeQuery.data`, or it would fire beside a door that saved fine), and `patchPerson` cancels the route query before writing so a serve built pre-patch can't overwrite a logged status on arrival.
- **The `not_a_voter` resident's refresh is deferred, not dropped.** They are the one resident neither trigger above reaches, because ADR 0008 holds their sheet open across their own knock so the "what happened?" follow-up can be answered — and a serve arriving mid-answer rebuilds `NotAVoterControl`, whose two branches switch on `notAVoterReason`, underneath the question. So the refresh waits for the follow-up to **resolve**, which is either of two things: answering it (hooked to `onNotAVoterChanged`, after `applyNotAVoter` so the patch's own query cancellation can't take the new serve with it) or walking away from it (`refreshFeedOnAbandonedFollowUp` on sheet close). The close path is deliberately narrow — `knockStatus === 'not_a_voter'` **and** no reason yet, so an answered resident doesn't pay a second serve and an ordinary door doesn't pay one at all. Refreshing on every sheet close would be the per-door serve ADR 0009 rejected; this outcome is precisely the one that does not auto-advance, so it is asked for once per held-open sheet. `WalkView.test.tsx` asserts the _interaction_ and not the fetch count: it waits for the query to be idle before reading the screen (a refresh fired on the knock is in flight at that point, so reading earlier passes vacuously — this was verified by mutation) and the fixture's second serve carries a reason a teammate set mid-walk, so a refresh that landed would visibly replace the question with the marker.
- **The door sheet's shape and the two things pinned outside its scroll are layout decisions, not styling.** `PersonSheet` is a bottom drawer below `lg` and a right-hand panel at `lg`, and `lg` is the feature's **only** breakpoint — the landing rail switches there too, so a second one would give the walk two layouts changing at different widths on the same phone. `PersonSheet.test.tsx` asserts both the class pair and the absence of any other breakpoint prefix, which is the only way jsdom can hold that. The **resident switcher sits in the header with the name**, not at the top of the scrolling body: the form is pinned to the footer, so logging a door scrolls the body past anything at its top, and the switcher is precisely the control someone reaches for at that moment — when the person who opened the door turns out to be the housemate. It changes the name it sits under, which is also where the prototype puts it. Everything else stays in the body, including the ADR 0009 feed. **Open in Maps is the stop's frozen coordinates through Google's universal maps URL** (`/maps/search/?api=1&query=lat,lng`): the documented form hands off to the Maps app on both phone platforms instead of opening a web map, and the coordinates are what the route was bought against — handing the address string to a geocoder is exactly what puts someone on the wrong rural driveway. New tab, for the reason the printed sheet uses one: leaving this tab unmounts `WalkView` and discards the per-target replay keys.
- **The Notes section is per-resident, reads off the payload, writes straight to the CRM, and survives a flag** (ADR 0011, 2026-08-20 product call). `DoorNotesCard` renders `target.notes` — ADR 0011's `{ entries, total }`, newest first, capped server-side at `ROUTE_TARGET_NOTE_LIMIT` — and **fetches nothing when the sheet opens**, for ADR 0009's reason with a sharper edge: a failed read here is invisible, since a blank card mid-conversation looks exactly like a resident nobody has ever written about. Writes are the CRM's own four `contacts/:personId/notes` routes, called directly, so a canvasser in a dead zone can read notes and cannot add one. That asymmetry is the ADR's, not an omission — a failed write is visible to the person who caused it and still has their text — and it is **not an offline queue's absence to be fixed here**: `clientKeys` in `WalkView` is a replay key for retrying one submit, not a queue. It sits in the sheet's **scrolling body**, second, above the demographic profile: the split from the footer fragment is the activity feed's (the body describes the person and keeps rendering when a flagged resident's script and form are withheld — a note reading "this is the son, not the registered voter" is what a mis-set flag looks like from the doorstep, and hiding it makes the flag unfalsifiable at the one place someone can check it), and the position is because it is the only card here read _before_ knocking. "Dog in the yard, use the side gate" under eleven rows the demographic card's own comment calls reference material scanned mid-conversation is a note nobody standing at a gate will find. Keyed on `stopTargetId`, unlike the feed beside it — not against a sibling collision, which it has none of out here, but so the draft and the open editor reset on the switcher: half a typed sentence about Dorian re-offered under Marisol's name is free text attached to the wrong named voter.
- **The list after a write is the cached route payload, and `total` is part of it.** `doorNotes.ts` holds the algebra; `WalkView` writes the result of it into the cache and the card is controlled off `target.notes`. Refetching was rejected for ADR 0009's reason — the serve is this feature's heaviest read and a walk runs on the payload it opened with — and it would also be asking the server to repeat itself, since the response to a create or an edit **is** the row. Where that result is _kept_ is the bullet below; what has to be true of it is these four rules, each of which has a wrong answer that reads fine: a created note **is not trimmed** back to the cap, because the cap is a payload-cost decision measured in gzipped kilobytes and a note already in the browser costs none of them — evicting one to imitate a wire limit hides something written seconds ago behind a count, and truncation is read off `total` rather than `entries.length`, which is the inference ADR 0011 rejected, so a locally-grown list still describes itself. An edited note is **replaced in place, never re-sorted**, or a client would undo at the door the exact thing ADR 0011's `created_at DESC` ordering exists to prevent. A delete **decrements `total`**, floored at `entries.length` — a resident at the cap who deletes one otherwise reads "2 of 9" forever, a count that sends someone looking for notes that are not there; deleting one of three shown out of nine leaves **two** of eight, because the fourth note is not in this browser and backfilling it is the fetch the sheet does not do. And an **absent** `notes` block stays distinguishable from an empty one all the way to the sentence on screen (`total: null` in `DoorNoteList`): "no notes about this resident" is a claim about the person, while a walk snapshotted before ADR 0011 shipped is a fact about the payload, and the card says which silence it is.
- **Three smaller decisions in that card, none cosmetic.** The stamp is **`createdAt`, not the CRM section's `updatedAt`** — product asked for when a note was written, and it is also the key this list is ordered by, so printing `updatedAt` would give a card whose visible dates run out of order the first time anyone fixes a typo; an edit says " · edited" beside it instead of silently restamping. The truncation line names the count and **carries no link to Contacts**, for the reason `ActivityFeedCard` strips its own "View outreach" links: a same-tab route change out of a walk unmounts `WalkView` and discards the replay keys. Dictation is wired into the **compose field only** (the shared `useDictationAppend` stack under the existing `door_knocking_note` label — don't add a second door-knocking dictation event), because composing one-handed on a doorstep is the case dictation exists for while editing is fixing a word, which an append-to-the-end transcript makes worse. Delete is the one write in this sheet behind a confirm: a knock, a flag and an edit are all one tap to reverse, and free text nobody can retype is not. **No new analytics event** — adding one is the `instrument-analytics-event` procedure with its provenance CSV, and nothing has asked to slice notes-at-the-door yet.
- **Notes are screen-only, and the assertion is in all three paper tests.** Both paper surfaces omit them for the reason they omit phone numbers and the demographic profile and with more force again: free text a named person typed about a named voter is the largest disclosure on this payload, on the surface that stops being access-controlled the moment it leaves the building. `walkListFixtures.ts` and `WalkSheet.test.tsx`'s fixture both carry a note and a `total` of nine, so `walkListRows.test.ts`, `WalkListPdf.test.tsx` and `WalkSheet.test.tsx` assert the omission rather than trusting it (verified by mutation). **The count is asserted too** — "9 notes on file" says how much has been written about a voter even with none of it printed. The assertions name the note's **body**, never `/notes/i`: both paper surfaces print a blank Notes field for every person to write in, and that blank is the point of the page.
- **A note goes into the cached route payload, by the same road a knock does, and there is no second copy of it anywhere.** #1406 shipped the list after a write as a `useState` map above the card, keyed by `personId`, and documented the hole that left: **the map died with the sheet**, so a note written on a door the canvasser then closed _without logging_ — which is the ordinary shape of a door nobody answered — read as gone when that door was reopened, since `target.notes` was still whatever the last serve carried and `openSheet`'s ADR 0009 refresh only fires for a resident logged this session. `WalkView.patchNotes` closes it: `doorNotes.ts`'s algebra is applied to the target's served block and the result is written through **`patchPerson`**, the same optimistic write `applyKnockStatus`, `applyDoNotKnock` and `applyNotAVoter` use. Reusing it is the point rather than a convenience. It **cancels the route query before writing**, so a serve built before the note was saved cannot land after it and take the note back off a card the canvasser just watched save — the same race that would otherwise put a logged door back to unknown. And a serve that genuinely arrives later **does** replace the patch, which is the only way a note a teammate wrote ever reaches this walk; a client-held list would shadow the server's for the rest of it. `PersonSheet` is now fully controlled here too, like `selectedTargetId`: it renders `seedDoorNotes(target.notes)` and reports writes up as `onNoteCreated` / `onNoteUpdated` / `onNoteDeleted`. **The local map is gone, deliberately — do not reintroduce one.** Two stores that have to agree about a resident's notes is the class of bug this removed, and it is the same reasoning that put the archive mirror on the server (#1405) and made `WalkView` own the walk's selection (#1409). The card keeps its `stopTargetId` key, which is about the draft and the open editor and not about the list.
- **`editServedNotes` is the one seam where the wire shape cannot say what the door knows, and the trade is deliberate.** `RoutePayloadTargetNotes.total` is an `int`, while `DoorNoteList.total` is `number | null` — so a payload that predates ADR 0011 (no `notes` key, hence `null`) has no honest count to write back once a canvasser adds a note to it, and the adapter materialises `total: entries.length`. Both alternatives are worse. Leaving the block absent would drop the note the moment it was written, which is the whole defect above. Deriving a count from the served rows is the inference ADR 0011 rejected outright. What is given up is the card's "this walk was saved before notes rode the route" line, for that resident, from their first note onward — and that line does its work on an **empty** card, where a blank section otherwise reads as "nobody has ever written about this person". A card showing a note written thirty seconds ago is not that false negative. It is also unreachable on any payload a live serve produced, since the server always sends the block. **This is not a reason to widen the contract**: `total` being a real count is what lets the door tell three-of-four from three-of-forty, and nullable-on-the-wire would put "rows with no count" back on the server's side of the line.

- **`PersonSheet` walks the route, and that is not the auto-advance rule loosened.** The canvas's panel header is a back chevron, the stop's number, the person, a forward chevron (`renderPanel`: `navBtn('chevron-left', ()=>this.openPanel(route[idx-1].id), hasPrev)`); ours was a dead end, so reaching the next house meant closing the sheet and finding a row that has usually scrolled away — three gestures, one-handed, at a door. `WalkView` resolves the neighbouring stops off `stops` (sorted by `seq`, so this is the planned order and the order the pins are numbered in) and hands them down as two nullable callbacks, both routed through **`openStopFromMap`** — the one entry that also brings the list to the stop it opens, and that picks the first resident still worth knocking. Without that, a canvasser four doors along closes the sheet onto a list still showing where they started. **Disabled at the ends rather than absent**, so the pair keeps its place instead of reflowing the header mid-walk, and so a missing chevron cannot read as a broken one. This does **not** relax `advanceFrom`, which stays forward-only for the reason recorded there: it moves the canvasser _without being asked_, and sending them back up a street they have walked is the failure it exists to avoid. These are asked for, and the list already allowed going back. The header also carries the stop's `seq` — never an index — so the sheet, the row, the pin and the printed sheet name one stop one way. The canvas's own chevrons are labelled with the icon name (`'aria-label':icon`, literally `chevron-left`); ours say "Previous door" and "Next door". One consequence of walking without unmounting: the scrolling body **keeps its offset between doors**, so a canvasser who had scrolled down to the activity feed at one house arrived at the next already past the address, the phones and Open in Maps — the half of the panel they need first at a door. An effect on **`stop.id`** returns it to the top. On the stop and not on the selected resident: switching residents at one door is a lateral move within the same page of content, and yanking the view to the top under a finger that has just picked a housemate is its own bug.
- **A stop row's people count says what it counts.** The canvas puts a person glyph in front of it (`this.icon('users',14), householdCount(v)`). Ours printed the bare numeral one gap from the stop's own numeral in its coloured circle, so the row read `12` `3` and named neither quantity — and to a screen reader, which has none of that layout, "Stop 12, 3". The glyph is `aria-hidden` and an `sr-only` noun carries the spoken half ("3 people to knock"). The dots after it stay decorative: they are per-resident status, and the expanded row labels each one in words.

### Paper — the printed sheet and the PDF

- **Offline means paper.** `print/` is a server component with no `'use client'` anywhere in it, deliberately: it has to render and print on a phone with one bar, and it sits outside `DashboardLayout` so no nav chrome hits the page. Its mark boxes are generated from `native/knockQuestions.ts`, the same constants `RecordKnockForm` renders — the paper is transcribed back into that form, so the two must not drift. Paper keeps the three-question layout and offers all five outcomes at once, because it cannot branch the way the screen does; re-keying a sheet means walking the app's two outcome steps to reach the ending that was ticked. Nothing written on the sheet reaches gp-api until someone re-keys it.
- **The PDF is built on the server, and that is load-bearing.** `print/[turfId]/pdf/route.ts` renders `print/pdf/WalkListPdf.tsx` with `@react-pdf/renderer` (already a dependency, for the onboarding campaign plan) and returns it as an attachment. Generating it in the browser instead would mean shipping ~1 MB of layout engine and PDF writer down the exact connection this feature exists to work around, and putting the first `'use client'` module into a directory deliberately kept at zero — so every entry point stays a plain `<a href>` that needs no JavaScript and no hydration. The cost lives on the other side: layout is CPU-bound in the number of **residents**, and node count per row is the lever — the answer columns are most of the nodes on the page. Measured at the 150-stop cap (250 residents, three runs, median), the design handoff's mark boxes took it from **16 pages / 2.97s to 19 pages / 3.79s**: +19% pages, +28% wall clock. The cause is geometry, not code — a 12px box with a 7px label beneath it is a taller row than an inline 7px tick, and there are eleven of them per row. The handler's `maxDuration` still covers it with room, but this is the budget, and anything that adds a node per row now spends against a worse baseline. Swapping the renderer means changing `renderWalkListPdf` only; the row model and the handler don't move.
- **Two paper formats, one grid, one set of facts.** Since the design handoff both surfaces rule **one row per resident** with the stop number and address merged down a household, so a shared front door reads as one door; the printable page used to stack a form per person and no longer does. Both quote `walkFacts.ts`'s `walkSummary`, which is built on `routeCounts.ts` — the app and the paper have reported different door counts for the same route before — and both quote its `WALK_COLUMNS`, `MARK_INSTRUCTION` and `RECORDS_NOTICE`, because a canvasser filling in one and a volunteer filling in the other hand the same answers to the same transcriber. Content decisions (who gets a blank form, who gets their logged status, who gets the skip instruction) live in `print/pdf/walkListRows.ts` as a pure model, which is also why the PDF structurally cannot print a phone number: it is never handed one. **`walkListRows` is the PDF's model, not a shared one** — `WalkSheet.tsx` builds its own rows and reads the shared helpers directly, so anything both surfaces must say goes in `statusPresentation.ts` or `walkFacts.ts` and is quoted twice. Adding it to the row model alone reaches the PDF only. Age is the one field that moved for the handoff: it has a column of its own on both surfaces now, so `describeTarget` no longer leads with it and `WalkListRow` carries it as its own field — printing it in both places would state a voter's age twice in one row.
- **Paper carries a last-contact line, because paper is where ENG-10876 is still open.** `deriveKnockStatus` collapses answered-but-unsure into `unknown` on purpose so the door stays worth knocking — which leaves both paper surfaces printing an identical blank form for a door that answered unsure and one nobody has ever been to. On screen ADR 0009's `ActivityFeedCard` answers that; paper carried no history at all. `lastContactLine` (`print/walkFacts.ts`, beside `describeTarget` — this is paper-only, the screen has the whole feed) turns `target.history` into one line: `Last contact: June 2026 · Door knock: Not home`. Read by `WalkSheet.tsx` and by `walkListRows.ts`, since those are the two independent renderers. Four decisions in it, none cosmetic: **outcome wording comes from `OUTCOME_OPTIONS`**, the same labels as the tick-boxes below it and the form the sheet is transcribed back into; **`STATUS_CHANGE` rows are skipped** because a flag set at a desk is a record edit, not contact, and dating the last conversation to it would be a lie (`skipInstruction` already says what a flag means); **the note never travels**, for the reason the phone numbers don't — `walkListRows.test.ts`, `WalkSheet.test.tsx` and `WalkListPdf.test.tsx` each assert the omission against a fixture that carries one; and **the month is formatted in UTC, with no day**, because both surfaces render in Node whose clock is UTC, so a door knocked at 9pm anywhere in the US would print as the following day. That is the same reason neither page stamps itself with today's date, and a consistently wrong day is not an improvement on a coarse right month — it is also the granularity ADR 0009 argued the feed for ("we spoke in June about the sidewalks"). Absent history prints nothing rather than "never contacted": a route the service worker snapshotted before ADR 0009 shipped has no `history` key, so absence is not a claim.
- **The abbreviations are gone; the one lossy column is still lossy.** The handoff's mark box puts the label *under* the box instead of beside it, which is the room the old `Y N ?` was short for — Support and Will-vote now spell "Yes / No / Unsure" on both surfaces, still generated from `SUPPORT_OPTIONS` / `WILL_VOTE_OPTIONS` in the app's order, because paper is transcribed back into that form. Answered is still the exception on the PDF: two of the five outcomes, labelled Yes / No but keyed to the real `answered` / `not_home` values, so a ticked box lands on something the form accepts. It is 8% of a landscape page and five labelled boxes need 24%; the three it drops are the three a canvasser writes a reason beside anyway, and Notes is the next column. The printable page keeps all five and pays 24% for them.
- **Where the design handoff and the canvas disagree, the canvas wins, and two of the handoff's tables are simply wrong.** The Voter Outreach 2.0 canvas is this feature's source of truth. Its door-knock form ticks **`Yes / No / Unsure`** for both support and will-vote and offers a three-way outcome; the handoff's **`Support: Strong / Lean / Undec / No`** and **`Answered: Yes / No / Moved`** contradict it as well as our enums. "Strong" occurs once in the whole canvas, as one of four values of a voter's CRM support *attribute* — a field on a record, not something a canvasser ticks at a door — and "Lean" occurs nowhere; the only "Moved" is the "Moved to archive" toast for a list. So these are an error in the handoff rather than a design decision to reconcile: **build the boxes from `SUPPORT_OPTIONS` / `WILL_VOTE_OPTIONS` / `OUTCOME_OPTIONS` and never from a list typed into a renderer.** The handoff's box *geometry* stands and is implemented — 12×12px, 1.5px border, 2px radius, 7px/700 uppercase label beneath, one non-wrapping row per column. **Will-vote is kept** though the handoff has no column for it: the canvas asks the question, so the handoff omitted it, and a sheet that cannot record an answer the form wants is a sheet that has to be walked twice. All of this is pinned by tests that fail if reverted, verified by mutation.
- **Two things are genuinely open with the designer; don't quietly settle either.** **The Phone column** the handoff rules at 11%: the canvas puts a phone number on the *call* sheet, where it is the entire point of the artifact, and has no walk sheet to set a precedent — so this is a new proposal, not the canvas overruling our disclosure decision. It stays unimplemented pending an answer, on the reasoning that paper stops being access-controlled the moment it leaves the building; note that adopting it is bigger than a column, because `walkListRows.ts` would have to start carrying the field and that makes it reachable by every renderer at once. **The last-contact line** the handoff has no row for: kept, because it is ENG-10876 and dropping it would regress a shipped fix, and the designer should know it exists rather than discover it. Also left alone, and worth a sentence to them: the handoff's footer tagline reads *empowering Independents* where both surfaces keep the brand line already in the codebase — brand copy is not this feature's to change.
- **Both surfaces print the per-leg walk time, and `legTravelLine` is the only place it is worded.** The printable sheet had always shown "3 min from last"; the PDF showed nothing, so the artifact you hand a volunteer was the one that couldn't say why the stops are in the order they are in. It is in `walkFacts.ts` and quoted twice, like every other fact both must state. **It costs nothing**: measured at the 150-stop cap (221 residents, 149 legs) it is 15 pages with the line and 15 without, and the render time difference sits inside the run-to-run spread — row height is set by the mark boxes, which are taller than the two or three lines of 8pt text the address cell holds, so the sub-line lands in space the row already paid for. Mode is deliberately not in the wording, though `WalkView` says "3m walk" per leg: on paper every leg belongs to one route whose header already reads "Walking loop", so repeating walk-or-drive 150 times spends the narrowest column on the page restating something above it.
- **Three scopes per row, and mixing any two of them misreads the route.** The **stop number** and the walk time from the last stop belong to the *stop*; the **address** belongs to the *household*; everything else belongs to the resident. It matters because a walkable multi-unit building routes as one stop with a door per unit: gate the number on the household and a two-unit building prints its number twice, which reads as two stops. Both surfaces carry `firstInStop` and `firstInHousehold` for this, and the printable sheet counts rows across the whole stop rather than per address. Colour tokens in `walkSheet.css` all carry the styleguide's own hex as a `var()` fallback — an undefined custom property invalidates the whole declaration, and in the mark box's `border` shorthand that means no border at all, i.e. a box nobody can see to tick.
- **Column widths are measured, not copied, and the measurements are the argument.** The handoff's percentages hold wherever a column means the same thing on both, and every departure traces to a column this grid has and the handoff's does not, or the reverse. Measured against a 960px content width (Letter landscape inside the handoff's half-inch margins): five labelled mark boxes in one row need **226px**, three need **79px**, and `#` at the handoff's 2% is 19px, which is not enough for "150" — the handoff's own fixture renders 1 to 40 rows and a route here is capped at 150 stops. The one thing that fits at no width is the last-contact line, whose longest form runs about 224px; the PDF buys it a single line at `Name 22%` and it is worth measuring before trimming, because at 18% it wrapped on a third of the rows and cost three pages. **Notes is charged last on both surfaces** — it is the column someone writes in.
- **Page numbers: the PDF's are real and the printable page's are blanks, and that asymmetry is not laziness.** The handoff asks for `counter(page)` / `counter(pages)`. `counter(pages)` resolves only inside an `@page` margin box, no browser implements margin boxes, and in flow content — the only place a document can put its own content — Chrome resolves it to nothing and prints "Page 0 of 0", a number that is wrong where a blank is at least honest. So the printable page prints `Page ____ of ____` beside its Canvasser and Date blanks, and browsers add page numbers of their own in the print dialog besides. The PDF fills the same slot from `@react-pdf/renderer`'s `render` callback, because it lays the whole document out before writing any of it and is the surface that knows the total.
- **The repeating regions are the table's, on the printable page.** The handoff's header, legend, column heads and footer all repeat per printed page; its prototype gets that from a paged-media component with a `header` slot, and a browser gives us exactly two regions it will repeat. So the header and legend ride in `<thead>` (in a `<td>` banner spanning the columns, so the eight `columnheader`s stay eight) and the signature rides in `<tfoot>`. Neither is decoration: flow content above the table prints once, on page one, and a sixteen-sheet route gets separated — page four would otherwise carry a grid belonging to no turf. The PDF marks the same three blocks `fixed`.

### Legacy surfaces (eCanvasser era)

- `components/interactionsColors.ts` is the only place colors should be defined for charts in this feature.
- **The `surveys/` tree is gated to control** (`surveys/layout.tsx`). Its questions are written to eCanvasser and are never asked at a native knock, so a pilot tester who reached `/dashboard/door-knocking/surveys` by URL — or from the Door Knocking Scripts tab — met a second script surface competing with `DoorScript` and could author a whole script that goes nowhere. The layout resolves `native-door-knocking` server-side (`getFlagVariants`, the same resolver that produces the SSR seed) and `redirect`s a flag-on user to `/dashboard/door-knocking` before the eCanvasser reads in the pages below it run. Gated at the segment, so `/surveys` and `/surveys/:id` are one branch. **Control is untouched on purpose** — flag off, unassigned, or unresolvable renders the legacy designer exactly as before, and `shared/DoorKnockingTabs.tsx` stays legitimate there because the only surfaces that render it (the eCanvasser dashboard and the designer) are both control-only.
