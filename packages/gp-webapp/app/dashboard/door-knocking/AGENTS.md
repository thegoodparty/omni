# app/dashboard/door-knocking/

Door-knocking / canvassing dashboard. Tracks volunteer interactions logged in the field, summarizes by day / rating / survey, and lets campaigns design custom door-knocking surveys.

## Key files

| File                                                                | Role                                                    |
| ------------------------------------------------------------------- | ------------------------------------------------------- |
| `page.tsx`                                                          | Route entry                                             |
| `components/DoorKnockingPage.tsx`                                   | Top-level layout                                        |
| `shared/DoorKnockingTabs.tsx`                                       | Tab navigation (overview / surveys / individual record) |
| `components/InteractionsByDay.tsx`                                  | Time-series chart                                       |
| `components/InteractionsSummary.tsx` + `InteractionsSummaryPie.tsx` | Aggregate counts + breakdown chart                      |
| `components/RatingSummary.tsx`                                      | Voter sentiment distribution                            |

| `surveys/`                                                          | Custom survey designer (per-campaign question sets)     |
| `print/[turfId]/page.tsx` + `print/WalkSheet.tsx`                   | Printable walk list (the v1 offline story)              |
| `native/doorScriptContent.ts` + `DoorScript.tsx`                    | Door script built from the candidate's saved issues      |
| `shared/`                                                           | Cross-tab primitives                                    |
| `components/`                                                       | Page-level widgets                                      |

## Patterns

- **Charts use shared color tokens** from `components/interactionsColors.ts` — keep palette centralized; don't inline hex values.
- **Surveys are campaign-scoped**: each campaign authors its own survey questions, used by canvassers in the field. Survey CRUD lives in `surveys/`.
- **Aggregations come from gp-api**, not computed client-side. The components display rather than compute.

## Gotchas

- The legacy tabs on this page only _display_ data sourced from third-party canvassing tools (eCanvasser etc.) via gp-api. Knocks are logged in-app from `native/` (`RecordKnockForm` → `POST /v1/door-knocking/interactions`), which writes to the CRM's own tables and never to eCanvasser.
- **Analytics live under `EVENTS.DoorKnocking`** (`Door Knocking - *`), not the legacy `EVENTS.Dashboard.VoterContact.DoorKnocking` group, which belongs to the script/eCanvasser surface. A completed walk also fires the canonical `Voter Outreach - Campaign Completed` with `medium: 'doorKnocking', method: 'native'` — that's what the door-knocking activation metric counts, so don't remove it while refactoring the walk exit.
- `components/interactionsColors.ts` is the only place colors should be defined for charts in this feature.
- **The voter pack and every turf read resolve a district server-side** (`resolveEligibleDistrictId` in gp-api's `doorKnockingPack` / `doorKnockingKnock` services), so an org with no resolvable district can only 400. `NativeDoorKnockingPage` gates both queries on `useDistrictResolution` (`app/dashboard/shared/`) and explains instead. Gating at the shell also covers the write paths (`POST turfs`, `POST turfs/:id/knock`, `POST interactions`) because their affordances never render. The unavailable branch has to come **before** `packQuery.isPending`, or that branch claims to be loading forever.
- **Two denominators live in the create flow — never mix them in one sentence.** `runFilter` answers "across the district", `polygonStats` answers "inside the drawn ring". The filters step has no polygon yet, so it shows the district-wide count and its label says so (`districtHouseholds`); the draw step reports only `turfStats`. These were once rendered side by side, which put a district-wide household count next to an in-polygon door count at the moment of commitment. `polygonStats`'s household count is person-level exact (a household counts only when someone in it survives the filter) — deliberately stricter than `maskToPolygon`'s dot-granular rollup, which counts every household sharing a matched coordinate and is a documented slight overcount used for the landing rail.
- **Stops, doors and people are three different numbers — `routeCounts.ts` owns the definitions.** A stop is a geocoded coordinate the router visits, a door is an address (unit included), a person is a targeted voter; a block of flats is one stop, many doors, more people. Anything user-facing that says "doors" must count doors: `countDoors` for a frozen route, `polygonStats().households` for a shape being drawn. This drifted badly once — `WalkView` printed `stopCount` as doors, `WalkSheet` summed targets as doors, and the same route reported two different door counts depending on the surface. The 150 cap is on **stops**, so a "150-stop limit" message next to a doors count is correct, not a mismatch. **Every people figure counts knockable people** — `knockableTargets` in the same file, which drops ADR 0007 do-not-knock residents. That covers the printed sheet's header, the details sheet's progress stat and `WalkView`'s reached-of-total, because a door nobody should knock is not a conversation anyone can have: counting it promises an evening that can't happen and holds a canvasser who correctly skipped it below 100%. The sheet still *lists* flagged residents one row each, since paper freezes at print time and has to carry their skip instruction — a sheet listing more names than its header counts is intended, the header being the evening's work and the rows the index. Status rollups follow the same rule: `rollupStopStatus` (the webapp's, and gp-api's call site in `doorKnockingServe.service.ts`) drops flagged residents, because `unknown` outranks every other status and one flagged neighbor would otherwise report a fully-logged stop as still-to-knock. Same reason the collapsed stop row omits their per-person dot.
- **The draw step's walking estimate is local, not the vendor's.** 45 doors/hour (`DOORS_PER_HOUR` in `createFlow/CreateListFlow.tsx`, from the POC) turns **doors** into a time before any route exists. The real duration only arrives once the route is built server-side. 100 stops warns and 150 blocks — the soft limit must stay non-blocking.
- **A filter the pack can't shade must be disclosed, not hidden.** `unpreviewableFilterKeys` (`createFlow/voterFilterPreview.ts`) reports selections with no pack bucket — age 65+ today, since the pack's legacy age buckets can't split it from 50-64. Those filters still apply at knock time, so the shaded preview is a superset of the real audience, and the draw step says so. Silently previewing a wider shape than the list targets is the failure this exists to prevent.
- **The live-location dot is a deck.gl layer, not maplibre's `GeolocateControl`** (`native/useLiveLocation.ts` + `LiveLocationControl.tsx`, drawn by `VoterMapCanvas`). Continuous tracking in `GeolocateControl` requires `trackUserLocation: true`, which also flies the camera to the user and fights the view's own `fitBounds` framing of the route and focused turfs; its one-shot mode doesn't watch at all. The layer also lets a coarse fix render as a muted dot plus a real-metre accuracy halo instead of the same confident blue dot at any accuracy. It is **opt-in** (the watch, and therefore the permission prompt, only starts when the canvasser taps the control) and `clearWatch` runs on unmount, on disable, and on a permission denial — a watch left running is a phone battery draining after the walk. **Coordinates are display-only**: nothing sends them to gp-api or to analytics.
- **Free-text notes use the shared dictation stack**, not a door-knocking one: `useDictationAppend` + `DictationMicButton` + `DictationFeedback` from `briefings/shared/`, wired into `RecordKnockForm`'s `Textarea` with `analyticsLabel: 'door_knocking_note'`. That label is what `EVENTS.Dictation.Started` / `Failed` are sliced by — don't add a door-knocking-specific dictation event. The knock event still reports only `hasNote`; a transcript is free text about a named voter and never travels.
- **`RecordKnockForm` has two exclusive paths, and the fast one is the default.** The brief asks for two-tap capture, one of which opens the sheet, so `QUICK_RESULTS` (`native/knockQuestions.ts`) is a flat row where each chip carries a **complete** result and saves on the single tap — no confirming press. The cascade (outcome → support → will-vote → note) sits behind "Add a note or more detail". Don't render both at once: a chip that saves instantly beside fields that don't is resolved by tapping the wrong thing. The chips are a flattening of the existing contract, not new enum members, and the brief's `lean` and `sign request` have nowhere to land (`lean` collapses into Undecided; a sign request is a note). `logMode` on `DoorLogged` is how we tell whether the two-tap path is the one actually used.
- **Saving advances to the next door** (`advanceFrom` in `WalkView`) — "always show the next door so there is no thinking between houses". Forward only, skipping anything already statused or flagged do-not-knock, and the sheet closes when nothing is left ahead; walking a canvasser backward up the street to a door they passed is worse than leaving it on the list. `advanceFrom` reads the **pre-patch** cache, so the just-logged target is excluded by id rather than by status. Because the sheet stays open across residents, `PersonSheet`'s selected person is controlled by `WalkView` — internal state would keep showing the person just logged.
- **Offline means paper.** `print/` is a server component with no `'use client'` anywhere in it, deliberately: it has to render and print on a phone with one bar, and it sits outside `DashboardLayout` so no nav chrome hits the page. Its tick-boxes are generated from `native/knockQuestions.ts`, the same constants `RecordKnockForm` renders — the paper is transcribed back into that form, so the two must not drift. Paper keeps the three-question layout, which is the **detail** path; a sheet is re-keyed through "Add a note or more detail", not the quick chips. Nothing written on the sheet reaches gp-api until someone re-keys it.
- **The door script is the candidate's own saved issues, not AI copy and not the survey designer.** `native/doorScriptContent.ts` assembles it from two stores the issues editor already writes to — `campaign_position` rows (`GET /v1/campaigns/:id/positions`, catalog stance in `position.name`, the candidate's wording in `description`) and the bespoke `details.customIssues` — because a candidate who only ever used one of them still needs a script. Titles are de-duplicated case-insensitively, since re-entering a curated issue as a custom one is easy and saying it twice reads as a glitch. An issue with a heading but no stance is dropped rather than printed bare, and with nothing written at all `DoorScript` renders `null`: the fix is in Campaign Details, not here. The `surveys/` designer is a different, eCanvasser-era surface — don't wire it. Deliberately **screen-only**: the printed sheet stays a transcription form.
- `doorKnockingServe.service.ts` in gp-api is about **serving a route** to a canvasser — it is not the Serve product. Door knocking is Win-only (`v2Category: 'campaign'` in `DashboardMenu.tsx`).
- **Phones are on screen only, and live only.** `cellPhone` / `landline` ride the route payload for `PersonSheet` and are **deliberately absent from `print/WalkSheet.tsx`** — paper leaves the building and stops being access-controlled when it does; `WalkSheet.test.tsx` asserts the omission rather than trusting it. They come from the live residents join, the same source `mayHaveMoved` is derived from, so a mover shows no number instead of one belonging to whoever lives there now. `otherResidents` stays name-only: a non-target resident is context for the conversation, not someone the candidate asked to contact. These are the same two columns the voter-file download already exposes as "Cell Phone" and "Landline" behind the same district access check, so this is not new disclosure. **Voter email does not exist** — no column on the `Voter` model, no field on the `Person` contract.
- **Editing a list is name and color only, and only while it is unlocked.** `PUT /v1/door-knocking/turfs/:id` also accepts `geoPoly`, which is exactly why gp-api's `update` runs `assertNotLocked`: the polygon is what the frozen route was computed from, so accepting one after a knock would desync the two. `EditTurfDialog` therefore follows the same rule as delete — hidden for a locked turf, and still handling the 409 for the case where a teammate knocks it while the dialog is open. Consequence worth knowing: **a knocked list cannot be renamed**, so a typo outlives the walk. Relaxing that means splitting the endpoint's fields, not loosening the lock.
- **`TurfDetailsSheet` reads `liveTurf` for name and color, not the prop.** The prop is the snapshot the page captured when the row was clicked; since the sheet can now rename and recolor, rendering it would leave the header showing the old name after a save. The prop stays the source for identity (`id`, `voterFileFilterId`), which no edit can change.
- **The sidebar entry mirrors `DoorKnockingPageGate`'s branch, and must keep doing so.** `getDashboardMenuItems` takes a `doorKnocking` gate: flag on needs a resolvable district (the eCanvasser record is irrelevant, because the route renders the native map either way), flag off or unsettled needs the eCanvasser record, because the legacy dashboard is all the page can render. The link was previously pushed on the eCanvasser record alone, which hid the native pilot from every candidate who had never integrated eCanvasser. The flag read here passes `trackExposure=false` — the page is the treatment surface, and counting a nav render as an exposure would inflate the denominator with people who never clicked.
- **There is no Pro gate on this feature, on purpose, and only while it is flagged.** Access is `native-door-knocking` plus `candidateAccess()`. See "Access and eligibility" in `gp-api/docs/door-knocking.md`: the allowlist is the entitlement for a pilot, but the flag cannot come off broadly until a real entitlement check exists, since each knock spends vendor routing credits.
- **Win-only filters are gated by prop, not by context.** `CreateListFlow` takes `isElectedOfficial` (like the CRM's `VoterFileStep`) and `NativeDoorKnockingPage` sources it from `useOrganization().electedOfficeId`. Keep the read in the page: `useOrganization` throws outside its provider, so a context read inside `CreateListFlow` forces every test of it to mount an organization provider. The prior-contacts (`contacts_made`) group is the one this hides — gp-api's `assertNoContactsMadeFilterForElectedOffice` rejects that selection from an elected-office org, so offering it there only ever surfaces as a failed knock.
