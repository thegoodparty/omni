# app/dashboard/door-knocking/

Door-knocking / canvassing dashboard. Tracks volunteer interactions logged in the field, summarizes by day / rating / survey, and lets campaigns design custom door-knocking surveys.

## Key files

| File                                                                | Role                                                    |
| ------------------------------------------------------------------- | ------------------------------------------------------- |
| `page.tsx`                                                          | Route entry                                             |
| `components/DoorKnockingPage.tsx`                                   | Top-level layout                                        |
| `shared/DoorKnockingTabs.tsx`                                       | Tab navigation (overview / surveys / individual record) |
| `components/InteractionsByDay.tsx`                                  | Time-series chart                                       |
| `components/InteractionsSummary.tsx` + `InteractionsSummaryPie.tsx` | Aggregate counts + breakdown chart                      |
| `components/RatingSummary.tsx`                                      | Voter sentiment distribution                            |
| `components/interactionsColors.ts`                                  | Color tokens for charts (single source)                 |
| `surveys/`                                                          | Custom survey designer (per-campaign question sets)     |
| `print/[turfId]/page.tsx` + `print/WalkSheet.tsx`                   | Printable walk list (the v1 offline story)              |
| `print/[turfId]/pdf/route.ts` + `print/pdf/WalkListPdf.tsx`         | The same list as a downloadable PDF grid                |
| `print/walkFacts.ts` + `routeCounts.ts`                             | The stop/door/people sentence both paper surfaces quote |
| `native/doorScriptContent.ts` + `DoorScript.tsx`                    | Door script built from the candidate's saved issues      |
| `shared/`                                                           | Cross-tab primitives                                    |
| `components/`                                                       | Page-level widgets                                      |

## Patterns

- **Charts use shared color tokens** from `components/interactionsColors.ts` — keep palette centralized; don't inline hex values.
- **Surveys are campaign-scoped**: each campaign authors its own survey questions, used by canvassers in the field. Survey CRUD lives in `surveys/`.
- **Aggregations come from gp-api**, not computed client-side. The components display rather than compute.

## Gotchas

- The legacy tabs on this page only _display_ data sourced from third-party canvassing tools (eCanvasser etc.) via gp-api. Knocks are logged in-app from `native/` (`RecordKnockForm` → `POST /v1/door-knocking/interactions`), which writes to the CRM's own tables and never to eCanvasser.
- **Analytics live under `EVENTS.DoorKnocking`** (`Door Knocking - *`), not the legacy `EVENTS.Dashboard.VoterContact.DoorKnocking` group, which belongs to the script/eCanvasser surface. A completed walk also fires the canonical `Voter Outreach - Campaign Completed` with `medium: 'doorKnocking', method: 'native'` — that's what the door-knocking activation metric counts, so don't remove it while refactoring the walk exit.
- `components/interactionsColors.ts` is the only place colors should be defined for charts in this feature.
- **The voter pack and every turf read resolve a district server-side** (`resolveEligibleDistrictId` in gp-api's `doorKnockingPack` / `doorKnockingKnock` services), so an org with no resolvable district can only 400. `NativeDoorKnockingPage` gates both queries on `useDistrictResolution` (`app/dashboard/shared/`) and explains instead. Gating at the shell also covers the write paths (`POST turfs`, `POST turfs/:id/knock`, `POST interactions`) because their affordances never render. The unavailable branch has to come **before** `packQuery.isPending`, or that branch claims to be loading forever.
- **Two denominators live in the create flow — never mix them in one sentence.** `runFilter` answers "across the district", `polygonStats` answers "inside the drawn ring". The filters step has no polygon yet, so it shows the district-wide count and its label says so (`districtHouseholds`); the draw step reports only `turfStats`. These were once rendered side by side, which put a district-wide household count next to an in-polygon door count at the moment of commitment. `polygonStats`'s household count is person-level exact (a household counts only when someone in it survives the filter) — deliberately stricter than `maskToPolygon`'s dot-granular rollup, which counts every household sharing a matched coordinate and is a documented slight overcount used for the landing rail.
- **Stops, doors and people are three different numbers — `routeCounts.ts` owns the definitions.** A stop is a geocoded coordinate the router visits, a door is an address (unit included), a person is a targeted voter; a block of flats is one stop, many doors, more people. Anything user-facing that says "doors" must count doors: `countDoors` for a frozen route, `polygonStats().households` for a shape being drawn. This drifted badly once — `WalkView` printed `stopCount` as doors, `WalkSheet` summed targets as doors, and the same route reported two different door counts depending on the surface. The 150 cap is on **stops**, so a "150-stop limit" message next to a doors count is correct, not a mismatch. **Every people figure counts knockable people** — `isKnockable`/`knockableTargets` in the same file, which drop ADR 0007 do-not-knock residents *and* ADR 0008 not-a-voter residents. One predicate covers both because they differ only in what to say at the door, which is the walk UI's problem; to a count they are the same fact — nobody to talk to. That covers the printed sheet's header, the details sheet's progress stat and `WalkView`'s logged-of-total, because a door nobody should knock is not a conversation anyone can have: counting it promises an evening that can't happen and holds a canvasser who correctly skipped it below 100%. The sheet still *lists* flagged residents one row each, since paper freezes at print time and has to carry their skip instruction — a sheet listing more names than its header counts is intended, the header being the evening's work and the rows the index. Status rollups follow the same rule: `rollupStopStatus` (the webapp's, and gp-api's call site in `doorKnockingServe.service.ts`) drops flagged residents, because `unknown` outranks every other status and one flagged neighbor would otherwise report a fully-logged stop as still-to-knock. Same reason the collapsed stop row omits their per-person dot. There are **four** suppression sites and they must not drift: `knockableTargets`, `rollupStopStatus`, `WalkView`'s `advanceFrom`, and `print/pdf/walkListRows.ts` — auto-advance would otherwise walk a canvasser back into the door they just flagged, and paper would print a blank form beside the name of someone who moved away.
- **`WalkView` says "logged", not "reached".** `not_home`, `inaccessible` and `refused` all satisfy the `knockStatus !== 'unknown'` predicate the progress bar counts, so a canvasser who knocked forty doors and spoke to nobody used to read "40/40 reached" — a claim about conversations that never happened. The quantity is doors with an answer written down. `TurfDetailsSheet` states the same figure and uses the same word.
- **A flagged resident's marker replaces their status, everywhere they are listed beside other people.** `targetMarker` (`native/statusPresentation.ts`) is the one source: `WalkView`'s collapsed and expanded stop rows, and **both** of `PersonSheet`'s rosters (the resident switcher and the Household section). The sheet's rosters were the gap — the same person read "Do not knock" in the list and "Support unknown" one tap later, two answers to one question. Do-not-knock outranks a not-a-voter reason, because it is an instruction about the door rather than a fact about one of the people behind it. Paper's longer form is `skipInstruction` in the same file, read by `print/WalkSheet.tsx` and `print/pdf/walkListRows.ts` so the two formats cannot word it differently. The short marker reuses `NOT_A_VOTER_LABELS` from contracts — the CRM activity feed's vocabulary — so one flag isn't called two things in one product.
- **A stop with nobody knockable says so.** Its rollup comes off an empty list, which is the same grey `unknown` as still-to-knock, so `WalkView`'s row prints "Nobody to knock here" in place of the count and dots. Without it a fully flagged household reads as an evening's work nobody has started.
- **Stop numbering is map-and-paper only.** `seq` still orders the route, and still renders on the map's `route-pin-numbers` TextLayer and in `print/WalkSheet.tsx`, but the list view carries no numerals — the Aug 14 walkthrough asked for them out. The list isn't walked top-to-bottom (`advanceFrom` skips anything already statused or flagged, and what a canvasser is actually standing in front of is a pin), so a numbered row implied a step order nothing holds them to. `WalkView`'s stop row keeps the circle and its `rollupStopStatus` fill: the color is the row's status and is the load-bearing half. `PersonSheet`'s header circle went entirely instead — its fill was a constant `bg-info`, so the numeral was the only thing in it and an empty blue dot is not a design. Paper keeps its numbering because ordering is the whole point of a sheet that can't reorder itself.
- **The landing legend's counts describe the selected scope, not the district.** `canvassStatusCounts` (`filterEngine.ts`) takes the scope's selections plus the selected turf's ring, so picking a list rescopes the seven chips along with the heading above them. They were previously one pass over the whole pack's `canvassStatus` plane, which left district-wide numbers sitting under a heading naming one list and a line reading "N voters in this list". They are memoized on `scopeSelections` and deliberately **not** on `selections`: the chips' own narrowing has to stay out of their counts, or pressing one would zero the other six and leave nothing to press back. The chips narrow **within** the selected list — `selections` merges a `canvassStatus` entry into the list's own filters rather than replacing them, which is safe because no saved-list filter key maps onto that dim. Before that merge the turf branch returned early, so a chip clicked with a list selected flipped its own `aria-pressed` and changed nothing on the map.
- **The pre-route walking estimate is local, not the vendor's.** 45 doors/hour (`DOORS_PER_HOUR` in `native/walkEstimate.ts`, from the POC) turns **doors** into a time before any route exists. The real duration only arrives once the route is built server-side — and building it is a billed, irreversible Geoapify call, so the surfaces that help someone decide whether a list is a reasonable evening all have to answer before it: the draw step while drawing, and `TurfDetailsSheet` on a saved-but-unknocked list. Both quote the shared helper and both **name the rate** in the copy, so it reads as a rule of thumb rather than a computed promise; that is why the constant does not live in the draw step that first needed it. Once a route exists, `route.totalSeconds` is the number. 100 stops warns and 150 blocks — the soft limit must stay non-blocking.
- **A filter the pack can't shade must be disclosed, not hidden.** `unpreviewableFilterKeys` (`createFlow/voterFilterPreview.ts`) reports selections with no pack bucket — age 65+ today, since the pack's legacy age buckets can't split it from 50-64. Those filters still apply at knock time, so the shaded preview is a superset of the real audience, and the draw step says so. Silently previewing a wider shape than the list targets is the failure this exists to prevent. The disclosure names the selected **option** ("65+", which stands on its own) except for prior contacts made, whose options are the bare counts `'0'`…`'5+'` — "the map can't shade by 0 yet" reads as a bug, so that group is named once however many of its buckets are selected.
- **The map opens at street level, and the page is what says so.** `NativeDoorKnockingPage` passes `initialZoom={16}` to `VoterMapCanvas`; without it the canvas falls back to `fitBounds` over the whole pack, which is district zoom — a candidate opening the page landed on a shape with no street names in it and nothing to orient against. 16 is where they first appear. The prop is read **at mount only** and names the opening view rather than controlling the camera: reacting to it later would fight the canvasser's own panning, and turf focus and route framing still `fitBounds` on purpose once there is something specific to frame.
- **Undo and Clear are requests to the canvas, not edits made in the flow.** `VoterMapCanvas` owns the in-progress ring, so `CreateListFlow` only renders the two controls and the page turns them into token bumps: `undoDrawToken` drops the last placed vertex, and Clear reuses `startDrawToken`, because a restarted drawing session (empty ring, still in draw mode) is exactly the state Clear returns to. Undo is **last-add only** — a dragged vertex is already correctable by dragging it again, and making undo drag-aware would turn the ring into an edit stack for a gesture that doesn't need one. Both paths re-emit `onPolygonChange(next.length >= 3 ? next : null)`, which is why undoing from three points to two drops the stats and disables `Continue` instead of leaving stale figures on screen. They sit bottom-right of the live map band, **in flow above** the stats bar rather than absolutely positioned over it, so a cap warning or a disclosure line pushes them up instead of covering them; only the button cluster is `pointer-events-auto`, since the rest of that row is map the canvasser is still drawing on. The instruction card deliberately does **not** come back after Clear: it is a first-run coach mark that covers the whole map (a full-inset button, so its dismissing tap can't drop a stray vertex), and someone who just cleared has already learned the gesture.
- **The live-location dot is a deck.gl layer, not maplibre's `GeolocateControl`** (`native/useLiveLocation.ts` + `LiveLocationControl.tsx`, drawn by `VoterMapCanvas`). Continuous tracking in `GeolocateControl` requires `trackUserLocation: true`, which also flies the camera to the user and fights the view's own `fitBounds` framing of the route and focused turfs; its one-shot mode doesn't watch at all. The layer also lets a coarse fix render as a muted dot plus a real-metre accuracy halo instead of the same confident blue dot at any accuracy. It is **opt-in** (the watch, and therefore the permission prompt, only starts when the canvasser taps the control) and `clearWatch` runs on unmount, on disable, and on a permission denial — a watch left running is a phone battery draining after the walk. **Coordinates are display-only**: nothing sends them to gp-api or to analytics.
- **Free-text notes use the shared dictation stack**, not a door-knocking one: `useDictationAppend` + `DictationMicButton` + `DictationFeedback` from `briefings/shared/`, wired into `RecordKnockForm`'s `Textarea` with `analyticsLabel: 'door_knocking_note'`. That label is what `EVENTS.Dictation.Started` / `Failed` are sliced by — don't add a door-knocking-specific dictation event. The knock event still reports only `hasNote`; a transcript is free text about a named voter and never travels.
- **The "not a voter" reason is asked _after_ the door is saved, never before it.** ADR 0008's follow-up ("What happened?" → Moved / Deceased) is optional, and the quick chip's whole claim is that it logs a door in one tap. So `NotAVoterControl` renders nothing until the target's `knockStatus` is already `not_a_voter`, and `RecordKnockForm` is untouched — `logMode: 'quick'` still reports on the same single tap it always did. The one concession is that `WalkView` does **not** auto-advance off a `not_a_voter` outcome: advancing would ask the question and take the answer away in the same frame. The door is saved either way, so a canvasser who ignores the prompt and walks on has still logged a valid door. Answering turns the prompt into the marker, which withholds the form the way do-not-knock does; the prompt keeps the form visible, because that is how a mis-tapped outcome gets corrected.
- **`RecordKnockForm` has two exclusive paths, and the fast one is the default.** The brief asks for two-tap capture, one of which opens the sheet, so `QUICK_RESULTS` (`native/knockQuestions.ts`) is a flat row where each chip carries a **complete** result and saves on the single tap — no confirming press. The cascade (outcome → support → will-vote → note) sits behind "Add a note or more detail". Don't render both at once: a chip that saves instantly beside fields that don't is resolved by tapping the wrong thing. The chips are a flattening of the existing contract, not new enum members, and the brief's `lean` and `sign request` have nowhere to land (`lean` collapses into Undecided; a sign request is a note). `logMode` on `DoorLogged` is how we tell whether the two-tap path is the one actually used.
- **Saving advances to the next door** (`advanceFrom` in `WalkView`) — "always show the next door so there is no thinking between houses". Forward only, skipping anything already statused or flagged do-not-knock, and the sheet closes when nothing is left ahead; walking a canvasser backward up the street to a door they passed is worse than leaving it on the list. `advanceFrom` reads the **pre-patch** cache, so the just-logged target is excluded by id rather than by status. Because the sheet stays open across residents, `PersonSheet`'s selected person is controlled by `WalkView` — internal state would keep showing the person just logged.
- **Offline means paper.** `print/` is a server component with no `'use client'` anywhere in it, deliberately: it has to render and print on a phone with one bar, and it sits outside `DashboardLayout` so no nav chrome hits the page. Its tick-boxes are generated from `native/knockQuestions.ts`, the same constants `RecordKnockForm` renders — the paper is transcribed back into that form, so the two must not drift. Paper keeps the three-question layout, which is the **detail** path; a sheet is re-keyed through "Add a note or more detail", not the quick chips. Nothing written on the sheet reaches gp-api until someone re-keys it.
- **The PDF is built on the server, and that is load-bearing.** `print/[turfId]/pdf/route.ts` renders `print/pdf/WalkListPdf.tsx` with `@react-pdf/renderer` (already a dependency, for the onboarding campaign plan) and returns it as an attachment. Generating it in the browser instead would mean shipping ~1 MB of layout engine and PDF writer down the exact connection this feature exists to work around, and putting the first `'use client'` module into a directory deliberately kept at zero — so every entry point stays a plain `<a href>` that needs no JavaScript and no hydration. The cost lives on the other side: layout is CPU-bound in the number of **residents**, ~4s and 11 pages for a route at the 150-stop cap, which is why the handler raises `maxDuration`. Node count per row is the lever if that ever needs to come down — the answer columns are most of the nodes on the page. Swapping the renderer means changing `renderWalkListPdf` only; the row model and the handler don't move.
- **Two paper formats, one set of facts.** The printable page stacks a form per person; the PDF rules one row per resident with the stop number and address merged down a household, so a shared front door reads as one door. Both quote `walkFacts.ts`'s `walkSummary`, which is built on `routeCounts.ts` — the app and the paper have reported different door counts for the same route before. Content decisions (who gets a blank form, who gets their logged status, who gets the skip instruction) live in `print/pdf/walkListRows.ts` as a pure model, which is also why the PDF structurally cannot print a phone number: it is never handed one.
- **The PDF's answer columns are abbreviated, and only two of the three are lossless.** Supports and Will-vote are generated from `SUPPORT_OPTIONS` / `WILL_VOTE_OPTIONS` as `Y ? N` — the app's three answers in the app's order, because paper is transcribed back into that form. Answered is `Y N`: the grid has no room for the five-way outcome, so "why not" goes in Notes and the transcriber picks. The printable page keeps all five; it has the room.
- **The door script is the candidate's own saved issues, not AI copy and not the survey designer.** `native/doorScriptContent.ts` assembles it from two stores the issues editor already writes to — `campaign_position` rows (`GET /v1/campaigns/:id/positions`, catalog stance in `position.name`, the candidate's wording in `description`) and the bespoke `details.customIssues` — because a candidate who only ever used one of them still needs a script. Titles are de-duplicated case-insensitively, since re-entering a curated issue as a custom one is easy and saying it twice reads as a glitch. An issue with a heading but no stance is dropped rather than printed bare, and with nothing written at all `DoorScript` renders `null`: the fix is in Campaign Details, not here. The `surveys/` designer is a different, eCanvasser-era surface — don't wire it. Deliberately **screen-only**: the printed sheet stays a transcription form.
- `doorKnockingServe.service.ts` in gp-api is about **serving a route** to a canvasser — it is not the Serve product. Door knocking is Win-only (`v2Category: 'campaign'` in `DashboardMenu.tsx`).
- **Phones are on screen only, and live only.** `cellPhone` / `landline` ride the route payload for `PersonSheet` and are **deliberately absent from both paper surfaces** — paper leaves the building and stops being access-controlled when it does; `WalkSheet.test.tsx`, `walkListRows.test.ts` and `WalkListPdf.test.tsx` each assert the omission rather than trusting it, and their fixtures carry a number so the assertion can fail. They come from the live residents join, the same source `mayHaveMoved` is derived from, so a mover shows no number instead of one belonging to whoever lives there now. `otherResidents` stays name-only: a non-target resident is context for the conversation, not someone the candidate asked to contact. These are the same two columns the voter-file download already exposes as "Cell Phone" and "Landline" behind the same district access check, so this is not new disclosure. **Voter email does not exist** — no column on the `Voter` model, no field on the `Person` contract.
- **The activity feed is per-resident, reuses the CRM's rows, and survives a flag** (ADR 0009). `ActivityFeedCard` renders `target.history` off the route payload — no fetch, because the sheet has to open a block into a walk with no signal — using `DoorKnockActivityRow` / `TextActivityRow` / `RobocallActivityRow` / `StatusChangeActivityRow` imported from `contacts/crm/person/ActivityFeedEntry`. Don't fork those: the point is that `do_not_knock` and `not_a_voter` can't read one way in Contacts and another at the door. It sits in the sheet's **scrolling body** with Contact information and Household, not in the footer fragment with the script, `RecordKnockForm`, `NotAVoterControl` and `DoNotKnockControl` — so it keeps rendering for a flagged resident whose footer is withheld, which is deliberate: the feed is where the flag's own `STATUS_CHANGE` row lives, and hiding it would hide who set the flag from the person best placed to spot it was set on the wrong resident. Being outside that fragment is also why it needs no `key`; moving it in requires a namespaced one (`not-a-voter-`/`do-not-knock-`), which has been a real collision twice. **The door's feed carries no navigation** — `ActivityFeedCard` strips `outreachId` before drawing, because `TextActivityRow`/`RobocallActivityRow` turn it into a same-tab "View outreach" link, and unmounting `WalkView` discards the per-target replay keys that let a retried knock upsert instead of duplicating; that's the same reason the printed sheet and Open in Maps use new tabs. Stripping locally rather than adding a prop to the shared row keeps Contacts unchanged. **`mayHaveMoved` is not a feed row** — it's a voter-file hint with no date and no author, so it stays a line in Contact information; it can co-occur with a canvasser's firsthand `notAVoterReason: 'moved'`, which *does* appear as a dated, attributed status change, and the two are meant to read as corroboration rather than one event logged twice. **A knock logged mid-walk joins the feed on the next serve, and `WalkView` asks for one when a resident logged this session is opened again** — via `openSheet` and the sheet's resident switcher, the two ways back to a door already logged. `patchPerson` still writes only `knockStatus`, so the feed alone would stay as served while the status landed everywhere else in the panel, which reads as a broken feature rather than a stale cache. The row stays the server's: widening `RecordKnockForm`'s callback so the card could be handed a client-built `DOOR_KNOCK` entry was the rejected option, because it invents a second construction of a row the serve already builds — and it lands in the save path beside the replay keys. Refetching after *every* door was rejected too: the serve is the feature's heaviest read and a walk is meant to run on the payload it opened with, so the cost is tied to the only moment the staleness is visible (`advanceFrom` never lands on a logged door, so a forward walk pays nothing). Two invariants hold it safe — a failed refresh is silent and never surfaced (`routeQuery.isError` gates the "route could not load" banner on `!routeQuery.data`, or it would fire beside a door that saved fine), and `patchPerson` cancels the route query before writing so a serve built pre-patch can't overwrite a logged status on arrival. The one resident who still sees a stale feed is the `not_a_voter` case, whose sheet deliberately stays open across their own knock; refreshing under the ADR 0008 follow-up would rebuild the control being answered.
- **Editing a list is name and color only, and only while it is unlocked.** `PUT /v1/door-knocking/turfs/:id` also accepts `geoPoly`, which is exactly why gp-api's `update` runs `assertNotLocked`: the polygon is what the frozen route was computed from, so accepting one after a knock would desync the two. `EditTurfDialog` therefore follows the same rule as delete — hidden for a locked turf, and still handling the 409 for the case where a teammate knocks it while the dialog is open. Consequence worth knowing: **a knocked list cannot be renamed**, so a typo outlives the walk. Relaxing that means splitting the endpoint's fields, not loosening the lock.
- **A missing saved list is not an unfiltered one.** `savedListFilterKeys(undefined)` is `{}`, and `polygonStats` reads `{}` as "no filters" and answers with every door in the polygon — the exact number `TurfDetailsSheet` exists to stop reporting. The list can be missing while `savedListsQuery` is in flight, after it errors, or because the filter was deleted in the CRM, so the page resolves it **before** computing and yields no stats in all three cases; the sheet then distinguishes pending (skeleton) from settled-with-nothing (`Unavailable` plus a line saying so). Never let an absent list fall through to a computation, in either direction — it fails silently and plausibly.

- **`route.totalSeconds` is travel time, not the evening.** It traces to Geoapify's `agentPlan.getTime()`, and the jobs gp-api sends carry an id and a location and **no `duration`** — so it is the walk between doors with zero time spent at them. A 100-door route reports 50-60 minutes against ~2h15m of actual work at the app's own 45-doors-an-hour figure. `TurfDetailsSheet` therefore labels it **"Travel time"** (mode-free: the adjacent "Route type" stat already says walk or drive, and the mode is unknown while the route is still loading), and keeps **"Knocking time"** for the pre-route estimate, which is the opposite quantity — a sustained pace with conversations included. Two labels rather than one that has to be a lie for one of them; the alternative, synthesizing travel + time-at-doors into one figure, would invent a number no other surface reports. **The word is "travel", everywhere the number appears**: `WalkView`'s stops header and `walkFacts.ts`'s `walkSummary` (which both paper surfaces read) print `31m travel` rather than a bare duration, matching the per-leg number that already reads `3m walk`. "travel" and not "walk" for the totals, because on a screen called WalkView "the walk" is the whole outing — the exact thing the number is not.
- **A locked turf HAS a route, so route-derived stats branch on lockedness, not on `routeQuery.data`.** Every stat that reads the route (`TurfDetailsSheet`'s doors, people, travel time, route type, people-logged) used to fall back to the unknocked copy on falsy data, so opening Details on a knocked list read "Not knocked yet" three times for the length of the fetch and permanently if it failed — while doors and people quietly swapped population mid-load. `routePending` / `routeFailed` come off `liveTurf.locked` instead: pending renders a skeleton, failure renders `Unavailable` plus a visible line saying the route could not be loaded. `Not knocked yet` is now reachable only when the turf really is unlocked.
- **Nothing says "reached".** `knockStatus !== 'unknown'` counts not-home, inaccessible and refused alongside the answers, so it is the count of doors **logged** — the detail sheet's stat is "People logged". Calling it reached credits a walk with conversations it did not have.
- **`TurfList` renders on an empty account.** It returns a real empty state (what a list is, and that "Create list" above makes one) rather than `null`, which left a new candidate's rail showing a heading, status chips and nothing else on the first screen of the feature. Pending gets a skeleton; a failed fetch stays silent, because the page already explains a map that could not load and "No lists yet" would be a guess about an account nobody has read.
- **`TurfDetailsSheet` reads `liveTurf` for name and color, not the prop.** The prop is the snapshot the page captured when the row was clicked; since the sheet can now rename and recolor, rendering it would leave the header showing the old name after a save. The prop stays the source for identity (`id`, `voterFileFilterId`), which no edit can change. Its PDF link follows the same lock rule as the `TurfList` row's, for the same reason — only a locked list has a route to print, so the link would 404 on an unknocked one.
- **The details sheet's pre-route stats are the list's audience, not the polygon's population.** `detailsListStats` (`NativeDoorKnockingPage`) runs `polygonStats` with the turf's **saved filters**, via the same `savedListFilterKeys` → `filtersToDimSelections` path the landing map's scoped preview uses. Computed with empty selections, as it originally was, "Doors"/"People" described everyone inside the ring while sitting directly above the "Applied filters" pills — a Democrats-only list reporting every person in its polygon, which the labels hedged at ("in this area") rather than fixed. Because it is now the same computation the draw step ran on the same shape, Details reproduces the number the list was committed against, and inherits that step's disclosed caveat instead of a new one: an unshadeable filter (age 65+) leaves it a superset, and knock-time evaluation stays canonical.
- **The sidebar entry mirrors `DoorKnockingPageGate`'s branch, and must keep doing so.** `getDashboardMenuItems` takes a `doorKnocking` gate: flag on needs a resolvable district (the eCanvasser record is irrelevant, because the route renders the native map either way), flag off or unsettled needs the eCanvasser record, because the legacy dashboard is all the page can render. The link was previously pushed on the eCanvasser record alone, which hid the native pilot from every candidate who had never integrated eCanvasser. The flag read here passes `trackExposure=false` — the page is the treatment surface, and counting a nav render as an exposure would inflate the denominator with people who never clicked.
- **There is no Pro gate on this feature, on purpose, and only while it is flagged.** Access is `native-door-knocking` plus `candidateAccess()`. See "Access and eligibility" in `gp-api/docs/door-knocking.md`: the allowlist is the entitlement for a pilot, but the flag cannot come off broadly until a real entitlement check exists, since each knock spends vendor routing credits.
- **Win-only filters are gated by prop, not by context.** `CreateListFlow` takes `isElectedOfficial` (like the CRM's `VoterFileStep`) and `NativeDoorKnockingPage` sources it from `useOrganization().electedOfficeId`. Keep the read in the page: `useOrganization` throws outside its provider, so a context read inside `CreateListFlow` forces every test of it to mount an organization provider. The prior-contacts (`contacts_made`) group is the one this hides — gp-api's `assertNoContactsMadeFilterForElectedOffice` rejects that selection from an elected-office org, so offering it there only ever surfaces as a failed knock.
