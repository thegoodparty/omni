# app/dashboard/door-knocking/

Door-knocking / canvassing dashboard. Tracks volunteer interactions logged in the field, summarizes by day / rating / survey, and lets campaigns design custom door-knocking surveys.

## The two surfaces, and what the orchestrator keeps

`NativeDoorKnockingPage` is an orchestrator, not a place to build UI. Two surfaces are rebuilt independently behind frozen prop interfaces, so **a change to one surface should not touch this page**. Each interface is documented in its own file above the props; read that comment before adding a prop, and prefer a new file to growing a shared one.

| Seam                                           | Owns                                                                                                                                                           | Gets from the orchestrator                                                                                                                                                                                                                                        |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `CreateListSurface` (`CreateListSurfaceProps`) | Every wizard step, the drawing surface over the uncovered map, and the whole ADR 0010 address preview (`previewRing`, the query, and the props derived from it) | `step`, `filters`, `ring`, `turfStats`, `districtHouseholds` and the three states that explain a zero (`districtHouseholdsPending`, `districtHouseholdsFailed`, `districtUnavailable`), `unpreviewableKeys`, `isServeOrg`, `orgSlug`, the draw controls |
| `WalkSurface` (`WalkSurfaceProps`)             | The stop list, the door sheet and its notes, the knock form, and which resident's sheet is open (`selectedTargetId`)                                            | `turfId`, `openStopRequest`, `selectedStopId`, `onSelectStop`, `onKnockRecorded`                                                                                                                                                                                   |

**Only one of the two can be on screen, and there is no third "landing" case.** Arriving at this route IS asking to build a campaign: the flow opens itself, and every way out of either surface leaves door knocking for the Outreach hub. Nothing renders a bare map with no surface over it, which is what the saved-lists rail used to be for.

**What stays in the orchestrator is what the MAP also reads.** `VoterMapCanvas` is shared by both modes, so any state the canvas consumes — the drawn `ring`, the filter draft, the walk's marked stop (`selectedStopId`), the live-location fix, how far up the bottom chrome reaches — lives on the page and arrives as props. **`selectedStopId` and `selectedTargetId` are not the same selection**: the marked stop is up here because the map rings it, while which resident's sheet is open stays inside the walk, which is why only the first crosses the seam. Everything else moved down. A surface still reports the **gesture** and never the consequence, and `changeFlowStep` is the surviving worked example: the flow says "the candidate moved to the draw step" and the page decides that this particular transition also starts a drawing session on the canvas.

**Two surfaces own a half of the canvas each, as hooks the page calls at the top level** — `useCreateListDraw` and `useWalkMapSession`. The canvas outlives both surfaces, so their map state (draw tokens, the point count, whether the drawing surface is up, the walk's coach mark, the route pins, the tapped-pin request) cannot live inside a component the page unmounts. Keeping it in the surface's own file is what lets an agent change what its step asks of the map without editing the orchestrator: the page only spreads the hook's result onto `VoterMapCanvas` and renders `WalkMapHint`.

**Display state that only one surface reads belongs to that surface, and resets by being unmounted.** `previewRing` is the worked example: closing the create flow unmounts `CreateListSurface` and the address panel goes with it, rather than the page remembering to clear it. The asymmetry is still the rule and not an oversight — anything the CANVAS reads cannot live in a surface the canvas outlives, so it sits on the page and is reset by hand. `locationEnabled` is the one left: `endWalk` sets it false explicitly, because a watch left running keeps the GPS radio warm for a surface with no way to see it.

**The seam list shrank twice, and neither shrink was a deletion of behaviour.** `KnockTurfDialog` used to sit between a list and its walk, because Knock was a purchase and a purchase needs a confirmation; there is nothing left to confirm — every list is born routed — so Knock opens the walk directly through the one `startKnocking` handler on the page, and the dialog's travel-mode and loop controls are now the create flow's final step, which is where the purchase happens. `DoorKnockingManageView` then went with the saved-lists rail it drew, and `TurfList` with it: the design enters door knocking from the outreach hub's tile and leaves it the same way, so there is nothing between the hub and a walk for a fourth seam to describe.

**Three components in this directory are currently unreachable, and that is deliberate rather than an oversight to fix.** `TurfDetailsSheet` is still rendered by the orchestrator and still reads its props correctly, but nothing sets `detailsTurf` — the saved-list row that used to open it is deleted, and the design's only route into a list's details is the outreach history drawer. `EditTurfDialog` is reachable only through that sheet, so it is unreachable too, which is where a list's colour and name are changed. `DeleteTurfControl` is unreachable for the same reason from the other direction: its one caller was that same deleted row. All three are left standing because rewiring them is one line each if the design grows a surface for them, and none of them costs anything sitting there. **Do not "fix" this by inventing a surface** — putting a details drawer or a delete back on a screen the design does not draw is a product decision, not a repair, and the knowledge each of them carries is recorded below with its constraint intact.

**`VoterMapCanvas` and `WalkSurface` have a second mount site now (ENG-11055): `app/volunteer/door-knocking/[turfId]/VolunteerWalkPage.tsx`.** A volunteer walks a route with no district pack behind it at all — `GET /v1/door-knocking/pack` stays 403 server-side for a volunteer — so both seams had to admit a caller with no pack rather than growing a third surface. Two contract changes, both backward compatible with `NativeDoorKnockingPage`:

- **`VoterMapCanvas`'s `pack` and `filterResult` props are `| null`.** Null omits the `voter-dots` layer outright (not an empty one) and leaves the opening camera to the route-fit effect that already reframes onto `routePins` — the candidate/manager mount always passes both non-null and renders byte-identically. `saved-turfs` still takes a `turfs` array; the volunteer page passes `[]`, since there is no rail to draw rings for.
- **`WalkSurfaceProps.onMoveToArchive` and `.archivePending` are optional.** `WalkView`'s `Move to archive` button renders only when a handler is given, rather than every caller having to hand in a no-op — a volunteer's turf is never theirs to shelve (`useWalkArchive` stays manager-only). `NativeDoorKnockingPage` still passes both.

The volunteer page composes `useWalkSession`, `useWalkMapSession`, `useWalkCompletion` and `useLiveLocation` unchanged — none of the shared walk machinery is Win/Serve- or pack-aware — and starts its own walk session once `GET /v1/door-knocking/turfs/:id` resolves, rather than reading `?walkTurfId=`: there is only one way onto this route. `useWalkMapSession` is given `{ id: turfId }` straight from the URL param rather than waiting on that turf-metadata call, so its route fetch and the page's own (used only to detect a revoked 404) start on the same tick and share one request — gating it behind the turf call instead re-fires a second, avoidable fetch once the query flips from disabled to enabled.

## Patterns

- **Charts use shared color tokens** from `components/interactionsColors.ts` — keep palette centralized; don't inline hex values.
- **Surveys are campaign-scoped**: each campaign authors its own survey questions, used by canvassers in the field. Survey CRUD lives in `surveys/`.
- **Aggregations come from gp-api**, not computed client-side. The components display rather than compute.

## Gotchas

Grouped by the surface each decision belongs to, and the headings are stable:
**append inside the section your change belongs to**, never at the end of the
file. The grouping exists because this list is edited by several agents at once
and a flat tail is a guaranteed conflict; the sections follow the seams above
and the objects they describe, plus the shared concerns none of them owns alone.
A decision that spans surfaces goes in a `Shared` section rather than being
written twice.

### Shared — the page, its gates and analytics

- The legacy tabs on this page only _display_ data sourced from third-party canvassing tools (eCanvasser etc.) via gp-api. Knocks are logged in-app from `native/` (`RecordKnockForm` → `POST /v1/door-knocking/interactions`), which writes to the CRM's own tables and never to eCanvasser.
- **Analytics live under `EVENTS.DoorKnocking`** (`Door Knocking - *`), not the legacy `EVENTS.Dashboard.VoterContact.DoorKnocking` group, which belongs to the script/eCanvasser surface. A completed walk also fires the canonical `Voter Outreach - Campaign Completed` with `medium: 'doorKnocking', method: 'native'` — that's what the door-knocking activation metric counts, so don't remove it while refactoring the walk exit.
- **The voter pack and every turf read resolve a district server-side** (`resolveEligibleDistrictId` in gp-api's `doorKnockingPack` / `doorKnockingCreate` services), so an org with no resolvable district can only 400. `NativeDoorKnockingPage` gates both queries on `useDistrictResolution` (`app/dashboard/shared/`) and explains instead. Gating at the shell also covers the write paths (`POST turfs`, `POST interactions`) because their affordances never render. The unavailable branch has to come **before** `packQuery.isPending`, or that branch claims to be loading forever.
- **The pack query never retries, and it has its own deadline.** `useVoterPack` sets `retry: 0` and a 90s `AbortSignal.timeout`, and both are load-bearing rather than tuning. Abandoning the request does not cancel the district scan behind it, so a retry competes with a build that is still running — on 2026-08-25 that turned one visible failure into 165 seconds of spinner. The 90s sits deliberately under the gateway's ~120s idle ceiling so the client fails first, cleanly, instead of waiting on a connection something upstream already killed. `packDecoder` also throws when the response ends before the pack arrives; a truncated body is a failed build, not an empty district. Background: gp-api `docs/door-knocking.md` § The pack.
- **Every count in the create flow is pack arithmetic, so the whole flow is gated on a download that runs 4.5s at p50 and 34s at p95.** `districtHouseholds` is `runFilter(...).households` and the draw step's stops/doors/people fall back to `polygonStats`; none of them is a server call, so all of them read zero until the pack lands. That zero is indistinguishable from an empty district, which is why the who step's CTA **drops its count entirely while the pack is pending or failed** rather than printing `Continue (0)` — the same shape phone banking's shell already uses. The wait and the failure are both stated **inside the sheet**: the map's `LoadingAnimation` is painted under the create flow, so during the one wait that matters nobody can see it. `retry: 0` (above) makes the error branch permanent, so a pack that fails without in-sheet copy is a dead button and no explanation anywhere. **The server's `POST /v1/contacts/count` is not a substitute for the district figure, and the reason is not that it cannot count households.** `buildCountSql` does `COUNT(DISTINCT householdKey())` on request and `ContactsService.segmentGroupsByHousehold` already returns true for `doorKnocking` — but the count path is the one that never asks: `fetchCount` passes `false`, and `CountContactsDTO` carries neither a segment nor the flag, so nothing on the wire can request the grouping `listContacts` and `downloadContacts` apply to that same segment. It also applies no `ROOFTOP_ONLY`, which every door-knocking read does. Both have to be closed server-side before the swap is defensible; either one alone silently inflates the number.
- **Doors logged on a walk are overlaid onto the pack, not refetched.** `endWalk` records the walk's pins through `recordLoggedKnocks` (`useVoterPack`) and `applyLoggedKnocks` (`filterEngine`) merges them into `statusPerDot` at render, because the alternative was re-downloading a district — hundreds of thousands of rows, 5-30s — to change a handful of status bytes. The overlay keys on the dot's own coordinate, which is what `runFilter` already rolls people up by, and it may only move a dot **less** actionable: the pack's status is a rollup over everyone at that address, so a logged knock at a multi-unit dwelling has not answered for the units nobody visited. `gcTime` is an hour for the same reason — a candidate who steps away and comes back should not pay the download twice.
- `doorKnockingServe.service.ts` in gp-api is about **serving a route** to a canvasser — it is not the Serve product, and the name collision predates the wiring below.
- **Door knocking runs on both surfaces now, and one page draws both.** Unlike social and phone banking, where the Serve caller is a separate page passing a `surface` prop, `/dashboard/door-knocking` is the only route — so the answer lives in a context, `native/doorKnockingSurface.tsx`. The page decides it once, from the same predicate `DoorKnockingPageGate` uses to admit the org at all: a `Campaign` takes precedence and an `ElectedOffice` is consulted only in its absence, which matches how gp-api's `POST /v1/door-knocking/turfs` answers the same question, so a list is always created onto the surface that asked for it. **Read the turf list through `useTurfsQuery` and never `turfsQueryOptions` directly** — the page is the one exception, because it is where the mode is decided and it passes its own `serveMode` in; everything below it reads the hook, so two readers cannot disagree about which org's lists they are looking at. The isolation is real and not cosmetic: an org holding both a Campaign and an ElectedOffice would otherwise see its Win lists on its Serve surface (ENG-10976), which door knocking could not even express before every turf had an outreach envelope to carry the scope.
- **Party appears nowhere on the Serve surface, and it took four gates rather than one, because party reaches this feature by four independent roads.** The system-wide invariant is gp-api's (`src/contacts/AGENTS.md`): the `eo-` org-slug prefix is the whole rule and a party value in any `eo-` response is a bug. Door knocking was the last surface still leaking one. (1) The **served route** nulls `politicalParty` per target server-side, which is what fixes the walk, the person sheet, the printed walk sheet and the PDF at once — `describeTarget` in `print/walkFacts.ts` collapses on the null with no branch of its own. (2) `voterDemographicFacts` **drops** the Political party row rather than leaving it to `withFallback`, which would print "Not on file" — a claim about a gap in the voter file, where the truth is that this product does not state party to an elected official. (3) The create flow's who step hides the `political_party`, `voter_likely` and `contacts_made` groups, matching the CRM wizard's `VoterFileStep` strip; party is the sharpest of the three, since gp-api 400s a party filter for an `eo-` org and an official who picked a pill got a dead address preview and then a create that could not buy its route. (4) `savedListFilterKeys` strips those same fields' option keys, and that one is the back door the other three leave open: it re-expands **every** boolean column on a saved row, so a list cut on the Win surface — or before any of this existed — would re-check party pills inside a group that is no longer rendered, shade the map to a cut nobody can see or clear, and then 400. `TurfDetailsSheet`'s read-back is gated for the same reason, since nothing backfills a saved filter. The field keys live once, in `savedListFilters.ts` as `WIN_ONLY_FILTER_FIELD_KEYS`, and the option keys are derived from `filters.config.ts` rather than written out — a party value added to the catalog cannot arrive un-stripped. **The pack's `party` dim is deliberately still there**: it is district-scoped and cacheable, nothing can select it once (3) and (4) hold, and removing it would fork the district cache for no user-visible gain. `PACK_FORMAT_REVISION` does not move.
- **All three client-side gates hang off one boolean, `isServeOrg`, and it is the org slug rather than either of the two booleans next to it in `NativeDoorKnockingPage`.** The question these gates ask is what gp-api will accept, and `ContactsService.hasElectedOfficeAccess` reads the `eo-` prefix and nothing else. `isElectedOfficial` (an ElectedOffice row exists) would hide a party pill the server would have honoured for a campaign-slug org. `serveMode` (`!campaign && isElectedOfficial`) is a different question again — it decides which rail's LISTS are on screen and lets a Campaign take precedence, so an `eo-` org holding one would be offered filters its every request 400s on. The orchestrator derives it once and passes it as a prop to `CreateListSurface` and `TurfDetailsSheet`; neither reads `useOrganization()` for itself, which is what keeps both testable without an organization provider and is why the prop is not named after the office.
- **`isServe` rides the route payload, and the reason it is not four context reads is the two paper surfaces.** `useDoorKnockingServeMode()` answers this for anything under the page, but `print/[turfId]` and its PDF sibling render server-side with no organization provider above them, so the printed sheet cannot get this answer any other way. One field on the payload also means the walk, the person sheet and the two paper formats cannot arrive at different answers about one list. It is optional on the contract for the reason `history` and `notes` are — a service worker's pre-ship snapshot carries no such key and has to keep parsing on a phone that cannot refetch — and absent reads as Win, which is the surface every route frozen before it shipped belonged to.
- **The native feature is Pro-gated (ENG-10888).** `canUseProFeatures` — `!!campaign?.isPro || !!electedOffice`, the CRM's own spelling (`ContactsTableProvider`) of gp-api's `ContactsService.assertProAccess` — decides the branch in `DoorKnockingPageGate`. Every `/v1/door-knocking` route enforces it server-side **except** `POST /do-not-knock` and `POST /not-a-voter` (ADR 0007 / ADR 0008), so a lapsed org can still honor "don't come back" — see "The Pro gate" in `gp-api/docs/door-knocking.md` for the full route table. Reads are gated too, so there is no locked-preview mode: a map you can open but not route is worse than a clean upgrade message, and creating a list spends real vendor routing credits. **The upgrade card lives in `DoorKnockingPageGate`, not a file of its own** — that keeps the `'use client'` ratchet flat (the gate is already a client component; a new one would need the baseline bumped). It is a safety net for a URL or a stale tab, not a funnel: it is deliberately shorter than `OpponentProLockedView` and fires no exposure event. **Control is untouched**: the flag-off eCanvasser dashboard was never Pro-gated and still isn't. Two consequences worth knowing before touching either surface: an in-flight `useElectedOffice` is **not** a refusal — a Serve org's access comes from that query and its campaign is never `isPro`, so the page gate waits (and only for a campaign that isn't already Pro) instead of flashing the upgrade card at the org most entitled to the feature; and `door-knocking-flag-gate.spec.ts` now has to provision a Pro campaign (`setupProCampaignUser`), because the entitlement it used to be able to ignore is upstream of the native arm it asserts.
- **Door knocking is a channel of Voter Outreach, not a peer of it — there is no standalone left-rail entry, and the outreach hub's tile is the only way in.** The product call is that a candidate picks a channel on the outreach hub, and the tile in `outreach/v2/ChannelTileGrid.tsx` is the only entry that can hand a saved list across (`?listId=`, ENG-10762); a top-level nav item would be a second front door that arrives with nothing. `DashboardMenu.tsx` carries no door-knocking gate or menu item at all. **Removing the entry removed no access check** — Pro is enforced by `DoorKnockingPageGate` and by every `/v1/door-knocking` route, and the hub tile is `requiresPro` in `OUTREACH_OPTIONS`, so it renders locked and opens `ProUpgradeModal` for a non-Pro candidate rather than navigating. What the nav entry carried was reachability, not entitlement. **The route and its deep links are untouched and must stay that way**: `/dashboard/door-knocking?create=1` (plus `&listId=`) is what the tile pushes, `OutreachDetailsDrawer`'s "Continue knocking" CTA links to `?walkTurfId=&outreachId=`, and `e2e-tests/src/helpers/door-knocking-e2e.ts` still reaches the surface by URL on purpose — deep links into this feature are the thing the tile depends on, so a spec that could only get here by clicking would be testing the nav and not the page.

- **This route draws no page header and no left nav, because the design draws door knocking as a modal over the outreach hub.** There is no `<h1>Door knocking</h1>` bar and no compact `PDF` link in one, and `DashboardLayout` is passed `hideMenu` so the sidebar is not rendered either — the map runs edge to edge at every width. Every title that row used to carry is already on the surface that owns it: the create flow names its own step through `OutreachFlowShell`'s stepper, and the walk names its list on its sheet at the `peek` snap. The sidebar is the same argument: door knocking is reached from the hub's tile and returns to the hub from every exit, so the nav it would offer leads exactly where the surface's own close button already goes. **`hideMenu` rather than rendering outside `DashboardLayout`**, which is what keeps the providers this tree sits in — `EcanvasserProvider`, `SidebarProvider`, the impersonation banner — and costs the map only the chrome the design does not draw. **Nothing paper-shaped was lost with the header's PDF link**: `WalkView` already renders the design's own full-width `Export this list to PDF` above the stop list, from the same `ExportWalkSheetButton`, so the canvasser who is about to walk out of signal gets it from the surface they are standing on.
- **The page is exactly the height the dashboard chrome leaves, and it gets there by measurement rather than by arithmetic.** `NativeDoorKnockingPage` asks `DashboardLayout` for a `min-h-0 overflow-hidden` content wrapper and fills it with `h-full`. It previously sized its own column with `h-[calc(100dvh-4rem)]`, and both halves of that were wrong. The `4rem` is `MobileMenuTrigger`'s `h-16`, which is `lg:hidden` — so above `lg` it subtracted a bar that was not on screen and **the map ended 64px short of the bottom of the window on every desktop**. And a hard height on the child did nothing about the parent: the wrapper is `flex-1` inside `SidebarInset` inside `SidebarProvider`'s `min-h-svh` row, and a flex item's default `min-height: auto` lets its CONTENT set the floor, so anything the layout rendered beside this page pushed the document past the window. Something does: when the campaign-story flag is on, `DashboardCampaignManagerChat` renders an in-flow `h-24` spacer next to the page, reserving scroll room for its fixed footer bar — **96px of pure overflow, and the reported "have to scroll to see the full map".** `min-h-0` removes the floor so the chain resolves the other way (the row settles at `min-h-svh`, the wrapper takes what the chrome above it leaves, at whatever width), and the spacer is then honoured INSIDE the window: the map stops 96px short and the bar sits in the gap instead of over the map. **Nothing in `DashboardLayout` changed to do this** — that file is every dashboard page's, and the classes this page needs are ones it already accepts through `wrapperClassName` and `hideMenu`. `svh` is inherited rather than chosen, and is the right value: it is the viewport with mobile browser chrome at its largest, so the page is whole in every chrome state — and a page that cannot scroll never retracts that chrome, which leaves `dvh` permanently equal to it here. **Do not re-introduce a viewport unit on the column.** The number it would have to encode is the height of chrome that changes at a breakpoint, and that is the layout's to measure, not this page's to guess. Both surfaces float over a map that fills this column at every width, so nothing under here has a height of its own to reconcile; MapLibre v4 carries its own `ResizeObserver` on the container and deck.gl's `MapboxOverlay` follows the map, so nothing here needs a resize call of its own.

- **Four query parameters reach this page, and each one is consumed once.** `?listId=` preselects a saved list in the create flow (the outreach tile's hand-off). `?walkTurfId=` opens that list's walk directly, and `?outreachId=` beside it says the walk was entered from the outreach history drawer. `?create=1` says the hub's tile was pressed, which no longer decides whether the create flow opens — it always does — only whether closing it pops that history entry or pushes the hub. The page reads them on mount and does not keep them in the URL as state: a walk is a mode, and a mode encoded in a query string comes back on the next Back button press.
- **Every exit from door knocking lands on the Outreach hub, and `WalkOrigin` still exists because one of them is more specific than that.** `WalkOrigin` is `hub`, `details` or `outreach`, set by whichever handler started the session and read by `endWalk`: the hub, that list's details sheet, or the outreach history row that sent the candidate here through `?outreachId=`, which reopens in its own drawer rather than merely being somewhere in the history table. `hub` is the default and the design's own exit — the prototype's `walkClose` falls through to `exitDoor` and lands on Voter Outreach. **It used to be `rail`, which meant "stay on this page"**, and that was correct while the landing surface was a rail of saved lists worth returning to; with no such surface, staying would leave a bare map with nothing on it and no control to make anything, so the constant `OUTREACH_HUB` is where every kind now goes but `details`. (`details` is currently unreachable along with the sheet that sets it — see the unreachable-surfaces note above.) **The origin is the page's** and not the walk surface's, for the same reason `endWalk` is: only the orchestrator knows both modes.
- **The create flow opens itself on arrival, always, and `closeFlow` is what reads how you got here.** Arriving at this route is asking to build a campaign — there is no landing surface to choose from — so a single effect opens the flow however the page was reached, whether the hub's tile sent us with `?create=1` or the URL was typed. It requires only three things: no walk being asked for or already running, a resolvable district, and a settled quota query. **It does not read the turf list to decide whether to open**, which is the shape of the old opener and must not come back: there were two openers, one gated on the org having no unarchived turfs and one on the tile's param, and collapsing them is what let the turf query stop being a precondition for opening a funnel that never looks at it. **A `?walkTurfId=` defers to the walk only while it could still become one.** Once the turf query has settled without that id in it — a stale bookmark, a list deleted in the CRM, another org's — `deadWalkLink` lets the arrival proceed as an ordinary one, because deferring forever is the bare-map dead end the exit rules above exist to prevent, and there is no longer a rail behind this screen to be stranded on. Settled rather than successful, so a failed turf read counts too rather than waiting on a query that is not coming back; until then the link is merely slow, and a list that arrives late still gets its walk, since the id is spent only once a turf is found. Waiting on the quota is deliberate and costs nothing, since nothing is on screen either way: the guard is spent on the first paint, so a refusal arriving a moment later would find the flow already open and return early. A failed read is settled and opens the flow — the two asserts inside the create transaction are the authority. What `?create=1` decides now is only where CLOSING goes: `tileOpened` makes `closeFlow` call `router.back()`, which pops the entry the tile pushed and keeps the hub's scroll position, and everything else pushes `OUTREACH_HUB` outright.
- **`landingOpened` is never unset, and that is load-bearing — do not merge it back into one ref.** The old `autoOpened` was both the once-guard and the record of where closing should return to, and `handleListCreated` cleared it because the second job needed clearing. Creating a list invalidates the quota query; the effect re-ran, found a turf list that had not refetched yet, and reopened the create flow at step one **on top of the walk that had just started**. The fix is that they are two refs with two lifetimes: `landingOpened` is spent for the life of the mount and never unset, and `tileOpened` is the close destination and is spent when the flow hands over to a walk. It is marked spent even when the daily allowance refuses, because re-firing would reopen the limit dialog every time it was dismissed. This is exactly the class of bug this file exists to prevent: a ref that answers two questions will eventually be cleared for one of them.
- **No e2e spec here may create a saved list, and the empty account is why there is still a spec at all.** A list IS a bought Geoapify route since 3.0 — one transaction — so the `seedTurf` helper that used to stand a row up for `door-knocking-turf-rail.spec.ts` had to go with it: seeding one would bill a shared credit pool on every run of the suite that gates every PR in the monorepo, and take a 30s vendor call as a dependency of the gate. `door-knocking-zero-state.spec.ts` replaced it, and covers the same cross-service question — page, flag, Pro gate and `GET /turfs` lining up on a live preview — through the one surface an org with no lists can reach. Everything about a list that exists is asserted in unit tests, where a list costs a fixture: `TurfDetailsSheet.test.tsx`, `WalkView.test.tsx`, `WalkSheet.test.tsx`, and gp-api's `doorKnocking.routes.test.ts` for the write itself.
- **Ending a walk marks the list Done, but only a walk that finished one.** `endWalk` calls `useWalkCompletion` (`native/walkCompletion.ts`), which imports `useTurfLifecycle` rather than posting `turfs/:id/complete` itself — one writer for the mutation, and it already invalidates the turf query before its snackbar, so the outreach history row the candidate lands back on reads Done rather than lagging the message. It lives on the page because `endWalk` does: only the orchestrator knows a walk is ending. **The unconditional version was rejected, and not narrowly.** Done is the one lifecycle write with no undo beside it — archive is a boolean that can be flipped back, delete has a confirm — and what it takes away is Knock. Leaving is also the ONLY way out of a walk, so stamping every exit would read "I am done for now" as "this list is finished" and take the way back in away from a canvasser who knocked three doors of fifty. **"Finished" is the walk's own progress bar**: every knockable person logged, per `routeCounts` — do-not-knock and not-a-voter residents dropped, `logged` meaning an answer is written down and not that a conversation happened. That is the number the canvasser has been watching climb all evening, so a list stamping itself Done as they leave a 40/40 walk is the outcome they already believe in. **Two states are deliberately not finished**: a route that isn't in cache (a serve that never landed reports zero targets, which is indistinguishable from a list with nobody in it — never stamp off a fetch that failed), and a list where nobody is knockable at all. Both are the same asymmetry: another walk of the same list is one tap away on the hub, while an unwanted Done cannot be taken back from anywhere in this feature, so erring toward not completing is the cheap mistake. **The turf the write runs against is held in a ref for the length of the mutation.** `useTurfLifecycle` reads its turf out of the render it was called in, and a mutation observer pushes each new render's options onto the request already in flight — so `walk.end()` clearing the session in the same handler that starts the write swapped the id out from under it and the POST went to the hook's standin turf. That is a property of calling a row-shaped hook from a page, not of this feature; anything else the orchestrator writes on the way out of a mode needs the same care.

### Shared — counting, vocabulary and status presentation

- **The Serve door asks one question where Win asks two, and it had to ask SOMETHING.** A canvasser for an elected official is asked neither "Do they support you?" nor "Will they vote this election?" — a constituent has no candidate to support and no election on the calendar — and `FOLLOW_UP_QUESTION` ("Do they need follow-up?") is the whole of the Serve engaged branch. **Deleting the two questions without replacing them breaks the Serve walk completely, and structurally rather than cosmetically.** `answered` is not a member of `DOOR_KNOCK_STATUSES`: derivation is support-first and the ladder beneath it is a list of ways a door failed, so a conversation with no answer derives to `unknown` — and `knockStatus !== 'unknown'` is the "logged" predicate in `WalkView`, `walkCompletion.ts`, gp-api's turf counts and both paper surfaces. The walk would never advance, the list would never complete, outreach history would read 0%, and paper would reprint every knocked door with blank boxes. So Serve gets a terminal answer of its own (`followUp`) and two statuses off it, `engaged` and `needs_follow_up`. Everything above and below the engaged branch is shared, because how a door answered and what the canvasser wrote down are the same questions whoever is knocking.
- **`STATUS_ACTIONABILITY` is an explicit rank table, and it used to be `DOOR_KNOCK_STATUSES`' own array order — read this before collapsing it back.** One array cannot fall out of step with itself, which was the argument, and it held while the vocabulary was closed. The Serve statuses had to be **appended** to that array: the pack encodes a status as an index into it and a frozen pack on a phone is read against whatever vocabulary the client shipped with, so inserting a member silently re-labels every existing byte during a deploy. Appending put the two endings of a Serve conversation below every way a door can fail, and `rollupStopStatus` off that order rolls a stop where one constituent engaged and another refused up to `refused` — a Serve walk reporting its successes as its worst outcome. So the rank is stated separately and the wire order is free. It is a `Record<DoorKnockStatus, number>` on purpose: exhaustive over the union, so a status added to the contract fails the typecheck rather than arriving silently ranked last. The Serve pair holds the support answers' ranks, because they are the same thing on their own surface and no route carries both vocabularies.
- **Two legend orders, one per surface, and neither is derived from the other.** `progressLegendOrder(isServe)` picks between them; Win keeps the canvas's order and Serve puts its two conversational endings where the support answers sat, because they are what the walk is for and listing them after "Not a voter" would read as an afterthought to a ladder of failures. They are separate arrays rather than one filtered, because the vocabularies are alternatives and not a superset and a subset. `surfaceStatuses(isServe)` is the same membership in the WIRE order, for readers that enumerate rather than lay out — the details drawer's outcome table reads it so its rows keep the order they have always had while dropping the pair the list cannot contain. `statusPresentation.test.ts` holds the two definitions to the same membership. **`knockStatusCounts` still buckets the whole vocabulary**, both surfaces' — a route only carries one surface's answers, so the other two buckets are zero and the seven on screen still sum to People.
- **The Serve palette reuses `supporter`'s green and picks blue rather than amber.** `engaged` is green because it holds supporter's place on its own surface — the good ending of a conversation — and the two surfaces never draw both, so no legend shows one colour twice. `needs_follow_up` is blue and specifically not amber: amber is `not_home`, and a door that needs following up is the opposite of a door nobody opened.
- **Existing `eo-` pilot rows carrying support answers are not backfilled.** They keep deriving `supporter`/`non_supporter`, so on a Serve legend they go uncounted. At internal-beta volume the rows are countable, and rewriting logged answers into a vocabulary their canvasser was never offered would be inventing data — while showing a Serve official two party-shaped buckets is worse than a handful of doors that read as unlogged on a beta list.
- **`PersonSheet` reads back one card or the other, never both, and the Serve card has no "As of" line.** `FollowUpCard` follows `VoterSupportCard`'s rule exactly — silent unless the status came from that surface's own answer, because every other status is a door with no answer behind it — and reads back the ANSWER ("Yes"/"No") rather than the status noun, since the question printed above it is the one the canvasser was asked. The date is absent because `RouteTargetActivity`'s door-knock row carries `supportAnswer` and nothing about follow-up, so there is no history row that could state it; approximating one from the newest knock is the same mistake `supportAsOf` documents at length. If an official asks for the date, the history row is where it comes from.
- **The map's filter engine ranks by the same table, addressed by pack byte.** `filterEngine.ts` never holds a status word — only the index the pack encoded it as — and it used to compare those bytes directly, on the same "array order IS actionability order" assumption `STATUS_ACTIONABILITY` replaced. Appending the Serve pair broke it in both directions at once: `runFilter` takes the minimum, so a dot where one constituent engaged (7) and another refused (5) would print black; `applyLoggedKnocks` merges by maximum, so the same pair would print green. `statusByteActionability(byte)` is derived from `DOOR_KNOCK_STATUSES` and `STATUS_ACTIONABILITY` rather than written out as a parallel array, since a hand-kept second copy is the drift the table exists to end. Unencoded bytes — the engine's own `255` "no matched people" sentinel among them — rank last so they can never win a comparison.
- **`statusLabel(status, isServe)` is the only way a surface gets a status word, and nothing indexes `STATUS_LABELS` directly any more.** `unknown` reads "Support unknown" on Win and "Not yet contacted" on Serve — it is the one status whose wording has to move, because it means both "never knocked" and "answered without a stance" and Win names it after the second. `SERVE_STATUS_LABELS` is deliberately sparse, so every status whose wording survives the change of surface keeps one definition and a copy correction to "Not home" cannot land on one rail only. The walk's legend and resident pills, the person sheet's roster, the details drawer's outcome table, the printed sheet and the PDF all read the accessor, because a Serve reader that forgot to check would print the Win question at a door where it was never asked. **Paper is included even though `unknown` is the one status it never prints** — both formats branch to a blank form instead — since the branch is what makes that true and the next status added may not have one.
- **The rest of the Serve vocabulary is three strings with no indirection at all, because each is a single string in a single place.** `DoorsPanel`'s per-door count noun ("4 constituents"), `useVoterPack`'s three pack sentences (`packLoadingTitle`, `packErrorMessage`, `districtUnavailableMessage` — each read by BOTH the map region and the create-flow sheet that covers it, so the pair cannot drift), and the person sheet's "Voter demographics" heading. **All of it follows `serveMode`, not `isServeOrg`** — the slug flag PR 1 introduced for party. The two diverge for an `eo-` org still holding a live campaign, and they answer different questions: party follows the slug because it is about what gp-api will accept, and copy follows the rail because it is about what is on screen. A dual-role org drawing its Win rail is looking at a Win map, and the covering sheet and the region under it must not disagree about which. **The two rows under that heading stay voter-file rows on both rails** — registration and turnout propensity are facts about the person whoever is asking — so only the word for the person changes.
- **The Serve copy is a ternary off `serveMode`, not a `surface` object, and that is a deliberate departure from phone banking.** `PhoneBankingFlow` takes a `PhoneBankingFlowSurface` because the two rails hit different endpoints and it is mounted by two different pages; door knocking is ONE route for both, so there is nothing to parametrize by — the flow already reads `useDoorKnockingServeMode()` for its purpose cards, and a surface object over four copy strings would be indirection with a single reader. Presentational leaves take the flag as a prop (`DoorsPanel`, `PersonSheet`, `WalkView`'s `ResidentRow`) for the reason `CreateListSurface` takes `isServeOrg` as one: their tests render them without a provider.
- **Paper prints one answer column whose heading changes, not a different grid.** `walkColumns(isServe)` swaps only the `support` column's label and `answerBoxes(isServe)` only its boxes; the key and the width are shared, which is what keeps `ANSWER_COLUMN_KEYS`, the skip instruction's `colSpan` and the already-logged row one definition for both surfaces. Both formats read `payload.isServe` and treat absent as Win — a service worker's pre-ship snapshot carries no such key, and every route frozen before it shipped belonged to that surface.
- **The Serve door script is the opener alone, and that is the finished shape rather than a stub.** `useDoorScript` returns `buildServeIntro(user, officeName)` with an empty issue list: the bullets under a Win intro are the candidate's own stances out of the campaign issues editor, and an elected official has no campaign to have written them in. The opener is not optional in the same way — it is the one line a canvasser at an official's door cannot invent — and Serve was getting it blank, or worse, getting the Win sentence off whatever campaign row a dual-role org happened to hold and introducing a sitting member as a candidate for their own seat. `buildServeIntro` runs the office through `grammarizeOfficeName`, the polls flow's helper, because offices arrive as the seat and "your City Council" is not a person. **`DoorScript` heads the Serve card "Introduction"**, since a card that can never hold a talking point should not be titled with one — a Win candidate who has written no issues yet keeps the Win heading, because for them the list is empty rather than absent.
- **The office name reaches the script through its own context, and the reason is that `useOrganization` throws.** `DoorKnockingOfficeProvider` sits beside the surface provider in `NativeDoorKnockingPage`, fed from `organization.positionName`. It is a second context rather than a widening of the first so that every consumer of `useDoorKnockingServeMode` keeps answering a yes/no question with a boolean; it is a context rather than a prop because the page is the only level that can read an organization at all — the provider is above this route and `useOrganization` throws rather than returning undefined below it, which would take the print route and every leaf test down with it. It defaults to `''`, and `buildServeIntro` drops the clause the way it drops every other missing one.
- **Both paper surfaces title themselves from `GET /v1/door-knocking/turfs/:id`, never from the rail.** `fetchTurfName` used to scan `GET /v1/door-knocking/turfs`, which is scoped by SURFACE as well as by org (`railTurfScope`) and derives that surface from what the org holds — so a Serve turf was absent from the list the print page searched and every elected official's sheet and PDF was titled "Walk list". The by-id route is org-scoped only, which is the right scope here for the same reason it is the right one there: the id came from a route this page has already fetched and authorized, so there is no surface left to choose. Printing is also where the fallback is invisible — a sheet is read on paper, away from the list it came from, with nothing on it to say which of an official's turfs it is.

- **Stops, doors and people are three different numbers — `routeCounts.ts` owns the definitions.** A stop is a geocoded coordinate the router visits, a door is an address (unit included), a person is a targeted voter; a block of flats is one stop, many doors, more people. Anything user-facing that says "doors" must count doors: `countDoors` for a frozen route, `polygonStats().households` for a shape being drawn. This drifted badly once — `WalkView` printed `stopCount` as doors, `WalkSheet` summed targets as doors, and the same route reported two different door counts depending on the surface. The 150 cap is on **stops**, so a "150-stop limit" message next to a doors count is correct, not a mismatch. **Every people figure counts knockable people** — `isKnockable`/`knockableTargets` in the same file, which drop ADR 0007 do-not-knock residents _and_ ADR 0008 not-a-voter residents. One predicate covers both because they differ only in what to say at the door, which is the walk UI's problem; to a count they are the same fact — nobody to talk to. That covers the printed sheet's header, the details sheet's progress stat and `WalkView`'s logged-of-total, because a door nobody should knock is not a conversation anyone can have: counting it promises an evening that can't happen and holds a canvasser who correctly skipped it below 100%. The sheet still _lists_ flagged residents one row each, since paper freezes at print time and has to carry their skip instruction — a sheet listing more names than its header counts is intended, the header being the evening's work and the rows the index. Status rollups follow the same rule: `rollupStopStatus` (the webapp's, and gp-api's call site in `doorKnockingServe.service.ts`) drops flagged residents, because `unknown` outranks every other status and one flagged neighbor would otherwise report a fully-logged stop as still-to-knock. Same reason the collapsed stop row omits their per-person dot. There are **four** suppression sites and they must not drift: `knockableTargets`, `rollupStopStatus`, `WalkView`'s `advanceFrom`, and `print/pdf/walkListRows.ts` — auto-advance would otherwise walk a canvasser back into the door they just flagged, and paper would print a blank form beside the name of someone who moved away.
- **`WalkView`'s progress pill says "reached", and that is the design's word rather than ours.** Ours was "logged", for a reason that is still true: `not_home`, `inaccessible` and `refused` all satisfy the `knockStatus !== 'unknown'` predicate the bar counts, so a canvasser who knocked forty doors and spoke to nobody reads "40/40 reached" — a claim about conversations that never happened. The 2026-09-01 design-adherence pass put the design's wording back (`Door knocking 2.0.dc.html` line 6447), and the plan the product owner approved names it explicitly, so it is a product decision and not drift. **What keeps it survivable is that no second surface repeats it**: `TurfDetailsSheet`'s Progress section states the same figure as a bare `X of Y · Z%` with no verb at all, so the two cannot disagree. If a verb is ever needed there, it is "logged", and this pill is the one exception. The colour is the design's own bubble — `bg-secondary-light` on `text-secondary-dark`, never the near-black `tertiary-dark`, which reads as a filled control rather than as a count.
- **A flagged resident's marker replaces their status, everywhere they are listed beside other people.** `targetMarker` (`native/statusPresentation.ts`) is the one source: `WalkView`'s collapsed and expanded stop rows, and **both** of `PersonSheet`'s rosters (the resident switcher and the Household section). The sheet's rosters were the gap — the same person read "Do not knock" in the list and "Support unknown" one tap later, two answers to one question. Do-not-knock outranks a not-a-voter reason, because it is an instruction about the door rather than a fact about one of the people behind it. Paper's longer form is `skipInstruction` in the same file, read by `print/WalkSheet.tsx` and `print/pdf/walkListRows.ts` so the two formats cannot word it differently. The short marker reuses `NOT_A_VOTER_LABELS` from contracts — the CRM activity feed's vocabulary — so one flag isn't called two things in one product.
- **The pre-route walking estimate is local, not the vendor's.** 45 doors/hour (`DOORS_PER_HOUR` in `native/walkEstimate.ts`, from the POC) turns **doors** into a time before any route exists. The real duration only arrives once the route is built server-side — and building it is a billed, irreversible Geoapify call, so the one surface that helps someone decide whether a saved list is a reasonable evening has to answer before it: `TurfDetailsSheet`'s "Estimated time". **The draw step no longer quotes it.** It used to print "About 1 hr 33 min of knocking, at 45 doors an hour" under the map preview, along with a party-mix breakdown; the design draws nothing under its preview, and the estimate belongs on the surface that can state it against a real route. 100 stops warns and 150 blocks — the soft limit must stay non-blocking, and both warnings stay on the draw step because they are things the _shape_ can be wrong about rather than facts about the audience.
- **The who step offers recommended lists, and everything about them is

  `GET /v1/campaigns/mine/recommended-lists`, for the intent the purpose maps

- **A missing saved list is not an unfiltered one.** `savedListFilterKeys(undefined)` is `{}`, and `polygonStats` reads `{}` as "no filters" and answers with every door in the polygon — the exact number `TurfDetailsSheet` exists to stop reporting. A list can be missing while its query is in flight, after it errors, or because the filter was deleted in the CRM, so whatever needs it resolves it **before** computing rather than letting the empty object mean "everyone": `TurfDetailsSheet` distinguishes pending (skeleton) from settled-with-nothing (`Unavailable` plus a line saying so), and the create flow's picker renders a row whose count has not arrived without a count rather than with the district's. "travel" and not "walk" for the totals, because on a screen called WalkView "the walk" is the whole outing — the exact thing the number is not.

Both labels are the design's and neither has a second line to say which half of the evening is on screen. **This overturns a recorded decision**: the drawer used to carry two labelled quantities, "Travel time" against the route and "Knocking time" against the pre-route rule of thumb, on the argument that each is real and neither is the whole. That argument still holds; what overrules it is that the design draws one metric with one label, and the honest thing to put under it is the whole evening rather than the 40% of it Geoapify measured. The arithmetic is the design's own — line 6421 builds `mins` as the route's travel plus a flat two minutes a stop — except that the per-door allowance is `DOORS_PER_HOUR`, because 45 doors an hour is the rate this product already publishes and a second, unexplained pace would be a third number for one thing. The two genuinely add rather than overlap: Geoapify's jobs carry no `duration`, so its figure has zero time AT the doors.
- **Nothing else says "reached".** `knockStatus !== 'unknown'` counts not-home, inaccessible and refused alongside the answers, so it is the count of doors **logged** — the detail sheet's stat is "People logged". Calling it reached credits a walk with conversations it did not have. The walk's own progress pill is the single, deliberate exception; see the note above.
- **One bucketing of a route's outcomes, read by every surface that reports them.** `knockStatusCounts` (`native/statusPresentation.ts`) turns a frozen route's stops into a count per `DoorKnockStatus`, and both the walk's seven-count strip and the details drawer's "How the walk went" table read it. It was a closure inside `WalkView` until the drawer needed the same seven numbers, and lifting it is the same argument `routeCounts.ts` makes about doors: the walk and the planning surface describing one list differently is the failure, and two local derivations of one quantity is how that happens rather than an implementation detail of either screen. It follows the counting rules above rather than restating them — the denominator is `knockableTargets`, so the seven sum to whatever the surface prints as People and the six non-`unknown` ones sum to its logged figure. **Every status is present at zero**, because the vocabulary is `DOOR_KNOCK_STATUSES` and "nobody refused" is an answer; a bucket that disappeared when it emptied would make a table's own shape a fact about the list, and it is also what lets the walk strip render a stable seven-chip row. **Nothing here re-derives a status**: `target.knockStatus` is already the override-aware value from gp-api's `doorKnockingStatus.service.ts`, and a client twin of that derivation is precisely the drift these helpers exist to prevent — this function only ever counts what the server decided. The `not_a_voter` bucket's partial membership is a decision of its own; it is recorded in the drawer's section, beside the surface that has to explain it.

### Shared — the map canvas

- **Don't put `items-center` on a `flex` `<button>` here.** `app/globals.css` carries an unlayered legacy rule (`a.flex.items-center:not([data-slot])`, and the `inline-flex` variants) forcing `display: flex; flex-direction: row`. Unlayered CSS outranks everything in `@layer utilities`, so `flex-col` **and** `lg:hidden` both silently lose on such a button — a sheet's grab handle here was laid out as a row and still displayed at desktop until it dropped `items-center` and centered its children instead. Styleguide `Button` carries `data-slot`, so this only bites raw `<button>`s.
- **The map opens at street level, and the page is what says so.** `NativeDoorKnockingPage` passes `initialZoom={16}` to `VoterMapCanvas`; without it the canvas falls back to `fitBounds` over the whole pack, which is district zoom — a candidate opening the page landed on a shape with no street names in it and nothing to orient against. 16 is where they first appear. **Where it opens is `packOpeningCenter`, not the middle of the pack's bounding box.** A bbox midpoint is a geometric artifact rather than a place: on an L-shaped or crescent district, one split by a lake or a park, or two towns with fields between them, it lands where nobody lives — and at zoom 16 that spot is the whole screen, which is how this opened as a street with no dots on it and got reported as the district's dots being missing. It is also the statistic one bad coordinate moves furthest, since it reads only the four extremes, and nothing bounds a coordinate on the way in — `MAPPABLE_ONLY` in gp-api's `voterPack.service.ts` gates on rooftop accuracy and a numeric-text regex, never on a range or on the district's own shape, and the district join is a registration fact rather than a geographic one. So the anchor is a component-wise **median** and the answer is the real dot nearest it: a cluster holding more than half the dots brackets the median rank on both axes, so a two-town district opens in the larger town rather than the farmland, one mis-keyed row moves the anchor by a rank instead of by its own distance, and snapping to a dot makes "there are voters here" unconditional rather than likely — including the even split where the median itself sits in the gap. A mean was rejected for the same reason the bbox was; the pack's own over-allocated `Float32Array` was **not** the cause and structurally cannot be, since `PackEncoder.toBuffer` writes exactly `positionsLength` and the manifest schema refines `positions.elementCount === counts.dots * 2` before `decodePack` mounts the view. The prop is read **at mount only** and names the opening view rather than controlling the camera: reacting to it later would fight the canvasser's own panning, and route framing still `fitBounds` on purpose once there is something specific to frame. **`focusTurf` is passed `null` and nothing sets it**, because the only gesture that ever asked the camera to frame a saved turf was picking one off the rail; the prop stays on the canvas so a surface that wants a specific ring framed does not have to reinvent the fit. Its standing `react-hooks/exhaustive-deps` warning is correct and must stay — `--quiet` means it never gates CI, so don't be surprised by it in an editor and don't silence it by adding the dep.
- **The map lives as long as its container, not as long as the pack.** The mount effect is keyed `[hasTilesKey]` and reads the pack through `packRef`, because its one use of it — `packBounds` for the opening view — is a mount-time fact of exactly the same kind as `initialZoom` beside it. Keyed on the pack object it wasn't: `endWalk` used to invalidate the pack whenever doors were logged, `decodePack` returns a fresh object, and the effect's cleanup runs `map.remove()`, so leaving a walk destroyed the MapLibre instance and re-framed the district. The camera lives on that instance, so a canvasser who had panned to one block came back to the whole district. The **overlay effect keeps its own `pack` dependency** and is what repaints — the dots still recolour, which was always the correct half. Don't collapse the two: one owns the instance for the container's life, the other owns everything dynamic.
- **One selection, drawn on both halves, and it lives on the page.** `selectedStopId` moved out of `WalkView` and into `useWalkMapSession` (`WalkSurface.tsx`, called by the orchestrator), which **supersedes the walk section's "the reverse direction is not built"** — read that sentence as history. The state had to move for the reason the canvas rule says: the map draws it, the canvas is shared by both modes, and a surface the page unmounts cannot hand the canvas anything. It sits beside `openStopRequest` on purpose, because the two are one conversation in opposite directions — a pin tap becomes a door the list opens, and whatever the list opens becomes the pin the map rings — and keeping the two ends in one hook is what stops the next change to either from needing the orchestrator. **The walk is still the only writer**: `WalkView` reports through `onSelectStop` from `openSheet`, which is the single place a row tap, a pin tap and `advanceFrom` all pass through, so the mark is always the door the sheet is offering rather than a history of taps. It is deliberately NOT set in `onPinTap`, where it would be one line shorter: a tap for a stop the served payload doesn't carry is dropped by the walk, and marking it on the map would ring a pin whose door never opened. `selectStop` takes a stop and never null, so the only thing that clears the mark is the session's own `reset()` on the way out — the mark outliving the sheet is the list's rule made structural, and every walk opens on a route with nowhere marked. On the canvas it is a **`route-pin-selection` layer of its own**, a hollow ring outside the pin rather than another accessor on `route-pins`: the pin's fill is already the stop's status and its stroke is already `knockable`, so both of its own channels are spoken for and taking either back would cost a fact the canvasser is standing in front of the house to read — the same reason the list row rings the numbered circle instead of filling it. Drawn after `route-path` (a ring the route's own blue runs over reads as a kink in the path) and before `route-pins` (so the pin sits inside it), `pickable: false` so the tap still reaches the door underneath. The colour is `#1e63ec` as a literal, which is `--primary`, matching the row's `ring-primary` — nothing on this canvas can read a CSS variable, and a near-miss shade would read as two different marks rather than one. **Matched on `stopId`, never on `seq`**: `seq` is what both surfaces draw, and selecting on the label rather than the identity is exactly how the two would come to disagree about the thing the numbering exists to keep in agreement.
- **An archived list's ring is dimmed, not dropped, and now nothing can take it off the map at all.** `saved-turfs` scales its fill and line alpha by `ARCHIVED_RING_ALPHA` when the row carries an `archivedAt`. Not removed, because archiving is a decision about which lists a candidate is working through and not a claim that the streets stopped existing — a ring that vanished on archive would make shelving indistinguishable from deleting on the surface where nothing else tells them apart. Not recoloured either: the ring's colour is the list's own, so a grey archived outline would break the only thing tying an outline to the list that names it. **The per-list eye it used to compose with is gone**, along with `hiddenTurfIds` and the row that drew the toggle, so the page hands the canvas every turf it has and the dimming is the only distinction drawn between them. That is the cost and it is worth naming: an archived outline can no longer be got off the map, and if a surface ever wants that back, the eye's rule was that it REMOVED a ring while the archive only quiets one — two different kinds of answer, which is why they composed rather than competing. **Read off `archivedAt` directly rather than through `turfStage`**: for "is it archived" the field read is the definition, and importing the lifecycle module would pull its mutations, its snackbars and its fetch client into the maplibre/deck.gl chunk to answer a one-field question — a chunk boundary the create flow is deliberately outside of, in the other direction.
- **The in-progress ring's colour is the page's, and framing it is a request rather than a reaction.** `drawColor` replaced the hardcoded draw blue for the reason the canvas rule at the top of this file gives: the new list has a colour, the shared canvas is what draws the ring in it, and a surface the page unmounts cannot hand the canvas anything — so the state moved up into `useCreateListDraw` (`CreateListSurface.tsx`) beside the draw tokens, and `clearDrawing` resets it by hand because leaving the flow no longer unmounts the `useState` that used to do it for free. The line and fill **alphas** stay the canvas's; only the hue crosses the seam, so a tinted ring can't come out stronger or weaker than the saved rings it is being cut alongside. The vertices take the same hue — a blue handle on a green ring reads as two shapes. **`frameDrawToken` is a token and not a dependency on the ring**: the ring changes on every tap and drag while the canvasser is the one aiming the camera, so only a step that has just covered part of the map asks for the shape back. **The mechanism is maplibre's `padding` object, not a computed centre.** The map fills its container, so uncovering the top strip of it reveals empty streets while the ring stays centred behind the sheet — the shape is in the middle of the canvas, not in the middle of what can be seen. `frameDrawBottomPct` names the covered fraction, becomes bottom padding against the canvas element's own height, and `fitBounds` does the rest; an offset centre would have to redo the zoom arithmetic `fitBounds` already does and would still be wrong on a ring wider than it is tall. Padding is clamped against the canvas height, because padding taller than the map is a fit with nothing left to compute — which is also what an unmeasured container (a fresh mount, a test) would otherwise ask for. The percentage is read through a ref rather than depended on, so dragging the sheet further open uncovers more map without re-aiming the camera mid-gesture. **`controlsHidden` goes with the shield, and it is one fact stated twice on purpose**: the confirm step covers the map's taps with `#confirm-map-band`, which also covers maplibre's zoom stack and the locate button standing in that corner — buttons that are still drawn, still look pressable, and can no longer answer. So the step that puts the shield up takes them down. maplibre owns the navigation stack's DOM, so it goes away by a CSS rule on the container rather than by `removeControl`; dropping and re-adding a control on a step change rebuilds it mid-session, and the locate button is ours to simply not render.
- **maplibre's controls go in the LEFT corners, and the reason is that nothing floats over the map's left half at any width.** `VoterMapCanvas` adds the navigation stack at `top-left` and the compact attribution at `bottom-left`, and the attribution is placed by hand (`attributionControl: false` on the `Map`, then `addControl`) because maplibre only offers a corner to a control that is added rather than defaulted. Both used to sit on the right — the stack at `top-right`, the attribution at maplibre's own `bottom-right` — and the landing surface of the day was an inset card `lg:right-4 lg:w-96 z-20` over a full-bleed map, so above `lg` it covered the map's right edge from top to bottom: at 1440px **all three zoom buttons and the attribution were behind the card**, drawn, looking pressable, and unreachable, with `elementFromPoint` at each button's own centre returning the card. That card is gone, but the placement stays, and not out of inertia: one corner that nothing can cover serves both surfaces without a breakpoint, and the bug is the kind that only reproduces at desktop widths, so a phone-width check would pass a regression. **The controls are deliberately NOT hidden on a phone**: they are the only non-gesture way to zoom, they collide with nothing at 320px, and pinch is an addition to them rather than a replacement. **What is still unfixed is vertical, not horizontal**: a sheet at its `peek` snap covers the attribution, and the create flow's draw step covers whichever top corner the stack is in because `StepHeader` is a full-width opaque bar — both want the surface that draws the chrome to leave a corner clear.
- **The control cluster's distance from the bottom edge is the covering surface's to report, and the drawing surface's number is 96.** `controlsBottomPx` is `DRAW_CONTROLS_BOTTOM_PX` while `draw.fullScreen` is true, matching the design's own 96 against its 88px footer bar; otherwise it is whatever the sheet covering the map reports through `onMapControlsOffsetChange`, or the 16px edge. The drawing surface used to get that 16 like everything else, which put the cluster **underneath** the footer bar: the zoom buttons came out half-covered and the locate toggle was hidden outright. This is the same shape as the left-corner rule one bullet up — a control that is drawn, looks pressable and cannot answer is worse than one that isn't there — except that the collision is with the bottom bar rather than a side card, so the fix is an offset rather than a corner. `controlsHidden` is the other half and answers a different question: off the flow it is the walk's sheet at `full` reporting that there is no map left to zoom, and inside the flow it is every step except the drawing surface, where the map is a shielded picture.
- **The live-location dot is a deck.gl layer, not maplibre's `GeolocateControl`** (`native/useLiveLocation.ts`, switched and drawn by `VoterMapCanvas`). Continuous tracking in `GeolocateControl` requires `trackUserLocation: true`, which also flies the camera to the user and fights the view's own `fitBounds` framing of the route; its one-shot mode doesn't watch at all. The layer also lets a coarse fix render as a muted dot plus a real-metre accuracy halo instead of the same confident blue dot at any accuracy. It is **opt-in** (the watch, and therefore the permission prompt, only starts when the canvasser taps the control) and `clearWatch` runs on unmount, on disable, and on a permission denial — a watch left running is a phone battery draining after the walk. **Coordinates are display-only**: nothing sends them to gp-api or to analytics. **The toggle is offered on the drawing surface as well as the walk**, which is `flowStep && !draw.fullScreen ? undefined : setLocationEnabled`: a boundary is cut standing on the street it covers about as often as it is cut at a desk, and knowing which block you are on is how you know which blocks to enclose. It stays withheld on the flow's other steps, where the map is a shielded picture and nobody should be asked for their position to look at one.
- **The in-progress boundary's two-point edge is dashed, and its vertices are hollow, because a placed dot is not a grab point.** A `PolygonLayer` needs three points, so a two-point shape drew nothing at all between its first two corners and read as a tap that missed; `draw-draft-edge` is a `PathLayer` rendering exactly at `drawPoints.length === 2`, dashed through `PathStyleExtension` from `@deck.gl/extensions` — a dependency added for this. Two details in it are load-bearing: the dash array is in **path-width multiples**, which the extension measures in the path's own pixel width, so the dashes hold their size as the canvasser zooms instead of stretching and collapsing the way a world-unit dash would; and the extension is instantiated **once at module scope**, because a new extension object per render makes deck.gl treat the layer as a different one and rebuild its model every frame. `draw-vertices` swapped its fill and line colours for the same reason the edge exists — white centre, boundary-coloured ring, `lineWidthMinPixels: 2.5`. The filled disc it replaced was indistinguishable from the voter pins underneath at the density a street is drawn at, and the hollow handle is what says "grab this" rather than "a dot landed here". The hue is still the ring's, so a handle cannot look like it belongs to a different shape than the line it corners.

### Saved lists — their counts, their lifecycle, and the surface they no longer have

- **Comparing anything here to the design means RENDERING BOTH AND LOOKING AT THE IMAGES. Reading the design's markup against our TSX does not work, and there are three passed audits proving it.** All three walked the prototype's JSX beside the list card we drew at the time, found the same text and the same sections, and pronounced it faithful. The product owner then opened the app and listed a dozen differences in a minute — a missing shoes icon on the CTA, a PDF button we invented, the progress figure in the wrong place and styled as body text, an exposed trash icon, wrong padding, wrong border weight. **Every one of those is invisible to a markup diff**, because a markup diff compares the things that have names in the source and skips the ones that only exist once styles are resolved: iconography, colour, weight, spacing, and above all ORDER and POSITION. Two components can have identical elements and identical strings and not look alike. The card those audits were about has since been deleted along with the surface that held it, but **the lesson is not about cards** and applies to every surface in this directory: the prototype at `Voter Outreach.dc.html` is self-contained and runnable — serve the directory over HTTP (it fetches its own source, so `file://` fails), drive it to the screen in question and screenshot it; bundle our real components against the app's own compiled Tailwind and screenshot the same thing. Then put the two images side by side. Any claim that something now matches should have a picture behind it. Pull computed styles too — padding, border, `fontSize`, `letterSpacing`, `textTransform`, `offsetTop` — because "close enough" by eye at 1x is how an 11px uppercase overline stayed 14px sentence case through three reviews.
- **A pre-route count is "About N", and the softening is not about arithmetic.** A pack-derived `people` figure is `sum(matchedPerDot)` — exact for the pack — and is still softened wherever it is printed, because it is a **superset of who gets knocked**: filters with no pack bucket don't narrow it at all (above), and knock time additionally applies the list's activity conditions, support status and prior-contact clauses — none of which the pack carries in any form — then drops do-not-knock and not-a-voter residents. So the wording is `About N` plus one always-on line naming the map as the limitation, and the `unpreviewableKeys` sentence verbatim when there is a specific filter to name. The **district** figure stays exact and un-softened; its existing caveat is that the pack is rooftop-geocoded rows only. The surface that printed this about a saved list on the landing map is gone, so the rule now lives on the create flow's own pre-route counts and on `TurfDetailsSheet` — and those two must keep agreeing, because they describe the same quantity.
- **The bar for putting a control on a resting list row is high, and the budget is four.** Whatever surface next lists saved lists will want to hang affordances off each row, and the count is the thing to hold: the design rests at four, ours reached five, and every one past that is paid for by the list's own name — the row's least discoverable and most important target — reading more like a label than a target. New affordances go in an overflow menu unless the design puts them on the row. This is written down here rather than deleted with the row it was learned on, because it is the constraint that kept that row legible, and it is the reason the delete note below reads the way it does.
- **List counts are gp-api's, and every list has them.** `GET /v1/door-knocking/turfs` carries `doorCount`, `knockedDoorCount`, `peopleCount` and `loggedCount`, none of them nullable. They used to be, and the reason was real: a turf with no route had no doors to count, and `0 of 0 logged` would have claimed a list somebody walked and found empty. 3.0 has no such turf, so the null branch and the `locked` flag it hung off are both gone from the schema — **if you find yourself adding a nullable count back, the invariant broke somewhere upstream and this is the symptom, not the bug**. **They are not computed client-side, and that is the whole point** — `TurfDetailsSheet` derives its own figures from the route payload (`countDoors`, `knockableTargets`, `knockStatus !== 'unknown'`), and a list of rows that disagreed with it about the same list would be worse than rows with no numbers on them. The rows are gone; the constraint is not, because the same counts feed the outreach history table and whatever surface lists saved lists next. gp-api's `doorKnockingStatus.service.ts` is the one derivation both paths read: `latestKnockStatuses` / `doNotKnockPersonIds` / `notAVoterReasons` used to be private to `doorKnockingServe.service.ts` and were extracted rather than copied. The equivalence is also asserted directly — `doorKnocking.routes.test.ts`'s "reports counts the details sheet derives identically" computes all three off the SERVE payload and compares, against a fixture carrying a shared door, a do-not-knock resident, a not-a-voter resident, an answered-but-unsure knock that derives back to `unknown`, and a not-home knock that counts as logged. **None of the three is a Prisma `_count`, and none could be.** Doors are `DISTINCT (stop_id, address_key)`, not stop rows — stops group by COORDINATE, so pairing the key with its stop is what makes this the same number `countDoors` reports rather than nearly the same one; shipping stops as doors is the bug this feature already had and fixed. People count knockable targets, so they need `ContactCurrentStatus`, joined on `(organizationSlug, personId)` with no relation to traverse. "Logged" is derived from `ContactInteractionDoorKnock` history (latest answer-bearing row preferred, manual `support_status` override winning) — there is no `knockStatus` column anywhere. **One batched aggregate for the whole response, never a fan-out.** `serve` is the feature's heaviest read — nested route fetch, people-api round trip, four CRM queries — so running it per list is exactly the cost this avoids; `DoorKnockingTurfCountsService.forRoutes` takes every route at once and the person-keyed reads deduplicate across lists, so a resident in three lists is looked up once. Measured on the dev database: **11 SQL statements for the whole request at 12 lists and still 11 at 25**, and median endpoint latency 27ms at a dozen 150-stop lists (2,760 targets / 2,128 people). A routes-suite test asserts `forRoutes` is called exactly once and `serve` not at all. **A progress ratio counts one noun on both sides of the slash, and `knockedDoorCount` exists so that the design's wording can.** The prototype writes `8 / 24 doors knocked` while its numerator is people-derived, which is the stops/doors/people rule above broken in a single sentence — so ours read `N / M people logged` (the quantity `TurfDetailsSheet` labels "People logged", worded with the same verb per the "nothing says reached" note) for as long as `GET /turfs` returned only `loggedCount`. `knockedDoorCount` was added to `doorKnockingTurfCounts.service.ts` for exactly that line, which is what makes the design's wording safe to state: doors over doors, and "knocked" rather than "reached" because a door counts once anybody behind it has an answer written down and not-home is an answer. **If a progress line ever reads people over doors again, the counts service is what regressed, not the surface printing it.** Wherever these land, a bare numeral beside an icon needs an `sr-only` noun — a screen reader has none of the column layout that makes them obvious, and these are exactly the three quantities that must never be read as each other.

- **`ListCard` is a shared component in `app/dashboard/shared/`, and door knocking is no longer one of its consumers.** The designer reuses it in voter data and campaign manager, so it is domain-agnostic: an accent colour, an eyebrow slot, a title, a `meta` list, an `actions` row and a `controls` cluster. It knows nothing about turfs, which is why deleting door knocking's own list of these cost the other consumers nothing. Three decisions in it are not cosmetic and are recorded here because they were paid for here. **Selection is a button on the title, never a handler on the card** — the prototype makes the whole card clickable and then needs `stopPropagation` on all five controls inside it, which is a bug waiting on the sixth, and announces to a screen reader as a button containing buttons. **Every `meta` figure carries an `sr-only` noun**, for the reason the counts note above gives. **The card is `shrink-0`**, because every list that stacks these is a column flex scroller: without it the cards divide the visible height between them instead of overflowing it, and the `overflow-hidden` that keeps the accent bar inside the rounded corner then clips whatever fell off the bottom — which on a phone took the two CTAs off two cards out of three, silently. Same failure mode as the layout note below, one component down.
- **Delete belongs behind an overflow menu, and its confirmation is rendered outside that menu.** `DeleteTurfControl` has **no caller at all** now — its one caller was the deleted saved-list row — and it is kept rather than deleted because both halves of its shape were learned the hard way. The design puts a three-dot menu in a card's corner and nothing destructive on the card itself; ours had an exposed red trash icon one brushed thumb from the row it names. So the control takes a `trigger` prop (`'button' | 'icon' | 'none'`) and an optional controlled `open`/`onOpenChange` pair, and a caller drives it with the menu item only setting state. **The control is mounted as a sibling of the menu, never inside it** — Radix unmounts `DropdownMenuContent`'s children on select, so a dialog rendered within it is torn down by the very gesture that opened it. That is what `trigger="none"` is for. Any surface that offers delete again inherits both rules; **do not wire this back onto a screen the design does not draw** just because the component is sitting there.
- ~~**The legend is one horizontally scrolling row of DS `FilterPill`s.**~~ ~~**Overturned 2026-08-26: the legend wraps, and the whole of it is on screen at once.**~~ **There is no legend and no status filter on this map.**

  The design builds a status legend at line 6700 and never renders it. `TurfLegend.tsx` is deleted, and so is everything that existed only to feed it: `statusFilter`, `statusCounts`, `canvassStatusCounts`, `MapScope`. The map has no status filter at all as a result. **If that filter turns out to be load-bearing for anyone it comes back as its own change**, with its own surface, rather than by reviving this one — and the seven-colour vocabulary it read (`STATUS_DOT_COLORS`, `PROGRESS_LEGEND_ORDER`) is still shared by the walk's strip, the map dots and the details sheet's outcome table, so a new legend must read those rather than restate them.

  Two rounds of argument are recorded here rather than deleted because both were real and both were about a constraint that has not gone away: a floating panel is a bounded card, its height is finite, and every row spent on chrome is a row taken from its content. The first answer was a scrolling row (26px, but a chip you have to scroll to is a filter you cannot clear); the second was wrapping (122px, all seven statuses reachable, verified at four viewport sizes). The lesson worth keeping from the second is the layout bug it exposed, because it is not about legends: **`shrink-0` inside a box with an indefinite height and `overflow-hidden` does not mean "stay whole", it means "get cut off"** — silently, with nothing to scroll, and `overflow: hidden` reports a larger `scrollHeight` than `clientHeight` exactly like a scroller does, so a reachability check comparing only those two numbers passes a layout that is losing content. A sheet is `h-[60dvh]` and not `max-h-[60dvh]` for the same reason: percentages inside an indefinitely-sized box resolve to `content` and `none` rather than failing loudly.

- **The list lifecycle is `turfLifecycle.ts`, and it is the one place the calls live.** `complete`, `archive` and `restore` share a module because they share every decision worth making once: archive and restore are the same endpoint with the boolean flipped, and all three must invalidate the turf query _before_ their snackbar fires, or the message announces a move the screen has not made. Nothing is optimistic — both stamping directions are idempotent server-side, so a retry is cheaper than a rollback path. **All three write the `Outreach` envelope now, not the turf**, though the client cannot tell: the endpoints still take a turf id and still answer with a turf, and the turf's `completed` and `archivedAt` are read off the envelope on the way out. What did change is that `canCompleteTurf` / `canArchiveTurf` no longer gate on `locked` — every list has a route, so none of the three can fail for want of one. **The walk's footer is the only surface that calls any of them now**: `Move to archive` through `useWalkArchive`, and `complete` through `useWalkCompletion` on a finished walk. `restore` has no caller, which is the cost the archive note below states plainly.
  - **`completeAndArchive` is one action over two endpoints, and it exists because the design's button and the design's handler disagree.** The walk's footer reads `Move to archive` while `completeWorklist` marks the list _completed_ and toasts "List completed"; production has complete and archive as two separate calls. So `turfLifecycle.ts` gained a fourth action that awaits `complete()` before `setArchived(true)` — the order matters, since archiving first would leave a list that never recorded being finished — and `useWalkArchive` in `walkCompletion.ts` is what the walk's button calls. **This is a resolution of an ambiguity in the design, not a reading of it**; if the intent was to complete only, the fix is to drop the archive half rather than to rename the button.
- **Archiving is one-way from this feature's own UI, and that is the recorded cost of having no list surface.** There used to be a sectioned `Archived (N)` group with a Restore beside each row, on the argument that the prototype's `filter(l => !l.archived)` makes a one-tap action irreversible from the only surface that offers it. Door knocking 2.0 dropped the section and the Restore, and there is now no surface here that lists saved lists at all — so `Move to archive` at the end of a walk is a shelving nobody can undo from inside door knocking. `GET /v1/door-knocking/turfs` still returns archived rows carrying `archivedAt` (see `gp-api/docs/door-knocking.md`) and the print route still scans that response to resolve a list's NAME, so nothing about the data changed and `setArchived(false)` is one call away whenever a surface wants it. The old argument against one-way archiving is above and is still the argument; what overrules it is that the outreach history table is where a shelved campaign is now managed.
- **Delete tombstones at every stage, the confirmation is the guard, and there is only one thing it can say.** gp-api's `delete` always writes `deletedAt`, because every list it can be pointed at was billed — so `DeleteTurfControl` takes no `locked` prop and the dialog has one description: the route, the frozen doors and the outreach-history entry are kept, and only the listing loses the list. It used to branch, warning about an unrouted turf as a drawing that really goes, and both `LOCKED_TURF_MESSAGE` and the disabled-with-a-reason trigger before it are gone with the state they described. **The 409 path survives as `STALE_SERVER_DELETE_MESSAGE`** and is the one thing here that is about deployment rather than product: a gp-api old enough to still run `assertNotLocked` will refuse a delete this client believes in, so the snackbar says the server is behind rather than inventing a rule, and it closes the confirm, because a server that refuses once will refuse the retry. Nothing calls any of this today — see the delete note above.
