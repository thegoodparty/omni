# app/dashboard/contacts/

Voter contact management. Browse the campaign's voter file, segment audiences, and drill into individual voter records. Powers audience selection for outreach.

This is the **unified, People-API-backed** voter experience shared by Serve (elected office) and Win (campaign). All contacts data — list, counts, downloads, saved segments, per-person detail, the outreach timeline — is served by people-api through gp-api (`GET /v1/contacts`, the voter-file filter endpoints, and the contact-engagement endpoints). There is no raw-SQL voter path behind this route. Win access is the new home for what the legacy `dashboard/voter-records/` page used to serve; that page still exists for un-migrated Win users until the post-rollout cleanup (ENG-10436), but new Win voter work goes here. See `docs/architecture.md` (voter/people data path).

**crm/ folder convention:** every new CRM surface goes in `crm/`, never mixed into
`[[...attr]]/components/`. Code shared by both UIs (the provider, `ContactProModal`,
`person/`, `shared/` types/fixtures, `configs/defaultSegments.config.ts`) lives in
`crm/` and the old code imports it from there — so deleting `[[...attr]]/components/`
at full ramp cannot break the CRM page (only `ContactsPageGate`'s old-page branch
needs collapsing).

## Patterns

- **One catch-all route** (`[[...attr]]`) — all "tabs" (people, segments, settings) are handled inside that route's components, not as separate Next.js routes. Easier to share filter state.
- **Filters and segments are distinct**: filters are ephemeral (current view); segments are saved (named, reused in outreach). Don't conflate.
- **A saved list can also carry a free-text search** (ENG-10518). When "Create list" opens with an active search (the `query` URL param), `FiltersSheet` saves that term on the `VoterFileFilter.search` column with no filter required, and `selectSegment` (in `ContactsTableProvider`) re-applies it to the `query` param when the list is selected — so the saved view reproduces the searched-down set. A live request search always wins over a list's stored search server-side (gp-api `findContacts`). Download does not re-apply stored search (people-api `/download` has no search param).
- **Live segment-builder count** (ENG-10517): while `FiltersSheet` is open, it shows a running "N voters match" for the in-progress (unsaved) filter set, fetched from `POST /v1/contacts/count`. That endpoint runs the same `convertVoterFileFilterToFilters` translation a saved segment would, then queries people-api with `resultsPerPage: 1` and returns only `pagination.totalResults` — no real rows are loaded. The webapp debounces the payload (~600ms, mirroring the search box) and keys a React Query on `['contacts-count', orgSlug, debouncedPayload]` (org-scoped per ENG-10511); `enabled` reads the _debounced_ payload's criteria so a request never fires with a payload that lags its own gate. The count is pro-gated like search/named segments (a non-pro requester only ever sees the base-list preview). The count honors any active create-mode search (ENG-10518), so the number matches the list it would save. It's a display affordance only — it does not change how segments are saved or how the main table counts.
- **Deleting a list** (ENG-10520) is handled by `DeleteSegment.tsx` (a styleguide `AlertDialog` confirmation that calls `DELETE /v1/voters/voter-file/filter/:id`, then `refreshCustomSegments`). It renders in two places off the same component: the bottom of the edit `FiltersSheet`, and a per-row trash `IconButton` next to each custom list in the `SegmentSection` dropdown (via the optional `trigger` prop). The per-row trigger stops pointer/click propagation so it doesn't select the Radix `SelectItem`. `afterDeleteCallback(deletedId)` lets the caller decide fallback: `SegmentSection` resets to `ALL_SEGMENTS` only when the deleted list is the active one; `FiltersSheet` always closes + resets. Only custom `VoterFileFilter`s get the affordance — default segments (all/doorKnocking/texting/…) never do. Backend delete is org-scoped (`deleteByIdAndOrganizationSlug` → `where: { id, organizationSlug }`), so a user can't delete another org's list.
- **Whole-page CRM gate** (ENG-10683): `[[...attr]]/page.tsx` renders `crm/ContactsPageGate` inside the provider. When `useCrmEnabled()` (app/dashboard/shared) reads `ready && enabled`, the user gets ONLY `crm/CrmContactsPage` — universe title ("Your Voter Universe" / "Your Constituent Universe" via `contactsLabels.ts`), the `ContactTypeahead`, "Create new list", and `PersonOverlay`. Flag off or unsettled renders the old `ContactsPage` exactly as it was pre-CRM (always `ContactSearch`; the ENG-10687 in-page typeahead swap is gone). The gate is the one treatment/control divergence point, so the experiment exposure fires there (`useCrmEnabled(true)`). Note: `Contacts - Contacts Viewed` fires only from the old page — the minimal CRM page deliberately doesn't emit it yet.
- **Locked-prototype presentation parity** (ENG-10721, presentation-only — no behavior change): `crm/wizard/CreateListWizard.tsx` moved from a side `Sheet` to a bottom `Drawer` (`@styleguide`'s vaul-backed `Drawer`/`DrawerHandle`/`DrawerBody`/`DrawerFooter`), with a centered per-step title, a header "Back" control (steps 2-3, the drawer's built-in X-close covers step 1's dismiss), and the existing `Stepper` bar-variant reused as-is for the "Step N of 3" + 3-segment progress bar (its rendering already matched the design). The footer CTA is step-keyed, not a fixed Next/Cancel pair: "Continue" (step 1) → "Build your list (N)" (step 2, both branches; only the voter-file branch dims it via `opacity-50` while nothing is selected — the activity branch's disabled state already covers "not ready") → "Save list" (step 3, the actual submit). `crm/wizard/VoterFileStep.tsx`'s checkbox rows became Radix `ToggleGroup` pills (`type="multiple"` per `filters.config.ts` field, plus a "Clear filters" link) driven off the exact same filter dimensions and `voterFileFilterTransform.util.ts` payload builder — no new filter dimensions. `crm/lists/ListsTable.tsx` became `ListsIndex.tsx` (section heading + subtitle) rendering a `ListCard.tsx` grid — each card's kebab "List options" menu now hosts the Rename/Duplicate/Delete dialogs that used to live only on `ListDetailPage.tsx`'s "More actions" menu (same dialogs/hooks, reused, not forked) — plus Details/Send-outreach buttons. The shared pill look (`PILL_TOGGLE_ITEM_CLASSNAME` in `crm/shared/constants.ts`) is reused by `ActivityStep.tsx`'s channel/outcome toggles so the two branches don't drift stylistically.
- **CRM typeahead search** (ENG-10687, now `crm/ContactTypeahead.tsx`): a debounced (300ms, min 3 chars) results dropdown over the same `GET /v1/contacts` client path (`resultsPerPage: 8`), fetched standalone via `crm/useContactTypeaheadSearch` (query key `['contacts-typeahead', orgSlug, term]`, never the table's `['contacts', ...]` key or the `query` URL param); selecting a row navigates via the provider's `selectPerson`. Non-pro: focus/typing opens the Pro modal and no request fires (gp-api still rejects non-pro search). The mode-specific Contact Searched events (ENG-10688) fire from the `settled` derivation inside `useContactTypeaheadSearch` — see Analytics below.
- **Voter file fetching** uses `helpers/createVoterFileFilter.ts` to build the filter payload — keep that helper as the single shape source.
- The `PersonOverlay` is a side-panel detail view that opens over the page. Drilling in DOES put the person id in the path (`/dashboard/contacts/:personId`, deep-linkable), but via **shallow navigation**: `selectPerson` calls `window.history.pushState` (never `router.push` — the route is `force-dynamic` with a `loading.tsx`, so a router navigation blanks the whole page through the loading boundary just to open/close the overlay). The provider derives `currentlySelectedPersonId` from `usePathname()`, not `useParams()` — `useParams` does not react to native pushState.
- **Person-record notes** (ENG-10697, `crm/person/NotesSection.tsx`): a per-person dated-notes CRUD panel mounted unconditionally in `PersonContent` but self-gated on `useCrmEnabled()` (`trackExposure=false` — it's not the treatment surface). Backed by the four `contacts/:personId/notes` / `contacts/notes/:noteId` routes from ENG-10693. React Query key `['contact-notes', orgSlug, personId]`; the API returns notes newest-first already (`ContactNoteService.listForPerson` orders by `createdAt desc`), so the frontend never re-sorts. Every write (create/edit/delete) invalidates that key plus a partial match on `['contact-engagement', 'activities']` so notes surface in the outreach/poll feed once ENG-10695 lands. Delete uses the `DeleteSegment.tsx` destructive-confirm (`AlertDialog`) pattern. The `InfoSection` card wrapper was extracted from `PersonOverlay.tsx` into its own `crm/person/InfoSection.tsx` so both files can share it without a circular import.
- **Manual interaction logging** (ENG-10698, `crm/person/LogInteraction.tsx`): mounted unconditionally in `PersonContent` right after `NotesSection`, self-gated on `useCrmEnabled()` (same `trackExposure=false` reasoning). A channel toggle (text / door knock / robocall) drives a per-channel outcome toggle whose vocabulary matches `LogContactInteractionInputSchema` exactly — text is optional (`No Outcome` / `Responded`; `opted_out` is a valid API value but deliberately left out of the manual form, it's normally system-recorded), door knock and robocall require a selection. A three-way support-answer toggle (`Yes`/`Unsure`/`No` → `supporter`/`unsure`/`non_supporter`) only renders for door knock. Posts to `POST /v1/contacts/:personId/interactions`, then invalidates `['contact-engagement', 'activities']` (feed) and `['person', orgSlug, personId]` (so a support answer refreshes `person.supportStatus`). The optional date field defaults to today and is capped at today (`max`); it's omitted from the payload entirely (not converted) whenever it's unchanged from today's default OR cleared to `''` — a cleared native date input parses to an Invalid Date, which `JSON.stringify` silently renders as `null` rather than throwing, and the server would coerce that to the 1970 epoch instead of rejecting it, so `''` is treated the same as "unchanged" (server defaults to now).
- **New feed entry types + support status** (ENG-10698): `crm/person/ActivityFeedEntry.tsx` renders the DOOR_KNOCK/TEXT/ROBOCALL/NOTE rows ENG-10695 added to the feed (manual badge when hand-logged, outcome/support-answer/timestamp framing, a link to `/dashboard/outreach` when a text/robocall row has a source `outreachId` — there's no per-outreach detail route yet, so it links to the list). `formatDateTime` lives there too (not in `PersonOverlay.tsx`) so `PersonOverlay` can import it without a circular dependency. Rendering these types (and counting them toward the feed's empty-state/pagination logic) is gated on `useCrmEnabled()` inside `ActivitiesContent` — CRM-off keeps the exact pre-CRM behavior of skipping them (the interim ENG-10695 comment trail). The Win-only `Contacts - Outreach Timeline Viewed` event stays scoped to legacy `OUTREACH` rows specifically (a separate `hasOutreachRows` check), so the CRM-widened entry types can't inflate that pre-existing adoption metric. `person.supportStatus` (ENG-10696) renders read-only as a `Field` inside the "Voter Demographics" `InfoSection`, also gated on `useCrmEnabled()`; there's no edit affordance since status is derived server-side.
- **Lists index + list-detail page** (ENG-10707, `crm/lists/`): `ListsIndex` (rendered inside `CrmContactsPage`; a card grid of `ListCard` as of ENG-10721, formerly the `ListsTable` table) reads `customSegments` from the provider. There's no bulk "count + last outreach" endpoint, so each card calls `GET /v1/contacts/list-detail` once (`useListRowDetail`) for a refreshed people count and `outreachHistory[0]` — an accepted N+1 for a small number of saved lists per org. The card's "Details" button navigates (`router.push`, a real navigation, not `selectPerson`'s shallow pushState) to `/dashboard/contacts/lists/:listId`, a separate literal route (`app/dashboard/contacts/lists/[listId]/page.tsx` → `crm/lists/ListDetailPageGate.tsx` → `crm/lists/ListDetailPage.tsx`) so the URL deep-links; "Send outreach" links to `/dashboard/outreach` for both Win and Serve (Serve renders it identically — no outreach-specific branching). The detail page renders four sections only — filter summary (`ListFilterSummary`, a pure sentence builder off the segment's demographic booleans + `activityConditions` + `supportStatus`, reusing `filters.config.ts` / `activityConditionOptions.tsx`'s label maps), demographics, reachable-by-channel (`ReachabilityGrid` — `email`/`metaAds` are always `null` server-side and render "Unavailable", never 0), and outreach history — **never** a member table. `firstUsedForOutreachAt` set means gp-api's `assertNotLocked` 409s both `PUT` and `DELETE`; both the card's kebab menu and the detail page's "More actions" menu swap the rename action for "Duplicate to edit" and hide Delete once locked, and treat a raced 409 (locked between page load and the mutation) the same way — a neutral message, not an error toast — via the shared `RenameListDialog`/`DeleteListDialog`. `useDuplicateList` reposts the segment's own criteria as a new create call (name suffixed `" (copy)"`, server-only fields stripped). The wizard's (`crm/wizard/CreateListWizard.tsx`) on-create-success navigation lands here now (`router.push`), not the old in-page `selectSegment`. The legacy `Download.tsx`'s cookie-poll top-level-download logic was extracted to `crm/shared/useContactsDownload.ts` so both surfaces share one implementation; `OUTREACH_CHANNEL_LABELS`/`OUTREACH_CHANNEL_ICONS` similarly moved from `PersonOverlay.tsx` to `crm/shared/outreachChannelLabels.tsx`. `ListDetailPageGate` redirects to `/dashboard/contacts` when the CRM flag isn't enabled — there's no legacy fallback for this route.

## Gotchas

- Optional catch-all route (`[[...attr]]`) means `/dashboard/contacts` and `/dashboard/contacts/whatever` both render the same page — sub-routing is internal. `lists/[listId]` is the one literal route under this path (Next.js gives literal segments precedence over the catch-all), so a person id that happened to literally be `"lists"` would collide — not a real risk given person ids are lalVoterId/UUID-shaped, but worth knowing if a future id scheme changes.
- Voter-file payloads can be huge — pagination + cursor are mandatory; never request without them.
- A feature flag gates parts of `PersonOverlay` (see `app/shared/experiments/`).
- This route is shared by Serve (elected office) and Win campaigns. Win access is gated by the `win-voter-data` flag alone (pro and non-pro): the nav entry is added in `DashboardMenu.tsx` (`WIN_CONTACTS_MENU_ITEM`, `campaign` category) for any flag-on Win campaign, and gp-api's `assertContactsAccess` enforces the flag, not pro. Pro gating is per-action, not page-level (ENG-10495): a non-pro Win candidate sees the real district aggregates and a blurred preview, and the Pro upgrade modal fires when they search, pick a non-default segment, open a person, or download. Backend mirrors this — `findContacts` rejects search/named-segment requests, `findPerson` rejects person-detail reads, and `downloadContacts` rejects downloads for non-pro, but the base list + `GET /v1/contacts/stats` are open to flag-on non-pro. **The base-list preview is synthetic, not real voter data (ENG-10508):** for a non-pro requester `findContacts` returns fabricated rows from `previewContacts.utils.ts` and never fetches real people rows — a frontend blur is not a real boundary (the values are copy-pastable), and our data contracts forbid sending real voter PII to non-pro users. It still reads the aggregate district stats to set the preview's `pagination.totalResults` to the real count, because the unblurred "Total Voters" stat card derives from `totalResults` (`stats.util.ts`) — so the number a non-pro user sees doesn't regress, while every row stays fake. The frontend blur on those rows is now just an upsell cue over fake data, and it covers every column (name/gender/age included) so a copy/paste test can't mistake the fabricated rows for readable real data. A Win campaign with no resolvable district gets a `400 { errorCode: 'VOTER_DATA_UNAVAILABLE' }`, which `ContactsTableProvider` surfaces as `isVoterDataUnavailable` so `ContactsPage` renders a clean ineligible state instead of an error.
- **Naming is Win-vs-Serve and must never cross over** (ENG-10448): Win reads "Voter Data" / "voters"; Serve reads "Constituent Data" / "constituents". Win must never say "constituent". The strings live in one place — `app/dashboard/shared/contactsLabels.ts` (`CONTACTS_DATA_TITLE` + `getContactsLabels(isWinContext)`) — consumed by the page heading/subheading (`ContactsPage`), stat labels (`ContactsStatsSection`), the sidebar items (`DashboardMenu`), and the mobile title (`DashboardLayout`). Add new user-facing copy through that helper, not as a local literal, so the surfaces can't drift.

## Analytics

Events live under the `Contacts` group in `helpers/analyticsHelper.ts` and fire frontend (screen views and user clicks the browser directly observes). Every event carries a `context: 'win' | 'serve'` property sourced from the provider's `isWinContext` — so Win adoption of the unified path is a property filter in Amplitude, not a duplicate event set. Don't mint per-context events.

- `Contacts - Contacts Viewed` — fires once on page entry (`ContactsPage`), `context` only.
- `Contacts - Outreach Timeline Viewed` — Win-only; fires when the Win outreach timeline renders rows in `PersonOverlay` (`context: 'win'`, `personId`). Not fired for an empty feed or the Serve poll-interaction timeline.
- `Contacts - Download` / `Segment Viewed` / `Segment Created` / `Segment Updated` / `Segment Deleted` — existing events, now carrying `context`.
- `Voter Data - Contact Searched` (Win) / `Constituent Data - Contact Searched` (Serve) — the one deliberate exception to the context-property rule: the CRM brief specs the typeahead search events as product-specific by nav surface, each with `resultCount`. They fire once per distinct resolved search from the `settled` derivation in `useContactTypeaheadSearch` (ENG-10688) — never on aborted/superseded requests, sub-3-char input, or the non-pro modal path; an empty result set fires with `resultCount: 0`. Mode comes from `useWinVoterContext()`, gated on `isReady` like the mount event.
- `Voter Data - Note Added` (Win) / `Constituent Data - Note Added` (Serve) — same product-specific naming exception, no properties. Fires from `NotesSection` exactly once per successful create (never on edit, delete, or a failed create). Mode comes from `useWinVoterContext()`, gated on `isReady`.
- `Voter Data - Contact Viewed` (Win) / `Constituent Data - Contact Viewed` (Serve) — same naming exception, no properties. Fires from `PersonContent` once per record open, gated on `useCrmEnabled()` and `useWinVoterContext().isReady` (a person remount via `key={person.id}` re-arms the latch). Distinct from `Contacts - Contacts Viewed`, which only fires from the pre-CRM page.
- `Voter Data - Contact Logged` (Win) / `Constituent Data - Contact Logged` (Serve) — same naming exception, `{ channel, outcome, supportAnswer }` (Serve carries `supportAnswer` too — the CRM brief's "confirm with Bryan" question resolved to give both modes the same properties). Fires from `LogInteraction` once per successful manual log; never on failure.
- `Voter Data - List Created` (Win) / `Constituent Data - List Created` (Serve) — same naming exception (ENG-10709). Fires from `crm/wizard/CreateListWizard.tsx`'s create-mutation `onSuccess`, once per successful create, only for the voter-file branch. `{ variableCount, hasParty }` — `variableCount` is the number of `filters.config.ts` categories with a selection (`crm/shared/voterFileFilterTransform.util.ts`'s `countSelectedFilterCategories`; a Support Status selection counts as one more category). `hasParty` (via that file's `hasPartyFilterSelection`) is Win-only — Serve never renders the Political Party section (`VoterFileStep` strips it for `isElectedOfficial`), so the property is omitted as a key entirely for Serve, never sent as `false`.
- `Voter Data - Activity List Created` (Win) / `Constituent Data - Activity List Created` (Serve) — same seam, fires only for the activity branch. `{ sourceCampaign, actionFilter }` — the wizard supports N stacked conditions (`crm/wizard/ActivityStep.tsx`), so both properties aggregate across all of them: `sourceCampaign` joins each condition's resolved outreach name (or `'any'`) with `', '`; `actionFilter` is the deduped union of every condition's selected outcome values, as an array (not a HubSpot-email-driving event, so no flatten-to-scalar requirement). `WizardActivityCondition` carries an `outreachName` field (resolved at selection time, never sent to the backend) purely so this handler doesn't need a second outreaches fetch.
- `Voter Data - List Exported` (Win) / `Constituent Data - List Exported` (Serve) — same naming exception, `{ listSize }` (the people count already shown on the list-detail page). Fires from `crm/lists/ListDetailPage.tsx`'s Download button via a new optional third argument to `crm/shared/useContactsDownload.ts`'s `download()` — invoked only from the cookie-poll **success** branch, never the ambiguous 15s-fallback branch or a failed download, and never if the demographics count isn't known yet at confirm time. The legacy (pre-CRM) `Download.tsx` caller omits the argument, so it never emits this CRM-only event.

Source the `context` from `isWinContext` (single source of truth in `ContactsTableProvider`) — don't recompute Win-vs-Serve. New events: follow `.claude/skills/instrument-analytics-event/SKILL.md`.
