# app/dashboard/contacts/

Voter contact management. Browse the campaign's voter file, segment audiences, and drill into individual voter records. Powers audience selection for outreach.

This is the **unified, People-API-backed** voter experience shared by Serve (elected office) and Win (campaign). All contacts data — list, counts, downloads, saved segments, per-person detail, the outreach timeline — is served by people-api through gp-api (`GET /v1/contacts`, the voter-file filter endpoints, and the contact-engagement endpoints). There is no raw-SQL voter path behind this route. This is the home for what the legacy `dashboard/voter-records/` page used to serve; that page was deleted after the rollout hit 100% (its route now redirects here), and all Win voter work goes here. See `docs/architecture.md` (voter/people data path).

**crm/ folder convention:** every new CRM surface goes in `crm/`, never mixed into
`[[...attr]]/components/`. Code shared by both UIs (the provider, `ContactProModal`,
`person/`, `shared/` types/fixtures, `configs/defaultSegments.config.ts`) lives in
`crm/` and the old code imports it from there — so deleting `[[...attr]]/components/`
at full ramp cannot break the CRM page (only `ContactsPageGate`'s old-page branch
needs collapsing).

## Patterns

- **One catch-all route** (`[[...attr]]`) — all "tabs" (people, segments, settings) are handled inside that route's components, not as separate Next.js routes. Easier to share filter state.
- **Filters and segments are distinct**: filters are ephemeral (current view); segments are saved (named, reused in outreach). Don't conflate.
- **A saved list can also carry a free-text search** (ENG-10518). When "Create list" opens with an active search (the `query` URL param), `FiltersSheet` saves that term on the `VoterFileFilter.search` column with no filter required, and `selectSegment` (in `ContactsTableProvider`) re-applies it to the `query` param when the list is selected — so the saved view reproduces the searched-down set. A live request search always wins over a list's stored search server-side (gp-api `findContacts`). Download does not re-apply stored search (people-api `/download` has no search param).
- **Live segment-builder count** (ENG-10517): while `FiltersSheet` is open, it shows a running "N voters match" for the in-progress (unsaved) filter set, fetched from `POST /v1/contacts/count`. That endpoint runs the same `convertVoterFileFilterToFilters` translation a saved segment would, then queries people-api with `resultsPerPage: 1` and returns only `pagination.totalResults` — no real rows are loaded. The webapp debounces the payload (~600ms, mirroring the search box) and keys a React Query on `['contacts-count', orgSlug, debouncedPayload]` (org-scoped per ENG-10511); `enabled` reads the _debounced_ payload's criteria so a request never fires with a payload that lags its own gate. The count is pro-gated like search/named segments (a non-pro requester only ever sees the base-list preview). The count honors any active create-mode search (ENG-10518), so the number matches the list it would save. It's a display affordance only — it does not change how segments are saved or how the main table counts.
- **Saved-list overlap strip** (ENG-10840, `crm/wizard/OverlapBar.tsx`): once any pill is selected on the wizard's conditions step and the org has ≥1 saved list, a full-bleed gray band (`border-y border-border bg-muted`, `CrmSheet`'s `banner` slot between body and footer — the 608px footer column would otherwise constrain it) renders above the CTA — "N (P%) voters already exist in lists you've saved." in text-xs muted with the count bold (`font-semibold text-foreground`), inner text aligned to the 608px footer column. The copy after the count lives in template literals, not JSXText: SWC/Turbopack drops the leading space of a text node following an expression (vite/jsdom keeps it), which shipped as "votersalready" while the unit test passed. Backed by `POST /v1/contacts/overlap-count` (same in-progress payload/Pro gate as `count`; gp-api resolves the org's saved `VoterFileFilter`s — capped at the 25 most recent, truncation logged — and unions them server-side against the current selection, so activity-based saved lists participate via their resolved person-id sets). `crm/wizard/useListWizardOverlapCount.ts` mirrors the ENG-10517 count hook exactly (600ms debounce, its own `['contacts-overlap', orgSlug, debouncedPayload]` query key). Percent is computed client-side (`overlapCount / count`, the wizard's own live count) and suppressed — falling back to the `formatFencedCount` "10,000+" convention — whenever either count is fenced; any error or an unsettled/zero live count just hides the strip, never blocking the CTA.
- **Deleting a list** (ENG-10520) is handled by `DeleteSegment.tsx` (a styleguide `AlertDialog` confirmation that calls `DELETE /v1/voters/voter-file/filter/:id`, then `refreshCustomSegments`). It renders in two places off the same component: the bottom of the edit `FiltersSheet`, and a per-row trash `IconButton` next to each custom list in the `SegmentSection` dropdown (via the optional `trigger` prop). The per-row trigger stops pointer/click propagation so it doesn't select the Radix `SelectItem`. `afterDeleteCallback(deletedId)` lets the caller decide fallback: `SegmentSection` resets to `ALL_SEGMENTS` only when the deleted list is the active one; `FiltersSheet` always closes + resets. Only custom `VoterFileFilter`s get the affordance — default segments (all/doorKnocking/texting/…) never do. Backend delete is org-scoped (`deleteByIdAndOrganizationSlug` → `where: { id, organizationSlug }`), so a user can't delete another org's list.
- **Whole-page CRM gate** (ENG-10683): `[[...attr]]/page.tsx` renders `crm/ContactsPageGate` inside the provider. When `useCrmEnabled()` (app/dashboard/shared) reads `ready && enabled`, the user gets ONLY `crm/CrmContactsPage` — universe title ("Your Voter Universe" / "Your Constituent Universe" via `contactsLabels.ts`), the `ContactTypeahead`, "Create new list", and `PersonOverlay`. Flag off or unsettled renders the old `ContactsPage` exactly as it was pre-CRM (always `ContactSearch`; the ENG-10687 in-page typeahead swap is gone). The gate is the one treatment/control divergence point, so the experiment exposure fires there (`useCrmEnabled(true)`). `Contacts - Contacts Viewed` fires from both pages since ENG-10767 — the CRM page's fire carries `surface: 'crm'` (absent = legacy page).
- **Lovable pixel parity** (ENG-10725, third and definitive parity round; supersedes ENG-10721’s presentation pass): the whole flag-on page lays out in ONE centered left-aligned 560px column (18px h1 + district-location subtitle + full-width bordered `DistrictStatCard` row + lists index). `crm/wizard/CreateListWizard.tsx` and `crm/lists/ListDetailSheet.tsx` both render in `crm/shared/CrmSheet.tsx` — a full-width vaul bottom drawer covering everything except the top 64px (`h-[calc(100dvh-4rem)]`, rounded-t-[10px], drag handle, 40x40 close, Back pinned to the sheet’s own top-left, 560px content column, 608px footer). Each dropdown's `onValueChange` PATCHes `/v1/contacts/:personId/status` (`{ field: 'voter_likelihood' | 'support_status', value }`), optimistically writing the `['person', orgSlug, personId]` query (the same key `ContactsTableProvider`'s `personQuery` uses) before the request settles, then invalidating `['contact-engagement', 'activities']` on success. **Every cache write (optimistic, rollback, and success-merge) is scoped to the single field the mutation owns** — never the whole `Person` object / whole `ContactStatuses` response. The two dropdowns can be changed in quick succession while the first PATCH is still in flight; a whole-object snapshot/restore or whole-response merge would silently clobber whichever field the other, faster-resolving mutation had already committed (caught in review — a mocked hang-then-reject repro). The rollback target and the analytics `from` are both `context.fromValue`, captured from the component's own prop-derived value at click time (not re-read from the cache), so a failed PATCH shows an error snackbar and reverts only its own field. Fires `Voter Data - Contact Status Changed` (`{ field, from, to }`) once per confirmed-successful change; no ConstituentData variant (Win-only surface). A reselect of the already-current value is a no-op (no PATCH, no event). Both `SelectContent`s carry `className="z-[1400]"`: `PersonOverlay`'s `SheetContent` sits at `z-[1301]` while the styleguide select's portaled popper defaults to `z-50`, so without the override the open menu paints invisibly BEHIND the sheet (and the next click reads as an outside-interaction that closes the panel). Any popover-style primitive added inside this sheet needs the same treatment.

Submit opens a right-side drawer that streams through the shared `app/dashboard/shared/agent-chat/` stack (`useStreamingTurn` + `chatUI`). **No new ChatScope**: Win rides `campaign_assistant` (the Campaign Manager scope — its handler resumes the latest conversation on create, so a "new" chat may open with prior manager history), Serve rides `chief_of_staff`; `assistantChat.ts` reuses each scope's canonical client + history key so conversation caches stay consistent with those surfaces. When a `crud_saved_filters` `tool_result` arrives in the stream, the drawer invalidates `['custom-segments', orgSlug]` + `['list-detail', orgSlug]` so the lists index refreshes without a reload. The bar renders only once `isWinContextReady` (scope must not bind on the unsettled Serve-default mode). Drawer heading comes from `contactsLabels.ts` (`assistantTitle`). E2E smoke (`e2e-tests/tests/app/contacts/crm-assistant-bar.spec.ts`) forces the flags via the override cookie and stubs the whole chat round trip — never a live LLM turn.

## Gotchas

- Optional catch-all route (`[[...attr]]`) means `/dashboard/contacts` and `/dashboard/contacts/whatever` both render the same page — sub-routing is internal. `/dashboard/contacts/lists/<id>` is also served by the catch-all (ENG-10725 removed the literal `lists/[listId]` route); the provider’s `extractPersonIdFromPathname` explicitly returns null for the `lists` segment so it can never be fetched as a person id, and `extractListIdFromPathname` only matches exactly `lists/<id>`.
- Voter-file payloads can be huge — pagination + cursor are mandatory; never request without them.
- A feature flag gates parts of `PersonOverlay` (see `app/shared/experiments/`).
- This route is shared by Serve (elected office) and Win campaigns, and is the default Win experience (the `win-voter-data` flag and the legacy `/dashboard/voter-records` page were removed after the rollout hit 100%): the nav entry is added in `DashboardMenu.tsx` (`WIN_CONTACTS_MENU_ITEM`, `campaign` category) for every Win campaign, pro and non-pro. Pro gating is per-action, not page-level (ENG-10495): a non-pro Win candidate sees the real district aggregates and a blurred preview, and the Pro upgrade modal fires when they search, pick a non-default segment, open a person, or download. Backend mirrors this — `findContacts` rejects search/named-segment requests, `findPerson` rejects person-detail reads, and `downloadContacts` rejects downloads for non-pro, but the base list + `GET /v1/contacts/stats` are open to non-pro. **The base-list preview is synthetic, not real voter data (ENG-10508):** for a non-pro requester `findContacts` returns fabricated rows from `previewContacts.utils.ts` and never fetches real people rows — a frontend blur is not a real boundary (the values are copy-pastable), and our data contracts forbid sending real voter PII to non-pro users. It still reads the aggregate district stats to set the preview's `pagination.totalResults` to the real count, because the unblurred "Total Voters" stat card derives from `totalResults` (`stats.util.ts`) — so the number a non-pro user sees doesn't regress, while every row stays fake. The frontend blur on those rows is now just an upsell cue over fake data, and it covers every column (name/gender/age included) so a copy/paste test can't mistake the fabricated rows for readable real data. A Win campaign with no resolvable district gets a `400 { errorCode: 'VOTER_DATA_UNAVAILABLE' }`, which `ContactsTableProvider` surfaces as `isVoterDataUnavailable` so `ContactsPage` renders a clean ineligible state instead of an error.
- **Naming is Win-vs-Serve and must never cross over** (ENG-10448): Win reads "Voter Data" / "voters"; Serve reads "Constituent Data" / "constituents". Win must never say "constituent". The strings live in one place — `app/dashboard/shared/contactsLabels.ts` (`CONTACTS_DATA_TITLE` + `getContactsLabels(isWinContext)`) — consumed by the page heading/subheading (`ContactsPage`), stat labels (`ContactsStatsSection`), the sidebar items (`DashboardMenu`), and the mobile title (`DashboardLayout`). Add new user-facing copy through that helper, not as a local literal, so the surfaces can't drift.

## Analytics

Events live under the `Contacts` group in `helpers/analyticsHelper.ts` and fire frontend (screen views and user clicks the browser directly observes). Every event carries a `context: 'win' | 'serve'` property sourced from the provider's `isWinContext` — so Win adoption of the unified path is a property filter in Amplitude, not a duplicate event set. Don't mint per-context events.

- `Contacts - Contacts Viewed` — fires once on page entry, from BOTH pages since ENG-10767: the legacy `ContactsPage` with `context` only, and `CrmContactsPage` with `context` + `surface: 'crm'` (same ready-gate + ref latch on both).
- `Contacts - Outreach Timeline Viewed` — Win-only; fires when the Win outreach timeline renders rows in `PersonOverlay` (`context: 'win'`, `personId`). Not fired for an empty feed or the Serve poll-interaction timeline.
- `Contacts - Download` / `Segment Viewed` / `Segment Created` / `Segment Updated` / `Segment Deleted` — existing events, now carrying `context`.
- `Voter Data - Contact Searched` (Win) / `Constituent Data - Contact Searched` (Serve) — the one deliberate exception to the context-property rule: the CRM brief specs the typeahead search events as product-specific by nav surface, each with `resultCount`. They fire once per distinct resolved search from the `settled` derivation in `useContactTypeaheadSearch` (ENG-10688) — never on aborted/superseded requests, sub-3-char input, or the non-pro modal path; an empty result set fires with `resultCount: 0`. Mode comes from `useWinVoterContext()`, gated on `isReady` like the mount event.
- `Voter Data - Note Added` (Win) / `Constituent Data - Note Added` (Serve) — same product-specific naming exception, no properties. Fires from `NotesSection` exactly once per successful create (never on edit, delete, or a failed create). Mode comes from `useWinVoterContext()`, gated on `isReady`.
- `Voter Data - Contact Status Changed` (ENG-10836) — Win-only (no Serve variant: the status row only renders for Win). Fires from `StatusRow` once per confirmed-successful PATCH `/v1/contacts/:personId/status`, `{ field: 'voter_likelihood' | 'support_status', from, to }`. Never fires on a failed PATCH or a reselect of the already-current value.
- `Voter Data - Contact Viewed` (Win) / `Constituent Data - Contact Viewed` (Serve) — same naming exception, no properties. Fires from `PersonContent` once per record open, gated on `useCrmEnabled()` and `useWinVoterContext().isReady` (a person remount via `key={person.id}` re-arms the latch). Distinct from `Contacts - Contacts Viewed`, which only fires from the pre-CRM page.
- `Voter Data - List Created` (Win) / `Constituent Data - List Created` (Serve) — same naming exception (ENG-10709). Fires from `crm/wizard/CreateListWizard.tsx`'s create-mutation `onSuccess`, once per successful create, only for the voter-file branch. `{ variableCount, hasParty }` — `variableCount` is the number of `filters.config.ts` categories with a selection (`crm/shared/voterFileFilterTransform.util.ts`'s `countSelectedFilterCategories`; a Support Status selection counts as one more category). `hasParty` (via that file's `hasPartyFilterSelection`) is Win-only — Serve never renders the Political Party section (`VoterFileStep` strips it for `isElectedOfficial`), so the property is omitted as a key entirely for Serve, never sent as `false`.
- `Voter Data - Activity List Created` (Win) / `Constituent Data - Activity List Created` (Serve) — same seam, fires only for the activity branch. `{ sourceCampaign, actionFilter }` — the wizard supports N stacked conditions (`crm/wizard/ActivityStep.tsx`), so both properties aggregate across all of them: `sourceCampaign` joins each condition's resolved outreach name (or `'any'`) with `', '`; `actionFilter` is the deduped union of every condition's selected outcome values, as an array (not a HubSpot-email-driving event, so no flatten-to-scalar requirement). `WizardActivityCondition` carries an `outreachName` field (resolved at selection time, never sent to the backend) purely so this handler doesn't need a second outreaches fetch.
- `Voter Data - List Exported` (Win) / `Constituent Data - List Exported` (Serve) — same naming exception, `{ listSize }` (the people count already shown on the list-detail page). Fires from `crm/lists/ListDetailPage.tsx`'s Download button via a new optional third argument to `crm/shared/useContactsDownload.ts`'s `download()` — invoked only from the cookie-poll **success** branch, never the ambiguous 15s-fallback branch or a failed download, and never if the demographics count isn't known yet at confirm time. The legacy (pre-CRM) `Download.tsx` caller omits the argument, so it never emits this CRM-only event.

ENG-10767 closed the remaining CRM gaps (all ready-gated on `isWinContextReady` like the events above):

- `Contacts - Segment Viewed` — also fires from `ListDetailSheet` on every sheet open once the segment resolves (`{ segment, type: 'custom', context }`), restoring the legacy segment-picker parity for "which lists get used".
- `Contacts - Segment Deleted` / `Segment Updated` / `Segment Created` — the CRM management surfaces reuse the legacy events: `DeleteListDialog` fires Deleted (`{ context }`), `RenameListDialog` fires Updated with `{ action: 'rename', context }` (no `filters` prop — distinguishes it from legacy filter edits), and `useDuplicateList` fires Created with `{ source: 'duplicate', context }` (the wizard's product-specific List Created events stay a pure wizard-outcome metric).
- `Contacts - List Wizard Method/Conditions/Name Viewed/Completed` — per-stage funnel for the URL-stable create-list wizard (`{ context }`, + `{ branch }` on conditions/name). Viewed re-fires on Back re-entry (effect keyed on the open session + active-stage identifier only); Name Completed fires alongside the List Created outcome on a successful create. Serve's 2-step wizard never fires the Method stage.
- `Contacts - Assistant Chat Opened` / `Assistant Message Sent` — `CrmAssistant` fires Opened per drawer open (`{ context, source: 'message' | 'history' }`) and Message Sent per user send (`{ context }`): the bar submit (which opens WITH a message) and every composer follow-up via `AssistantDrawer`'s `onMessageSent` callback.
- `Voter Data - Send Outreach Clicked` — the CRM list → outreach funnel entry, fired from all three "Send outreach" surfaces with `{ surface: 'listCard' | 'listDetail' | 'universeRow' }` + `{ listId }` on the two saved-list surfaces. Win-only by construction (ENG-10749), so no ConstituentData variant. It joins to the outreach wizard: `AudienceStep` reports `audienceSource: 'savedList' | 'deepLink' | 'customFilters'` (+ `audienceListId`) on advance, and `TaskFlow` carries it onto the audience-step `Schedule Text Campaign: Next` event (as `audienceSource`/`listId`) and both `Voter Outreach - Campaign Completed` call sites — so a campaign completed after a CRM "Send outreach" click is attributable end to end.

Source the `context` from `isWinContext` (single source of truth in `ContactsTableProvider`) — don't recompute Win-vs-Serve. New events: follow `.claude/skills/instrument-analytics-event/SKILL.md`.
