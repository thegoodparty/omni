# app/dashboard/contacts/

Voter contact management. Browse the campaign's voter file, segment audiences, and drill into individual voter records. Powers audience selection for outreach.

This is the **unified, People-API-backed** voter experience shared by Serve (elected office) and Win (campaign). All contacts data — list, counts, downloads, saved segments, per-person detail, the outreach timeline — is served by people-api through gp-api (`GET /v1/contacts`, the voter-file filter endpoints, and the contact-engagement endpoints). There is no raw-SQL voter path behind this route. This is the home for what the legacy `dashboard/voter-records/` page used to serve; that page was deleted after the rollout hit 100% (its route now redirects here), and all Win voter work goes here. See `docs/architecture.md` (voter/people data path).

**crm/ folder convention:** every new CRM surface goes in `crm/`, never mixed into
`[[...attr]]/components/`. Code shared by both UIs (the provider, `ContactProModal`,
`person/`, `shared/` types/fixtures, `configs/defaultSegments.config.ts`) lives in
`crm/` and the old code imports it from there — so deleting `[[...attr]]/components/`
at full ramp cannot break the CRM page (only `ContactsPageGate`'s old-page branch
needs collapsing).

## Patterns

- **One catch-all route** (`[[...attr]]`) — all "tabs" (people, segments, settings) are handled inside that route's components, not as separate Next.js routes. Easier to share filter state.
- **Filters and segments are distinct**: filters are ephemeral (current view); segments are saved (named, reused in outreach). Don't conflate.
- **A saved list can also carry a free-text search** (ENG-10518). When "Create list" opens with an active search (the `query` URL param), `FiltersSheet` saves that term on the `VoterFileFilter.search` column with no filter required, and `selectSegment` (in `ContactsTableProvider`) re-applies it to the `query` param when the list is selected — so the saved view reproduces the searched-down set. A live request search always wins over a list's stored search server-side (gp-api `findContacts`). Download does not re-apply stored search (people-api `/download` has no search param).
- **Live segment-builder count** (ENG-10517): while `FiltersSheet` is open, it shows a running "N voters match" for the in-progress (unsaved) filter set, fetched from `POST /v1/contacts/count`. That endpoint runs the same `convertVoterFileFilterToFilters` translation a saved segment would, then queries people-api with `resultsPerPage: 1` and returns only `pagination.totalResults` — no real rows are loaded. The webapp debounces the payload (~600ms, mirroring the search box) and keys a React Query on `['contacts-count', orgSlug, debouncedPayload]` (org-scoped per ENG-10511); `enabled` reads the _debounced_ payload's criteria so a request never fires with a payload that lags its own gate. The count is pro-gated like search/named segments (a non-pro requester only ever sees the base-list preview). The count honors any active create-mode search (ENG-10518), so the number matches the list it would save. It's a display affordance only — it does not change how segments are saved or how the main table counts.
- **Deleting a list** (ENG-10520) is handled by `DeleteSegment.tsx` (a styleguide `AlertDialog` confirmation that calls `DELETE /v1/voters/voter-file/filter/:id`, then `refreshCustomSegments`). It renders in two places off the same component: the bottom of the edit `FiltersSheet`, and a per-row trash `IconButton` next to each custom list in the `SegmentSection` dropdown (via the optional `trigger` prop). The per-row trigger stops pointer/click propagation so it doesn't select the Radix `SelectItem`. `afterDeleteCallback(deletedId)` lets the caller decide fallback: `SegmentSection` resets to `ALL_SEGMENTS` only when the deleted list is the active one; `FiltersSheet` always closes + resets. Only custom `VoterFileFilter`s get the affordance — default segments (all/doorKnocking/texting/…) never do. Backend delete is org-scoped (`deleteByIdAndOrganizationSlug` → `where: { id, organizationSlug }`), so a user can't delete another org's list.
- **Whole-page CRM gate** (ENG-10683): `[[...attr]]/page.tsx` renders `crm/ContactsPageGate` inside the provider. When `useCrmEnabled()` (app/dashboard/shared) reads `ready && enabled`, the user gets ONLY `crm/CrmContactsPage` — universe title ("Your Voter Universe" / "Your Constituent Universe" via `contactsLabels.ts`), the `ContactTypeahead`, "Create new list", and `PersonOverlay`. Flag off or unsettled renders the old `ContactsPage` exactly as it was pre-CRM (always `ContactSearch`; the ENG-10687 in-page typeahead swap is gone). The gate is the one treatment/control divergence point, so the experiment exposure fires there (`useCrmEnabled(true)`). `Contacts - Contacts Viewed` fires from both pages since ENG-10767 — the CRM page's fire carries `surface: 'crm'` (absent = legacy page).
- **Lovable pixel parity** (ENG-10725, third and definitive parity round; supersedes ENG-10721’s presentation pass): the whole flag-on page lays out in ONE centered left-aligned 560px column (18px h1 + district-location subtitle + full-width bordered `DistrictStatCard` row + lists index). `crm/wizard/CreateListWizard.tsx` and `crm/lists/ListDetailSheet.tsx` both render in `crm/shared/CrmSheet.tsx` — a full-width vaul bottom drawer covering everything except the top 64px (`h-[calc(100dvh-4rem)]`, rounded-t-[10px], drag handle, 40x40 close, Back pinned to the sheet’s own top-left, 560px content column, 608px footer). Step 2 shares one heading for both branches ("Build a voter/constituent list"). The footer CTA is step-keyed: "Continue" → "Build your list (N)" (truly disabled while nothing is selected — ENG-10751 reversed the earlier muted-but-clickable empty-selection submit; the count still fires unfiltered so the disabled button shows the full universe total) → "Save list". Serve drops the branch chooser entirely (ENG-10750): its wizard opens on the constituent-file filters as a 2-step flow (`steps` array in `CreateListWizard.tsx` is the single Serve gate). `VoterFileStep.tsx` renders sentence-cased 12px group labels (`sentenceCase` in `crm/shared/labels.util.ts` — filters.config.ts labels stay title case because the legacy flag-off page renders them byte-identically) over `ToggleGroup` pills (`PILL_TOGGLE_ITEM_CLASSNAME` in `crm/shared/constants.ts`, shared with `ActivityStep.tsx`). `ActivityStep.tsx` is chip-rows-only: "Previous activity" channel chips (with icons), a "Campaign" chip row (Any campaign + one chip per completed outreach) replacing the old Select, and outcomes hidden behind a "Filter on activity" progressive reveal (trash clears + re-hides); the per-condition trash is disabled (not hidden) when only one condition exists; "Add condition" is centered. `ListsIndex.tsx` renders full-width row cards (title 16/600 + kebab, 13px status line, small person-icon count bottom-left, ghost "Details" + small filled "Send outreach" bottom-right — the outreach button is Win-only since ENG-10749) with an "All voters"/"All constituents" universe row first (count from `districtStatsQueryOptions`; no Details — `GET /v1/contacts/list-detail` requires a saved-segment id). `BranchStep.tsx`’s cards use the check-fill radio indicator + primary/5 tint + 2px primary/20 ring selected state (`RadioCardItem`’s `indicator="check"`).
- **CRM typeahead search** (ENG-10687, now `crm/ContactTypeahead.tsx`): a debounced (300ms, min 3 chars) results dropdown over the same `GET /v1/contacts` client path (`resultsPerPage: 8`), fetched standalone via `crm/useContactTypeaheadSearch` (query key `['contacts-typeahead', orgSlug, term]`, never the table's `['contacts', ...]` key or the `query` URL param); selecting a row navigates via the provider's `selectPerson`. Non-pro: focus/typing opens the Pro modal and no request fires (gp-api still rejects non-pro search). The mode-specific Contact Searched events (ENG-10688) fire from the `settled` derivation inside `useContactTypeaheadSearch` — see Analytics below.
- **Voter file fetching** uses `helpers/createVoterFileFilter.ts` to build the filter payload — keep that helper as the single shape source.
- The `PersonOverlay` is a side-panel detail view that opens over the page. Drilling in DOES put the person id in the path (`/dashboard/contacts/:personId`, deep-linkable), but via **shallow navigation**: `selectPerson` calls `window.history.pushState` (never `router.push` — the route is `force-dynamic` with a `loading.tsx`, so a router navigation blanks the whole page through the loading boundary just to open/close the overlay). The provider derives `currentlySelectedPersonId` from `usePathname()`, not `useParams()` — `useParams` does not react to native pushState.
- **Person-record notes** (ENG-10697, redesigned to the lovable prototype in ENG-10711, `crm/person/NotesSection.tsx`): the FIRST section card on the record (per the prototype), a per-person dated-notes CRUD panel mounted unconditionally in `PersonContent` but self-gated on `useCrmEnabled()` (`trackExposure=false` — it's not the treatment surface). Prototype states: collapsed shows only a full-width pill "Add a note" (no persistent textarea); clicking it opens a compose form (textarea + stacked "Save note"/"Cancel"); each note row is body → one row of muted date + pencil + red trash; edit is an in-place textarea with "Save changes"/"Cancel". Delete keeps the confirm `AlertDialog` (deliberate deviation — the prototype hard-deletes with no confirm). `InfoSection` carries the prototype's header-divider card shell for every section. Backed by the four `contacts/:personId/notes` / `contacts/notes/:noteId` routes from ENG-10693. React Query key `['contact-notes', orgSlug, personId]`; the API returns notes newest-first already (`ContactNoteService.listForPerson` orders by `createdAt desc`), so the frontend never re-sorts. Every write (create/edit/delete) invalidates that key plus a partial match on `['contact-engagement', 'activities']` so notes surface in the outreach/poll feed once ENG-10695 lands. Delete uses the `DeleteSegment.tsx` destructive-confirm (`AlertDialog`) pattern. The `InfoSection` card wrapper was extracted from `PersonOverlay.tsx` into its own `crm/person/InfoSection.tsx` so both files can share it without a circular import.
- **New feed entry types + support status** (ENG-10698): `crm/person/ActivityFeedEntry.tsx` renders the DOOR_KNOCK/TEXT/ROBOCALL/NOTE rows ENG-10695 added to the feed (manual badge when hand-logged, outcome/support-answer/timestamp framing, a link to `/dashboard/outreach` when a text/robocall row has a source `outreachId` — there's no per-outreach detail route yet, so it links to the list). There is NO manual interaction-logging UI (removed in ENG-10711 to match the prototype — interaction rows come from outreach flows); `POST /v1/contacts/:personId/interactions` still exists API-side with no webapp caller. `formatDateTime` lives there too (not in `PersonOverlay.tsx`) so `PersonOverlay` can import it without a circular dependency. Rendering these types (and counting them toward the feed's empty-state/pagination logic) is gated on `useCrmEnabled()` inside `ActivitiesContent` — CRM-off keeps the exact pre-CRM behavior of skipping them (the interim ENG-10695 comment trail). The Win-only `Contacts - Outreach Timeline Viewed` event stays scoped to legacy `OUTREACH` rows specifically (a separate `hasOutreachRows` check), so the CRM-widened entry types can't inflate that pre-existing adoption metric. `person.supportStatus` (ENG-10696) renders read-only as a `Field` inside the "Voter Demographics" `InfoSection`, also gated on `useCrmEnabled()`; there's no edit affordance since status is derived server-side.
- **Opted In/Out header chip** (ENG-10732): `PersonOverlay.tsx`'s `OptedInChip` renders next to the person's name, gated on `useCrmEnabled()` and `!hidePoliticalParty` (the same Serve/`isElectedOfficial` signal the political-party field already uses — reused rather than threading a second prop). Reads `person.optedOutAt` (ISO timestamp or null, gp-api `ContactInteractionTextService.latestOptOutAt`, org-scoped max across the org's text interactions) — `success`/`destructive` outline `Badge` pill, "Opted Out" when set else "Opted In". Deliberately suppressed for Serve: elected-office orgs have no texting and therefore no real opt-out data, so a permanently-green chip would be misleading (flagged product decision, not a bug — flip is a one-line change if product wants it always-on). Independent of `supportStatus`: an opted-out person can still be a supporter.
- **Lists index + list-detail sheet** (ENG-10707/10725, `crm/lists/`): `ListsIndex` (rendered inside `CrmContactsPage`; full-width row cards as of ENG-10725, formerly a grid/table) reads `customSegments` from the provider. There’s no bulk "count + last outreach" endpoint, so each row calls `GET /v1/contacts/list-detail` once (`useListRowDetail`) for a refreshed people count and `outreachHistory[0]` — an accepted N+1 for a small number of saved lists per org. The row’s "Details" button opens `ListDetailSheet` via the provider’s `selectList` — a SHALLOW `window.history.pushState` to `/dashboard/contacts/lists/:listId` (same pattern and rationale as `selectPerson`); the URL stays deep-linkable because the catch-all route serves that path and `CrmContactsPage` derives `currentlySelectedListId` from `usePathname()`. "Send outreach" links to `/dashboard/outreach` and is Win-only (ENG-10749, reversing the earlier build-Serve-as-if-it-has-outreach stance): Serve outreach is deferred and that route dead-ends for an eo- org, so the index row, list cards, and the detail-sheet footer all hide it unless `isWinContextReady && isWinContext`. The sheet renders four sections — filter summary (`ListFilterSummary`, a pure sentence builder off the segment’s demographic booleans + `activityConditions` + `supportStatus`, reusing `filters.config.ts` / `activityConditionOptions.tsx`’s label maps, joined as one comma-and sentence), demographics tiles (People / Avg age (rounded to an integer) / Avg income / Last outreach / Last method — `SectionLabel` (primary-colored uppercase micro-label) / `StatTile` (bordered card, leading icon) in `crm/lists/ListDetailSection.tsx`, under a mode-aware "Voter/Constituent list details" heading from `contactsLabels.ts`), reachable-by-channel (`ReachabilityGrid` — `email`/`metaAds` are always `null` server-side and render "Unavailable", never 0), and an outreach-history table (Date/Name/Channel — no Attempts/Open% column: no per-outreach metric exists in the list-detail contract) — **never** a member table; Download (44px icon button) + "Send outreach" are pinned to the sheet footer. `firstUsedForOutreachAt` set means gp-api’s `assertNotLocked` 409s both `PUT` and `DELETE`; both the row’s kebab menu and the sheet header swap the rename action for "Duplicate to edit" and hide Delete once locked, and treat a raced 409 (locked between load and the mutation) the same way — a neutral message, not an error toast — via the shared `RenameListDialog`/`DeleteListDialog` (delete leaves the sheet via `selectList(null)`, also shallow). `useDuplicateList` reposts the segment’s own criteria as a new create call (name suffixed `" (copy)"`, server-only fields stripped) and opens the copy’s sheet. The wizard’s (`crm/wizard/CreateListWizard.tsx`) on-create-success navigation lands here too (`selectList(response.id)`). The legacy `Download.tsx`’s cookie-poll top-level-download logic was extracted to `crm/shared/useContactsDownload.ts` so both surfaces share one implementation; `OUTREACH_CHANNEL_LABELS`/`OUTREACH_CHANNEL_ICONS` similarly moved from `PersonOverlay.tsx` to `crm/shared/outreachChannelLabels.tsx`. Flag-off users hitting `/dashboard/contacts/lists/<id>` get the legacy `ContactsPage` at that URL (the old `ListDetailPageGate` redirect is gone with the route).

- **Contacts assistant bar** (ENG-10737, `crm/assistant/`): the CRM page's persistent bottom pill ("Describe the list you want and I'll make it for you") mirrors the Chief of Staff `FooterChatBar` placement (fixed bottom, `lg:left-64`) but carries a real input and no mic (epic ships text-only). Submit opens a right-side drawer that streams through the shared `app/dashboard/shared/agent-chat/` stack (`useStreamingTurn` + `chatUI`). **No new ChatScope**: Win rides `campaign_assistant` (the Campaign Manager scope — its handler resumes the latest conversation on create, so a "new" chat may open with prior manager history), Serve rides `chief_of_staff`; `assistantChat.ts` reuses each scope's canonical client + history key so conversation caches stay consistent with those surfaces. When a `crud_saved_filters` `tool_result` arrives in the stream, the drawer invalidates `['custom-segments', orgSlug]` + `['list-detail', orgSlug]` so the lists index refreshes without a reload. The bar renders only once `isWinContextReady` (scope must not bind on the unsettled Serve-default mode). Drawer heading comes from `contactsLabels.ts` (`assistantTitle`). E2E smoke (`e2e-tests/tests/app/contacts/crm-assistant-bar.spec.ts`) forces the flags via the override cookie and stubs the whole chat round trip — never a live LLM turn.

## Gotchas

- Optional catch-all route (`[[...attr]]`) means `/dashboard/contacts` and `/dashboard/contacts/whatever` both render the same page — sub-routing is internal. `/dashboard/contacts/lists/<id>` is also served by the catch-all (ENG-10725 removed the literal `lists/[listId]` route); the provider’s `extractPersonIdFromPathname` explicitly returns null for the `lists` segment so it can never be fetched as a person id, and `extractListIdFromPathname` only matches exactly `lists/<id>`.
- Voter-file payloads can be huge — pagination + cursor are mandatory; never request without them.
- A feature flag gates parts of `PersonOverlay` (see `app/shared/experiments/`).
- This route is shared by Serve (elected office) and Win campaigns, and is the default Win experience (the `win-voter-data` flag and the legacy `/dashboard/voter-records` page were removed after the rollout hit 100%): the nav entry is added in `DashboardMenu.tsx` (`WIN_CONTACTS_MENU_ITEM`, `campaign` category) for every Win campaign, pro and non-pro. Pro gating is per-action, not page-level (ENG-10495): a non-pro Win candidate sees the real district aggregates and a blurred preview, and the Pro upgrade modal fires when they search, pick a non-default segment, open a person, or download. Backend mirrors this — `findContacts` rejects search/named-segment requests, `findPerson` rejects person-detail reads, and `downloadContacts` rejects downloads for non-pro, but the base list + `GET /v1/contacts/stats` are open to non-pro. **The base-list preview is synthetic, not real voter data (ENG-10508):** for a non-pro requester `findContacts` returns fabricated rows from `previewContacts.utils.ts` and never fetches real people rows — a frontend blur is not a real boundary (the values are copy-pastable), and our data contracts forbid sending real voter PII to non-pro users. It still reads the aggregate district stats to set the preview's `pagination.totalResults` to the real count, because the unblurred "Total Voters" stat card derives from `totalResults` (`stats.util.ts`) — so the number a non-pro user sees doesn't regress, while every row stays fake. The frontend blur on those rows is now just an upsell cue over fake data, and it covers every column (name/gender/age included) so a copy/paste test can't mistake the fabricated rows for readable real data. A Win campaign with no resolvable district gets a `400 { errorCode: 'VOTER_DATA_UNAVAILABLE' }`, which `ContactsTableProvider` surfaces as `isVoterDataUnavailable` so `ContactsPage` renders a clean ineligible state instead of an error.
- **Naming is Win-vs-Serve and must never cross over** (ENG-10448): Win reads "Voter Data" / "voters"; Serve reads "Constituent Data" / "constituents". Win must never say "constituent". The strings live in one place — `app/dashboard/shared/contactsLabels.ts` (`CONTACTS_DATA_TITLE` + `getContactsLabels(isWinContext)`) — consumed by the page heading/subheading (`ContactsPage`), stat labels (`ContactsStatsSection`), the sidebar items (`DashboardMenu`), and the mobile title (`DashboardLayout`). Add new user-facing copy through that helper, not as a local literal, so the surfaces can't drift.

## Analytics

Events live under the `Contacts` group in `helpers/analyticsHelper.ts` and fire frontend (screen views and user clicks the browser directly observes). Every event carries a `context: 'win' | 'serve'` property sourced from the provider's `isWinContext` — so Win adoption of the unified path is a property filter in Amplitude, not a duplicate event set. Don't mint per-context events.

- `Contacts - Contacts Viewed` — fires once on page entry, from BOTH pages since ENG-10767: the legacy `ContactsPage` with `context` only, and `CrmContactsPage` with `context` + `surface: 'crm'` (same ready-gate + ref latch on both).
- `Contacts - Outreach Timeline Viewed` — Win-only; fires when the Win outreach timeline renders rows in `PersonOverlay` (`context: 'win'`, `personId`). Not fired for an empty feed or the Serve poll-interaction timeline.
- `Contacts - Download` / `Segment Viewed` / `Segment Created` / `Segment Updated` / `Segment Deleted` — existing events, now carrying `context`.
- `Voter Data - Contact Searched` (Win) / `Constituent Data - Contact Searched` (Serve) — the one deliberate exception to the context-property rule: the CRM brief specs the typeahead search events as product-specific by nav surface, each with `resultCount`. They fire once per distinct resolved search from the `settled` derivation in `useContactTypeaheadSearch` (ENG-10688) — never on aborted/superseded requests, sub-3-char input, or the non-pro modal path; an empty result set fires with `resultCount: 0`. Mode comes from `useWinVoterContext()`, gated on `isReady` like the mount event.
- `Voter Data - Note Added` (Win) / `Constituent Data - Note Added` (Serve) — same product-specific naming exception, no properties. Fires from `NotesSection` exactly once per successful create (never on edit, delete, or a failed create). Mode comes from `useWinVoterContext()`, gated on `isReady`.
- `Voter Data - Contact Viewed` (Win) / `Constituent Data - Contact Viewed` (Serve) — same naming exception, no properties. Fires from `PersonContent` once per record open, gated on `useCrmEnabled()` and `useWinVoterContext().isReady` (a person remount via `key={person.id}` re-arms the latch). Distinct from `Contacts - Contacts Viewed`, which only fires from the pre-CRM page.
- `Voter Data - List Created` (Win) / `Constituent Data - List Created` (Serve) — same naming exception (ENG-10709). Fires from `crm/wizard/CreateListWizard.tsx`'s create-mutation `onSuccess`, once per successful create, only for the voter-file branch. `{ variableCount, hasParty }` — `variableCount` is the number of `filters.config.ts` categories with a selection (`crm/shared/voterFileFilterTransform.util.ts`'s `countSelectedFilterCategories`; a Support Status selection counts as one more category). `hasParty` (via that file's `hasPartyFilterSelection`) is Win-only — Serve never renders the Political Party section (`VoterFileStep` strips it for `isElectedOfficial`), so the property is omitted as a key entirely for Serve, never sent as `false`.
- `Voter Data - Activity List Created` (Win) / `Constituent Data - Activity List Created` (Serve) — same seam, fires only for the activity branch. `{ sourceCampaign, actionFilter }` — the wizard supports N stacked conditions (`crm/wizard/ActivityStep.tsx`), so both properties aggregate across all of them: `sourceCampaign` joins each condition's resolved outreach name (or `'any'`) with `', '`; `actionFilter` is the deduped union of every condition's selected outcome values, as an array (not a HubSpot-email-driving event, so no flatten-to-scalar requirement). `WizardActivityCondition` carries an `outreachName` field (resolved at selection time, never sent to the backend) purely so this handler doesn't need a second outreaches fetch.
- `Voter Data - List Exported` (Win) / `Constituent Data - List Exported` (Serve) — same naming exception, `{ listSize }` (the people count already shown on the list-detail page). Fires from `crm/lists/ListDetailPage.tsx`'s Download button via a new optional third argument to `crm/shared/useContactsDownload.ts`'s `download()` — invoked only from the cookie-poll **success** branch, never the ambiguous 15s-fallback branch or a failed download, and never if the demographics count isn't known yet at confirm time. The legacy (pre-CRM) `Download.tsx` caller omits the argument, so it never emits this CRM-only event.

ENG-10767 closed the remaining CRM gaps (all ready-gated on `isWinContextReady` like the events above):

- `Contacts - Segment Viewed` — also fires from `ListDetailSheet` on every sheet open once the segment resolves (`{ segment, type: 'custom', context }`), restoring the legacy segment-picker parity for "which lists get used".
- `Contacts - Segment Deleted` / `Segment Updated` / `Segment Created` — the CRM management surfaces reuse the legacy events: `DeleteListDialog` fires Deleted (`{ context }`), `RenameListDialog` fires Updated with `{ action: 'rename', context }` (no `filters` prop — distinguishes it from legacy filter edits), and `useDuplicateList` fires Created with `{ source: 'duplicate', context }` (the wizard's product-specific List Created events stay a pure wizard-outcome metric).
- `Contacts - List Wizard Method/Conditions/Name Viewed/Completed` — per-stage funnel for the URL-stable create-list wizard (`{ context }`, + `{ branch }` on conditions/name). Viewed re-fires on Back re-entry (effect keyed on the open session + active-stage identifier only); Name Completed fires alongside the List Created outcome on a successful create. - `Contacts - Assistant Chat Opened` / `Assistant Message Sent` — `CrmAssistant` fires Opened per drawer open (`{ context, source: 'message' | 'history' }`) and Message Sent per user send (`{ context }`): the bar submit (which opens WITH a message) and every composer follow-up via `AssistantDrawer`'s `onMessageSent` callback.

Win-only by construction (ENG-10749), so no ConstituentData variant.
