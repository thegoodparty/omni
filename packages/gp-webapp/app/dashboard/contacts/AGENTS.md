# app/dashboard/contacts/

Voter contact management. Browse the campaign's voter file, segment audiences, and drill into individual voter records. Powers audience selection for outreach.

This is the **unified, people-db-backed** voter experience shared by Serve (elected office) and Win (campaign). All contacts data — list, counts, downloads, saved segments, per-person detail, the outreach timeline — is served from people-db through gp-api (`GET /v1/contacts`, the voter-file filter endpoints, and the contact-engagement endpoints). There is no raw-SQL voter path behind this route. All Win voter work goes here. See `docs/architecture.md` (voter/people data path).

## Patterns

- **One catch-all route** (`[[...attr]]`) — all "tabs" (people, segments, settings) are handled inside that route's components, not as separate Next.js routes. Easier to share filter state.
- **Filters and segments are distinct**: filters are ephemeral (current view); segments are saved (named, reused in outreach). Don't conflate.
- **A saved list can also carry a free-text search** (ENG-10518). `selectSegment` (in `ContactsTableProvider`) re-applies a list's stored search to the `query` URL param when the list is selected, so the saved view reproduces the searched-down set it was created from. A live request search always wins over a list's stored search server-side (gp-api `findContacts`). Download does not re-apply stored search (the people-db download path has no search param).
- **Live wizard count** (ENG-10517, `crm/wizard/useListWizardCount.ts`): the wizard's footer CTA shows a running count for the in-progress (unsaved) filter set, fetched from `POST /v1/contacts/count`. That endpoint runs the same `convertVoterFileFilterToFilters` translation a saved segment would, then queries people-db with `resultsPerPage: 1` and returns only `pagination.totalResults` — no real rows are loaded. The webapp debounces the payload (~600ms) and keys a React Query on `['list-wizard-count', orgSlug, debouncedPayload]` (org-scoped); `enabled` reads the _debounced_ payload's criteria so a request never fires with a payload that lags its own gate. The count is pro-gated like search/named segments (a non-pro requester only ever sees the base-list preview). It's a display affordance only — it does not change how segments are saved or how the wizard counts on save.
- **Saved-list overlap strip** (ENG-10840, `crm/wizard/OverlapBar.tsx`): once any pill is selected on the wizard's conditions step and the org has ≥1 saved list, a full-bleed gray band (`border-y border-border bg-muted`, `CrmSheet`'s `banner` slot between body and footer — the 608px footer column would otherwise constrain it) renders above the CTA — "N (P%) voters already exist in lists you've saved." in text-xs muted with the count bold (`font-semibold text-foreground`), inner text aligned to the 608px footer column. The copy after the count lives in template literals, not JSXText: SWC/Turbopack drops the leading space of a text node following an expression (vite/jsdom keeps it), which shipped as "votersalready" while the unit test passed. Backed by `POST /v1/contacts/overlap-count` (same in-progress payload/Pro gate as `count`; gp-api resolves the org's saved `VoterFileFilter`s — capped at the 25 most recent, truncation logged — and unions them server-side against the current selection, so activity-based saved lists participate via their resolved person-id sets). `crm/wizard/useListWizardOverlapCount.ts` mirrors the ENG-10517 count hook exactly (600ms debounce, its own `['contacts-overlap', orgSlug, debouncedPayload]` query key). Percent is computed client-side (`overlapCount / count`, the wizard's own live count) and suppressed only when the live count is zero; any error or an unsettled/zero live count just hides the strip, never blocking the CTA.
- **Lovable pixel parity** (ENG-10725, third and definitive parity round; supersedes ENG-10721’s presentation pass): the whole page lays out in ONE centered left-aligned 560px column (18px h1 + district-location subtitle + full-width bordered `DistrictStatCard` row + lists index). `crm/wizard/CreateListWizard.tsx` and `crm/lists/ListDetailSheet.tsx` both render in `crm/shared/CrmSheet.tsx` — a full-width vaul bottom drawer covering everything except the top 64px (`h-[calc(100dvh-4rem)]`, rounded-t-[10px], drag handle, 40x40 close, Back pinned to the sheet’s own top-left, 560px content column, 608px footer). Step 2 shares one heading for both branches ("Build a voter/constituent list"). The footer CTA is step-keyed: "Continue" → "Build your list (N)" (truly disabled while nothing is selected — ENG-10751 reversed the earlier muted-but-clickable empty-selection submit; the count still fires unfiltered so the disabled button shows the full universe total) → "Save list". ENG-10781 added a second disable condition: a valid selection that resolves to a SETTLED zero (`!isLoading && !isStale && !isError && count === 0` in `CreateListWizard.tsx`) also disables the CTA and blocks `handleNext`; an errored count is unknown, not zero. While the count is unsettled (`isCounting = isLoading || isStale || count === undefined`) the CTA additionally shows the styleguide Button `loading` state — spinner + "Build your list" with no number, disabled — reversing ENG-10781's enabled-while-loading stance per product feedback. Serve drops the branch chooser entirely (ENG-10750): its wizard opens on the constituent-file filters, and gains a boundary step between them and the name, so both products run three steps by different routes (`steps` array in `CreateListWizard.tsx` is the single Serve gate for both differences). `VoterFileStep.tsx` renders sentence-cased 12px group labels (`sentenceCase` in `crm/shared/labels.util.ts` — filters.config.ts labels stay title case because door-knocking's `TurfDetailsSheet.tsx` renders them byte-identically) over `ToggleGroup` pills (`PILL_TOGGLE_ITEM_CLASSNAME` in `crm/shared/constants.ts`, shared with `ActivityStep.tsx`). Every multi-option group header (including the hardcoded Support status block) carries a "Select all"/"Clear" link button (ENG-10948) that toggles the whole group via the existing `handleFieldValueChange` writer; gated on `field.options.length > 1`, so the single-option `cell_phone`/`landline` groups render no button. Since `VoterFileStep` is shared, this reaches the CRM wizard, robocall, and phone banking for free. The wizard renders the whole filter list in the Lovable prototype's order (ENG-10847, superseding ENG-10838's single-field pull-out): Prior contacts made (`CONTACTS_MADE_FIELD_KEY`, Win-only — stripped for Serve like `political_party`, ENG-10839) directly above the hardcoded Support status block, then every other `filters.config.ts` field below it via `FIELD_ORDER_BELOW_SUPPORT_STATUS` in `VoterFileStep.tsx` — Voter likelihood first, then Political party, Age, and the demographics, with the product-only fields the prototype doesn't have (Gender, Cell phone, Landline) trailing at the end; a config field missing from the order array still renders after the ordered set. Support status has no `filters.config.ts` entry, so no config reorder could express this — and `filters.config.ts` itself must stay untouched anyway because door-knocking's `TurfDetailsSheet.tsx` renders it directly too. **Three filter groups are Win-only and stripped for Serve — `political_party`, `contacts_made`, and `voter_likely`** (an elected official serves everyone in the district, so how reliably a constituent votes isn't a segmentation an office holder gets). Both `VoterFileStep.tsx` (the CRM wizard) and `ListFilterSummary.tsx`'s generic per-field summary loop (the read side — a Serve list saved before the exclusion, or one the assistant writes, must not surface the clause either) strip all three; they must move together. `ActivityStep.tsx` is chip-rows-only: "Previous activity" channel chips (with icons), a "Campaign" chip row (Any campaign + one chip per completed outreach) replacing the old Select, and outcomes hidden behind a "Filter on activity" progressive reveal (trash clears + re-hides); the per-condition trash is disabled (not hidden) when only one condition exists; "Add condition" is centered. `ListsIndex.tsx` renders full-width row cards (title 16/600 + kebab, 13px status line, small person-icon count bottom-left, ghost "Details" + small filled "Send outreach" bottom-right — the outreach button is Win-only since ENG-10749) with an "All voters"/"All constituents" universe row first (count from `districtStatsQueryOptions`; Details opens `ListDetailSheet`'s universe mode — ENG-10778 reversed the earlier "no Details on the universe row" call, since `GET /v1/contacts/list-detail` now accepts an omitted `segment`). `BranchStep.tsx`’s cards use the check-fill radio indicator + primary/5 tint + 2px primary/20 ring selected state (`RadioCardItem`’s `indicator="check"`).
- **The universe card carries two numbers for Serve** (`crm/DistrictStatCard.tsx`): a 2020-census district population row above the L2 record count. The two measure different populations — the census counts everyone who lives in the district, the L2 scan counts the voter records we hold for it — so the lower row is labelled "Records available" rather than a total of anything, and the two are never presented as the same quantity. The census figure comes from `districtPopulation` on the existing `GET /v1/contacts/stats` response (no new endpoint, no second fetch); mart coverage is partial, so it arrives `null` for some districts and the row then renders **not at all** — no "Unavailable", no zero, and no leftover `border-t` under nothing (one `showPopulationRow` boolean gates the row and that border together). **Win is unchanged**: it passes no `populationLabel`, so it gets no census row at all — a campaign is sizing an electorate, not a population.
- **CRM typeahead search** (ENG-10687, now `crm/ContactTypeahead.tsx`): a debounced (300ms, min 3 chars) results dropdown over the same `GET /v1/contacts` client path (`resultsPerPage: 8`), fetched standalone via `crm/useContactTypeaheadSearch` (query key `['contacts-typeahead', orgSlug, term]`, never the table's `['contacts', ...]` key or the `query` URL param); selecting a row navigates via the provider's `selectPerson`. Non-pro: focus/typing opens the Pro modal and no request fires (gp-api still rejects non-pro search). The mode-specific Contact Searched events (ENG-10688) fire from the `settled` derivation inside `useContactTypeaheadSearch` — see Analytics below.
- **Recommended-list filter dimensions** (`crm/shared/recommendedListFilters.config.ts`): Independent affinity, Ideology, and Phone/`hasAnyPhone`. Deliberately NOT in `filters.config.ts` — that config is rendered verbatim by door-knocking's `TurfDetailsSheet`, which must not gain these groups. `VoterFileStep` renders them only when its `showRecommendedListFilters` prop is true, which `CreateListWizard` and the outreach v2 audience step both pass; the prop defaults false so a caller that must not show them stays unchanged. **The prop is visibility only.** `voterFileFilterTransform.util.ts` merges these option keys into `ALL_FILTER_OPTION_KEYS`/`ALL_FILTER_FIELDS` unconditionally, and `ListFilterSummary`'s loop reads them unconditionally, so a list saved with them keeps round-tripping and describing itself on a surface that does not render the groups — an ungated payload key is what lets an edit clear the filter, since the transform persists an explicit boolean per key. **Affinity and ideology are Win-only** like `political_party` (gp-api 400s both for an `eo-` org), stripped in `VoterFileStep` and `ListFilterSummary` via `WIN_ONLY_RECOMMENDED_FIELD_KEYS`; `hasAnyPhone` is `both` — plain contactability, and Serve runs phone banking and robocall. That Win gate is a **permanent product rule and a separate mechanism from the visibility prop**: the prop decides whether a surface renders the groups, the gate decides who may filter on them, and both apply independently. A Serve org therefore sees only the Phone group. `hasAnyPhone` is the OR of `hasCellPhone`/`hasLandline`, which AND together, so it cannot be expressed by combining them and has to be its own option; holding it alongside either is redundant rather than contradictory (every phone option is presence-only), and `handleFieldValueChange` makes the three mutually exclusive of the "any" option — whichever side was just touched wins. gp-api keeps plain AND semantics, so a saved row carrying both still resolves. The Ideology pill reads "Progressive" but persists `ideologyLiberal`: the mart column's own value is `Liberal` and the key follows the data.
- **Voter file fetching** uses `helpers/createVoterFileFilter.ts` to build the filter payload — keep that helper as the single shape source.
- The `PersonOverlay` is a side-panel detail view that opens over the page. Drilling in DOES put the person id in the path (`/dashboard/contacts/:personId`, deep-linkable), but via **shallow navigation**: `selectPerson` calls `window.history.pushState` (never `router.push` — the route is `force-dynamic` with a `loading.tsx`, so a router navigation blanks the whole page through the loading boundary just to open/close the overlay). The provider derives `currentlySelectedPersonId` from `usePathname()`, not `useParams()` — `useParams` does not react to native pushState.
- **Person-record notes** (ENG-10697, redesigned to the lovable prototype in ENG-10711, `crm/person/NotesSection.tsx`): the FIRST section card on the record (per the prototype), a per-person dated-notes CRUD panel mounted unconditionally in `PersonContent`. Prototype states: collapsed shows only a full-width pill "Add a note" (no persistent textarea); clicking it opens a compose form (textarea + stacked "Save note"/"Cancel"); each note row is body → one row of muted date + pencil + red trash; edit is an in-place textarea with "Save changes"/"Cancel". Delete keeps the confirm `AlertDialog` (deliberate deviation — the prototype hard-deletes with no confirm). `InfoSection` carries the prototype's header-divider card shell for every section. Backed by the four `contacts/:personId/notes` / `contacts/notes/:noteId` routes from ENG-10693. React Query key `['contact-notes', orgSlug, personId]`; the API returns notes newest-first already (`ContactNoteService.listForPerson` orders by `createdAt desc`), so the frontend never re-sorts. Every write (create/edit/delete) invalidates that key only — notes were unioned into the activity feed by ENG-10695 but removed from it in ENG-10780 (they live only in this dedicated Notes section now), so the feed's `['contact-engagement', 'activities']` query no longer needs invalidating on a note write. Delete uses the same `AlertDialog` destructive-confirm pattern as `crm/lists/DeleteListDialog.tsx`. The `InfoSection` card wrapper was extracted from `PersonOverlay.tsx` into its own `crm/person/InfoSection.tsx` so both files can share it without a circular import.
- **New feed entry types + support status** (ENG-10698): `crm/person/ActivityFeedEntry.tsx` renders the DOOR_KNOCK/TEXT/ROBOCALL rows ENG-10695 added to the feed (manual badge when hand-logged, outcome/support-answer/timestamp framing, a link to `/dashboard/outreach` when a text/robocall row has a source `outreachId` — there's no per-outreach detail route yet, so it links to the list). ENG-10695 also unioned a NOTE row into the feed; ENG-10780 removed it (server-side and from the contract) since notes duplicated the dedicated Notes section — notes are never in the feed now. There is NO manual interaction-logging UI (removed in ENG-10711 to match the prototype — interaction rows come from outreach flows); `POST /v1/contacts/:personId/interactions` still exists API-side with no webapp caller. `formatDateTime` lives there too (not in `PersonOverlay.tsx`) so `PersonOverlay` can import it without a circular dependency. The Win-only `Contacts - Outreach Timeline Viewed` event stays scoped to legacy `OUTREACH` rows specifically (a separate `hasOutreachRows` check), so the CRM-widened entry types can't inflate that pre-existing adoption metric. `person.supportStatus` (ENG-10696) renders read-only as a `Field` inside the "Voter Demographics" `InfoSection` for **Serve only** since ENG-10836 (see below) — Win's copy of this Field was replaced by the status row's editable dropdown.
- **Editable status row** (ENG-10836, `crm/person/StatusRow.tsx`): a three-column row (label above value, stacks vertically below `md`) rendered directly under the name/demographics line, mounted unconditionally in `PersonContent` but self-gated on `isWinContextReady && !hidePoliticalParty` — Win only. Voter Likelihood and Support Status are editable `Select` dropdowns (color-coded trigger pill per selected value — Voter Likelihood: unknown neutral, unlikely red/`destructive`, unreliable amber/`warning`, likely blue/`info`, super green/`success`; Support Status: supporter green/`success`, non_supporter red/`destructive`, undecided/refused/unknown neutral); Opt In Status is a read-only field with no menu affordance (TCPA product decision, 2026-07-28 — a manual opt-in override on a texted STOP has no safe semantics): a `success`/`destructive` outline `Badge` ("Opted Out" when `person.optedOutAt` is set else "Opted In") sized to match the sibling `SelectTrigger`s (h-10 w-full rounded-md px-3, left-aligned) so the three fields read as one row — product feedback replaced the original small `OptedInChip`-style pill. This row **replaces** the pre-ENG-10836 Win-only read-only Support Status `Field` above and the name-adjacent `OptedInChip` (both retired); Serve's page is untouched (its Field stays read-only, it never had the chip). Each dropdown's `onValueChange` PATCHes `/v1/contacts/:personId/status` (`{ field: 'voter_likelihood' | 'support_status', value }`), optimistically writing the `['person', orgSlug, personId]` query (the same key `ContactsTableProvider`'s `personQuery` uses) before the request settles, then invalidating `['contact-engagement', 'activities']` on success. **Every cache write (optimistic, rollback, and success-merge) is scoped to the single field the mutation owns** — never the whole `Person` object / whole `ContactStatuses` response. The two dropdowns can be changed in quick succession while the first PATCH is still in flight; a whole-object snapshot/restore or whole-response merge would silently clobber whichever field the other, faster-resolving mutation had already committed (caught in review — a mocked hang-then-reject repro). The rollback target and the analytics `from` are both `context.fromValue`, captured from the component's own prop-derived value at click time (not re-read from the cache), so a failed PATCH shows an error snackbar and reverts only its own field. Fires `Voter Data - Contact Status Changed` (`{ field, from, to }`) once per confirmed-successful change; no ConstituentData variant (Win-only surface). A reselect of the already-current value is a no-op (no PATCH, no event). Both `SelectContent`s carry `className="z-[1400]"`: `PersonOverlay`'s `SheetContent` sits at `z-[1301]` while the styleguide select's portaled popper defaults to `z-50`, so without the override the open menu paints invisibly BEHIND the sheet (and the next click reads as an outside-interaction that closes the panel). Any popover-style primitive added inside this sheet needs the same treatment.
- **Serve follow-up toggle** (`crm/person/FollowUpRow.tsx`): a single "Asked for follow-up" `Switch` under the name/demographics line, mounted unconditionally in `PersonContent` and self-gated on `isServe` — the mirror of `StatusRow`'s Win gate, so Win's record is untouched. It is Serve's only editable per-contact status: the two Win dropdowns are rejected for an `eo-` org server-side, and this one is rejected for a Win org. `onCheckedChange` PATCHes `/v1/contacts/:personId/follow-up` (`{ value: 'requested' | 'cleared' }`), optimistically writing `['person', orgSlug, personId]` — scoped to the one field it owns, same rationale as `StatusRow`'s two mutations — then invalidating `['contact-engagement', 'activities']` so the feed shows the change it just made. A failed PATCH rolls back to `context.fromValue` and shows an error snackbar. A switch rather than a dropdown because the door and the call both ask a yes/no question, and an absent value means nothing is owed (nothing derives this field, so there is no seed to distinguish "no override" from "answered no"). The same flag is written from phone banking's and door knocking's follow-up question, latest answer wins, so the toggle can read on without anyone having touched it here.
- **STATUS_CHANGE feed entries** (ENG-10835): the contact-statuses epic's two editable overrides (voter likelihood, support status — opt-in stays read-only, TCPA) union into the feed as a `STATUS_CHANGE` row via `crm/person/ActivityFeedEntry.tsx`'s `StatusChangeActivityRow` ("<Field> updated" title; "<Actor> changed <field> from 'A' to 'B'", or "set ... to 'B'" for the never-seen-before edge where `fromLabel` is null). `fromLabel`/`toLabel` are resolved server-side from `resolveContactStatusLabel` + `VOTER_LIKELIHOOD_LABELS`/`SUPPORT_STATUS_ROLLUP_LABELS` in `@goodparty_org/contracts` (`ContactStatus.schema.ts`) — the one label-map source for this vocabulary; don't add a second local copy (`PersonOverlay.tsx`'s read-only Support Status field reads the same `SUPPORT_STATUS_ROLLUP_LABELS` import, not its own map). "You" vs. the teammate's name is resolved client-side (`useUser()`'s id compared against the row's `actorUserId`), since the feed endpoint carries no viewer/session context server-side. Gated by **field**, twice: `ContactEngagementService` reads `field: follow_up` for an `eo-` org and `field: { not: follow_up }` otherwise, and the `ActivitiesContent` switch in `PersonOverlay.tsx` mirrors that (`isWinContext !== isServeField`, held back until `isWinContextReady` since the default reads Win). So Win sees its three statuses and Serve sees only the follow-up flag — the row a Serve official reads is "Follow-up updated / <who> changed Follow-up from 'No' to 'Yes'" plus the timestamp, which is the whole point of surfacing it (`FOLLOW_UP_STATUS_LABELS` in contracts maps `requested`/`cleared` to Yes/No).
- **Lists index + list-detail sheet** (ENG-10707/10725, `crm/lists/`): `ListsIndex` (rendered inside `CrmContactsPage`; full-width row cards as of ENG-10725, formerly a grid/table) reads `customSegments` from the provider. - **List map, Serve only** (`crm/map/`): the list-detail sheet renders a map of the list's own members for an elected office, gated on `isElectedOfficial`. Everywhere else in the CRM a list is a filter summary and a set of counts and never the people themselves; this is the one place that inverts, because an officeholder is being asked to go and talk to these constituents and where they are IS the answer, whereas a candidate's list is an audience to send to. The gate is NOT the Pro gate — `canUseProFeatures` is `isPro || electedOffice`, so an elected office always clears that and it protects nothing here.
  Data is `GET /v1/contacts?segment=<listId>` at `MAX_RESULTS_PER_PAGE` (`useListPeople`), which is the same route the rest of the CRM uses — a saved-list id IS the `segment` param (`resolveCustomSegment` coerces it with `Number`). No new endpoint, and no new columns: `Person.address.latitude/longitude` already ride on every row. A list longer than the cap is truncated, not paged, and says so — silently drawing the first page of a longer list would show a map that looks complete.
  **Points group by coordinate, never by address string** (`contactListPoints.ts`). Every unit in an apartment building shares one lat/lon in the voter file, so grouping by address stacks a dozen coincident dots on one building and hides the one thing a housing segment is asking about. Radius is `sqrt(count)` because area is what the eye compares. A dot holding one person selects them through the provider's `selectPerson` (the existing `PersonOverlay`, no second detail view); a dot holding several lists them first. People with no or unparseable coordinates are counted and surfaced, never dropped.
  Rendering reuses door-knocking's stack — MapLibre GL + deck.gl `ScatterplotLayer` on Geoapify tiles — so the two maps in the product read as one. It deliberately does NOT reuse the door-knocking voter pack: that wire format strips person ids and draws anonymous dots, with identity arriving separately via route stops, which is the opposite of what this needs.

- **A transcript's map can draw too** (`chief-of-staff/components/chat/`): `ChatListMap` carries the same Draw/Edit area CTA the list detail sheet does, opening the same `ListBoundaryOverlay` through the same `useSaveListBoundary` hook — so a boundary drawn in a conversation is the identical write, narrowing the list in place with the same 409-lock and people-cap handling. Two things differ. The card holds only a `listId`, so it reads the list's `geoPoly` and lock state via `useSavedList`, which shares ContactsTableProvider's `['custom-segments', orgSlug]` cache entry rather than fetching by id — the save already invalidates that key, so the outline under a transcript's map refreshes with no second invalidation to remember. And **the overlay is mounted by `ChiefOfStaffChatBody`, never by the card**: a streaming turn's row is dropped and rebuilt under a history key the moment it commits, so an overlay owned by the card unmounts mid-draw and takes the holder's ring with it. There is a test that fails when it is moved (`keeps the drawing surface open when the streaming turn commits`); do not "simplify" it back into the card.
- **Drawing a boundary to narrow a list, Serve only** (`crm/map/`, `crm/wizard/BoundaryStep.tsx`): the shape is **an additional filter on the same list** — not a sub-list, not a turf, no child records. It persists as `geoPoly` on the saved `VoterFileFilter` row, so the whole feature is one nullable column and two UI entry points. **A boundary can have several parts.** The surface holds `rings: PolygonRing[]` with one of them active: the map edits the active part and draws the rest read-only beneath it, "Add another shape" appears once the active part reaches three corners, and a chip row switches between them. It serialises through `ringsToGeoJsonShape` — one part stays a plain `Polygon`, so a single-shape save is byte-identical to every list saved before this, and several parts become a `MultiPolygon`. Parts may overlap: everyone inside any part is counted once, and nothing on screen mentions the overlap.
  `ContactListMap` gained three additive props (`drawRing`, `onDrawRingChange`, and the `isDrawing` they derive): a `PolygonLayer` for the ring and a `ScatterplotLayer` of hollow vertex handles, plus maplibre `click`/`mousedown`/`mousemove`/`mouseup` handlers that place and drag corners. **With no writer the component is byte-identical to what it was** — one `contacts` layer, no extra handlers firing — which is what the Chief of Staff chat card (`chief-of-staff/components/chat/ChatListMap.tsx`) depends on; `ContactListMap.test.tsx` pins that by asserting the layer ids the overlay is handed. Handed a `drawRing` and no writer, the map draws a saved outline read-only, which is how a locked list still shows the geography it was cut with.
  `ringInsertIndex` and the ring type moved out of door knocking's `VoterMapCanvas.tsx` into `app/dashboard/shared/ringGeometry.ts` (which re-exports from there, so every existing door-knocking import still resolves) alongside `isPointInRing` and the GeoJSON open/close pair. The draw CHROME is deliberately **copied** from `door-knocking/native/createFlow/DrawFullScreen.tsx` rather than shared: that surface carries a 150-stop cap, a shake animation and an instructions dialog none of which belong here, and refactoring door knocking while shipping a Serve feature is the adjacent-issue rule.
  **Two entry points.** `crm/map/ListMapSection.tsx` puts the CTA under the list-detail map, inside the existing `isElectedOfficial` gate so the gate and the map stay together; it opens `ListBoundaryOverlay` (full-bleed, `z-[1400]`) and confirms with `PUT /v1/voters/voter-file/filter/:id` carrying `{ geoPoly }`. The CTA is hidden on a locked list (`firstUsedForOutreachAt`), and a raced 409 goes to `LOCKED_LIST_MESSAGE` like the wizard's update rather than an error toast. `crm/wizard/BoundaryStep.tsx` is the Serve wizard's new third stage.
  **The live count comes from a different place on each surface, and the difference is not cosmetic.** The list-detail overlay ray-casts `useListPeople`'s own dots (`isPointInAnyRing` — per part, then OR'd, never one even-odd cast over the concatenation, which would make two overlapping parts subtract each other), which answers on every drag of a handle; it marks the number an estimate whenever the list is truncated (`MAX_RESULTS_PER_PAGE`, 10,000) **or already carries a boundary**, because in both cases the dots on screen are not the set the save will be measured against. The wizard cannot ray-cast anything: its list is unsaved, so nothing client-side knows which district dots the filters kept. It asks `POST /v1/contacts/polygon-preview` through `useListWizardPolygonCount.ts`, which mirrors `useListWizardCount` exactly (600ms debounce, its own `['list-wizard-polygon-count', orgSlug, debouncedPayload]` key, the same `isStale`-during-debounce contract, the same `voterDataUnavailable` gate). **`audienceEmpty` is why that endpoint returns two fields:** a zero count means either "this shape holds none of your audience" (move it) or "your filters match nobody" (no shape can fix it), and `BoundaryStep` says a different thing for each.
  **The preview and the save count different populations, and a shape can pass one and fail the other.** `polygon-preview` applies the list's filters; the save re-runs the enclosing scan UNFILTERED, because the frozen set is the geographic half of a list and the criteria re-apply on read. Both share the same 50,000-person cap, so the unfiltered side reaches it first: measured on Buncombe (67,194 records), one ring returned `5,254` filtered and `400` unfiltered. The wizard cannot warn about this in advance — it would need a second, unfiltered preview call per drag — so the handling is after the fact: `isBoundaryBlocked` includes `isPolygonError` so an *errored* preview cannot reach the name step, and `boundarySaveErrorMessage` (`crm/shared/boundarySaveError.ts`) surfaces gp-api's own "draw a smaller boundary" wording on the save's 400 instead of a generic failure, on both entry points. **This is a decided trade-off, not an oversight — don't "fix" it by freezing the filtered set.** Doing that would make the preview and the save agree, and would quietly break the thing the unfiltered freeze exists for: widening a saved list's filters later would never pick up the newly-matching people inside its shape, and nothing on screen would say why. That swaps a rare, loud, recoverable failure for a rare, silent, wrong answer. Serve districts do reach 100,000 constituents, so the cap IS reachable on a large one — it is the minority case, and the legible refusal above is the accepted handling for it (PO call, 2026-09-19). The remaining option, if it ever earns the work, is to preview the unfiltered count alongside the filtered one so the wizard can warn before the holder names the list; that costs a second query per drag and changes no semantics.

  **Once a boundary exists it supersedes the pre-shape count everywhere downstream** — `NameStep`'s sentence, the Save gate (`canSubmitName`), and the boundary step's own Continue all read `effectiveCount`. Saving against the `/count` total would write a `voterCount` the saved list never matches.
  **The wizard's map draws the list being built** (`useFilterPoints` → `POST /v1/contacts/points`), not the district it sits in. It drew the whole district as a backdrop until the count and the dots were found to be answering about different populations: the pill counted only the filtered audience while the map showed every contactable person in the district, so a shape around visible dots came back holding fewer people than it enclosed, and on a narrow list it read as zero. The endpoint takes the same draft payload `polygon-preview` takes, so the two cannot drift again.
  That hook is deliberately **not debounced**, unlike `useListWizardPolygonCount` beside it: the shape changes on every drag of a handle and the count has to keep up, but the filters cannot change while this step is on screen, so a debounce would only delay the map. The response is bare `{ id, lat, lng }` — the step has no person overlay behind its dots — and `groupCoordinates` (`crm/map/contactListPoints.ts`) groups them by coordinate the same way `toContactPoints` groups people, so one apartment building stays one dot. `ContactListMap` takes them through `contactPoints`, which replaces `people` as the source of dots; `ContactPoint.residents` is typed to the id-and-name minimum the map actually reads rather than to `Person`, which is what lets a caller holding coordinates group them without inventing thirty empty columns.
  **Known gap: this step shows no unmappable count.** The points query selects on lat/lng, so the response cannot describe the rows it dropped, and `contactPoints` therefore reports `unmappable: 0` where the `people` path would count them. Measured live on a 5,356-person Buncombe list, 5,347 points came back — about 0.2%. Nothing on screen is wrong as a result: the pill's in-boundary count comes from `polygon-preview`, which runs the same query over the same population, so the dots and the number agree with each other. The gap is only against the pre-shape total on the previous step. Closing it needs the endpoint to return a count of what it could not place, which is a second query, not a spare field.
  **Two product defaults, both deliberate.** The step is **skippable** (Continue is live with no shape) — making it mandatory would stop Serve building a list from criteria alone; only a drawn boundary that settles on nobody blocks it. And **one shape only**: `GeoJsonPolygonSchema` allows further rings but reads them as HOLES, so a second drawn area would subtract rather than add.
  **Edit mode gets no boundary step.** `steps` stays `['conditions']` for `isEditing`, and the wizard's update never sends `geoPoly`, so a partial PUT leaves a saved boundary alone — the list-detail map button is the geography-editing affordance. That is asserted off the source in `CreateListWizard.editMode.test.tsx`, because a second step added to the edit branch is invisible from outside (edit renders no stepper and its footer carries Save, not Continue).

- **Editing a saved list** (`crm/wizard/CreateListWizard.tsx`, `editingSegment` prop): the same `CrmSheet` wizard reopened over the list, seeded from its persisted columns, saving with `PUT /v1/voters/voter-file/filter/:id` instead of `POST`. Entry points are the list row's kebab ("Edit") and the detail sheet's header pencil, both routed through the provider's `editList(segment)` — which closes the detail sheet on the way in (two full-height drawers must not stack) and is what lets surfaces well below `CrmContactsPage` drive the single mounted wizard. Edit collapses to ONE step: no branch chooser (the branch is derived from whether the list has `activityConditions` — switching is what Duplicate is for), no stepper, no Back, and the name moves into the header as an input, so edit covers renaming too and there is no separate rename dialog. The CTA reads "Save changes (N)" off the same live count the create flow uses, and gates on the name, a settled count, a non-empty selection, and a non-zero match together — there is no second step left to enforce the last two. **The payload backing that count IS the save payload.** A PUT is a partial update, so any key the payload omits keeps whatever the row already holds, while the count only reflects what was sent — an omitted key is therefore a filter that narrows the saved list without appearing in the number on the Save button. `CLEARED_VOTER_FILE_FILTERS` (`voterFileFilterTransform.util.ts`) is the whole set of voter-file columns the wizard can express at their empty values, and edit mode sends it as the baseline under both branches: the voter-file branch overlays its own selection on top (so clearing every support-status or precinct pill still writes `[]` rather than dropping the key), and the activity branch sends the baseline entire, because a list can carry voter-file columns alongside its activity conditions — the assistant's `crud_saved_filters` tool takes the whole filter schema flat with no mutual-exclusion constraint — and that branch renders none of them. The baseline also covers ENG-10752's retired age columns, which have no honest remap onto the current buckets (legacy 18-25 straddles 18-24 and 25-34) and which the wizard can neither render nor count. It is deliberately scoped to what the wizard renders: `voterStatus` and the legacy registration keys belong to other surfaces, and clearing a filter no one here can see would be its own silent edit. A list's saved `search` term rides along for the same reason, carried into both the count and the save rather than dropped. Seeding is `segmentToVoterFileFilters` (the inverse of `transformVoterFileFiltersForBackend`; only a literal `true` seeds a pill, since the persisted shape writes an explicit `false` per key and a segment carries plenty of non-filter fields) plus `toWizardActivityConditions`. **The count in edit mode names the list being edited.** `countPayload` is `backendPayload` plus `boundaryFromSegmentId`, and it goes to `useListWizardCount` ONLY — never to the save. That separation is the point: `backendPayload` is also the save payload, and the wizard's update deliberately never sends `geoPoly` so a partial PUT leaves a saved boundary alone, which is exactly why the count has to go and find it instead of being handed it. Without the hint an inline filter carries neither an `id` nor a `geoPoly`, so the boundary was invisible to the count and a list whose detail sheet read 339 offered "Save changes (5,356)". **The saved-list overlap strip is hidden in edit mode** — the overlap union counts the list being edited among the org's saved lists, so an untouched selection would report ~100% already-saved; restoring it needs an `excludeSegmentId` on `POST /v1/contacts/overlap-count`. The create funnel's stage events are suppressed (an edit reuses the conditions screen but can never reach Name Completed).

## Gotchas

- Optional catch-all route (`[[...attr]]`) means `/dashboard/contacts` and `/dashboard/contacts/whatever` both render the same page — sub-routing is internal. `/dashboard/contacts/lists/<id>` is also served by the catch-all (ENG-10725 removed the literal `lists/[listId]` route); the provider’s `extractPersonIdFromPathname` explicitly returns null for the `lists` segment so it can never be fetched as a person id, and `extractListIdFromPathname` only matches exactly `lists/<id>`.
- Voter-file payloads can be huge — pagination + cursor are mandatory; never request without them.
- A feature flag gates parts of `PersonOverlay` (see `app/shared/experiments/`).
- This route is shared by Serve (elected office) and Win campaigns, and is the default Win experience (the `win-voter-data` flag was removed after the rollout hit 100%): the nav entry is added in `DashboardMenu.tsx` (`WIN_CONTACTS_MENU_ITEM`, `campaign` category) for every Win campaign, pro and non-pro. Pro gating is per-action, not page-level (ENG-10495): a non-pro Win candidate sees the real district aggregates and a blurred preview, and the Pro upgrade modal fires when they search, pick a non-default segment, open a person, or download. Backend mirrors this — `findContacts` rejects search/named-segment requests, `findPerson` rejects person-detail reads, and `downloadContacts` rejects downloads for non-pro, but the base list + `GET /v1/contacts/stats` are open to non-pro. **The base-list preview is synthetic, not real voter data (ENG-10508):** for a non-pro requester `findContacts` returns fabricated rows from `previewContacts.utils.ts` and never fetches real people rows — a frontend blur is not a real boundary (the values are copy-pastable), and our data contracts forbid sending real voter PII to non-pro users. It still reads the aggregate district stats to set the preview's `pagination.totalResults` to the real count rather than a fabricated one, while every row stays fake. The district totals the page actually renders come from `GET /v1/contacts/stats` via `districtStatsQueryOptions`, not from this response. The frontend blur on those rows is now just an upsell cue over fake data, and it covers every column (name/gender/age included) so a copy/paste test can't mistake the fabricated rows for readable real data. See **Unresolvable districts** below for the no-district case.
- **Unresolvable districts are predicted client-side, not discovered by failing.** `ContactsTableProvider` carries two signals plus their union:
  - `isDistrictUnresolvable` — proactive, `useOrganization()?.district === null`. `GET /v1/organizations` returns a resolved `district` on every org and `OrganizationProvider` loads it eagerly with SSR-seeded `initialOrganizations`; `OrganizationsService.makeFriendly` resolves it as `overrideDistrict ?? position?.district`, byte-identical to the precedence `ContactsService.resolveDistrictInfoFromOrg` uses to decide whether to 400. So a null district predicts the 400 without spending a request. Strict `=== null` (not `== null`): the `Organization` type declares `district` as a required nullable key, and an absent field should fall back to asking the server rather than hiding a page that might work.
  - `isVoterDataUnavailable` — reactive, kept because `assertVoterDataEligibility` (the federal/state voter-file rule) throws the same `VOTER_DATA_UNAVAILABLE` code from a district-carrying org and needs campaign, district, and ballotLevel together, so it can't be predicted client-side.
  - `voterDataUnavailable` — the union. Every read-path query is gated on it: the provider's `contactsQuery` (gated on the proactive predicate alone — gating on the union would let the query's own error disable the query that produced it), `useListRowDetail`, `ListDetailSheet`, and the wizard's count/overlap-count.

  The page (`crm/VoterDataUnavailableState.tsx`, support handoff to `support@goodparty.org` with the office and org slug prefilled) renders an unavailable state. **It unmounts the whole 560px column, the top bar, and `CrmAssistant` rather than disabling queries** — `DistrictStatCard` and `ListsIndex`'s `AllContactsCard` both observe the shared `['contacts-stats']` key, and React Query fires a query when ANY mounted observer is enabled, so `enabled: false` on one of them would change nothing. One known divergence: a dangling `overrideDistrictId` (set but unresolvable in election-api) makes the server proceed while the client predicts failure — the client is deliberately more conservative there.

  **The predicate lives in `app/dashboard/shared/useDistrictResolution.ts`, not in this provider.** `ContactsTableProvider` is mounted only on the contacts route, so polls (Serve), door knocking, campaign manager and onboarding cannot read its context — they call the hook directly. The provider consumes the same hook, so there is one definition of "unresolvable". **Serve is why this matters:** `canUseProFeatures` is `isPro || electedOffice`, i.e. always true for an `eo-` org, so the district gate is the only protection Serve has and the Pro gate does nothing for it.

  Every district-gated endpoint is now gated client-side: `GET /v1/contacts`, `POST /count`, `POST /overlap-count`, `GET /list-detail`, `GET /contacts/:id` (the deep link — `PersonOverlay` mounts outside the empty-state branch), `GET /contacts/download` (refused inside `useContactsDownload`, before the anchor click — it is a top-level navigation, not a fetch), `GET /contacts/stats` (all nine callers), and the door-knocking pack/turf reads. The one deliberate hole is `AudienceStep`'s **non-pro** case; its district case is gated.

  **Two traps this class of gating keeps setting.** First, `enabled: false` is not enough wherever a consumer branches on `status !== 'success'` or `isPending` to render a spinner — a disabled query is neither success nor error, so it spins forever. `useTotalConstituentsWithCellPhone` therefore returns an explicit `isUnavailable`, and every such consumer branches on that _before_ its loading branch. Second, `queryClient.prefetchQuery` ignores `enabled` entirely, so `ConfidenceAlert` gates by not calling it.

  Polls **blocks** rather than degrades (product call, 2026-08-06): a poll sent against an unknown audience cannot be priced, and `calculateRecommendedPollSize` was returning `NaN` from `MAX_CONSTITUENTS_PER_RUN - undefined` straight into the audience options and cost preview. `polls/onboarding/OnboardingPage` renders a terminal state mirroring the existing `NotEnoughConstituents` bail-out and routes to `/dashboard/contacts`, where the state above already explains the problem and offers support — so polls does not repeat the support handoff. That terminal state is checked **before** the `< 500` viability guard, which required `statsQuery.data` and so never fired for these orgs.

  `CountsInfoModal` and `PathToVictoryStep` already degraded to a hidden row, but both also `reportErrorToSentry` on failure — so a write-in office generated Sentry noise on every onboarding run. Both are gated now.

- **Naming is Win-vs-Serve and must never cross over** (ENG-10448): Win reads "Voter Data" / "voters"; Serve reads "Constituent Data" / "constituents". Win must never say "constituent". The strings live in one place — `app/dashboard/shared/contactsLabels.ts` (`CONTACTS_DATA_TITLE` + `getContactsLabels(isWinContext)`) — consumed by the page heading/subheading (`CrmContactsPage`), the typeahead and assistant, the lists index and list-detail sheet, the wizard, the sidebar items (`DashboardMenu`), and the mobile title (`DashboardLayout`). Add new user-facing copy through that helper, not as a local literal, so the surfaces can't drift. `filters.config.ts` section titles are the one exception the helper can't cover directly — that config renders byte-identically for door-knocking's `TurfDetailsSheet.tsx`, so it must stay untouched. `PersonOverlay.tsx`'s "Voter Demographics" `InfoSection` heading (Serve-visible) is still a hardcoded literal and needs the same treatment if that surface is ever touched.

## Analytics

Events live under the `Contacts` group in `helpers/analyticsHelper.ts` and fire frontend (screen views and user clicks the browser directly observes). Every event carries a `context: 'win' | 'serve'` property sourced from the provider's `isWinContext` — so Win adoption of the unified path is a property filter in Amplitude, not a duplicate event set. Don't mint per-context events.

- `Contacts - Contacts Viewed` — fires once on page entry from `CrmContactsPage`, `{ context, surface: 'crm' }` (ready-gated + ref-latched). `surface: 'crm'` dates from ENG-10767, when this page's users had vanished from the Viewed chart under the old (flag-gated) event; historical rows without the tag predate that fix.
- `Contacts - Outreach Timeline Viewed` — Win-only; fires when the Win outreach timeline renders rows in `PersonOverlay` (`context: 'win'`, `personId`). Not fired for an empty feed or the Serve poll-interaction timeline.
- `Contacts - Voter Data Unavailable` — fires once per page entry from `CrmContactsPage` when `voterDataUnavailable` is true, i.e. the org has no resolvable district and the page can only offer the support handoff. `{ context }`, same `isWinContextReady` gate and ref latch as `Contacts Viewed` (firing before the mode settles would label a Win user as Serve). 437 active campaigns are in that state; this measures how many actually land there, which is the input to whether self-serve remediation is worth building.
- `Contacts - Download` / `Segment Viewed` / `Segment Created` / `Segment Updated` / `Segment Deleted` — existing events, now carrying `context`.
- `Voter Data - Contact Searched` (Win) / `Constituent Data - Contact Searched` (Serve) — the one deliberate exception to the context-property rule: the CRM brief specs the typeahead search events as product-specific by nav surface, each with `resultCount`. They fire once per distinct resolved search from the `settled` derivation in `useContactTypeaheadSearch` (ENG-10688) — never on aborted/superseded requests, sub-3-char input, or the non-pro modal path; an empty result set fires with `resultCount: 0`. Mode comes from `useWinVoterContext()`, gated on `isReady` like the mount event.
- `Voter Data - Note Added` (Win) / `Constituent Data - Note Added` (Serve) — same product-specific naming exception, no properties. Fires from `NotesSection` exactly once per successful create (never on edit, delete, or a failed create). Mode comes from `useWinVoterContext()`, gated on `isReady`.
- `Constituent Data - Follow Up Changed` — Serve-only, the mirror of the Win event below. Fires from `FollowUpRow` once per confirmed-successful PATCH `/v1/contacts/:personId/follow-up`, `{ from, to }`. Never on a failed PATCH.
- `Voter Data - Contact Status Changed` (ENG-10836) — Win-only (no Serve variant: the status row only renders for Win). Fires from `StatusRow` once per confirmed-successful PATCH `/v1/contacts/:personId/status`, `{ field: 'voter_likelihood' | 'support_status', from, to }`. Never fires on a failed PATCH or a reselect of the already-current value.
- `Voter Data - Contact Viewed` (Win) / `Constituent Data - Contact Viewed` (Serve) — same naming exception, no properties. Fires from `PersonContent` once per record open, gated on `useWinVoterContext().isReady` (a person remount via `key={person.id}` re-arms the latch). Distinct from `Contacts - Contacts Viewed`, which fires from the contacts page itself.
- `Voter Data - List Created` (Win) / `Constituent Data - List Created` (Serve) — same naming exception (ENG-10709). Fires from `crm/wizard/CreateListWizard.tsx`'s create-mutation `onSuccess`, once per successful create, only for the voter-file branch. `{ variableCount, hasParty }` — `variableCount` is the number of `filters.config.ts` categories with a selection (`crm/shared/voterFileFilterTransform.util.ts`'s `countSelectedFilterCategories`; a Support Status selection counts as one more category). `hasParty` (via that file's `hasPartyFilterSelection`) is Win-only — Serve never renders the Political Party section (`VoterFileStep` strips it for `isElectedOfficial`), so the property is omitted as a key entirely for Serve, never sent as `false`.
- `Voter Data - Activity List Created` (Win) / `Constituent Data - Activity List Created` (Serve) — same seam, fires only for the activity branch. `{ sourceCampaign, actionFilter }` — the wizard supports N stacked conditions (`crm/wizard/ActivityStep.tsx`), so both properties aggregate across all of them: `sourceCampaign` joins each condition's resolved outreach name (or `'any'`) with `', '`; `actionFilter` is the deduped union of every condition's selected outcome values, as an array (not a HubSpot-email-driving event, so no flatten-to-scalar requirement). `WizardActivityCondition` carries an `outreachName` field (resolved at selection time, never sent to the backend) purely so this handler doesn't need a second outreaches fetch.
- `Voter Data - List Exported` (Win) / `Constituent Data - List Exported` (Serve) — same naming exception. Carries `{ surface: 'listDetail' | 'recommendedDetail' }` plus `{ listSize }` (the people count already shown on the sheet). **Two export surfaces, both in `crm/`:** `crm/lists/ListDetailSheet.tsx` (`listDetail`, the saved-list CSV) and `crm/recommended/RecommendedListDetailSheet.tsx` (`recommendedDetail`, the variant download route) — the only two consumers of `crm/shared/useContactsDownload.ts`, and the event fires from nowhere else. The two former outreach surfaces (`outreachWizard`, `outreachTable`) and the `outreach/util/downloadVoterList.util.ts` helper they routed through were all deleted in the outreach v2 rewrite; historical rows still carry those `surface` values. Fires only from the cookie-confirmed **success** branch, never the ambiguous 15s fallback or a failed download (`awaitDownloadStarted` resolves a boolean specifically to keep that distinction), and is additionally gated on `isWinContextReady` and on the demographics count being known at confirm time — so a click landing before `GET /v1/contacts/list-detail` resolves emits nothing at all rather than a `listSize`-less event.

  **Counting exports: use this event, not `Contacts - Download`.** `Contacts - Download` fires at click time and always fires; `List Exported` fires only on confirmed success behind the gates above. A union of the two double-counts, and substituting `Contacts - Download` overstates. The gap between them is a useful health signal (failed downloads plus the readiness race), not a demand signal. Audited 2026-09-16 (DATA-2343).

ENG-10767 closed the remaining CRM gaps (all ready-gated on `isWinContextReady` like the events above):

- `Contacts - Segment Viewed` — also fires from `ListDetailSheet` on every sheet open once the segment resolves (`{ segment, type: 'custom', context }`), restoring the legacy segment-picker parity for "which lists get used".
- `Contacts - Segment Deleted` / `Segment Updated` / `Segment Created` — the CRM management surfaces reuse the legacy events: `DeleteListDialog` fires Deleted (`{ context }`), `CreateListWizard`'s edit mode fires Updated with `{ action: 'filters', context }`, and `useDuplicateList` fires Created with `{ source: 'duplicate', context }` (the wizard's product-specific List Created events stay a pure wizard-outcome metric).
- `Contacts - List Wizard Method/Conditions/Boundary/Name Viewed/Completed` — per-stage funnel for the URL-stable create-list wizard (`{ context }`, + `{ branch }` on conditions/name). Viewed re-fires on Back re-entry (effect keyed on the open session + active-stage identifier only); Name Completed fires alongside the List Created outcome on a successful create. Serve's wizard never fires the Method stage, and Win's never fires Boundary. **Boundary Completed carries `{ hasBoundary }`** — the step is skippable, and how often it is skipped is the question the stage exists to answer. `STAGE_VIEWED_EVENTS: Record<WizardStepName, string>` is exhaustive over the step union on purpose: a step added without a registered event fails the typecheck.
- `Constituent Data - List Boundary Saved` — Serve-only (the list map is), so there is no `Voter Data` twin, the same way `Voter Data - Contact Status Changed` has no Serve twin in the other direction. Fires once per confirmed-successful `PUT /v1/voters/voter-file/filter/:id` from `crm/map/useSaveListBoundary.ts`, the hook both drawing surfaces write through, `{ listId, cleared, surface }` — `cleared: true` is a boundary removed, which is a different act from setting one and has to be countable apart from it, and `surface` is `listDetail` or `chat` because "does anyone ever draw from inside a conversation" is the question the second surface was built to answer and cannot be asked of one undifferentiated event. Never fires on a 409 or any other failure. The wizard's own boundary rides `List Created` and the funnel stage instead; there is no second Saved event for a list that is born with one.
- `Contacts - Assistant Chat Opened` / `Assistant Message Sent` — `CrmAssistant` fires Opened per drawer open (`{ context, source: 'message' | 'history' }`) and Message Sent per user send (`{ context }`): the bar submit (which opens WITH a message) and every composer follow-up via `AssistantDrawer`'s `onMessageSent` callback.
- `Voter Data - Send Outreach Clicked` — the CRM list → outreach funnel entry, fired when a "Send outreach" button opens the channel picker, from every surface, with `{ surface: 'listCard' | 'listDetail' | 'universeRow' | 'recommendedCard' | 'recommendedDetail' }` + `{ listId }` wherever a saved list is behind the click (the two saved-list surfaces, and a recommended card that already matches one) + `{ variant }` on the two recommended surfaces. Win-only by construction (ENG-10749), so no ConstituentData variant. **It is the funnel's entry point only.** The `audienceSource`/`audienceListId` half of the join lived in the legacy outreach wizard's audience step; the v2 channel flows emit no counterpart, so a completed campaign cannot currently be attributed back to the CRM click that started it. Closing that needs a deliberate event decision, not a revived property name.

Source the `context` from `isWinContext` (single source of truth in `ContactsTableProvider`) — don't recompute Win-vs-Serve. New events: follow `.claude/skills/instrument-analytics-event/SKILL.md`.
