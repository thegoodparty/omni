# app/dashboard/outreach/

Voter outreach hub. Lets a campaign create text/voicemail/script/social outreach to voter audiences and tracks impact. Note: the directory is `outreach/` even though the tech design refers to it as "voter-outreach."

## The outreach hub

`page.tsx` (server component, fetches rows + compliance) renders
`v2/OutreachHubPage.tsx` directly — the hub (`v2/`) is the unconditional
outreach page for every candidate. The social and phone-banking tiles always
use their new flows (`SocialFlow`, `PhoneBankingFlow` with upgrade-at-entry).

Two channels are still mid-rollout and keep their own tile-target swap flag:
`voter-outreach-v2-robocall` (`@shared/experiments/voterOutreachV2RobocallFlag.ts`)
gates the robocall tile (on → the new robocall flow, off/unsettled → the
legacy robocall TaskFlow), and `voter-outreach-v2-sms`
(`@shared/experiments/voterOutreachV2SmsFlag.ts`) gates the SMS tile
(on → `v2/sms/SmsFlow.tsx`, off → the legacy TaskFlow). The text gate
(Pro/compliance) runs in front of BOTH SMS targets.

Phone banking's upgrade-at-entry: a non-Pro click on the tile redirects
straight to `/dashboard/pro-upgrade` (firing
`EVENTS.ProUpgrade.Compliance.LockedItemClicked`) instead of a legacy Pro
modal. The predicate is `ChannelTileGrid`'s own `canUseProFeatures`
(`!!campaign?.isPro || !!electedOffice`, not imported from
`ContactsTableProvider` — that hook is contacts-scoped) and a pending
`useElectedOffice()` query is never read as a refusal.

## Patterns

- **Context-driven**: `OutreachContext` holds the outreach rows. Components read from context rather than threading props through action menus.
- **Audience downloads** go through `helpers/createOutreach.ts` and `helpers/createP2pPhoneList.ts` — don't reinvent the file shape.

## Draft-first purchase flow (text/p2p)

The paid text flow persists the campaign BEFORE payment: entering the purchase
step in `components/tasks/flows/TaskFlow.tsx` creates the outreach with
`draft: true` (server stores it as `pending_payment`, hidden from
`GET /outreach`), and the draft's id rides in the checkout session metadata as
`outreachId`. The SERVER finalizes (Peerly + CAS Slack) during payment
completion — the client no longer POSTs the campaign after paying, it just
refetches the list. A tab that dies after payment loses nothing: the Stripe
webhook finalizes the draft on its own. Going back from the purchase step
discards the draft id; re-entry creates a fresh draft (stale ones stay hidden
server-side).

## Gotchas

### Shared

- Status labels in `constants.tsx` are mirrored on gp-api — keep them in sync if either side changes.
- **`OutreachType` is hand-rolled in four places** (`gpApi/types/outreach.types.ts`, `hooks/OutreachContext.tsx`, `constants.tsx`'s `OutreachTypeKey`/`OUTREACH_TYPES`, and `util/getEffectiveOutreachType.ts`'s `VALID_OUTREACH_TYPES`) instead of importing the contracts `OutreachType` enum. Consolidating onto the contracts enum is a real cleanup, deliberately deferred rather than folded into a feature ticket — file it separately if you're touching this area again.
- **`nativeDoorKnocking` is in three of those four, and its absence from the fourth is deliberate.** `VALID_OUTREACH_TYPES` is named like a type registry but is really the allowlist of types a **task** may open a create-flow for, and the knock transaction is the only writer of a `nativeDoorKnocking` envelope — `createOutreachSchema` rejects the type from clients outright. Adding it there would let `TasksList` open a flow modal for a channel that has no create flow. Don't "fix" the inconsistency without renaming the constant to match what it actually gates.
- **Card copy and default campaign names are two records per channel, and the custom purpose is excluded from the second one.** A purpose card's label answers "what do you want to do"; a name suggestion is the title the campaign carries in outreach history forever. Sharing one record means the next copy correction silently renames campaigns (#1385), and it means "Write my own message" / "Write my own script" — a purpose with no subject to name — becomes a campaign name verbatim. The audit as of #1385 plus this change: **social, phone banking, Serve social, and Serve phone banking** auto-fill from the purpose, so each reads its own `*_PURPOSE_NAME_SUGGESTIONS` (`SOCIAL_PURPOSE_NAME_SUGGESTIONS` / `PHONE_BANKING_PURPOSE_NAME_SUGGESTIONS` / `SERVE_SOCIAL_PURPOSE_NAME_SUGGESTIONS` / `SERVE_PHONE_BANKING_PURPOSE_NAME_SUGGESTIONS`) and all four flows skip the fill for `custom`, leaving the field empty and the CTA disabled until the candidate types one. **Robocall is not affected and needs no guard**: `goToSchedule` names the campaign off the selected _list_ (`"<list> robocall"`), never the purpose, so `ROBOCALL_PURPOSE_LABELS` only ever feeds cards. A channel (or surface) that starts naming campaigns off its purpose has to add its own suggestions record; `socialPurposes.test.ts` / `phoneBankingPurposes.test.ts` / `serveSocialPurposes.test.ts` / `servePhoneBankingPurposes.test.ts` each assert no purpose shares a string across the two records, which is what keeps them from collapsing back into one.
- **A missing `CHANNEL_META` key degrades silently, and `getChannelLabel` is why.** It falls back to capitalizing the raw type, so an unmapped channel renders as a plausible-looking `NativeDoorKnocking` in a grey badge rather than throwing. `CHANNEL_META` is typed `Record<OutreachType, ChannelMeta>`, so widening the union is what forces the entry to exist — keep that typing.

### Door knocking in the outreach surfaces

- **The shared list details drawer lives in `v2/listDetails/`, and the outreach drawer is its reference caller.** `ListDetailsSheetShell` (container, 608px content column, close inside that column, header/body/footer split), `ListDetailsMetric` (Overview cell, the two-column grid, the labelled filter-pill group, the section eyebrow) and `ListDetailsFooter` (the action row) were lifted out of `OutreachDetailsDrawer` so `door-knocking/native/TurfDetailsSheet.tsx` could land on the same anatomy. They stay here rather than moving somewhere neutral because this drawer is the one the canvas draws and the one every channel already opens; door knocking is the surface that joined it. **What each caller keeps is the body**, since the two answer about different objects — an envelope read from `GET /v1/outreach/:id`, or a saved list whose figures come from the voter pack and a frozen route. That is why `Metric` carries `pending` and `progress` that only door knocking passes: the shared cell is the union of what the two needed, not the intersection. The shell's `DrawerTitle` renders `asChild` as a `span`, because every caller's `header` already carries the visible `h2` with the same words and two headings reading the same campaign name is one more than the sheet has sections to head.
- **The footer is a closed set of four modes (`v2/listDetails/footerMode.ts`), keyed on lifecycle × "can this candidate do anything about it from here".** Lifecycle comes from the **displayed status label**, not from `status`, so the footer can never contradict the badge two inches above it — a p2p row with a live Peerly job reads "Done" while its spine status is still `paid`. Self-serve is the two channels we run ourselves. The consequences worth knowing: a scheduled **paid** campaign gets `automatic` ("This campaign is sending automatically. No action needed.") rather than the canvas's `edit`, because Peerly sends it and there is no edit or delete endpoint anywhere to put behind those two buttons — `edit` lands in the door-knocking drawer instead, on an unknocked list, which really does have both. `in_progress` + self-serve is `continue`, which is where **"Continue knocking"** sits beside phone banking's "Continue calling"; both labels are one map in `footerMode.ts` so a third drivable channel cannot invent a third verb. Draft, In review, Denied and Pending payment have no canvas position and render no footer at all — inventing one for them is exactly the fifth mode the closed set exists to prevent. **`done`'s canvas primary ("Show results" / "Show post") was deliberately not landed**: phone banking's results are in this drawer's own body, `OutreachSocialAsset` carries no post URL (which is why the canvas itself draws that button disabled), and no other channel has a results surface — a permanently disabled button is not a design to port.
- **The door-knocking tile hands its list over in the URL, and stops there deliberately.** Every other tile opens a flow in place and passes `preselectedListId` as a prop; door knocking navigates, so the id travels as `?listId=` — the same param the CRM's "Send outreach" links already use to reach this hub, parsed on the far side by the same `util/parsePositiveListId.util.ts`. The far end is `door-knocking/native/createFlow/CreateListFlow.tsx`, which matches the id against the who step's own picker rows before applying it, so a deleted, archived, foreign or invented id is a missed preselection and never a broken step. **The param is deliberately not stripped from the address bar** the way `OutreachComposeDeepLink` strips this hub's: there the deep link opens a flow on mount and the id is spent immediately, whereas the door-knocking create flow opens whenever the candidate presses Create list, so stripping on arrival would throw the list away before anything could read it. Because it stays, the arrival is spent **in state instead of in the URL**: `CreateListFlow` raises `onPreselectApplied` the moment it applies the id, and `NativeDoorKnockingPage` records it as spent above the flow's mount boundary — the flow is unmounted on every close, so its own ref cannot remember, and without this a dismissed list would snap back on each reopen. It is recorded as the spent **id**, not a boolean, so pressing the tile again with a different list still preselects. **And arriving with a list does NOT auto-open the create flow** — that is a separate deferred decision with a named precondition (`/v1/door-knocking/pack` latency and reliability), argued in `door-knocking/VOTER-OUTREACH-2.0-AUDIT.md`; a deep link that auto-opened would land in exactly the false "No matching households" state that deferral exists to avoid. Don't wire it here without re-reading that section.
- **A `nativeDoorKnocking` row's figures ride `OutreachDetail.doorKnocking`.** The block carries the turf id, the route id, the turf's live name, doors / knockable people / logged, and the turf's `completedAt` + `archivedAt`. gp-api fills it by hopping the envelope's `doorKnockingRouteId` to `door_knocking_route.doorKnockingTurfId` (`@unique`, so route → turf is one hop and no column was added), and its counts come from the SAME `DoorKnockingTurfCountsService` aggregate the door-knocking rail reads. **Do not compute a door, people or logged figure here** — a second derivation of a number already printed on the rail is the two-denominator failure ADR 0010 forbids. A walk whose saved list has been tombstoned gets no block at all: the envelope and its paid route survive a soft delete, the list does not, so the drawer says so rather than rendering cells that can only read "—". See `packages/gp-api/docs/door-knocking.md`.
- **The archive seam: a door-knocking row is the projection, and this drawer archives by writing the SOURCE.** `DoorKnockingTurf.archivedAt` (#1375) and `Outreach.archivedAt` are two flags for one walk, and only gp-api's `DoorKnockingTurfService.setArchived` moves both in one transaction. The drawer's Archive/Restore therefore calls `POST /v1/door-knocking/turfs/:id/archive` with `doorKnocking.turfId` — never `PATCH /v1/outreach/:id/archive`, which can reach the envelope alone and is precisely how the two come apart. What used to block the button was reach rather than policy: nothing here could name the turf until the block carried its id. For the same reason the archived STATE is read off `doorKnocking.archivedAt` rather than `row.archivedAt`: a list archived before the server-side mirror shipped has an envelope still reading active, and trusting the projection would draw "Move to archive" on a list already on the shelf. `useTurfLifecycle` (`door-knocking/native/turfLifecycle.ts`) remains the rail's caller of the same endpoint; both surfaces write one row through one server-side writer.
- **The `done` footer's primary slot is empty because nothing can go in it — audited, not overlooked (ADR 0012).** `done` itself renders: Delete on phone banking, Archive/Restore, and door knocking's archive note. What is missing is only the canvas's CTA. **"Show results" has no destination:** no route renders campaign results, and the sole outcomes view is a section in this drawer's own body (`nativePhoneBanking`'s "Results", off `OutreachDetail.phoneBanking`) — so on the one channel that has results, the button would point at itself. Door knocking is not an exception: `TurfDetailsSheet` shows doors/people/logged, which is progress, not outcomes. Text and p2p do store per-recipient `respondedAt`/`optedOutAt` (`ContactInteractionText`, swept hourly), but nothing aggregates them and the sweep documents its own Peerly ingestion as unverified — validate that feed before publishing a rate off it. Robocall materializes recipients and captures no outcome at all: `answeredAt`/`voicemailLeftAt` are written only by the manual per-person log, which sets `outreachId: null`. **That one is not a sweep we forgot to wire, it is a phase that does not exist (ADR 0013):** no robocall vendor is integrated — CallHub is named only in prose, Peerly's reports are its SMS product, and the channel has no send step — so a robocall "Show results" is blocked behind a vendor decision, not behind UI work. **"Show post" cannot be backed at all** — `OutreachSocialAsset` is generated copy, there is no publish step anywhere in the product, and no URL is recorded on the asset, in a webhook or in an audit row. If results ship, they belong in the body beside Overview the way phone banking's do, not behind this slot. Do not add a disabled button here.
