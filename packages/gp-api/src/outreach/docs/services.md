| `outreachPurchase.service.ts`                       | The `PurchaseType.TEXT` purchase handler (registered in the module constructor). A p2p checkout is priced from the DRAFT it pays for, never from a count or list handle in the checkout metadata: it requires the `outreachId` (400 without one), reads the draft scoped `{ id, campaignId, outreachType: p2p, status: pending_payment }` (so a checkout for a draft finalize already claimed is a 400 and mints no session), and bills the list `Outreach.phoneListId` names, looked up `{ peerlyListId, campaignId }` — the same list the send goes to (Peerly `leads_loaded`, falling back to captured recipient rows). The client's `contactCount` is never trusted for p2p, and `validatePurchase`'s `contactCount` pre-check applies only to the other types, so a list Peerly scrubbed to 0 reaches the $0 path. The `text` type is still priced from the request's `contactCount`. Applies the free-texts (5,000) discount server-side; a discounted remainder under the 50c Stripe minimum (1-14 texts over the allowance) is forgiven to $0 too — the same sub-floor forgiveness the hold path applies — rather than minting a checkout session Stripe would reject. A zero-amount fulfilment stamps `Outreach.freePurchaseSessionId`, the positive fact the CAS approval gate reads. Behind the managed Amplitude flag `win_sms_hold_billing` (per-user, resolved once by `PurchaseService` at checkout-session creation and threaded through as `OutreachPurchaseMetadata.winSmsHoldBillingEnabled`; inert when off): on a READY build, a send the free-texts offer FULLY covers (count <= 5,000) takes the free path (amount 0, no hold — exactly like the flag-off path, fixing a prod bug where it priced the undiscounted amount and the client's free-completion call 400'd); a send it only PARTIALLY covers still authorizes a manual-capture Stripe hold on the UNDISCOUNTED count (the free-texts discount is applied later at capture, so capture can never exceed the hold), a sub-50c hold is forgiven (amount 0 → free path), the session allows Stripe promotion codes like every other checkout (Stripe takes the code off the hold itself, and the session carries a server-stamped `winSmsHoldBilling: 'true'` marker so the webhook can recognise a hold checkout a code covered in full, which has no PaymentIntent to read `capture_method` off; a client-sent value is dropped), and `outreachP2pSmsHold.service.ts` records the verified hold on the `OutreachP2pSms` satellite. PAY-BEFORE-BUILD (flag on): when the phone-list build is NOT yet `ready`, the hold is sourced from the pre-pay match-count estimate — `ContactsService.getListDetail(reachability.sms)` on the build's saved voter list, a proven UPPER BOUND of the eventual `leads_loaded` (the build is strictly subtractive), re-derived server-side (never a client count). The free-texts offer is NEVER consulted pre-build — a pre-build estimate is always priced undiscounted, even when it's within the 5,000 free-texts count, so a covered send still pays (and holds) the full estimate rather than taking the free path before the list is `ready`; the discount still applies at capture once the build finishes. An offer-eligible campaign whose per-send redemption has not run yet is NOT captured (it waits for the webhook retry to finalize). A final amount below Stripe's 50c floor VOIDs the hold (no $0 capture), except on a send a promotion code helped pay for that reached at least one recipient: that remainder is the discount, not a failed payment, so the hold is released and the row commits `captured` at $0 (approvable, free-texts offer left spent; a hold already gone on recovery settles the same way). A `promoCoversTotal` row (no intent) commits `captured` at $0 with no Stripe call once the send is out. A list scrubbed to nobody (`leadsLoaded` 0) still voids and restores the offer, promo or not; an already-`succeeded` PI reconciles off `amount_received` UNCONDITIONALLY (records a capture that already happened, regardless of the flag); the FRESH `requires_capture → capture`/void branches carry NO flag gate at all — a hold already placed always settles regardless of the flag or rollout cohort; the only thing that can route this to void instead of a fresh charge is the PI's own live state (lapsed/anomalous/sub-floor), never a flag read; a lapsed/`canceled` hold parks `voided` + CRITICAL (never blind-charged). HARD SEND CAP (team decision 2 — never oversend): `resolveSendCapForBuild(buildId)` returns the paid count the hold covers; `p2pPhoneListUpload.service.ts` reads it before the Peerly upload and truncates `buildPhoneList`'s recipients to it, so a filter that re-resolves larger than the pre-pay estimate can never send/materialize more than was billed. ORDER-INDEPENDENT (slice D2b): the cap is read PRIMARILY from the build's own persisted `PeerlyPhoneList.sendCapTexts`, stamped in `resolveWinSmsHoldAmount` at checkout-session creation (`persistSendCap`, `maxTextsForAmountInCents(holdAmount)`) — when the hold amount is first computed, BEFORE the payment webhook links the hold. The satellite `peerlyPhoneListId` lookup (`maxTextsForAmountInCents(authorizedAmountInCents + promoDiscountInCents)`, the smallest across linked holds) remains a FALLBACK for a build whose cap was never persisted; the discount is added back so a promo-shrunk hold never shrinks the list (the persisted cap is computed before any code applies, so it is unaffected). Null (no persisted cap and no paid hold — the flag-off population) applies no cap; the only ordering with no persisted cap is a resolve that runs before the user reaches checkout, where the pre-pay estimate is already an upper bound of that already-smaller resolve |
| `outreachP2pSmsCancel.service.ts`                   | RELEASE (void + refund) for a Win p2p SMS HOLD-MODEL row. `cancel` is dispatched at the TOP of `OutreachService.cancelOutreach` for a p2p row that carries an `OutreachP2pSms` satellite (like the robocall branch, never a fork of the shared body) — it claims the spine (`→ canceled`, CAS on its current status, booking-guarded for a candidate's `in_progress` row) FIRST, then deletes the vendor job, releases the money and restores the free-texts offer; a delete or release failure hands the claim back to the original status. `releaseForDeny` is the money half the admin console's hold-model deny calls. SATELLITE-gated, NOT flag-gated: once a row IS a hold its money guards apply regardless of the `win_sms_hold_billing` flag; a non-satellite row never reaches here. MONEY SAFETY: the shared `releaseHold` re-reads the LIVE PaymentIntent on every attempt and branches on its REAL status (succeeded → refund, requires_capture → void) — never a stale satellite state, so it can never void a capture or refund a hold; a bounded retry re-settles when a capture races in (authorized → captured) by refunding the now-succeeded intent instead of voiding. Defense in depth: after winning the `authorized → voided` claim, `voidAuthorized` RE-READS the live PI — a capture can have landed even though it won the claim (a lost capture-response reverts `capturing → authorized` while the PI is already `succeeded`), so if the PI reads `succeeded` it undoes the void claim and routes to the refund path rather than ever stranding a captured charge in `voided`; and if that re-read FAILS it reverts `voided → authorized` and returns not-settled so the outer release loop re-reads and re-routes (refunds a succeeded charge, or surfaces a retryable 502 with the hold intact) rather than ever voiding an unconfirmed, possibly-captured PI. Exactly ONE refund per charge: the refund is claimed to the in-flight `refunding` state (single-owner CAS) BEFORE the Stripe call and keyed on the durable charge id (`p2p-sms-refund-<chargeId>`), so a deny and a cancel racing the same charge can neither both claim it nor both pass the key; a transient refund failure reverts `refunding → captured` to retry. A caller that OBSERVES another owner's `refunding` never assumes success: it polls until the row resolves — `refunded` → report it, reverted to `captured` → re-attempt (claim the CAS itself), still `refunding` past the bound (owner crashed between claim and Stripe) → surface UNRESOLVED (`ServiceUnavailable`) WITHOUT reporting a refund or flipping the spine, so a candidate is never told "refunded" unless the refund committed (the stranded row is a slice-F reconcile case). A `capturing` row is REFUSED (money mid-flight). A row a promotion code settled at $0 (`captured`, `capturedAmountInCents: 0`) or covered before capture (`authorized`, no intent) has nothing to void or refund: it is released to `voided` with no Stripe call and the free-texts offer handed back. Stripe has already counted the code's redemption; a release does not reactivate it. A refund of a promo send refunds the charge, which returns only what was captured. The refund resolves off the satellite intent (`chargeIntentId`, falling back to the live PI's charge for a stale authorized→succeeded row), never the checkout session, and a refund Stripe accepts but does not process (status not `succeeded`/`pending`) is reverted, never reported refunded. `cancel` posts the CAS "canceled" Slack notice (best-effort), parity with the shared immediate-charge body. A row the live paths deliberately leave non-terminal (stranded `refunding`, denied-but-unreleased, or a failed best-effort void/restore) is healed by `outreachP2pSmsReconcile.service.ts` below Rows with any other Direction are counted (`unexpectedDirectionRows`) and never read for an opt-out. This pass never requests the question-responses report. Cadence decays per Peerly's request-frequency ask (ENG-11038): a job under `INBOUND_SWEEP_FRESH_WINDOW_DAYS` (2) old is swept every pass, an aged one only on hours divisible by `INBOUND_SWEEP_AGED_HOUR_INTERVAL` (6). A per-process `Set<jobId>` skips a job whose previous fetch is still outstanding when the next hour's pass starts. **Opt-out reconcile** (`outreachOptOutReconcile`, `45 * * * *` ET): the backstop for Peerly's own opt-out flags (its AI and texters flag replies that contain no stop word), read from the question-responses report. Peerly builds that report while we wait (up to about 3 minutes for a big job), so each job is read about every `OPT_OUT_RECONCILE_INTERVAL_HOURS` (6, less 30 minutes of slack so a pass starting a moment early in its hour still counts), with one 300s request and `PeerlyHttpService` retries off. Each hourly pass reads `OPT_OUT_RECONCILE_CONCURRENCY` (2) jobs at a time and starts none after `OPT_OUT_RECONCILE_BUDGET_MS` (20 minutes), so it ends long before the next hour's pass; nothing else stops two passes reading the same job at once. `OutreachOptOutReconcile.attemptedAt` records every attempt, a timeout included, so a pass cut short by a deploy or the budget resumes with the never-read jobs first, then the longest-waiting. It lives off the outreach row because a write there bumps `updatedAt`, which holds a send inside the sweep's window. A failure or timeout logs a warn and moves on; the summary counts due, polled, failed, timed-out, deferred (budget spent) and recently read jobs, plus the opt-outs applied, and a pass that ran out of budget also logs a warn.
