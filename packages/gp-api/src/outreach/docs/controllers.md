| `POST /outreach` (multipart) + `GET /outreach`                                                                                                                                                           | `outreach.controller.ts`              | Legacy create/list. A p2p create is ALWAYS draft-first: the schema requires `draft: true` (p2p only) or a `draftOutreachId` resume, so a p2p body carrying neither 400s before any service code runs, and the row is stored `pending_payment`, hidden from the list. `text` and `robocall` creates still write a `pending` row directly. Image required for text/p2p (skipped, and an unexpected file ignored, when `draftOutreachId` resumes a saved draft — that row already holds the image). Every p2p write is Pro-gated unconditionally (`@UseOrganization()` + `ContactsService.assertProAccess`, the robocall create's gate): `filterAccessCheck` only fires when a `voterFileFilterId` rides along, which a resume body need not carry. Text stays ungated (the legacy free-texts path). p2p create (draft included) enforces the CAS compliance list deterministically via `requireCompliantScript` (contracts `checkSmsStandards`: opt-out, {first_name}, candidate name, paid-for-by + committee token, length) — a non-compliant message 400s before payment. There is no candidate edit route (product decision 2026-09-02: CAS fixes messages via the admin console; candidates can only cancel). The cancel rule splits by who cancels (`attribution.byAdmin`), on both the shared and the hold-model path. Staff can always cancel an unsent campaign from the console (`pending`, `pending_payment` on the hold path, or a p2p `in_progress` row, booked or not, past its send time or not): they unbook canvassers through our portal, not Peerly, so the console shows a booked-canvassers warning instead of a refusal, and no live Peerly read gates their cancel. A candidate cannot cancel a BOOKED send (`approvedAt`/`canvassRequestedAt` stamped) once `outreach.date` has passed (the 2026-09-02 no-mid-send-cancel rule, now candidate-only); an unbooked row past its date never sends, so it stays cancelable/refundable (QA 2026-09-10), including an unbooked p2p row the completion sweep has already ratcheted to `in_progress` on its send day (prod outreach 85286, 2026-10-15). Because canvassers can also be booked by hand in Peerly (which stamps nothing on the row), a candidate's cancel of an `in_progress` row at or past its send time first reads the live job (`util/peerlyCanvassersBooked.util.ts`, the same predicate the completion sweep uses) and refuses a booked one; a failed read refuses with a 502 rather than deleting a job it could not check. A `completed` row is refused for everyone. Both paths claim the spine with a CAS on its current status BEFORE the vendor delete or any money moves (a candidate's `in_progress` claim is also guarded on `approvedAt`/`canvassRequestedAt` null, so an approve landing mid-cancel wins), and a failed cancel reverts the row to the status it was claimed from. Create also persists the candidate's picked wall-clock send time as `scheduledLocalTime` ("HH:mm", schema-validated to 09:00-20:00 — 20:00 is the latest start that leaves a non-zero window before the 21:00 cutoff), which opens BOTH of Peerly's per-job windows: the job's own Schedule (`PeerlyScheduleService.createSchedule`, minted at create/finalize with that start) and approve's canvasser request. Peerly's console shows the Schedule as the job's hours, so the two must agree — CAS read a 9am schedule next to a 5pm canvasser booking when only the request honored the time (2026-09-21) must stay outside `OutreachNotificationInterceptor` — a 404 there would fire
a CAS failure Slack meant for send attempts. Same reasoning keeps

failed create or delete must not page CAS.
