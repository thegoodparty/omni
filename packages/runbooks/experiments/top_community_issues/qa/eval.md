# top_community_issues — eval rubric

Converted from the experiment's own instruction.md spot-check/failure-mode rules, 2026-07-14; not reliability-validated — observe-only. Source: `experiments/top_community_issues/instruction.md` ("Spot-check" and "Failure modes" sections).

You are grading a `top_community_issues` artifact, generated by an LLM for an elected official. Grade it against the criteria in this rubric. That is the whole job: read the artifact, apply each check, and record a verdict with a short note.

## Keep this evaluation editorial, not investigative

Keep this lightweight. You are EDITORIAL, not investigative. Score the artifact's OWN embedded content as written, in a single read. Do NOT re-fetch sources, web-search, or fact-check against reality — none of that is available to you and none of it is your job. In particular, do NOT verify whether a source's `retrieved_text_or_snapshot` genuinely supports a claim, do NOT check whether an `article_date` is genuinely within the freshness window, and do NOT check for leaked internal data-vendor names ("Haystaq"/"L2") — those are claim-grounding, freshness-math, and mechanical-substring checks that belong to the deterministic stage (`qa/main.py`, not yet built for this experiment), never to you. The question is always "does this read as well-selected, honestly labeled, and honestly reported, as written?", never "is this true in reality?".

You have ONLY `Bash`, and only to read the artifact under `/workspace`. You cannot write to the workspace, fan out subagents, web-search, or use MCP. Your one job is to read the artifact once, grade it on the checks below, and write your verdict fragments to the result file.

## Inputs

- **The artifact** is a JSON `top_community_issues` output under `/workspace` (read-only evidence — find it with `Bash`, e.g. `ls /workspace` then `ls /workspace/output`). You MUST NOT modify `/workspace` or the artifact.
- The artifact carries a top-level `issues[]` (each with `title`, `category`, `priority`, `rank`, `detail.overview.summary`, `detail.sources[]`) and `sources_used`/`data_quality`/`data_quality_reason`/`notes`.

## Gate A — eligibility, checked FIRST

Read `issues` (the array) and `data_quality`.

- If `issues` is empty — this is a correct, honest output for a quiet jurisdiction (`data_quality: "insufficient_signal"` with no groundable issues), not a quality failure. There is nothing to grade. Emit ONLY the `gate_a_eligibility` fragment with `passed: false` and a `detail` naming the empty-list reason, do NOT emit any check fragments, and stop.
- If `issues` has one or more entries — the gate passes. Emit `gate_a_eligibility` with `passed: true` and grade every applicable check below.

## The checks at a glance

| Check                        | What you are grading                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------ |
| `named_issue`                | Every issue is a specific named instance, not a taxonomy category                                |
| `demand_side`                | The list reads as resident demand, not the governing body's own agenda                           |
| `lead_tight`                 | `priority: "high"` is reserved for the 1-3 best-evidenced issues; not padded toward the 5 cap    |
| `attribution_labeling`       | Resident demand is sourced or honestly labeled when only press/agenda-carried                    |
| `no_official_voice`          | The recipient official's own quotes/votes/press are never used as resident-demand evidence       |
| `category_diversity`         | Issues span more than one category, unless too few issues exist to show it                       |
| `lean_is_annotation`         | The internal-data lean reads as an annotation in prose, never cited as the ranking rationale     |
| `advocacy_nonpartisan`       | A partisan advocacy group's claim is flagged or independently corroborated                       |
| `summary_substantive`        | Every issue's `detail.overview.summary` is a real, sourced 2-3 sentence summary, not boilerplate |
| `honest_data_quality_reason` | `data_quality_reason`/`notes` honestly name gaps (missing layers, dropped domains, short list)   |

## Grading scale

Every check gets one of three outcomes.

| Outcome | What it means                               | Fragment encoding                         |
| ------- | ------------------------------------------- | ----------------------------------------- |
| Pass    | Meets the bar. No issues.                   | `passed: true`, `detail` OMITTED          |
| Fail    | Something is clearly wrong or missing.      | `passed: false`, `detail` = the fail note |
| N/A     | This check does not apply to this artifact. | OMIT the fragment entirely                |

Only `category_diversity` (fewer than 2 issues total) can be N/A. Every other check always gets Pass or Fail once Gate A passes.

**On a Pass, write no `detail`.** A pass means "assume correct" — omit the field. The fail note is the only place reasoning is recorded.

### The fail note

A fail note is read by a downstream LLM, so it must be cheap and high-signal: the minimum needed to locate and understand the failure, and nothing else. Write it as a single line, **hard cap 300 characters**, structured as three pipe-separated parts:

```
<defect: which rule was broken> | <locator: issue id / title / field> | <evidence: the offending snippet, quoted verbatim and trimmed>
```

- **defect** — name what is wrong in a few words ("title is a category not an instance", "official's own quote used as demand evidence", "3 of 4 issues at priority:high").
- **locator** — the issue `id`/`title` or field path, so the downstream reader can go straight to it.
- **evidence** — the smallest verbatim fragment from the artifact that proves it. Trim to the offending words; do not paste a paragraph.

Rules for the fail note:

- Stay within 300 characters total. If multiple issues fail the same check, cite the single clearest one (a re-run surfaces the rest) or at most two, still within the cap.
- Only artifact-specific facts. Do NOT restate the rubric, do NOT suggest a fix, do NOT hedge ("seems", "possibly"), do NOT add framing.
- One line, no internal newlines.

## The checks

### 1. Named issue → `named_issue`

**Fail if:** any issue `title` reads like a policy category ("Housing", "Public safety", "Infrastructure") rather than a specific, named, currently-relevant instance (a project, a rate change, a vote, a location).

**Pass if:** every `title` names the concrete instance — e.g. "the proposed 40-unit development on Route 3" or "the 21% jump in the local tax rate."

### 2. Demand-side, not agenda-driven → `demand_side`

**Fail if:** an issue's `summary`/`detail` reads as if its presence is justified by the governing body's own record (a council vote, an agenda item, an ordinance) rather than by resident-raised coverage — i.e. no news/letters/advocacy/petition/311/survey source is doing the work of establishing the issue matters to residents.

**Pass if:** every issue's inclusion is grounded in resident-facing sources (news, letters/op-eds, advocacy groups, petitions, 311, survey), consistent with `detail.sources[]`.

### 3. Lead is tight, not padded → `lead_tight`

**Fail if:** `priority: "high"` is assigned to more than 3 issues, or the list reads as padded with thin/marginal rows to approach the schema's 5-item cap rather than stopping at a tight, well-evidenced lead.

**Pass if:** `priority: "high"` is reserved for at most the top 1-3 issues, and any additional issues are clearly independently well-evidenced, not filler.

### 4. Resident-attribution labeling → `attribution_labeling`

**Fail if:** an issue's `summary` asserts or implies residents are raising/demanding something, but `detail.sources[]` for that issue shows only `reporting`/`press_release`/`government_communication` `article_type`s with no direct resident voice (opinion/editorial, petition, advocacy statement, poll, 311) — and the summary does not honestly flag this (e.g. "resident voice not yet evidenced").

**Pass if:** every issue either has direct resident-voice sourcing, or is honestly labeled as press/agenda-carried without a resident-voice claim, and is not marked `priority: "high"` on the strength of that labeling alone.

### 5. No official's-own-voice as demand → `no_official_voice`

**Fail if:** any `quotes` item or cited evidence attributed to the recipient official (or their office) is used as evidence that residents are raising the issue.

**Pass if:** the recipient official's own statements/votes/press appear, if at all, only as context (e.g. actionability notes), never as resident-demand evidence.

### 6. Category diversity → `category_diversity`

**Fail if:** there are 2 or more issues and every one shares the same `category`.

**N/A if:** fewer than 2 issues total (cannot show diversity).

**Pass if:** 2+ issues span more than one `category`.

### 7. Internal-data lean is an annotation, not the ranker → `lean_is_annotation`

**Fail if:** any issue's `summary`/`detail` text states or implies that its rank or priority was driven by the internal-data lean (e.g. "ranked first due to strong internal-data lean") rather than resident attention.

**Pass if:** where mentioned at all, the internal-data lean chip reads as a secondary annotation ("+11 pro-transit lean") alongside a resident-attention rationale, never as the stated reason for rank/priority.

### 8. Advocacy-group framing is nonpartisan or flagged → `advocacy_nonpartisan`

**Fail if:** an issue relies on a partisan advocacy group's framing as its sole or primary source, with no independent corroboration and no flag of the group's affiliation.

**Pass if:** every advocacy-group-sourced issue either uses a nonpartisan group, or flags the affiliation and is corroborated by an independent source.

**N/A if:** no issue cites an advocacy-group source at all.

### 9. Summary is substantive → `summary_substantive`

**Fail if:** any issue's `detail.overview.summary` is empty, boilerplate, or too thin to convey the specific instance and why it matters (not 2-3 sourced sentences naming the concrete instance).

**Pass if:** every issue's summary is a substantive, sourced 2-3 sentences naming the concrete instance.

### 10. Data-quality reason is honest → `honest_data_quality_reason`

**Fail if:** the list is short (fewer than 5 issues) or a source layer is visibly missing (no 311, no survey, no advocacy-group source) and `data_quality_reason`/`notes` does not name it — i.e. the artifact is silent about a gap a reader would want to know about.

**Pass if:** `data_quality_reason`/`notes` honestly account for any missing layer and for why the list is short, when applicable.

**N/A if:** the list has 5 issues and every source layer is evidently present (nothing to disclose).

## Output — write a contract-C fragment array to the result file

The harness appends a result-file path to this instruction (look for "write your fragment array ... to this exact path"). Write your verdict there as a single JSON array of fragments — nothing else in that file, no prose, no markdown fences. The engine reads the fragments back from that exact path; a missing, non-array, or unparseable file makes the stage error.

Each fragment is an object. Only `name` (string) and `passed` (bool) are required. This rubric is Pass/Fail throughout (no `score`/`min_score`):

```json
{"name": "<id>", "type": "agent", "passed": <bool>, "detail": "<one-line, only on a fail>"}
```

- Gate fragment (`gate_a_eligibility`): `passed: false` when it DISQUALIFIES (empty `issues[]`; carry a short `detail`), `passed: true` when it passes (no `detail`).
- Every other check: `passed: true` carries NO `detail`; `passed: false` MUST carry the terse fail note. **N/A → omit the fragment entirely.**

Which fragments to emit:

- Gate A disqualifies (`issues` empty) → emit ONLY `gate_a_eligibility` (`passed: false`). Stop.
- Gate A passes → emit `gate_a_eligibility` (`passed: true`) PLUS every applicable check from the ten above (omit any N/A check). Emit at least one check — an all-omitted set makes the engine score `pass: null` (empty checks are not a pass).

Constraints:

- Keep every `detail` to one concise line, hard cap 300 characters.
- Never write `BROKER_TOKEN`, any token-shaped string, or raw auth headers anywhere.
- The result file must contain EXACTLY the JSON array and nothing else.
