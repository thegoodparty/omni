# TDD — Campaign Tracker dynamic tasks + community events (CAP-driven)

Status: Draft (for review — do not merge implementation to prod until reviewed).
Epic: ENG-10406. Product context + decisions: `campaign-tracker-v3-context.md`.
Scope: gp-api + `@goodparty_org/contracts` + `packages/runbooks/experiments` +
gp-webapp.

## 1. Summary

The Campaign Tracker renders a candidate's plan as phased, prioritized weekly
tasks. The static catalog (Pre-launch/Launch + GOTV ops) and the client-side
sequencer/UI already ship (see context doc). This TDD covers the **dynamic
half**: personalizing and curating Active-campaign / GOTV tasks and community
events per candidate, generated by **CAP** (the agent-experiment engine) and
kept current by a **weekly cron**, modeled on the existing `meeting_briefing`
scheduled dispatch.

It also decides the **community-events generation** question: move it off the
standalone Gemini pipeline and onto CAP, so events and tasks share context and
one dispatch/monitoring path.

## 2. Goals / non-goals

Goals:
- Generate the full personalized set of dynamic tasks + community events once
  (initial), then re-evaluate the upcoming week weekly with completion context.
- Use CAP for both, consistent with `meeting_briefing`'s cron→dispatch→result.
- Keep the hard rules deterministic in gp-api (gates, windows, caps, dates).

Non-goals (this TDD):
- The static catalog, sequencer, and UI gating (shipped).
- The weekly digest email — handled separately: change top-5 → **top-3** to
  complete, match the UI's prioritization (outreach prioritized), and notify Joe
  (no change needed on their end).
- The fundraising thermometer and intake-dependent pills (future).

## 3. Background / current state

- **Shipped (webapp):** hand-authored catalog (`taskCatalog.ts`, 58 tasks),
  client-side `buildCampaignStrategy` sequencer, four-phase UI with the June 17
  rules (3/week cap, Active lock, 30-day GOTV banner). Dynamic-task copy is the
  template copy today — no personalization yet.
- **Community events today:** `CommunityEventsService.generate`
  (`gp-api/src/campaignStrategy/services/communityEvents.service.ts`) is a
  **Gemini** two-stage search→structured pass, window `[today, electionDate]`,
  **capped at 3** (schema `CommunityEventsResultSchema.max(3)`, `MAX_EVENTS`,
  prompt), persisted to `campaign_strategy.community_events` (replace-only). It
  is triggered on-demand (`POST /v1/campaignStrategy/mine/community-events`) and
  pre-warmed in onboarding. It is **not** CAP, and a single search only surfaces
  near-term announced events.
- **CAP engine:** author an experiment in `packages/runbooks/experiments/<id>/`
  (`manifest.json` + `instruction.md`), publish via `publish_experiments.py`,
  types generate into `AgentJobContracts`. Dispatch:
  `ExperimentRunsService.dispatchRun({ type, organizationSlug, clerkUserId,
  params })` → `ExperimentRun` row (runId, RUNNING) → agent-dispatch FIFO SQS →
  cloud agent (Claude + web search) → S3 artifact → `AGENT_EXPERIMENT_RESULT`
  SQS → `queueConsumer.handleAgentExperimentResult` → feature
  `onExperimentRunCompleted` → parse + persist (race-guarded). Partial→resume;
  stale runs swept after 45 min; runs observable in `admin/agentRuns`.
- **Scheduled-CAP precedent — `meeting_briefing`** (the pattern we copy):
  `MeetingBriefingsService.dispatchDailyBriefings` `@Cron('0 7 * * *')`
  (`gp-api/src/meetings/services/meetingBriefings.service.ts:625`):
  - **Multi-pod dedup via DB lease**, not SQS dedup: `CronLockService`
    (`src/cron/services/cronLock.service.ts`) — unique `(jobName, runDate)` on
    `CronRun`; first INSERT wins; 6-hour stale takeover.
  - **Select → gate → throttle → dispatch:** load offices, skip if a future row
    already exists (coverage dedup), gate on imminence + a fail-closed flag,
    batch **100 per cycle with 20-min sleeps**, then `dispatchRun(...)`.
  - **Result:** `onExperimentRunCompleted` reads the artifact, validates status,
    and **fail-closed**: placeholder statuses are not persisted so the next cron
    retries. Upsert on a natural key.

## 4. Requirements (June 17 decisions)

- Three phases: P1 static/programmatic (shipped), P2 dynamic/CAP, P3 weekly
  re-gen/CAP.
- Initial generation = all dynamic tasks + all community events.
- Weekly cron re-evaluates the **upcoming week's** dynamic tasks using the
  current week's tasks + completion status, and the full prior set, to
  re-prioritize (push incomplete-but-important forward) and avoid repeating
  same-type tasks. It also curates community events.
- Active Campaign + GOTV: show 3/week; generate up to 7; progressive reveal.
- Lock Active until Pre-launch/Launch done; GOTV tasks only in the last 30 days
  (blue banner before). Last-30-days reframes context to GOTV.
- Community events: lookahead to end of campaign, curate prior events, multiday
  appears once.
- Schema: add `priority`.

## 5. Decision: move community events to CAP

Recommendation: **yes — retire the standalone Gemini community-events pipeline
and generate events via a CAP experiment.**

Why:
- Consistency: one dispatch/result/monitoring/cron path (the `meeting_briefing`
  pattern) instead of a parallel Gemini service + bespoke caching/polling.
- Curation needs state: weekly we must feed prior events back in (update/drop
  changed, multiday-dedup, lookahead to end of campaign). CAP runs are stateful
  via params + artifact; the agent has web search.
- Shared context: dynamic-task curation should see the events (so it doesn't
  emit a generic "attend an event" task that duplicates a real event card).

Trade-off: a CAP agent run costs more than a single Gemini call and has higher
latency. Mitigated by weekly cadence + batching + cost tracking (`costUsd`).

Plan-PDF coupling: the plan's Section 7 still reads
`campaign_strategy.community_events` and slices its top 3 — unchanged. The CAP
experiment writes that same field (cap raised; PDF slices). Initial events are
generated at onboarding (replacing the Gemini pre-warm) so the PDF still has
events before the candidate finishes setup.

## 6. Architecture

Two CAP experiments, one weekly cron, deterministic gating in gp-api + webapp.

### 6.1 Experiments

`community_events` (replaces the Gemini pipeline):
- Input: `race_id`, identity, district context (city/state/zip/office),
  `today`, `election_date`, `prior_events` (curate), `mode: initial | weekly`.
- Output artifact: `{ events: [{ title, description, date, address, url }] }`,
  full `[today, electionDate]` window, multiday collapsed to one, curated
  against `prior_events`. Cap raised (e.g. ~20); PDF slices 3.
- `instruction.md`: real district events only (no generic recurring filler),
  lookahead to end of campaign, curate prior (update/re-date/drop), never invent
  addresses.

`campaign_tracker_tasks` (dynamic-task personalization + weekly curation):
- Input: identity + `race_id`, campaign context (issues, opponents, win number,
  contact goal, budget, dates), `today`, `election_date`, the **dynamic task
  catalog** (the menu), `current_community_events` (so it won't duplicate event
  tasks), `prior_tasks` (previously generated + completion status),
  `mode: initial | weekly`.
- Output artifact: `{ dynamic_tasks: [{ catalog_id, title, description,
  priority_tier, phase, channel }] }` — full personalized set on initial; the
  curated upcoming-week set on weekly.
- `instruction.md`: personalize copy in voice; avoid repeating same-type tasks
  (sees the full set); weekly = push incomplete-but-important forward, re-rank;
  GOTV reframe in the last 30 days; never invent dates/numbers/compliance.

Why two experiments, not one: events must generate at onboarding (before setup),
tasks only after setup; coupling them in one experiment ties event timing to
task timing. Keeping them separate lets the task experiment take the current
events as input for the no-repeat goal. (Alternative considered: one experiment
for shared context — simpler context, but worse onboarding timing; rejected.)

### 6.2 Initial generation (on-demand, not cron)

Start sequence (per "Decision (Terry+Co)"):
- **Pre-launch + Launch (~23 tasks)** come from the static catalog, instantiated
  when the candidate first opens the Campaign Tracker. They are programmatic
  (Phase 1, no AI); the candidate's story can inform light selection/ordering,
  but these are global tasks, not model-written.
- **Community events:** at onboarding, dispatch `community_events`
  `mode=initial` (replaces `prewarmCommunityEvents`). Same `getOrGenerate` +
  inFlight-guard + generating/ready polling the strategic-landscape uses.
- **Dynamic tasks (Active/GOTV):** the **first generation is triggered when the
  candidate finishes their Pre-launch/Launch tasks** (Active is locked until
  then). Dispatch `campaign_tracker_tasks` `mode=initial` with the current events
  as input; persist the full personalized set. After that, the weekly cron takes
  over and **only re-generates what was generated before** (it curates the
  existing pool against completion — it does not invent brand-new task types).

### 6.3 Weekly cron (the core of this TDD)

New `CampaignTrackerDispatchService`, modeled on `dispatchDailyBriefings`:

```
@Cron('0 23 * * 0', { timeZone: 'America/Chicago' })   // weekly, Sun 11pm CT
async dispatchWeeklyRegen() {
  if (!isAutomationEnabled()) return
  // 1. Multi-pod dedup: DB lease (consistent with meeting_briefing)
  if (!await cronLock.tryClaimDailyRun('campaignTrackerWeeklyRegen', now)) return
  // 2. Select eligible campaigns
  const campaigns = await selectEligible()   // active, has strategy, future
                                             // election, dynamic phase started
  // 3. Batch + throttle (100 / 20m) to bound CAP cost/load
  for (const batch of chunk(campaigns, 100)) {
    for (const c of batch) await dispatchRegenIfNeeded(c, now).catch(log)
    await sleep('20m')
  }
  await cronLock.markCompleted('campaignTrackerWeeklyRegen', now)
}
```

`dispatchRegenIfNeeded` gates (coverage dedup): skip if
`dynamicTasksRefreshedAt` is within this week; skip campaigns still in
Pre-launch/Launch (Active not unlocked). Then dispatch both experiments
`mode=weekly` with prior context (events first, then tasks with current events as
input — eventual consistency across the week is fine). FIFO `MessageGroupId =
agent-dispatch-{organizationSlug}`.

Schedule: weekly on Sunday night (digest aligns Monday). Open: confirm exact day
with product; the digest currently fires Sunday 23:00 CT.

### 6.4 Result + persistence

Reuse `handleAgentExperimentResult` → add `onExperimentRunCompleted` cases for
`community_events` and `campaign_tracker_tasks` (mirror
`campaignStrategy.onExperimentRunCompleted`):
- Load artifact from S3, parse against the output schema, persist race-guarded.
- Fail-closed like `meeting_briefing`: if the artifact is a placeholder/error,
  do not overwrite — let the next weekly run retry.
- Stamp `dynamicTasksRefreshedAt` / events updatedAt on success.

### 6.5 Deterministic vs CAP (Layer-3 guardrail)

- CAP: personalize copy, select/prioritize the week's dynamic tasks, avoid
  repeats, discover/curate real events.
- Deterministic (gp-api persist + webapp sequencer): Active lock, 30-day GOTV
  window, 3-visible cap + progressive reveal, date placement (timing model),
  event merge/multiday-dedup safety net. The model never sets gates or dates.

## 7. Data model (gp-api Prisma)

On `campaign_strategy` (JSON columns + scalars; follow Rule 25 — prefer real
columns where queryable):

- `dynamic_tasks` (new JSON) — personalized pool + per-week selection +
  completion mirror. Each task carries `priority` (the meeting's schema add).
- `dynamicTasksRunId`, `dynamicTasksRefreshedAt`, `communityEventsRunId` (new

- New `CronRun` job name `campaignTrackerWeeklyRegen` (reuses the existing table).

Contracts: raise `CommunityEventsResultSchema.max(3)` (or split a tracker list
from the PDF's 3); add the `dynamic_tasks` + experiment I/O schemas. Cross-service
change lands in one PR (contracts + gp-api + webapp).

Migration: add the new `campaign_strategy` columns; backfill not required
(generated lazily). No destructive change to `community_events`.

## 8. Webapp consumption

The section keeps its client-side `buildCampaignStrategy` sequencer but, instead
of rendering template copy, **merges the persisted `dynamic_tasks`** (personalized
copy + per-week selection) onto the catalog by `catalog_id`, falling back to
template copy while generating. The deterministic gates/caps/banner stay in the
sequencer. A `useDynamicTasks` hook (mirrors `useCommunityEvents`) fetches +
polls generating/ready.

## 9. Idempotency, cost, failure

- Cron multi-pod: DB lease (`CronLock`). Per-campaign coverage: weekly
  `refreshedAt` guard. Result: optimistic-lock + RUNNING guard (existing).
- Cost: one (or two) CAP runs per eligible campaign per week; batched + throttled;
  `costUsd` tracked per run; admin/agentRuns for visibility.
- Failure: fail-closed persistence (don't overwrite good data with a bad run);
  stale-run sweeper (45 min) already covers hung runs; resume covers partials.
